DB2 & VSAM Data Storage Architecture

1. Overview

This page maps how the GenApp PL/I insurance application stores and accesses data. It covers the following:

  • DB2 relational tables. There are eight: CUSTOMER, CUSTOMER_SECURE, POLICY, ENDOWMENT, HOUSE, MOTOR, COMMERCIAL and CLAIM.
  • VSAM KSDS counterparts for customer data. These are reached through the LGACVS01, LGICVS01 and LGUCVS01 programs.
  • Dual-write synchronization. The customer add and update paths write to both DB2 and VSAM.
  • Program-level data dependencies. The page traces which programs read or write each table and which CICS entry points reach them.

The application has these main parts:

  • Customer domain. CICS transaction SSC1 and its menu program LGTESTC1 drive it. CUSTOMER is the master entity, and CUSTOMER_SECURE holds sensitive payment and security details separately.
  • Policy and product domain. POLICY is the hub table. The product tables MOTOR, ENDOWMENT, HOUSE and COMMERCIAL and the CLAIM table hang off it. Menus LGTESTP1 to LGTESTP4 drive this domain.
  • Batch and reporting domain. LGBATCH, LGBATDB2 and LGMOTOUT run under JCL and read DB2 directly. LGBATCH and LGBATDB2 read CUSTOMER. LGMOTOUT reads and writes MOTOR.

In total, 12 distinct programs access DB2 tables directly. Eleven were found in the scanned metadata database. LGUPDB01 was confirmed from its source.

2. System Architecture

2.1 Layered Component View

The application is layered. Terminal transactions call menu programs, which call orchestrators. The orchestrators call backend persistence programs, and those programs reach DB2 and VSAM. A shared error logger, LGSTSQ, writes to a CICS TS queue.

POLICY is the hub of policy processing. It has 5 direct programs and more than 30 references. Any change to its columns affects LGAPDB01, LGIPDB01, LGDPDB01, LGUPDB01 and LGACUS01, plus all four policy menus.

4. VSAM KSDS Layer and Dual-Write Synchronization

4.1 VSAM Counterparts

Each customer DB2 backend has a VSAM counterpart that keeps the KSDS dataset aligned with CUSTOMER:

Operation DB2 backend VSAM backend Effect on VSAM
Add LGACDB01 (INSERT into CUSTOMER) LGACVS01 Writes the customer record to the KSDS dataset
Inquire LGICDB01 (SELECT from CUSTOMER) LGICVS01 Reads the customer record from VSAM
Update LGUCDB01 (UPDATE CUSTOMER) LGUCVS01 Updates the customer record in VSAM

LGACDB01 calls LGACVS01 after its DB2 insert. LGUCDB01 links to LGUCVS01 after its DB2 update. LGICUS01 links to both LGICDB01 and LGICVS01.

The product and claim tables (POLICY, MOTOR, ENDOWMENT, HOUSE, COMMERCIAL, CLAIM) have no VSAM counterpart in the analyzed material. They are DB2-only.

4.3 Add Customer Sequence

LGACUS01 orchestrates onboarding across several data stores. It also reads and writes POLICY directly (SELECT, INSERT, DELETE), which is a documented coupling between the customer and policy domains. LGACUS01 itself inserts into CUSTOMER and links to LGACDB02. LGACDB01 has no caller in the repository.

4.6 Consistency Considerations

  • DB2 first, then VSAM. On add and update, the DB2 backend performs its SQL and then links to the VSAM backend. The two writes are separate steps in one call chain. There is no single database unit of work covering both stores.
  • Error logging. LGSTSQ is called by the customer programs, and by the policy programs too, to log errors to a TS queue. These programs are LGACDB01, LGACDB02, LGACUS01, LGICDB01, LGICUS01, LGUCDB01, LGUCUS01, LGACVS01, LGICVS01 and LGUCVS01. Each failure in either store has one common place where it is recorded.
  • Not mirrored. CUSTOMER_SECURE is written only by LGACDB02 and is not part of the documented VSAM mirroring.

6. Batch Access

The batch programs read DB2 directly and do not run through online CICS transactions:

  • LGBATCH and LGBATDB2 read CUSTOMER in bulk. They format data for reporting and for sequential flat-file distribution through LGBATCHF.
  • LGMOTOUT reads and writes MOTOR.

7. Domain Boundaries

Boundary Contract
Customer vs. Policy Linked by CUSTOMER_NUMBER (CA_CUSTOMER_NUM). Customer records are the master. Policy tables hold references to the customer number. LGACUS01 is a documented coupling point because it runs SQL against POLICY.
Customer vs. Batch / Reporting Batch routines read CUSTOMER only. They never run online CICS transactions.
Customer vs. Security data Demographic data in CUSTOMER is kept apart from payment and security details in CUSTOMER_SECURE, which only LGACDB02 writes.

8. Findings and Caveats

  1. LGUPDB01 missing from the scan. The metadata database has no SQL references for it. Its source contains a POLICY_CURSOR (SELECT … FOR UPDATE) and UPDATE statements on POLICY, ENDOWMENT, HOUSE and MOTOR. It is included here from source inspection, and a rescan is advisable.
  2. LGIPDB01 read/write flags. The scanner flags LGIPDB01 as write on several tables, such as POLICY and CLAIM. This is probably because INTO :host-variable targets are treated as writes. The source and inventory describe it as SELECT-only, so this page shows it as read-only.
  3. LGACDB01 has no in-repository caller. LGACUS01 inserts into CUSTOMER itself and links only to LGACDB02. It does not link to LGACDB01.
  4. Dynamic program names. Some LINKs use variables initialized with program names (for example LGAPDB01). These were resolved by reading the DCL … INIT('…') declarations and the LINK statements.
  5. VSAM detail limits. The analyzed material identifies the VSAM programs and their roles (write, read, update). It does not give dataset names, key layouts or record definitions for the KSDS file. Those should be taken from the VSAM backend sources (LGACVS01, LGICVS01, LGUCVS01) and the associated JCL or CICS file definitions.
  6. Scan method. The metadata database joins SQL-table references (resource type 1) to statement occurrences. Access is classed as write when bRead is 0 or 2, and as read otherwise. Upstream reach comes from program-call references (resource type 5) and from EXEC CICS LINK statements in the pli/ source.
