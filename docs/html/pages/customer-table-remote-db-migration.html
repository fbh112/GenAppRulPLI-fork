Customer Table Remote DB Migration Impact Analysis

Created: 2026-11-01 · Author: IBM Bob — Z Architect · Confidence Level: High

1. Overview

This document presents the impact analysis for the planned migration of the CUSTOMER table from the local z/OS DB2 subsystem to a remote database (e.g., PostgreSQL, Oracle, or a cloud RDBMS), targeted for November 2026. The migration is driven by objectives to decouple customer data from the z/OS DB2 subsystem, reduce DB2 licensing costs, and consolidate customer data in a central enterprise data platform.

Six PL/I programs within the GenApp application currently access the CUSTOMER table via EXEC SQL embedded SQL. All must be modified to replace those SQL statements with calls to a new CICS service program that proxies the remote database via a REST API. Batch programs present an additional architectural challenge, as they cannot use EXEC CICS LINK and require a separate remote-call mechanism.

Scope boundary confirmed: Only GenApp programs in this repository access the CUSTOMER table. No external systems, data warehouses, or other applications are affected.

LGACUS01 INSERT (×4), SELECT (×2), DELETE CICS online (orchestrator)

2. System Architecture

The current architecture routes all CUSTOMER table access through embedded DB2 SQL in PL/I programs, organised across three tiers: a presentation tier, an orchestration tier, and a DB2 backend tier, alongside independently executing batch programs. After migration, the DB2 backend tier for customer data is replaced by a new CICS Customer Service Program that acts as a REST proxy to the remote database. Batch programs must be rerouted through a separate non-CICS remote-call mechanism (e.g., EXCI, HTTP stub, or MQ).

4.2 New Components to Create

4.2.1 New CICS Customer Service Program (name TBD)

This new program acts as the central REST proxy for all CICS callers and is the only component that needs to know about the remote database endpoint.

  • CICS-linked proxy program invoked via EXEC CICS LINK
  • Accepts a COMMAREA with a function code (SEL, INS, UPD, DEL) plus customer fields
  • Internally constructs and issues an HTTP REST API call to the remote database endpoint
  • Returns data and a return code in the COMMAREA to the caller
  • Fully encapsulates the DB2→REST translation; no caller needs knowledge of REST
PLI 
/* Skeleton structure for new CICS Customer Service Program */
DCL 1 CUSTOMER_COMMAREA BASED(DFHCOMMPTR),
      3 COMM_FUNCTION    CHAR(3),   /* SEL / INS / UPD / DEL */
      3 COMM_RETCODE     CHAR(2),   /* 00=OK, 04=NOTFND, 08=ERR */
      3 COMM_REASON      CHAR(50),  /* Diagnostic text          */
      3 COMM_CUST_ID     FIXED DEC(10),
      3 COMM_FIRSTNAME   CHAR(20),
      3 COMM_LASTNAME    CHAR(20),
      /* ... remaining CUSTOMER columns ... */
      3 COMM_PHONE       CHAR(20);

SELECT (COMM_FUNCTION);
  WHEN ('SEL') CALL PERFORM_SELECT;
  WHEN ('INS') CALL PERFORM_INSERT;
  WHEN ('UPD') CALL PERFORM_UPDATE;
  WHEN ('DEL') CALL PERFORM_DELETE;
  OTHERWISE    COMM_RETCODE = '08';
END;

4.2.2 New COMMAREA %INCLUDE Member

A shared PL/I %INCLUDE layout used by all 4 CICS callers and the new service program to enforce a single data contract.

  • Fields: function code, return code, reason text, customer key (CUST_ID), all CUSTOMER table columns
  • Types: Fixed-length CHAR(n) and FIXED DEC; null indicators represented as flags within the structure
  • Constraint: Total structure size must remain under the 32 KB COMMAREA limit; if exceeded, migrate to CICS Channels and Containers

8. Recommended Remediation Steps

Based on the full impact and risk analysis, the following prioritised remediation steps are recommended:

  1. Resolve Critical Blockers First (R1, R2)

    • Design the Remote DB REST API contract and COMMAREA %INCLUDE layout (A3).
    • Decide the batch remote-call mechanism — EXCI, HTTP stub, or MQ (A4). This is a critical blocker before any batch code changes begin.

  2. Create Shared Infrastructure

    • Implement the new COMMAREA %INCLUDE member and verify its total size is under 32 KB.
    • Implement and unit-test the new CICS Customer Service Program against the remote DB endpoint.

  3. Migrate CICS Programs — Simplest First

    • Begin with LGICDB01 (cyclomatic 8, one SELECT) as a proof-of-concept migration to establish patterns.
    • Proceed with LGUCDB01 (cyclomatic 8, one UPDATE) and LGACDB01 (cyclomatic 13, two INSERTs).
    • Tackle LGACUS01 (cyclomatic 25, 7 SQL statements) last, after patterns are fully established and the test suite is in place.

  4. Migrate Batch Programs

    • Apply the agreed batch remote-call mechanism to LGBATDB2 (cyclomatic 1 — trivial) first.
    • Then apply to LGBATCH (cyclomatic 6).

  5. Update Build Configuration

    • Remove SQL precompiler options and DB2 link-edit stubs from application-conf/PLI.properties for all 6 impacted programs.
    • Add the new service program entry.

  6. Verify Unit-of-Work Integrity

    • Audit all EXEC SQL COMMIT / EXEC SQL WHENEVER usages and replace with EXEC CICS SYNCPOINT where applicable (R3, R7).
    • Validate compensation and idempotency logic in the new service program.

  7. Execute Test Strategy

    • Unit test each modified program in isolation.
    • Integration test the full CICS call chain: LGTESTC1 → LGxCUS01 → LGxCDB01 → new service.
    • Batch regression: LGBATCH, LGBATDB2.

  8. Deploy in Sequence and Retire DB2 Artefacts

    • Deploy remote DB schema → REST API → CICS service program → modified programs → update CICS CSD.
    • Only after all 6 programs are confirmed in production: retire DB2 packages/plans, remove EXECUTE privileges, and drop DB2ENTRY/DB2TRAN definitions (R8).
