DB2 Table & Program Dependencies

This document provides comprehensive technical documentation of the database dependencies and data access patterns across the GenApp PL/I application on IBM z/OS. It details which PL/I programs interact with specific Db2 relational tables—including CUSTOMER, CUSTOMER_SECURE, POLICY, ENDOWMENT, HOUSE, MOTOR, COMMERCIAL, and CLAIM—and outlines their respective access modes (Create/INSERT, Read/SELECT, Update/UPDATE, and Delete/DELETE).

1. Overview

GenApp PL/I is an enterprise insurance core application hosted under CICS Transaction Server and z/OS Batch. Core business entities are maintained within Db2 tables, backed by parallel VSAM KSDS files for specific entities.

Db2 access is primarily concentrated within dedicated Tier 3 backend I/O service programs, though specific orchestrator programs (such as LGACUS01) and standalone batch jobs (LGBATCH, LGBATDB2, LGMOTOUT) also interact directly with Db2 using embedded SQL.

2. System Architecture and Database Tiering

2.1 Architectural Layers

The GenApp application is organized into a strict three-tier architecture:

  1. Tier 1: Presentation Layer (BMS Menu Programs): Handles 3270 terminal user interfaces (LGTESTP1–LGTESTP4, LGTESTC1) and transfers control via EXEC CICS LINK to Tier 2. It contains no embedded SQL.
  2. Tier 2: Business Logic & Orchestration Layer: Validates COMMAREA structures, coordinates cross-entity workflows, and routes requests to backend processors. While most Tier 2 programs delegate database actions, LGACUS01 performs direct SQL inserts into CUSTOMER and POLICY.
  3. Tier 3: Backend Persistence Layer:
    • Db2 Programs: Contain embedded SQL (EXEC SQL) statements, cursor handling, and host structure mappings.
    • VSAM Programs: Handle CICS File Control commands against key-sequenced datasets (KSDSCUST, KSDSPOLY).
  4. Batch Processing Layer: Standalone PL/I programs executing outside CICS for sequential reporting and extract generation.

5. Detailed Table Analysis and Program Access Patterns

5.1 CUSTOMER Table

  • Primary Consumers: LGACDB01 (Add), LGICDB01 (Inquire), LGUCDB01 (Update), LGACUS01 (Orchestration direct insert), LGBATCH (Batch report), and LGBATDB2 (Batch connectivity verification).
  • Access Patterns:
    • Single-row point lookups via SELECT using customer number keys from the COMMAREA.
    • Updates perform modification of demographic and address attributes.
    • Sequential reads driven via batch input files (CUSTIN).

5.2 CUSTOMER_SECURE Table

  • Primary Consumers: LGACDB02 (Add Customer Security).
  • Access Patterns:
    • Append-only (INSERT). This table is isolated from standard customer maintenance programs and serves strictly security and identity management workflows.

5.3 POLICY Table

  • Primary Consumers: LGAPDB01 (Add), LGIPDB01 (Inquire), LGUPDB01 (Update), LGDPDB01 (Delete), and LGACUS01 (Orchestration initial policy creation).
  • Access Patterns:
    • Acts as the central header entity for all insurance policy instances.
    • LGUPDB01 uses an explicit cursor (POLICY_CURSOR) to retrieve policy headers with hold before applying updates.
    • LGDPDB01 executes physical row deletion (DELETE FROM POLICY WHERE ...).

5.4 Policy Subtype Tables (ENDOWMENT, HOUSE, MOTOR, COMMERCIAL, CLAIM)

  • Primary Consumers: LGAPDB01, LGIPDB01, LGUPDB01, LGMOTOUT.
  • Access Patterns:
    • Multi-table writes in LGAPDB01: Dispatches child records to the corresponding subtype table based on policy type indicator.
    • Cursor-based joins and scans in LGIPDB01: Drives multi-row inquiries utilizing specialized cursors (Cust_Cursor, Zip_Cursor, CusClaim_Cursor).
    • Batch extract in LGMOTOUT: Uses MOTOR_CSR to iterate over the entire MOTOR table and format sequential output records.

6. Program-Level Db2 Interactions and Code Structures

6.1 Backend CICS Db2 Modules

Backend Db2 programs receive communication buffers via pointer structures and execute static SQL under CICS transaction control.

6.1.1 Policy Inquiry Module (LGIPDB01)

LGIPDB01 utilizes host structures and multiple Db2 cursors to retrieve policy subtypes.

PLI 
/* LGIPDB01: Inquire Policy Backend Entry & Data Structures */
 LGIPDB01: Proc(COMM_AREA_PTR) Options(Main);
    Dcl COMM_AREA_PTR Pointer;
    
    %INCLUDE LGCMAREA;
    %INCLUDE LGPOLICY;
    EXEC SQL INCLUDE SQLCA;

    /* Cursor declaration for claim and customer policy scanning */
    EXEC SQL DECLARE Cust_Cursor CURSOR FOR
        SELECT POLICYNUMBER, CUSTOMERNUMBER, POLICYTYPE
        FROM POLICY
        WHERE CUSTOMERNUMBER = :LGCMA_CUSTOMER_NUMBER;
        
    EXEC SQL OPEN Cust_Cursor;
    /* Fetch and populate COMMAREA response buffer */
 End LGIPDB01;

6.1.2 Policy Update Module (LGUPDB01)

LGUPDB01 retrieves policy records using cursor locking, then updates subtype tables (ENDOWMENT, HOUSE, or MOTOR).

PLI 
/* LGUPDB01: Update Policy Backend */
 LGUPDB01: Proc(COMM_AREA_PTR) Options(Main);
    Dcl COMM_AREA_PTR Pointer;
    
    %INCLUDE LGCMAREA;
    %INCLUDE LGPOLICY;
    EXEC SQL INCLUDE SQLCA;

    EXEC SQL DECLARE POLICY_CURSOR CURSOR FOR
        SELECT POLICYNUMBER, POLICYTYPE
        FROM POLICY
        WHERE POLICYNUMBER = :LGCMA_POLICY_NUMBER
        FOR UPDATE;

    EXEC SQL OPEN POLICY_CURSOR;
    EXEC SQL FETCH POLICY_CURSOR INTO :HV_POLICY_NUM, :HV_POLICY_TYPE;
    
    /* Conditional update targeting sub-entity */
    EXEC SQL UPDATE POLICY
        SET POLICYTYPE = :HV_POLICY_TYPE
        WHERE CURRENT OF POLICY_CURSOR;
 End LGUPDB01;

6.1.3 Policy Delete Module (LGDPDB01)

LGDPDB01 handles deletion of records from the central POLICY table.

PLI 
/* LGDPDB01: Delete Policy Backend */
 LGDPDB01: Proc(DFHEIPTR, COMM_AREA_PTR) Options(Main, Reentrant);
    Dcl (DFHEIPTR, COMM_AREA_PTR) Pointer;
    
    %INCLUDE LGCMAREA;
    EXEC SQL INCLUDE SQLCA;

    EXEC SQL DELETE FROM POLICY
        WHERE POLICYNUMBER = :LGCMA_POLICY_NUMBER;
 End LGDPDB01;

6.2 Orchestration Tier Direct Access (LGACUS01)

LGACUS01 combines orchestration with direct database insertion before calling secondary services (LGACVS01 and LGACDB02).

PLI 
/* LGACUS01: Add Customer Orchestrator - Direct DB2 Operations */
 LGACUS01: Proc(COMM_AREA_PTR) Options(Main);
    Dcl COMM_AREA_PTR Pointer;
    
    %INCLUDE LGCMAREA;
    EXEC SQL INCLUDE SQLCA;

    /* Insert Customer Record */
    EXEC SQL INSERT INTO CUSTOMER (CUSTOMERNUMBER, FIRSTNAME, LASTNAME)
        VALUES (:LGCMA_CUST_NUM, :LGCMA_FIRST_NAME, :LGCMA_LAST_NAME);

    /* Insert Default Policy Header */
    EXEC SQL INSERT INTO POLICY (POLICYNUMBER, CUSTOMERNUMBER, POLICYTYPE)
        VALUES (:LGCMA_POL_NUM, :LGCMA_CUST_NUM, :LGCMA_POL_TYPE);

    /* Link to Security Module and VSAM Mirror */
    EXEC CICS LINK PROGRAM('LGACDB02') COMMAREA(LGCMAREA);
    EXEC CICS LINK PROGRAM('LGACVS01') COMMAREA(LGCMAREA);
 End LGACUS01;

6.3 Batch Processing and Extract Programs

6.3.1 Motor Table Batch Extract (LGMOTOUT)

LGMOTOUT reads the MOTOR table sequentially via a cursor and outputs 132-byte records to MOTOROUT.

PLI 
/* LGMOTOUT: Batch Motor Table Extract */
 LGMOTOUT: Proc Options(Main);
    EXEC SQL INCLUDE SQLCA;

    EXEC SQL DECLARE MOTOR_CSR CURSOR FOR
        SELECT POLICYNUMBER, REGNUMBER, MAKE, MODEL, VALUE
        FROM MOTOR;

    EXEC SQL OPEN MOTOR_CSR;
    /* Fetch loop writes extracted rows to MOTOROUT sequential file */
 End LGMOTOUT;

6.3.2 Customer Batch Report (LGBATCH)

LGBATCH reads input keys sequentially from CUSTIN and queries the CUSTOMER table before invoking the report line formatter LGBATCHF.

PLI 
/* LGBATCH: Batch Customer Report Generator */
 LGBATCH: Proc Options(Main);
    EXEC SQL INCLUDE SQLCA;
    EXEC SQL INCLUDE LGCMAREA;

    /* Read CUSTIN sequentially, then fetch customer record */
    EXEC SQL SELECT FIRSTNAME, LASTNAME, ADDRESS
        INTO :HV_FIRST_NAME, :HV_LAST_NAME, :HV_ADDRESS
        FROM CUSTOMER
        WHERE CUSTOMERNUMBER = :HV_CUST_NUM;

    /* Invoke format subroutine */
    CALL LGBATCF(HV_CUST_NUM, COMM_PTR, LS_LINE);
 End LGBATCH;

7. Key Architectural Observations and Data Integrity Insights

  1. Broadest Write Dependency (LGAPDB01): LGAPDB01 (Add Policy DB2) represents the single most database-intensive writing program in GenApp, issuing inserts across 6 tables (POLICY, ENDOWMENT, HOUSE, MOTOR, COMMERCIAL, and CLAIM).
  2. Broadest Read Dependency (LGIPDB01): LGIPDB01 (Inquire Policy DB2) is the primary inquiry consumer, maintaining query access across the CUSTOMER table, POLICY header, and all 5 policy subtype tables via cursors (Cust_Cursor, Zip_Cursor, CusClaim_Cursor).
  3. Cross-Domain Orchestration (LGACUS01): Unlike other Tier 2 orchestrators that delegate database persistence entirely to Tier 3 modules, LGACUS01 holds direct ownership of CUSTOMER and POLICY inserts, coordinating relational and VSAM writes across multiple tiers.
  4. Security Isolation (CUSTOMER_SECURE): The CUSTOMER_SECURE table has the smallest operational footprint, touched only by LGACDB02 via INSERT.
  5. Heterogeneous Workload on MOTOR Table: MOTOR is the only policy subtype accessed simultaneously by online transaction processing (LGAPDB01, LGIPDB01, LGUPDB01) and asynchronous batch extract processing (LGMOTOUT).
