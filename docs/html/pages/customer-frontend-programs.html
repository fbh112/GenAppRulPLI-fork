Customer Business Logic Programs

1. Overview

The Customer Business Logic Programs form the core business-logic layer of the IBM General Insurance Application (GenApp). These CICS-hosted Enterprise PL/I programs handle every customer lifecycle operation: onboarding new customers, retrieving existing customer records, and updating customer details. They act as orchestrators — validating inbound requests, enforcing business rules, coordinating downstream database and VSAM access, and returning structured outcomes to their callers.

Three programs comprise this layer:

Program Responsibility
LGACUS01 Customer add (onboard), policy offer, policy transfer, and policy delete
LGICUS01 Customer inquiry with MQ-based routing override
LGUCUS01 Customer update

All three programs share a common architectural pattern:

  • They receive a CICS COMMAREA as their input/output contract.
  • They validate the COMMAREA before performing any business logic.
  • They delegate database work to downstream DB2-layer programs via EXEC CICS LINK.
  • They report errors through a shared transient-data-queue (TDQ) logging utility (LGSTSQ).
  • They return a CA_RETURN_CODE to the caller to signal success or failure.

The shared COMMAREA structure is defined in the LGCMAREA copybook (plinc/LGCMAREA.inc), a 32,500-byte UNION that carries request identifiers, return codes, customer identity, and all customer/policy detail fields across every program boundary.

2. System Architecture

The customer business logic programs sit in the middle tier of a three-tier architecture. A front-end terminal program (e.g., LGTESTC1) receives user input, populates the COMMAREA, and LINKs to these programs. They in turn LINK to DB2 or VSAM backend programs to perform the actual data access.

3. LGACUS01 — Customer Add, Policy Offer, Transfer, and Delete

3.1 Purpose

LGACUS01 is the central orchestrator for customer lifecycle management. It handles four distinct operations dispatched by an internal ACTION_CODE:

Action Code Operation Downstream Target
'1' Onboard new customer DB2 CUSTOMER table, LGACVS01, LGACDB02
'2' Offer new policy DB2 POLICY table
'3' Transfer customer policy DB2 POLICY table
'4' Delete customer policy DB2 POLICY table

Important: In the current PL/I port, ACTION_CODE is permanently initialised to '0' and never modified at runtime. This means none of the four routing branches are ever entered — the program returns after COMMAREA validation only. This is a known, documented behaviour carried over from the original COBOL program.

3.2 COMMAREA Contract

The program’s input/output contract is defined by the LGCMAREA copybook. The key fields are:

Request / Response Control

Field Type Direction Description
CA_REQUEST_ID CHAR(6) In/Out Operation identifier (01ICUS, 02OCUS, 02UCUS, 02DCUS)
CA_RETURN_CODE PIC 99 Out 00=success, 70=RI violation, 90=SQL error, 98=short COMMAREA
CA_CUSTOMER_NUM PIC 9999999999 Out Newly assigned customer number after successful INSERT
CA_POLICY_NUM PIC 9999999999 Out Newly assigned policy number after successful INSERT
CA_LASTCHANGED CHAR(26) Out DB2-assigned timestamp after policy INSERT

Customer Personal Details (input to DB2 INSERT)

Field Size Description
CA_FIRST_NAME CHAR(10) Customer first name
CA_LAST_NAME CHAR(20) Customer last name
CA_DOB CHAR(10) Date of birth
CA_HOUSE_NAME CHAR(20) House/property name
CA_HOUSE_NUM CHAR(4) House number
CA_POSTCODE CHAR(8) Postal code
CA_PHONE_MOBILE CHAR(20) Mobile phone
CA_PHONE_HOME CHAR(20) Home phone
CA_EMAIL_ADDRESS CHAR(100) Email address

Minimum COMMAREA length: 90 bytes (18-byte header + 72-byte customer record). A COMMAREA shorter than this causes an immediate return with CA_RETURN_CODE = '98'.

3.4 Validation Rules

  • No COMMAREA (EIBCALEN = 0): Issues EXEC CICS ABEND ABCODE('LGCA') NODUMP. No further processing.
  • COMMAREA too short (< 90 bytes): Returns CA_RETURN_CODE = '98' immediately.
  • Claim requests blocked on policy operations: If CA_REQUEST_ID = '01ACLM', the policy insert/transfer/delete sub-procedures are skipped entirely.
  • Policy insert RI violation (SQLCODE -530): Returns CA_RETURN_CODE = '70' — the parent CUSTOMER row does not exist.
  • Policy delete SQLCODE 100 treated as success: “Row not found” is an acceptable outcome — the desired end-state (row absent) is achieved.

3.5 Customer Number Assignment Strategy

graph TD A[OBTAIN_CUSTOMER_NUMBER] --> B{{EXEC CICS GET COUNTER\nGENACUSTNUM / GENA pool}} B -- Success --> C[DB2_CUSTOMERNUM_INT = LASTCUSTNUM\nLGAC_NCS = ON] B -- Failure --> D[LGAC_NCS = NO\nDB2_CUSTOMERNUM_INT = 0] C --> E[INSERT CUSTOMER\nwith explicit CUSTOMERNUMBER] D --> F[INSERT CUSTOMER\nwith DEFAULT identity] F --> G[SET DB2_CUSTOMERNUM_INT\n= IDENTITY_VAL_LOCAL] E --> H[CA_CUSTOMER_NUM = DB2_CUSTOMERNUM_INT] G --> H

The dual-path strategy ensures customer numbering is resilient. If the CICS Named Counter Service (GENACUSTNUM in the GENA pool) is unavailable, DB2’s own IDENTITY column auto-assigns the number and IDENTITY_VAL_LOCAL() retrieves it immediately after the INSERT.

3.7 Error Handling

All error paths call the shared WRITE_ERROR_MESSAGE procedure, which:

  1. Obtains a timestamp via EXEC CICS ASKTIME / EXEC CICS FORMATTIME.
  2. Populates the ERROR_MSG structure with program name (LGACUS01), customer number, policy number, SQL request label, and SQLCODE.
  3. Calls LGSTSQ (via EXEC CICS LINK) to write the record to the CICS Transient Data Queue.
  4. Calls LGSTSQ a second time with up to 90 bytes of raw COMMAREA content for diagnostic context.
Condition Return Code Termination
No COMMAREA N/A ABEND LGCA NODUMP
COMMAREA < 90 bytes 98 EXEC CICS RETURN
DB2 customer INSERT failed 90 EXEC CICS RETURN
DB2 policy INSERT — RI violation (SQLCODE -530) 70 EXEC CICS RETURN
DB2 policy INSERT — other SQL error 90 EXEC CICS RETURN
DB2 policy DELETE — non-zero, non-100 SQLCODE 90 EXEC CICS RETURN
LGACDB02 returns non-zero Propagated EXEC CICS RETURN

Linked Program COMMAREA Length Purpose
LGACVS01 225 bytes VSAM customer record write (dual-write pattern)
LGACDB02 32,500 bytes Customer security record creation (D2_REQUEST_ID = '02ACUS')

3.9 Code Example — Customer INSERT with Named Counter Fallback

PLI 
/* INSERT_CUSTOMER — named counter path */
IF LGAC_NCS = 'ON' THEN DO;
    EM_SQLREQ = ' INSERT CUSTOMER';
    EXEC SQL INSERT INTO CUSTOMER
        (CUSTOMERNUMBER, FIRSTNAME, LASTNAME, DATEOFBIRTH,
         HOUSENAME, HOUSENUMBER, POSTCODE,
         PHONEMOBILE, PHONEHOME, EMAILADDRESS)
    VALUES
        (:DB2_CUSTOMERNUM_INT, :CA_FIRST_NAME, :CA_LAST_NAME,
         :CA_DOB, :CA_HOUSE_NAME, :CA_HOUSE_NUM, :CA_POSTCODE,
         :CA_PHONE_MOBILE, :CA_PHONE_HOME, :CA_EMAIL_ADDRESS);
    IF SQLCODE <> 0 THEN DO;
        CA_RETURN_CODE = '90';
        CALL WRITE_ERROR_MESSAGE;
        EXEC CICS RETURN;
    END;
END;
ELSE DO;
    /* DB2 IDENTITY fallback — no named counter */
    EXEC SQL INSERT INTO CUSTOMER
        (CUSTOMERNUMBER, FIRSTNAME, LASTNAME, DATEOFBIRTH,
         HOUSENAME, HOUSENUMBER, POSTCODE,
         PHONEMOBILE, PHONEHOME, EMAILADDRESS)
    VALUES
        (DEFAULT, :CA_FIRST_NAME, :CA_LAST_NAME,
         :CA_DOB, :CA_HOUSE_NAME, :CA_HOUSE_NUM, :CA_POSTCODE,
         :CA_PHONE_MOBILE, :CA_PHONE_HOME, :CA_EMAIL_ADDRESS);
    IF SQLCODE <> 0 THEN DO;
        CA_RETURN_CODE = '90';
        CALL WRITE_ERROR_MESSAGE;
        EXEC CICS RETURN;
    END;
    /* Retrieve the DB2-generated customer number */
    EXEC SQL SET :DB2_CUSTOMERNUM_INT = IDENTITY_VAL_LOCAL();
END;
CA_CUSTOMER_NUM = DB2_CUSTOMERNUM_INT;

4. LGICUS01 — Customer Inquiry with MQ Routing

4.1 Purpose

LGICUS01 is the business-logic entry point for all customer inquiry operations. Its unique responsibility — distinguishing it from the other two programs — is a runtime routing decision: before delegating to the DB2 backend, it reads a CICS Temporary Storage queue (GENAWMQC) to detect an MQHIT= control record. If found, the request is routed to an alternate (MQ-based) program rather than the standard DB2 inquiry program LGICDB01.

The program performs no database access itself. Its sole responsibilities are:

  1. COMMAREA validation.
  2. TS queue scan for the MQ routing override.
  3. CICS LINK to the appropriate downstream program.
  4. Error logging on fatal failures.

4.2 COMMAREA Contract

Field Type Direction Description
CA_REQUEST_ID CHAR(6) In Operation identifier (e.g., '01ICUS')
CA_RETURN_CODE PIC 99 Out 00=success, 98=COMMAREA too short
CA_CUSTOMER_NUM PIC 9999999999 In Customer identifier for the inquiry
CA_NUM_POLICIES PIC 999 Out Policy count — initialised to 0, populated by LGICDB01
CA_FIRST_NAME CHAR(10) Out Populated by downstream DB2 program
CA_LAST_NAME CHAR(20) Out Populated by downstream DB2 program
CA_POLICY_DATA CHAR(32,267) Out Serialised policy records buffer

Minimum COMMAREA length: 90 bytes (WS_CUSTOMER_LEN(72) + WS_CA_HEADERTRAILER_LEN(18)). Short COMMAREA → CA_RETURN_CODE = '98', immediate return.

4.4 MQ Routing Logic

The MQ routing mechanism is a runtime switch implemented entirely through a CICS TS queue. This allows the processing path to be changed without recompiling the program.

sequenceDiagram participant LGICUS01 participant TS_Queue as CICS TS Queue (GENAWMQC) participant LGICDB01 as LGICDB01 (DB2 Path) participant AltProg as AAAAAAAA (MQ Path) LGICUS01->>TS_Queue: READQ TS QUEUE('GENAWMQC') ITEM(1) alt Queue empty or read fails TS_Queue-->>LGICUS01: Non-NORMAL response → MQ_HIT stays 0 else Queue has records loop Read each record with NEXT TS_Queue-->>LGICUS01: 80-char record LGICUS01->>LGICUS01: Check SUBSTR(record,1,6) = 'MQHIT=' opt Match found LGICUS01->>LGICUS01: MQ_HIT = 1 end end end alt MQ_HIT = 0 (standard path) LGICUS01->>LGICDB01: EXEC CICS LINK (COMMAREA 32500) LGICDB01-->>LGICUS01: Customer data populated in COMMAREA else MQ_HIT = 1 (override path) LGICUS01->>AltProg: EXEC CICS LINK (COMMAREA 32500) AltProg-->>LGICUS01: Response end

Key routing rules:

  • The TS queue GENAWMQC is scanned sequentially from item 1.
  • A record activates MQ routing only if its first 6 characters exactly equal 'MQHIT=' (case-sensitive, positional match).
  • If the queue is empty or inaccessible, MQ_HIT remains 0 — the DB2 path is the safe default.
  • The two paths are mutually exclusive within a single invocation.

4.5 Error Handling

LGICUS01 logs errors only on the fatal no-COMMAREA path. The WRITE_ERROR_MESSAGE procedure:

  1. Retrieves a timestamp via EXEC CICS ASKTIME + EXEC CICS FORMATTIME.
  2. Populates the ERROR_MSG structure (program name LGICUS01, customer number, SQL request label, SQLCODE).
  3. Writes the structured error record to the TDQ via EXEC CICS LINK PROGRAM('LGSTSQ').
  4. Conditionally appends up to 90 bytes of raw COMMAREA content (only if EIBCALEN > 0).
Condition Action Return Code
EIBCALEN = 0 Log error + ABEND LGCA NODUMP N/A
EIBCALEN < 90 EXEC CICS RETURN immediately 98
TS queue inaccessible Silent fallback to DB2 path —
TS queue record matches MQHIT= Route to alternate program —

4.6 Code Example — TS Queue Scan for MQ Routing

PLI 
/* GET_CUSTOMER_INFO — MQ routing flag detection */
MQ_HIT = 0;
EXEC CICS READQ TS
    QUEUE(MQ_CONTROL)       /* 'GENAWMQC' */
    INTO(MQ_READ_RECORD)
    RESP(WS_RESP)
    ITEM(1);

IF WS_RESP = DFHRESP(NORMAL) THEN DO;
    DO UNTIL (WS_RESP > 0);
        IF WS_RESP = DFHRESP(NORMAL) THEN DO;
            IF SUBSTR(MQ_READ_RECORD, 1, 6) = 'MQHIT=' THEN
                MQ_HIT = 1;
        END;
        EXEC CICS READQ TS
            QUEUE(MQ_CONTROL)
            INTO(MQ_READ_RECORD)
            RESP(WS_RESP)
            NEXT;
    END;
END;

/* Route based on MQ_HIT flag */
IF MQ_HIT = 0 THEN
    EXEC CICS LINK
        PROGRAM(LGICDB01)
        COMMAREA(COMM_AREA)
        LENGTH(32500);
ELSE
    EXEC CICS LINK
        PROGRAM('AAAAAAAA')
        COMMAREA(COMM_AREA)
        LENGTH(32500);

5. LGUCUS01 — Customer Update

5.1 Purpose

LGUCUS01 is the business-logic entry point for updating an existing customer record. It is the simplest of the three programs: it validates the inbound COMMAREA and request identifier, then delegates the entire database update to LGUCDB01 via a single EXEC CICS LINK. No SQL is issued by LGUCUS01 itself.

CA_RETURN_CODE PIC 99 Out 00=accepted, 99=invalid request ID
CA_CUSTOMER_NUM PIC 9999999999 In Customer identifier for the record to update
CA_NUM_POLICIES PIC 999 In/Out Initialised to 0 on entry
CA_FIRST_NAME CHAR(10) In Updated first name
CA_LAST_NAME CHAR(20) In Updated last name

5.4 Validation Rules

LGUCUS01 applies two sequential guards before delegating to LGUCDB01:

  1. COMMAREA presence (EIBCALEN = 0): Fatal — abends with LGCA, logs to TDQ.
  2. Request ID (CA_REQUEST_ID ≠ '01UCUS'): Non-fatal — returns CA_RETURN_CODE = '99' immediately. No database call is made and no error is logged.

The sequencing is mandatory: field access depends on a valid COMMAREA pointer, so the presence check must always precede the request ID check.

5.7 Code Example — Request Validation and Delegation

PLI 
/* LGUCUS01 Mainline — request ID gate and delegation */

/* Step 1: Capture EIB context */
WS_TRANSID = EIBTRNID;
WS_TERMID  = EIBTRMID;
WS_TASKNUM = EIBTASKN;

/* Step 2: COMMAREA presence check */
IF EIBCALEN = 0 THEN DO;
    EM_MSG_TEXT = ' NO COMMAREA RECEIVED';
    CALL WRITE_ERROR_MESSAGE;
    EXEC CICS ABEND ABCODE('LGCA') NODUMP;
END;

/* Step 3: Initialise COMMAREA */
CA_RETURN_CODE  = '00';
CA_NUM_POLICIES = 0;
WS_CALEN        = EIBCALEN;
WS_ADDR_DFHCOMMAREA = COMM_AREA_PTR;
EM_CUSNUM = CA_CUSTOMER_NUM;   /* echo for error tracing */

/* Step 4: Request ID validation */
IF CA_REQUEST_ID ^= '01UCUS' THEN DO;
    CA_RETURN_CODE = '99';
    EXEC CICS RETURN;
END;

/* Step 5: Delegate to DB2 backend */
CALL UPDATE_CUSTOMER_INFO;

EXEC CICS RETURN;


/* UPDATE_CUSTOMER_INFO internal procedure */
UPDATE_CUSTOMER_INFO: PROCEDURE;
    EXEC CICS LINK
        PROGRAM(LGUCDB01)
        COMMAREA(COMM_AREA)
        LENGTH(32500);
END UPDATE_CUSTOMER_INFO;

6. Cross-Program Patterns and Shared Contracts

6.1 Common COMMAREA Structure

All three programs use the LGCMAREA copybook (plinc/LGCMAREA.inc) as the shared COMMAREA definition. The structure is a UNION of 32,500 bytes providing multiple named overlays:

7. Constraints and Limitations

7.1 COMMAREA Size Constraints

Program Minimum (bytes) Maximum (bytes) Behaviour if too short
LGACUS01 90 (18 header + 72 customer) 32,500 CA_RETURN_CODE = '98', immediate return
LGICUS01 90 (18 header + 72 customer) 32,500 CA_RETURN_CODE = '98', immediate return
LGUCUS01 Present (> 0) 32,500 Only presence checked; no minimum length enforced

All three programs pass exactly 32,500 bytes to downstream programs via EXEC CICS LINK … LENGTH(32500).

7.2 Field Size Constraints

Field Size Constraint Notes
CA_REQUEST_ID CHAR(6) Positional — values longer than 6 chars are truncated
CA_CUSTOMER_NUM PIC 9999999999 Maximum value: 9,999,999,999
CA_POLICY_NUM PIC 9999999999 Maximum value: 9,999,999,999
CA_RETURN_CODE PIC 99 Only 00, 70, 90, 98, 99 are defined
CA_PAYMENT PIC 999999 Maximum: 999,999
CA_EMAIL_ADDRESS CHAR(100) Truncated to 27 chars on the BMS terminal screen
DB2_CUSTOMERNUM_INT FIXED BIN(31) Maximum: 2,147,483,647
Error message COMMAREA dump CHAR(90) Always capped at 90 bytes regardless of actual COMMAREA size

7.3 Known Limitations

  • LGACUS01 ACTION_CODE defect: The routing switch (ACTION_CODE) is hardcoded to '0' and never modified. No business operations (add, offer, transfer, delete) are ever executed at runtime. This is a known porting artefact from the original COBOL program.
  • LGICUS01 AAAAAAAA placeholder: The MQ-routing alternate program is identified by the placeholder name 'AAAAAAAA'. This must be replaced with the actual MQ-processing program name before the MQ routing path can function.
  • Policy claim requests blocked: In LGACUS01, all policy sub-operations check CA_REQUEST_ID ≠ '01ACLM'. Claim-type requests are explicitly excluded from triggering policy insert, transfer, or delete logic.
  • CA_LASTCHANGED is always DB2-generated: Callers cannot supply a LASTCHANGED timestamp; it is always set to CURRENT TIMESTAMP by DB2 at INSERT time.
  • POLICYNUMBER is always DB2-generated: Callers cannot pre-assign a policy number; the value is always assigned by DB2 identity and retrieved via IDENTITY_VAL_LOCAL().
