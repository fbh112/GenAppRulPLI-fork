Project Overview

The IBM General Insurance Application (GenApp) is a mainframe-based reference application that demonstrates end-to-end insurance business processing on z/OS. Written in Enterprise PL/I, it runs as a CICS online system backed by DB2 relational storage and VSAM key-sequenced datasets, with a complementary batch tier for bulk reporting. GenApp covers two core business domains — customer management and insurance policy lifecycle — and serves as both a functional insurance platform and a showcase for IBM z/OS middleware integration.

1. System Architecture

The application is structured as a classic z/OS layered architecture: a 3270 terminal presentation layer feeds into CICS-linked business orchestrators, which delegate all persistence to dedicated DB2 and VSAM backend programs. A separate batch tier handles offline reporting, and a set of infrastructure utilities manages environment setup, error logging, and statistics collection.

2. Overview

2.1 Purpose & Scope

GenApp models a simplified general insurance company. It allows operators to:

  • Create, retrieve, and update customer records, including a security-separated sensitive data record.
  • Manage the full lifecycle of insurance policies across four product lines: Motor, Endowment, House, and Commercial.
  • Run batch reports against customer and motor-policy data.
  • Optionally invoke IBM Operational Decision Manager (ODM) to apply configurable business rules during Endowment policy creation.

2.3 Functional Domains

GenApp is divided into two primary functional domains:

Customer Management Covers the complete lifecycle of a customer entity: adding a new customer (with an optional security record), inquiring on existing customers, and updating customer details. All customer operations are dual-written to both DB2 and VSAM to ensure data consistency across the two storage tiers.

Insurance Policy Lifecycle Covers Add, Inquire, Update, and Delete operations for four policy types:

Policy Type CICS Transaction Orchestrator DB2 Detail Table
Motor SSP1 LGAPOL01 / LGUPOL01 MOTOR
Endowment SSP2 LGAPOL01 / LGUPOL01 ENDOWMENT
House SSP3 LGAPOL01 / LGUPOL01 HOUSE
Commercial SSP4 LGAPOL01 COMMERCIAL

3. Functional Layers

GenApp’s 35 PL/I programs are organized into six architectural layers, each with a distinct responsibility.

3.1 Presentation Layer

The presentation layer consists of five BMS-driven menu programs — one for each domain. They accept 3270 terminal input, populate a COMMAREA, and issue EXEC CICS LINK calls to the appropriate orchestrator.

Transaction Program Domain
SSC1 LGTESTC1 Customer menu
SSP1 LGTESTP1 Motor policy menu
SSP2 LGTESTP2 Endowment policy menu
SSP3 LGTESTP3 House policy menu
SSP4 LGTESTP4 Commercial policy menu

All menu programs include SSMAP.inc for BMS map I/O structures and LGCMAREA.inc for the shared COMMAREA. They are declared as reentrant procedures, receiving DFHEIPTR and COMM_AREA_PTR as parameters.

PLI 
/* Example: Motor Policy Menu invokes Add Policy orchestrator */
EXEC CICS LINK
    PROGRAM('LGAPOL01')
    COMMAREA(CA_DATA)
    LENGTH(CA_LEN);

3.2 Business Orchestration Layer

Orchestrators receive the COMMAREA from the presentation layer, validate the CA_REQUEST_ID field, and dispatch to the appropriate backend. They contain no direct SQL or VSAM file I/O.

Customer Orchestrators

Program Operation Cyclomatic Complexity
LGACUS01 Add Customer 25
LGICUS01 Inquire Customer 11
LGUCUS01 Update Customer 6

Policy Orchestrators

Program Operation Cyclomatic Complexity
LGAPOL01 Add Policy 9
LGIPOL01 Inquire Policy 5
LGDPOL01 Delete Policy 8
LGUPOL01 Update Policy 11

The CA_REQUEST_ID convention used by all orchestrators follows a six-character scheme:

CODE 
CA_REQUEST_ID = XX + VERB + ENTITY  (6 characters total)

XX     = '01'  (standard operation)
VERB   = A(dd) | I(nquire) | D(elete) | U(pdate)
ENTITY = CUS(tomer) | MOT(or) | END(owment) | HOU(se) | COM(mercial)

Examples:
  '01ACUS'  —  Add Customer
  '01IMOT'  —  Inquire Motor
  '01DEND'  —  Delete Endowment
  '01UHOU'  —  Update House

Return codes: '00' = success · '98' = bad COMMAREA length · '99' = DB2/system error.

The data access layer is split symmetrically between DB2 backends and VSAM backends. Each backend program has a single, well-defined responsibility.

3.4 Data Storage Layer

GenApp uses a dual-store pattern: every customer and policy write is mirrored to both DB2 and VSAM.

DB2 Schema — GENASA1

Table Tablespace Key Parent
CUSTOMER GENATS01 customerNumber (identity) —
CUSTOMER_SECURE GENATS0A customerNumber → CUSTOMER (cascade delete)
POLICY GENATS02 policyNumber (identity) → CUSTOMER (cascade delete)
ENDOWMENT GENATS03 policyNumber → POLICY (cascade delete)
HOUSE GENATS04 policyNumber → POLICY (cascade delete)
MOTOR GENATS05 policyNumber → POLICY (cascade delete)
COMMERCIAL GENATS06 policyNumber → POLICY (cascade delete)
CLAIM GENATS07 claimNumber (identity) → POLICY (cascade delete)

The entity relationship between DB2 tables is shown below:

erDiagram CUSTOMER ||--o{ POLICY : "has" CUSTOMER ||--o| CUSTOMER_SECURE : "has" POLICY ||--o| ENDOWMENT : "typed as" POLICY ||--o| HOUSE : "typed as" POLICY ||--o| MOTOR : "typed as" POLICY ||--o| COMMERCIAL : "typed as" POLICY ||--o{ CLAIM : "has"

Policy type is encoded in the POLICY.policyType column: M = Motor · E = Endowment · H = House · C = Commercial.

3.5 Batch Layer

The batch tier runs outside CICS and performs bulk customer and motor-policy reporting using sequential file I/O and direct DB2 access.

Program Role Input Output
LGBATCH Customer batch report CUSTIN (seq), CUSTOMER (DB2) CUSTRPT (seq)
LGBATDB2 DB2-driven customer report CUSTOMER (DB2) via LGBATCHF
LGBATCHF Formatting subprogram Called by LGBATCH / LGBATDB2 Formatted records
LGMOTOUT Motor policy output MOTOR (DB2) MOTOROUT (seq)

Batch programs use static CALL for subprogram invocation and Proc Options(Main) — they do not accept a COMMAREA parameter.

5. PL/I Include Files

All CICS programs share a common set of PL/I include files that standardize inter-program communication and data structures.

Include File Used By Purpose
LGCMAREA.inc All CICS programs 32,500-byte COMMAREA with CA_REQUEST_ID, CA_RETURN_CODE, CA_CUSTOMER_NUM, and UNION branches for each policy type
LGCMARER.inc LGAPOL01 → LGAPBR01 Compact 152-byte request/response area for IBM ODM business rules
SSMAP.inc Menu programs BMS map I/O structures (SSMAPP1I/O, SSMAPC1I/O, etc.)
DCLPOLIC.inc Policy backends Policy field declarations
DCLENDOW.inc Endowment backend Endowment-specific field declarations
LGPOLICY.inc Policy programs Policy data structure
SQLCA.inc All DB2 programs SQL Communication Area (SQLCODE, SQLERRM, etc.)

The COMMAREA layout — defined in LGCMAREA.inc — is the primary contract between all layers:

PLI 
/* Simplified LGCMAREA structure */
DCL 1 CA_AREA,
      3 CA_REQUEST_ID     CHAR(6),   /* e.g. '01ACUS' */
      3 CA_RETURN_CODE    CHAR(2),   /* '00'=OK, '98'=bad len, '99'=error */
      3 CA_CUSTOMER_NUM   CHAR(10),
      3 CA_POLICY_NUM     CHAR(10),
      3 CA_POLICY_DATA    UNION,
        5 CA_MOTOR_DATA   CHAR(...), /* Motor-specific fields   */
        5 CA_ENDOW_DATA   CHAR(...), /* Endowment-specific fields */
        5 CA_HOUSE_DATA   CHAR(...), /* House-specific fields    */
        5 CA_COMM_DATA    CHAR(...); /* Commercial-specific fields */

6. External Services & Integration

6.1 IBM Operational Decision Manager (ODM)

LGAPOL01 optionally invokes LGAPBR01 — an external IBM ODM business rules program — via EXEC CICS LINK when processing Endowment policy additions. The request and response are exchanged through the compact 152-byte LGCMARER.inc structure rather than the full COMMAREA.
