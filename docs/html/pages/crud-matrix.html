1. Overview

The GenApp system is a general insurance application running on z/OS that manages customers, policies, and claims across multiple insurance product lines — Motor, Endowment, House, and Commercial. All persistent data resides in the GENASA1 Db2 database, which contains eight core tables.

This document provides a comprehensive cross-reference matrix showing which programs perform Create (INSERT), Read (SELECT/FETCH), Update (UPDATE), and Delete (DELETE) operations against each Db2 table. It covers all online CICS-driven programs as well as offline batch programs, enabling impact analysis, migration planning, and governance for any data layer change.

Legend:

Symbol Operation
C INSERT — creates a new row
R SELECT / FETCH — reads one or more rows
U UPDATE — modifies an existing row
D DELETE — removes a row

5. Key Observations

The following architectural patterns and risk areas emerge from the full CRUD analysis:

5.1 High-Impact Programs

  • LGAPDB01 is the most data-intensive program in the system. It is the sole Create path for all six policy-related tables (POLICY, ENDOWMENT, HOUSE, MOTOR, COMMERCIAL, CLAIM) and additionally performs READ and UPDATE operations against POLICY. Any change to the policy creation logic or the schema of any child table requires modification of this single program.

  • LGIPDB01 is the sole Read path for all policy-type detail tables. It uses cursors for CLAIM and COMMERCIAL to handle multiple rows per policy. It is the universal inquiry backend and must be updated for any schema extension to a policy-type table.

  • LGACUS01 (orchestration layer) contains its own embedded SQL against both CUSTOMER and POLICY, bypassing the dedicated DB2 backend programs for the combined add-customer-and-policy use case. This dual-path design means schema changes to CUSTOMER or POLICY must be applied to LGACUS01 in addition to the dedicated backend programs.

5.2 Cascade-Only Deletion Pattern

No program issues a direct DELETE against the policy-type detail tables (ENDOWMENT, HOUSE, MOTOR, COMMERCIAL, CLAIM). All deletions of child rows are handled entirely by the ON DELETE CASCADE foreign key constraint triggered when LGDPDB01 deletes a POLICY parent row. This is an important constraint to preserve during any migration or schema refactoring.

5.3 Write-Once Security Table

The CUSTOMER_SECURE table is written exactly once per customer (LGACDB02) and is never read by any program in the GenApp core transaction flow. It exists purely for authentication purposes outside the main GenApp transaction set.

5.4 Read-Only Batch Programs

All batch programs (LGBATCH, LGBATDB2, LGMOTOUT) are strictly read-only against Db2. They perform no inserts, updates, or deletes, making them lower-risk candidates for independent migration or replacement.

5.5 Policy Deletion Sequence

The following sequence diagram illustrates the full flow when a policy is deleted, showing how the cascade works:

sequenceDiagram participant User as User (BMS Menu) participant Orch as LGDPOL01 (Orchestration) participant BE as LGDPDB01 (DB2 Backend) participant DB as Db2 — GENASA1 User->>Orch: CICS LINK (delete policy request) Orch->>BE: CICS LINK (COMMAREA with policy key) BE->>DB: EXEC SQL DELETE FROM POLICY WHERE POLICYNUM=:key DB-->>DB: ON DELETE CASCADE → removes child rows in\nENDOWMENT / HOUSE / MOTOR /\nCOMMERCIAL / CLAIM DB-->>BE: SQLCODE 0 (success) BE-->>Orch: Return COMMAREA (result code) Orch-->>User: Return response to BMS screen

This cascade behaviour means that LGDPDB01 is effectively the Delete path for seven tables — POLICY directly and all five product-type tables implicitly.
