Policy Presentation & Terminal Handlers

1. Overview

The Policy Presentation & Terminal Handlers layer is the interactive front-end of the GenApp general insurance application. It comprises four CICS PL/I pseudo-conversational programs — LGTESTP1, LGTESTP2, LGTESTP3, and LGTESTP4 — each responsible for managing a distinct class of insurance policy through a dedicated BMS terminal screen. Together, they cover the full spectrum of policy types supported by the application:

Program Transaction ID Policy Type BMS Map
LGTESTP1 SSP1 Motor Insurance SSMAPP1
LGTESTP2 SSP2 Endowment (Life) Insurance SSMAPP2
LGTESTP3 SSP3 House Insurance SSMAPP3
LGTESTP4 SSP4 Commercial Property Insurance SSMAPP4

Each program follows the same fundamental design pattern: present a BMS screen to the terminal operator, accept a single-character option to select an operation (Inquire, Add, Delete, or Update), package the screen data into a shared 32,500-byte COMMAREA, and delegate business logic to a set of backend policy orchestrator programs via EXEC CICS LINK. Results are reflected back to the screen with confirmation or error messages. All four programs are pseudo-conversational — they terminate the CICS task after each interaction and reschedule themselves under their respective transaction IDs, passing the COMMAREA forward to preserve session state.

2. System Architecture

The terminal handler layer sits at the topmost tier of a three-tier CICS architecture. The programs act purely as screen-handling and routing components — they contain no SQL, no file I/O, and no direct database access. All persistence is delegated downward through a chain of CICS LINK calls.

All four presentation programs share the same COMMAREA structure (LGCMAREA) and the same BMS mapset (SSMAP), which defines all five policy screen layouts in a single compiled resource. The CA_REQUEST_ID field within the COMMAREA acts as the routing key that tells each orchestrator which policy type and operation to execute.

3. Shared Design Patterns

3.1 Pseudo-Conversational Execution Model

All four programs implement the CICS pseudo-conversational pattern. Rather than holding a CICS task open while waiting for terminal input (which would waste server resources), each program:

  1. Processes the current user input.
  2. Sends the updated BMS map to the terminal.
  3. Issues EXEC CICS RETURN TRANSID('SSPx') COMMAREA(COMM_AREA) to terminate the task and re-arm the same transaction.
  4. On the next keypress, CICS restarts the program passing the saved COMMAREA back as program parameters.

3.2 COMMAREA Structure and Request Routing

All four programs share the LGCMAREA copybook, which defines a 32,500-byte union COMMAREA. The first few fields are common to all policy types; the remainder is a policy-type-specific union overlaid by CA_REQUEST_INITIALISER:

Field Type Purpose
CA_REQUEST_ID CHAR(6) Operation routing key (e.g., 01IMOT, 01AEND)
CA_RETURN_CODE PIC '99' Backend result — 0 = success, non-zero = error
CA_CUSTOMER_NUM PIC '9999999999' 10-digit customer identifier
CA_POLICY_NUM PIC '9999999999' 10-digit policy identifier
CA_ISSUE_DATE CHAR(10) Policy effective date
CA_EXPIRY_DATE CHAR(10) Policy expiry/maturity date
CA_REQUEST_INITIALISER CHAR(32482) Policy-specific data union / reset overlay
