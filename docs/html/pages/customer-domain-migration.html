Customer Domain Migration Analysis

This document provides a comprehensive analysis of the considerations, risks, and strategies for migrating the Customer Management domain from its current PL/I on z/OS implementation to a Java/REST microservice architecture. The domain comprises 10 PL/I programs interacting with DB2, VSAM, CICS, and shared infrastructure services. This analysis identifies critical cross-domain couplings, architectural constraints, and a recommended migration sequence to guide the modernisation effort.

1. Overview

The Customer Management domain is implemented across 10 PL/I programs running under CICS on z/OS, backed by DB2 tables (CUSTOMER, CUSTOMER_SECURE) and a VSAM dataset (KSDSCUST). The domain handles customer lifecycle operations — add, inquire, and update — and is tightly coupled to the Policy domain via shared DB2 tables, a shared flat binary COMMAREA contract, and CICS-managed transactional boundaries.

The migration targets a Java/REST microservice architecture. This is not a lift-and-shift: the implicit guarantees provided by CICS (single unit of work across a linked call chain, named counters, advisory locks, TS queues) must each be deliberately re-engineered. Ten discrete migration items have been identified, ranging from cross-domain data coupling to dead code stubs, and ranked by severity.

The architecture is characterised by a three-tier CICS LINK chain: a terminal-facing orchestrator links to typed backend programs (one for DB2, one for VSAM), which in turn call shared infrastructure services. All links execute within a single CICS transaction and a single DB2 unit of work — a guarantee that does not survive migration to REST microservices.

3. Ranked Migration Risks

The ten migration risks are ordered from most to least severe. The three critical risks must be resolved before any code migration begins.

3.1 🔴 RISK 1 — LGACUS01 Writes Directly to the POLICY Table

Category: Cross-domain data coupling · Severity: CRITICAL

LGACUS01 contains procedures INSERT_CUSTOMER_POLICY, TRANSFER_CUSTOMER_POLICY, and DELETE_CUSTOMER_POLICY — it writes to and reads from GENASA1.POLICY, a table owned by the Policy Management domain.

Why it matters: You cannot migrate the Customer domain independently. If LGACUS01 is lifted to a microservice while LGAPDB01 / LGDPDB01 / LGIPDB01 remain on the mainframe, both the new service and the remaining mainframe programs will be writing to the same POLICY table with no API boundary between them. This forces a choice: migrate both domains together, or carve out Policy ownership before touching Customer.

Migration actions:

  • Define which domain owns the POLICY table (Policy domain).
  • Replace LGACUS01’s direct POLICY SQL with an API call to a Policy service.
  • Design a Saga for the “add customer + add policy” combined flow that is currently a single synchronous operation.

3.2 🔴 RISK 2 — CICS LINK Shares One Transaction Unit of Work Across the Entire Call Chain

Category: Architecture · Severity: CRITICAL

Every call in the chain — LGTESTC1 → LGACUS01 → LGACDB01 → LGACVS01 + LGACDB02 — runs in a single CICS transaction with a single DB2 unit of work. If LGACDB02’s INSERT into CUSTOMER_SECURE fails, the entire chain rolls back automatically, including the CUSTOMER INSERT. This atomicity is implicit and free in CICS.

The sequence below illustrates the current implicit atomicity versus the explicit Saga pattern required after migration:

sequenceDiagram participant Caller as LGTESTC1 participant Orch as LGACUS01 participant DB1 as LGACDB01 participant DB2P as LGACDB02 participant VSAM as LGACVS01 Note over Caller,VSAM: Current: Single CICS Transaction (implicit rollback on any failure) Caller->>Orch: EXEC CICS LINK Orch->>DB1: EXEC CICS LINK DB1->>DB1: INSERT INTO CUSTOMER DB1->>DB2P: EXEC CICS LINK DB2P->>DB2P: INSERT INTO CUSTOMER_SECURE DB2P-->>DB1: Return DB1-->>Orch: Return Orch->>VSAM: EXEC CICS LINK VSAM->>VSAM: WRITE KSDSCUST VSAM-->>Orch: Return Orch-->>Caller: Return (CICS SYNCPOINT — all committed or all rolled back)

Why it matters: REST calls across microservice boundaries do not share a DB2 unit of work. Once LGACDB01’s INSERT into CUSTOMER is committed, there is no automatic rollback if LGACDB02 subsequently fails. Every inter-service call now requires an explicit compensating action (delete the customer row) or a Saga coordinator.

Migration actions:

  • Implement a Saga pattern for the Add Customer flow (DB2 insert → VSAM write → security insert).
  • Define a compensating transaction (DELETE FROM CUSTOMER WHERE CUSTOMERNUMBER = ?) that fires if the security step fails.
  • The VSAM write (Risk 4) further complicates this because VSAM does not participate in DB2 rollback.

3.3 🔴 RISK 3 — LGCMAREA.inc Is the Contract for All 10 Programs and the Caller

Category: Shared module · Severity: CRITICAL

LGCMAREA.inc is a 32,500-byte flat binary structure shared by all 10 programs plus LGTESTC1. Customer fields (CA_FIRST_NAME through CA_EMAIL_ADDRESS) are accessed by byte offset within this buffer. There are no accessor methods, no type safety, and no versioning. PIC '9999999999' fields are zoned decimal; CHAR(n) fields are EBCDIC space-padded.

Why it matters: The COMMAREA is the API contract. Every field must be mapped to a typed Java DTO. Any field offset misidentified during this mapping produces silent data corruption — no compile-time check catches it. The COMMAREA also has no version field, so the new API must introduce versioning from day one.

Migration actions:

  • Produce a complete field-level mapping document from every CA_* customer field to a typed Java DTO.
  • Pay particular attention to data type conversions (see table below).
  • Version the REST API from the outset (/api/v1/customers); the COMMAREA has no version concept.

COMMAREA to Java DTO type mapping:

PL/I / COMMAREA Type Java DTO Type Notes
PIC '9(10)' (zoned decimal) long Numeric customer/policy numbers
CHAR(n) (EBCDIC) String (trimmed) Space-padded; must trim on read
PIC '99' return code enum / int Map to HTTP status or domain enum
PIC '9(8)' date LocalDate Parse YYYYMMDD string
Binary signed halfword short / int Check endianness on extraction

3.4 🟠 RISK 4 — VSAM KSDSCUST Has No Rollback Coordination with DB2

Category: Shared data · Severity: HIGH

KSDSCUST is a parallel store written synchronously after every DB2 INSERT/UPDATE. The VSAM write is not part of the DB2 unit of work. If LGACVS01 abends on WRITE (abend LGV0), the customer row already committed in DB2 is not rolled back.

Why it matters:

  • Option A (Decommission): KSDSCUST appears to serve primarily as a mirror and a customer-number discovery source for demo/test purposes (LGICVS01). If no external system reads it directly, it can be dropped — eliminating three programs and their risk.
  • Option B (Migrate): If KSDSCUST has external consumers, it must be replaced with a cache layer that has explicit consistency guarantees.

Migration actions:

  • Confirm whether any system outside this codebase reads KSDSCUST directly.
  • If not: decommission LGACVS01, LGICVS01, LGUCVS01 as part of migration.
  • If yes: replace with an event-driven cache update pattern (CustomerCreated/CustomerUpdated events → cache service).

3.5 🟠 RISK 5 — GENACUSTNUM Named Counter Creates a Dual ID-Generation Path

Category: Shared infrastructure · Severity: HIGH

Both LGACDB01 and LGACUS01 call EXEC CICS GET COUNTER(GENACUSTNUM) before the DB2 INSERT. If the counter fails, both fall back to IDENTITY_VAL_LOCAL() — a DB2 function that returns the last identity value assigned on the current connection. In a Java connection pool, the connection may be returned to the pool between the INSERT and the IDENTITY_VAL_LOCAL() call, returning a wrong value.

CODE 
/* Current PL/I pattern — fragile under Java connection pooling */
EXEC CICS GET COUNTER('GENACUSTNUM')
     VALUE(WS-CUSTOMER-NUM)
     RESP(WS-CICS-RESP);

IF WS-CICS-RESP NOT = DFHRESP(NORMAL) THEN
    /* Fall back to DB2 identity — UNSAFE under connection pool */
    EXEC SQL SELECT IDENTITY_VAL_LOCAL()
             INTO :WS-CUSTOMER-NUM
             FROM SYSIBM.SYSDUMMY1;
END-IF;

Why it matters: The CICS Named Counter Server has no Java equivalent. It must be replaced. The CUSTOMER table already has GENERATED BY DEFAULT AS IDENTITY (START WITH 1000001), so the fallback is already correct — but the counter call must be removed, and IDENTITY_VAL_LOCAL() must be replaced with JDBC getGeneratedKeys().

Migration actions:

  • Remove CICS counter calls; use DB2 identity exclusively.
  • Replace IDENTITY_VAL_LOCAL() with JDBC PreparedStatement.RETURN_GENERATED_KEYS + stmt.getGeneratedKeys().
  • Ensure the identity start value does not collide with existing customer numbers.

Java replacement pattern:

JAVA 
String sql = "INSERT INTO GENASA1.CUSTOMER (FIRSTNAME, LASTNAME, ...) VALUES (?, ?, ...)";
try (PreparedStatement stmt = conn.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {
    stmt.setString(1, customer.getFirstName());
    stmt.setString(2, customer.getLastName());
    // ... bind remaining parameters
    stmt.executeUpdate();

    try (ResultSet keys = stmt.getGeneratedKeys()) {
        if (keys.next()) {
            long customerId = keys.getLong(1); // Safe: connection-scoped
        }
    }
}

3.6 🟠 RISK 6 — DB2 FK CASCADE from POLICY to CUSTOMER Creates Silent Cross-Domain Deletes

Category: Cross-domain dependency · Severity: HIGH

GENASA1.POLICY has FOREIGN KEY(customerNumber) REFERENCES GENASA1.CUSTOMER ON DELETE CASCADE. There is currently no Delete Customer operation in the domain. Any future delete built into the migrated service will silently delete all policies for that customer without notifying the Policy service.

Why it matters: A Customer microservice that issues DELETE FROM CUSTOMER WHERE CUSTOMERNUMBER = ? will cascade-delete all POLICY rows, all ENDOWMENT/HOUSE/MOTOR/COMMERCIAL/CLAIM rows — all Policy domain data — without the Policy service being aware. This is an invisible cross-domain dependency.

Migration actions:

  • Document the FK cascade as a cross-domain constraint before migration begins.
  • Any DELETE /customers/{id} endpoint must call the Policy service first to confirm no active policies exist (or explicitly request their deactivation).
  • Do not rely on the DB2 cascade in a microservice architecture.

3.7 🟡 RISK 7 — LGSTSQ Is a Shared Cross-Cutting Error Service

Category: Shared module · Severity: MEDIUM

All 10 programs call LGSTSQ (Operations domain) on every error path. LGSTSQ writes to TDQ CSMT and TS queue GENAERRS. It is not a domain-internal component.

Why it matters: If LGSTSQ is retired before all programs are migrated, error logging breaks silently — EXEC CICS LINK to a missing program causes PGMIDERR with no fallback logging path. This is the worst possible failure mode for an error handler.

Migration actions:

  • Replace all EXEC CICS LINK PROGRAM('LGSTSQ') calls with structured logging (e.g., SLF4J/Logback to a centralised log system) before migrating any program.
  • Keep the mainframe LGSTSQ operational until the last program in the domain is decommissioned.

Java replacement pattern:

JAVA 
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class CustomerService {
    private static final Logger log = LoggerFactory.getLogger(CustomerService.class);

    public CustomerDTO addCustomer(CustomerRequest req) {
        try {
            // ... business logic
        } catch (DataAccessException ex) {
            // Replaces: EXEC CICS LINK PROGRAM('LGSTSQ')
            log.error("CustomerService.addCustomer failed for request={} error={}",
                      req, ex.getMessage(), ex);
            throw new CustomerServiceException("ADD_FAILED", ex);
        }
    }
}

3.8 🟡 RISK 8 — CICS ENQ/DEQ in LGICVS01 Has No Direct Java Equivalent

Category: Architecture · Severity: MEDIUM

LGICVS01 wraps its GENACNTL TS queue read-modify-write in EXEC CICS ENQ/DEQ to prevent concurrent corruption of the LOW/HIGH CUSTOMER range. CICS advisory locks have no direct equivalent in stateless Java microservices.

Why it matters: LGICVS01 is a demo/test utility for customer number discovery. However, ENQ/DEQ represents the general CICS pattern for shared mutable in-memory state — any future discovery of similar patterns elsewhere in the application must be handled the same way.

Migration actions:

  • Since LGICVS01 is a demo utility: decommission it or replace with a simple DB2 query (SELECT MIN/MAX(CUSTOMERNUMBER) FROM CUSTOMER), which is inherently transactionally safe.
  • For the general ENQ/DEQ pattern: establish a project policy that all shared mutable state must be backed by DB2 (SELECT ... FOR UPDATE) or a distributed lock (Redis Redlock).

3.9 🟡 RISK 9 — Batch Programs Read CUSTOMER Table Outside the Domain

Category: Shared data · Severity: MEDIUM

Both LGBATCH and LGBATDB2 (Batch Reporting domain) execute SELECT against GENASA1.CUSTOMER. They are read-only but bypass any API layer the migrated Customer service introduces.

Why it matters: If the migrated Customer microservice owns the CUSTOMER table, these batch programs will be reaching directly into the new service’s database — violating the database-per-service principle and bypassing any future business rules applied at the API layer.

Migration actions:

  • Short term (strangler fig): Allow the batch programs to continue reading CUSTOMER directly from DB2 while the migration proceeds.
  • Long term: Expose a batch-query API from the Customer service, or provide a dedicated reporting read replica that batch programs access without touching the transactional database.

3.10 🟢 RISK 10 — Dead MQ Cache Stub in LGICUS01

Category: Dead code · Severity: LOW

LGICUS01 checks TS queue GENAWMQC for an MQHIT= record and, if found, calls the non-existent program AAAAAAAA. This code has never been completed and will cause PGMIDERR if triggered.

Why it matters: This is a latent defect that must not be carried forward. It also signals that a caching layer for customer inquiries was once planned — the migration is an opportunity to implement it properly.

Migration actions:

  • Remove the GENAWMQC check and the AAAAAAAA branch from LGICUS01 before migration.
  • Optionally implement the originally intended cache as a Redis GET/SET around the SELECT FROM CUSTOMER query in the new service.

Intended Redis cache pattern (Java):

JAVA 
public CustomerDTO getCustomer(long customerId) {
    String cacheKey = "customer:" + customerId;

    // Check cache first (replaces the intended GENAWMQC TS queue lookup)
    String cached = redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) {
        return objectMapper.readValue(cached, CustomerDTO.class);
    }

    // Cache miss: query DB2
    CustomerDTO dto = customerRepository.findById(customerId)
        .orElseThrow(() -> new CustomerNotFoundException(customerId));

    // Populate cache with TTL
    redisTemplate.opsForValue().set(cacheKey,
        objectMapper.writeValueAsString(dto),
        Duration.ofMinutes(10));

    return dto;
}
