Statistics & Monitoring

The GenApp insurance application includes a purpose-built, self-sustaining statistics pipeline that continuously tracks, aggregates, and exposes transaction activity data for operational monitoring and dashboard consumption. This pipeline is composed of two cooperating CICS PL/I programs — LGASTAT1 and LGWEBST5 — that together form a complete event-counting and rate-reporting subsystem. LGASTAT1 acts as the event-processing adapter target, incrementing named counters for each business transaction outcome, while LGWEBST5 acts as the periodic collector daemon that harvests those counters every minute, computes per-interval deltas, and persists the results into CICS Temporary Storage Queues (TSQs) for downstream consumers.

1. System Architecture

The statistics subsystem operates as a two-stage pipeline within a CICS region. Business transactions trigger LGASTAT1 on every completion event, feeding named counters in the GENA pool. Independently, LGWEBST5 runs on a one-minute self-scheduling loop, reading those counters, computing delta rates, and writing structured TSQ records for dashboards or monitoring screens to consume.

2. Overview

The statistics pipeline addresses two distinct operational concerns:

  • Event counting (LGASTAT1): Each time a GenApp business operation completes — successfully or not — LGASTAT1 is invoked and increments the appropriate named counter in the GENA pool. Counter names encode both the operation type and the outcome, providing a fine-grained, always-current tally of activity.

  • Rate reporting (LGWEBST5): Once per minute, LGWEBST5 wakes up, reads all 35 named counters, computes the delta since the previous run, and persists three values per counter (new snapshot, old snapshot, delta) into dedicated TSQs. It also writes rolled-up totals by operation category (inquire, add, update, delete) and reschedules itself for the next minute.

Together, these programs provide a lightweight, CICS-native monitoring solution requiring no external database, no batch jobs, and no manual intervention to sustain.

3. LGASTAT1 — Event-Processing Adapter

3.1 Purpose

LGASTAT1 is the statistics counter update program that acts as the event-processing adapter target for all GenApp business transactions. It is invoked after each transaction completes and uses the supplied request identifier and return code to construct a named counter key of the form GENA<request><type> in the GENA pool. It normalises certain request codes to canonical equivalents and collapses all non-success return codes into a generic failure suffix (99), ensuring consistent bucketing. It also performs a one-time initialisation of the GENASTRT temporary storage queue, recording the statistics start date and time on first invocation.

3.2 Inputs

LGASTAT1 accepts input from two sources, tried in priority order:

Source Field Width Description
CICS Channel Container DFHEP.DATA.00001 WS_DATA_REQ 6 chars Request identifier (primary source)
CICS Channel Container DFHEP.DATA.00002 WS_DATA_RC 2 chars Return code (primary source)
COMMAREA fallback CA_REQUEST_ID 6 chars Business operation code (e.g. 01IMOT)
COMMAREA fallback CA_RETURN_CODE 2 digits Transaction outcome code

If both sources are unavailable (no channel data and EIBCALEN = 0), the program returns immediately with no output.

3.3 Counter Naming Convention

Named counters in the GENA pool follow a fixed 16-character structure:

CODE 
GENA  +  <GENACOUNTER>  +  <GENATYPE>  +  <4 trailing spaces>
 4ch        6 chars          2 chars          4 chars

Example counter names:

Counter Name Meaning
GENA01IMOT00 Successful motor policy inquiry
GENA01ACUS99 Failed add-customer request
GENA01ICOM00 Successful commercial policy inquiry
GENA01ICUS00 Successful customer inquiry

The outcome suffix is binary: 00 = success, 99 = any failure. No per-error-code granularity is stored.

3.4 Counter Normalisation Rules

Before the counter name is assembled, LGASTAT1 applies the following business-rule normalisations to prevent counter fragmentation:

Raw Input Value Normalised To Reason
02ACUS 01ACUS Add Customer variant 2 merged into variant 1
02ICOM 01ICOM Inquire Commercial variant 2 merged into variant 1
03ICOM 01ICOM Inquire Commercial variant 3 merged into variant 1
05ICOM 01ICOM Inquire Commercial variant 5 merged into variant 1
Any non-00 return code 99 All failures grouped into a single failure bucket
CODE 
/* PL/I normalisation logic */
IF GENACOUNTER = '02ACUS' THEN GENACOUNTER = '01ACUS';
IF GENACOUNTER = '02ICOM' |
   GENACOUNTER = '03ICOM' |
   GENACOUNTER = '05ICOM' THEN GENACOUNTER = '01ICOM';
IF GENATYPE ^= '00'       THEN GENATYPE   = '99';

3.5 Startup Initialisation — GENASTRT Queue

On the very first invocation of LGASTAT1 in a CICS region session, the program writes a startup timestamp record to the TS queue GENASTRT. This record serves as a persistent marker showing when statistics collection began.

  • Queue name: GENASTRT (8 chars, hardcoded)
  • Record content: 16-byte WS_QAREA containing formatted date (DD/MM/YYYY) and time (HH:MM:SS)
  • Write condition: Only when READQ TS returns DFHRESP(QIDERR) — i.e., the queue does not yet exist
  • Subsequent runs: The queue is read but not rewritten
CODE 
/* PL/I initialisation guard */
EXEC CICS READQ TS QUEUE(WS_QNAME) INTO(WS_QAREA)
          LENGTH(WS_QLEN) RESP(WS_RESP);
IF WS_RESP = DFHRESP(QIDERR) THEN DO;
    EXEC CICS ASKTIME ABSTIME(WS_ABSTIME);
    EXEC CICS FORMATTIME ABSTIME(WS_ABSTIME)
              DDMMYYYY(WS_DATE) TIME(WS_TIME);
    WS_AREA_D = WS_DATE;
    WS_AREA_T = WS_TIME;
    WS_QLEN   = STG(WS_QAREA);
    EXEC CICS WRITEQ TS QUEUE(WS_QNAME) FROM(WS_QAREA)
              LENGTH(WS_QLEN) RESP(WS_RESP);
END;

Channel container GET fails Silently falls back to COMMAREA

Non-zero return code Collapsed to 99 preventing lookup of undefined counters
All EXEC CICS commands RESP(WS_RESP) used globally; automatic CICS abend suppressed

4. LGWEBST5 — Self-Scheduling Statistics Collector

4.1 Purpose

LGWEBST5 is a CICS-hosted PL/I statistics collection daemon that runs as transaction SSST. On each invocation it queries all 35 CICS named counters representing GenApp business operations, computes per-interval delta rates (new minus old), and writes the results — along with rolled-up totals by operation category — into CICS Temporary Storage Queues. Before finishing, it schedules its own re-invocation one minute later via EXEC CICS START TRANSID('SSST') AFTER MINUTES(1), creating a perpetually self-sustaining collection cycle.

4.2 The SSST Transaction Scheduling Loop

The self-scheduling mechanism is the backbone of the collection pipeline. It ensures continuous operation without any external scheduler, batch job, or operator intervention.

sequenceDiagram autonumber participant CICS as CICS Region participant LGWEBST5 as LGWEBST5 (SSST) participant NC as Named Counter Pool GENA participant TSQ as Temporary Storage Queues participant SCHED as CICS Scheduler CICS->>LGWEBST5: Dispatch transaction SSST LGWEBST5->>LGWEBST5: Capture EIB fields, get current time LGWEBST5->>TSQ: READQ TS GENA000V (previous timestamp) TSQ-->>LGWEBST5: Previous HHMMSS (or default 120000) LGWEBST5->>TSQ: DELETEQ + WRITEQ GENA000V (current time + elapsed seconds) LGWEBST5->>SCHED: EXEC CICS START TRANSID(SSST) AFTER MINUTES(1) LGWEBST5->>NC: QUERY COUNTER GENACUSTNUM NC-->>LGWEBST5: Current customer count LGWEBST5->>TSQ: Write GENAX05V (new/old/delta) loop For each of 17 operation counters LGWEBST5->>NC: QUERY COUNTER CT_SUCCESS(I) NC-->>LGWEBST5: Current success count LGWEBST5->>TSQ: READQ/DELETEQ/WRITEQ GENAV LGWEBST5->>NC: QUERY COUNTER CT_ERROR(I) NC-->>LGWEBST5: Current error count end LGWEBST5->>TSQ: Write GENAX00V–GENAX04V (aggregate totals) LGWEBST5->>CICS: EXEC CICS RETURN Note over CICS,SCHED: 60 seconds elapse CICS->>LGWEBST5: Re-dispatch SSST (cycle repeats)

The scheduling call is placed early — inside TRAN_RATE_INTERVAL, before any counter queries — so that the next run is always registered even if subsequent processing encounters minor errors.

4.3 Named Counters Harvested

LGWEBST5 queries 35 named counters per run, all residing in pool GENA:

Category Counter Pattern Count Example
Customer number sequence GENACUSTNUM 1 Tracks total customers created
Success counters GENA01<OP><ENTITY>00 17 GENA01ICUS00, GENA01AMOT00
Error counters GENA01<OP><ENTITY>99 17 GENA01ICUS99, GENA01DCOM99

The 17 operation/entity combinations cover all GenApp business operations:

Operation Code Type Entities covered
I Inquire Customer, Motor, Endowment, House, Commercial
A Add Customer, Motor, Endowment, House, Commercial
U Update Motor, Endowment, House, Commercial
D Delete Motor, Endowment, House, Commercial

4.4 TSQ Layout and Naming Convention

Each counter managed by LGWEBST5 has a dedicated 3-item TSQ:

CODE 
TSQ Name: GENA + <3-or-4-char code> + V   (total 8 chars)

Item 1  — NRATEVAL (9 chars)  — Current counter snapshot
Item 2  — ORATEVAL (9 chars)  — Previous counter snapshot (from last run)
Item 3  — DRATEVAL (9 chars)  — Absolute delta (NRATEVAL − ORATEVAL)

Inventory of all TSQs written by LGWEBST5:

TSQ Name Contents
GENA000V Item 1: previous run HHMMSS; Item 2: elapsed seconds
GENAX05V GENACUSTNUM customer counter (new/old/delta)
GENA100V GENA01ICUS00 — Inquire Customer success
GENA200V GENA01ACUS00 — Add Customer success
GENA300V GENA01IMOT00 — Inquire Motor success
GENA400V GENA01AMOT00 — Add Motor success
(one per counter, codes 100–H00) Per-operation success counters (17 total)
GENAX00V Total success count (all operations)
GENAX01V Total inquire count
GENAX02V Total add count
GENAX03V Total update count
GENAX04V Total delete count

4.5 Internal Subroutines

4.5.1 TRAN_RATE_INTERVAL

This subroutine is called once per execution, immediately after time retrieval. It is responsible for:

  1. Reading the previous run timestamp from GENA000V item 1 (defaults to '120000' if absent — first run)
  2. Deleting and rewriting GENA000V item 1 with the current HHMMSS
  3. Converting both timestamps to seconds-since-midnight and computing the absolute difference (ICOUNTVAL)
  4. Writing the elapsed seconds to GENA000V item 2
  5. Scheduling the next execution via EXEC CICS START TRANSID('SSST') AFTER MINUTES(1)
CODE 
/* PL/I elapsed-seconds calculation */
NCOUNTVAL = (HHVAL * 3600) + (MMVAL * 60) + SSVAL;   /* current  */
OCOUNTVAL = (HHVAL * 3600) + (MMVAL * 60) + SSVAL;   /* previous */
ICOUNTVAL = ABS(NCOUNTVAL - OCOUNTVAL);               /* delta    */
WS_NEWV   = ICOUNTVAL;

EXEC CICS START TRANSID('SSST')
          AFTER MINUTES(1)
          RESP(WS_RESP);

4.5.2 TRAN_RATE_COUNTS

This reusable subroutine is called once per counter (18 individual counters + 5 aggregates = 23 calls per run). It manages the 3-item TSQ for any given counter:

CODE 
/* PL/I TRAN_RATE_COUNTS logic */
EXEC CICS READQ TS QUEUE(WS_TSQNAME) INTO(WS_TSQDATA)
          LENGTH(WS_TSQLEN) ITEM(1) RESP(WS_RESP);

IF WS_RESP = DFHRESP(NORMAL) THEN
    ORATEVAL = WS_TSQDATA;   /* use stored previous value */
ELSE
    ORATEVAL = 0;             /* first run — default to zero */

EXEC CICS DELETEQ TS QUEUE(WS_TSQNAME) RESP(WS_RESP);

EXEC CICS WRITEQ TS QUEUE(WS_TSQNAME) FROM(NRATEVAL)  /* item 1: new   */
          LENGTH(WS_TSQLEN) RESP(WS_RESP);
EXEC CICS WRITEQ TS QUEUE(WS_TSQNAME) FROM(ORATEVAL)  /* item 2: old   */
          LENGTH(WS_TSQLEN) RESP(WS_RESP);
DRATEVAL = ABS(NRATEVAL - ORATEVAL);
EXEC CICS WRITEQ TS QUEUE(WS_TSQNAME) FROM(DRATEVAL)  /* item 3: delta */
          LENGTH(WS_TSQLEN) RESP(WS_RESP);

4.7 Accumulator and Aggregation Logic

After the 17-counter loop completes, the six accumulators hold the following rolled-up totals:

Accumulator TSQ Written Description
COUNTSUCCESS GENAX00V All successful transactions across all operation types
COUNTERRORS (internal only) All failed transactions — not written to a TSQ in current implementation
COUNTINQ GENAX01V Successful inquiry operations
COUNTADD GENAX02V Successful add operations
COUNTUPD GENAX03V Successful update operations
COUNTDEL GENAX04V Successful delete operations

Each aggregate is written via TRAN_RATE_COUNTS, producing the same new/old/delta 3-item TSQ structure as individual counters.

4.8 Error Handling

Scenario Handling Strategy
GENA000V queue missing on first run WS_OLDV defaulted to '120000' — prevents uninitialised arithmetic
Any rate TSQ missing on first run ORATEVAL defaulted to 0 — delta equals full cumulative value
DELETEQ TS failure RESP captured, not evaluated — silently tolerated
WRITEQ TS failure RESP captured, not evaluated — processing continues
QUERY COUNTER failure RESP captured, not evaluated — COUNTVAL retains prior value; accumulators may be slightly off
START TRANSID('SSST') failure RESP captured, not evaluated — collection chain halts silently if scheduling fails
Negative delta (counter wrap or midnight crossing) ABS() applied to all delta computations — prevents negative TSQ values

6. Worked Examples

6.1 Example: First-Run Behaviour

On the very first execution of the statistics pipeline, no TSQs exist. The following describes how both programs initialise gracefully:

LGASTAT1 — first invocation:

  • Input: channel containers carry 01ACUS / 00 (successful add customer)
  • READQ TS GENASTRT returns QIDERR → startup record written with current date/time
  • Counter name assembled: GENA01ACUS00
  • GET COUNTER retrieves current value (may be 0 on a fresh region); counter is incremented

LGWEBST5 — first invocation:

  • GENA000V is absent → elapsed time defaults to seconds since 12:00:00
  • All 17 rate TSQs are absent → ORATEVAL = 0 for every counter; delta = full cumulative value
  • All TSQs are created fresh; SSST is scheduled for T+1 minute
  • Aggregate TSQs GENAX00V–GENAX04V written with deltas equal to total cumulative counts

6.2 Example: Subsequent Run with Activity

Scenario: Sixty seconds after the previous run, 25 new successful motor policy inquiries have occurred.

Named Counter Previous Value Current Value Delta
GENA01IMOT00 30 55 25

TSQ GENA300V after TRAN_RATE_COUNTS:

CODE 
Item 1  →  000000055   (new snapshot)
Item 2  →  000000030   (previous snapshot)
Item 3  →  000000025   (delta — 25 new inquiries this minute)

A dashboard reads item 3 to display “25 motor inquiries in the last interval” without needing to maintain any state of its own.

6.3 Example: Counter Normalisation in Action

A caller invokes LGASTAT1 with CA_REQUEST_ID = '02ACUS' and CA_RETURN_CODE = '05':

CODE 
Step 1  GENACOUNTER = '02ACUS',  GENATYPE = '05'
Step 2  Normalisation: '02ACUS' → '01ACUS'
Step 3  Normalisation: '05' ≠ '00' → GENATYPE = '99'
Step 4  Counter name: GENA + 01ACUS + 99 + '    '
                    = 'GENA01ACUS99    '
Step 5  GET COUNTER on 'GENA01ACUS99    ' in pool 'GENA'

The failed add-customer variant is correctly tallied under the single canonical failure counter GENA01ACUS99, regardless of whether the call arrived with code 01ACUS or 02ACUS and regardless of which specific non-zero return code was returned.

7. Constraints and Limitations

7.1 Counter and Field Size Constraints

Element Size / Limit Implication
Counter name 16 chars (fixed) Pool GENA + 6-char request + 2-char type + 4 spaces
Rate value fields (NRATEVAL, ORATEVAL, DRATEVAL) PIC '999999999' (9 digits, max 999,999,999) Silent overflow if counters exceed ~1 billion
TSQ name 8 chars (fixed) GENA prefix + fixed suffix; no dynamic variation
Elapsed-seconds field (ICOUNTVAL) PIC '999999' (6 digits) Max 999,999 seconds; practical limit is 86,399 (one day)
COMMAREA raw size 32,500 bytes Hard upper bound on COMMAREA data accessible to LGASTAT1

7.2 Scheduling Constraints

  • Restart interval is fixed at 1 minute — not configurable at runtime.
  • If LGWEBST5 abends before TRAN_RATE_INTERVAL executes, no START TRANSID('SSST') is issued and the collection chain halts permanently until manually restarted.
  • Midnight crossing is handled by ABS() but produces an anomalous interval value (~23.9 hours) for the single run that spans midnight. This is a known design limitation.

7.3 Structural Constraints

  • Exactly 17 counters are processed per LGWEBST5 run. The counter arrays are statically sized; no runtime extension is possible.
  • CT_OPS must contain only I, A, U, or D at each position. Any other character causes an unhandled PL/I SELECT condition.
  • All counters must reside in pool GENA — the pool name is a compile-time constant in both programs.
  • TSQs are globally shared — queue names include no terminal, task, or user qualifier, meaning concurrent instances of LGWEBST5 would corrupt each other’s state.
