Customer Domain Migration & Risk Analysis

This document provides a comprehensive application-level impact analysis and risk assessment for modernizing, refactoring, and decoupling the Customer Domain within the GenApp PL/I application. It evaluates data integrity constraints, dual-store consistency issues, shared infrastructure elements, monolithic contract couplings, and cross-domain dependencies to inform architectural migration strategies.

1. Overview

The Customer Domain is responsible for Customer Lifecycle Management across the GenApp insurance suite, providing business functions to create, inquire, update, and manage customer master records, provision security credentials, and maintain shadow records.

1.1 Business Objectives and Scope

The primary objective of this analysis is to establish an evidence-based risk inventory before committing to a target architecture or modernization path. The analysis encompasses:

  • Core presentation and menu dispatching (LGTESTC1 under CICS transaction SSC1).
  • Orchestration and business logic programs (LGACUS01, LGICUS01, LGUCUS01).
  • Relational data persistence routines against DB2 tables (CUSTOMER, CUSTOMER_SECURE).
  • Parallel shadow persistence routines against VSAM KSDS dataset (KSDSCUST).
  • Shared memory contracts (LGCMAREA.inc, LGPOLICY.inc), temporary storage queues (GENACNTL, LGSTSQ), and CICS Named Counters (GENACUSTNUM).
  • Cross-domain interactions with the Policy Domain (POLICY table) and external Batch extract consumers (LGBATCH, LGBATDB2).

1.2 Summary of Key Findings

  1. Monolithic Multi-Domain Orchestrator (LGACUS01): High cyclomatic complexity (CC=25) with cross-domain SQL (INSERT, SELECT, DELETE) targeting the POLICY table directly.
  2. Dual-Store Inconsistency Risk: Asynchronous / non-2PC dual-writes across DB2 (CUSTOMER) and VSAM (KSDSCUST) lead to split-brain states when VSAM writes fail after DB2 commits.
  3. Pervasive Monolithic Data Contract (LGCMAREA.inc): A single 32,500-byte shared buffer binds every CICS program across all domains.
  4. Referential Integrity Constraints: Hard DB2 foreign keys exist between POLICY.CUSTOMERNUMBER and CUSTOMER.CUSTOMERNUMBER, posing data integrity risks if data stores are partitioned into microservices.

The Customer Domain spans three functional tiers: the presentation layer, the business orchestration layer, and the persistence backend layer (supporting dual DB2 and VSAM storage).

3.2 Deep-Dive: LGACUS01 (Primary Critical Hot-Spot)

LGACUS01 is the single highest-risk program in the Customer Domain. Rather than functioning strictly as a Customer orchestrator, it incorporates end-to-end policy lifecycle management directly within its procedure divisions.

Three of its thirteen internal procedures perform direct data manipulation on the Policy Domain’s POLICY table:

  1. INSERT_CUSTOMER_POLICY (Lines 590–647): Direct SQL INSERT INTO POLICY.
  2. TRANSFER_CUSTOMER_POLICY (Lines 653–710): Direct SQL INSERT INTO POLICY during customer transfer.
  3. DELETE_CUSTOMER_POLICY (Lines 717–734): Direct SQL DELETE FROM POLICY WHERE CUSTOMERNUMBER = :hv_custnum.

3.3 Deep-Dive: LGTESTC1 Presentation Complexity

LGTESTC1 acts as the terminal-facing controller. Key migration obstacles in this program include:

  • Pseudo-Conversational Coupling: State is passed back and forth within the 32,500-byte COMMAREA using EXEC CICS RETURN TRANSID('SSC1') COMMAREA(COMM_AREA).
  • Presentation-Layer Transaction Boundaries: Contains explicit transaction control statements:
    PLI 
    EXEC CICS SYNCPOINT ROLLBACK;
  • Shared Memory Locking: Uses explicit EXEC CICS ENQ and DEQ against resource GENACNTL to safely synchronize customer number ranges in temporary storage.
  • Unstructured Control Flow: Uses legacy non-structured branching (GO TO NO_DATA, GO TO NO_ADD, GO TO ERROR_OUT).

3.4 Deep-Dive: LGACDB01 Logic Duplication

LGACDB01 duplicates the OBTAIN_CUSTOMER_NUMBER and INSERT_CUSTOMER logic found in LGACUS01. It provides a standalone DB2 Add path that accesses the CICS Named Counter server, falling back to database default identity generation on failure:

PLI 
/* CICS Named Counter invocation in LGACDB01 / LGACUS01 */
 EXEC CICS GET COUNTER(GENACOUNT)
           POOL(GENAPOOL)
           VALUE(LASTCUSTNUM)
           RESP(WS_RESP);

 IF WS_RESP ^= DFHRESP(NORMAL) THEN DO;
     LGAC_NCS = 'NO';
     /* Falls back to DB2 identity column generation */
 END;

4. Shared Code and Infrastructure Couplings

Decoupling the Customer Domain requires addressing shared data structures, duplicated routines, and platform-specific middleware APIs.

4.1 Monolithic COMMAREA Structure (LGCMAREA.inc)

The universal interface contract across all CICS programs is LGCMAREA.inc (32,500 bytes).

Because Customer, Policy, and Security sub-structures overlap within this single buffer, any modification to field offsets or widths requires a global recompilation of all 10 Customer programs and all Policy programs.

4.2 Shared Include Dependency (LGPOLICY.inc)

While LGCMAREA.inc governs program-to-program linkages, LGPOLICY.inc supplies DB2 host variable structures for CUSTOMER, POLICY, MOTOR, HOUSE, ENDOWMENT, and COMMERCIAL tables. LGACUS01 includes this file via EXEC SQL INCLUDE LGPOLICY, creating a compile-time dependency on Policy database definitions.

4.3 Redundant Error Logging (LGSTSQ and Duplicated Code)

Every Customer program contains an identical internal procedure WRITE_ERROR_MESSAGE that formats timestamp data and links to LGSTSQ:

PLI 
WRITE_ERROR_MESSAGE: PROCEDURE;
     /* Timestamp formatting and buffer population */
     EXEC CICS LINK PROGRAM('LGSTSQ')
               COMMAREA(ERROR_MSG_BUFFER)
               LENGTH(LENGTH(ERROR_MSG_BUFFER));
 END WRITE_ERROR_MESSAGE;

There are 9 duplicate implementations across the Customer domain programs. LGSTSQ writes these records to a CICS Transient Data (TD) queue, creating a cross-cutting infrastructure dependency.

4.4 CICS Infrastructure Resources: Named Counters and TS Queues

  • GENACUSTNUM: Distributed CICS Named Counter server providing atomic customer ID increments. Replicating this off-mainframe requires DB2 Sequence objects or auto-increment identity columns.
  • GENACNTL: An in-memory Temporary Storage Queue containing low/high customer key boundaries. If the CICS region restarts without queue recoverability enabled, the boundary data is lost.

5.2 Dual-Store Shadow Inconsistency (DB2 vs. VSAM)

Every customer creation and update is dual-written to both DB2 (CUSTOMER) and VSAM (KSDSCUST).

No two-phase commit (2PC) or rollback on DB2. else VSAM Write Succeeds VSAMBackend->>VSAM: EXEC CICS WRITE FILE('KSDSCUST') VSAMBackend-->>DB2Backend: Return Normal (DFHRESP) end DB2Backend-->>Orch: Return Orch->>SecBackend: EXEC CICS LINK LGACDB02 SecBackend->>SecDB2: SQL INSERT INTO CUSTOMER_SECURE SecBackend-->>Orch: Return Orch-->>User: Acknowledge Add Operation

Dual-Write Operational Risks

  1. Absence of Two-Phase Commit (2PC): LGACDB01 executes the SQL INSERT, and then links to LGACVS01 to write to KSDSCUST. A failure in LGACVS01 does not roll back the DB2 insert, causing permanent divergence between DB2 and VSAM.
  2. Anomalous Random Inquiries (LGICVS01): LGICVS01 relies on the VSAM file KSDSCUST with READ GTEQ to discover active customer IDs for random lookups. If KSDSCUST is decommissioned, LGICVS01’s discovery mechanism will fail unless replaced with a relational equivalent.

5.3 Database Referential Integrity Constraints

At the relational layer, a hard foreign key constraint links the Policy Domain to the Customer Domain:

SQL 
ALTER TABLE POLICY
    ADD CONSTRAINT FK_POLICY_CUSTOMER
    FOREIGN KEY (CUSTOMERNUMBER)
    REFERENCES CUSTOMER (CUSTOMERNUMBER);

Impact on Migration

If the Customer and Policy domains are split into separate microservices with isolated databases:

  • Relational foreign keys cannot span database boundaries.
  • The constraint must be re-implemented as API-level validation logic in Policy onboarding services.
  • Deleting customer records requires coordinated distributed transactions (or Sagas) to prevent orphaned policy records.

7. Architectural Decomposition Strategy for LGACUS01

Decomposing LGACUS01 is the central architectural prerequisite for cleanly decoupling the Customer Domain from the Policy Domain.

7.1 Decomposition Options

Option A: Monolithic Lift (Migrate As-Is)

  • Description: Migrate LGACUS01 as a combined multi-domain service retaining direct connections to both CUSTOMER and POLICY tables.
  • Trade-offs:
    • Advantages: Preserves local database ACID transactions; minimizes upfront code restructuring.
    • Disadvantages: Perpetuates tight coupling between Customer and Policy domains; prevents independent service scaling and deployment.

Option B: Pre-Migration Decomposition (Recommended)

  • Description: Refactor LGACUS01 in the source environment before modernizing. Split the program into a dedicated Customer Lifecycle Service and delegate all Policy table operations to existing Policy Domain routines (e.g., LGAPDB01).
  • Trade-offs:
    • Advantages: Establishes clean bounded contexts; allows each domain to be migrated and tested independently.
    • Disadvantages: Replaces single-phase database commits with distributed compensation logic (Saga pattern); requires pre-migration PL/I refactoring.

Option C: Joint Dual-Domain Migration Stream

  • Description: Modernize both Customer and Policy domains concurrently, carving out service boundaries during target-platform implementation.
  • Trade-offs:
    • Advantages: Eliminates intermediate PL/I refactoring steps.
    • Disadvantages: Expands project scope; requires coordination across multiple domain teams simultaneously.
