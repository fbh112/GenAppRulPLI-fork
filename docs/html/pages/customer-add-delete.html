Customer Add & Delete Programs

1. Overview

This page documents the customer add and delete operations of the General Insurance application. It covers three CICS programs written in Enterprise PL/I:

Program Role
LGACUS01 Lifecycle orchestrator. It validates the COMMAREA and routes to one of four operations: onboard customer, offer policy, transfer policy, delete policy.
LGACDB01 DB2 insert program. It assigns the customer number (CICS named counter, with a DB2 IDENTITY fallback), inserts the CUSTOMER row, and triggers the downstream synchronisation steps.
LGACVS01 VSAM synchronisation program. It writes the customer record to the KSDSCUST KSDS file so VSAM stays in step with DB2.

1.1 Business Capabilities

  • Customer onboarding:
    • Obtain a unique customer number.
    • Insert the customer into DB2.
    • Mirror the customer to VSAM.
    • Create an initial security record.
  • Policy offer and transfer: insert a new POLICY row for an existing customer. DB2 generates the policy number and the LASTCHANGED timestamp.
  • Policy delete: remove a POLICY row by customer number and policy number. DB2 foreign-key cascades remove the policy-type detail rows.
  • Structured outcome reporting: every operation returns a 2-digit CA_RETURN_CODE in the COMMAREA. Failures are logged to a transient data queue through LGSTSQ.

1.2 Important Behavioural Note

In LGACUS01, ACTION_CODE is initialised to '0' and never changed at runtime. The program header records this as a defect ported from the original COBOL. As a result, the OTHERWISE branch is always taken, and LGACUS01 performs validation and then returns without running any business operation. The routing branches are documented here as designed, and the examples in section 11 show the intended behaviour.

LGACDB01 has no such routing. It performs the full customer-add sequence each time it is invoked with a valid COMMAREA.

2.3 Shared Interface: COMMAREA

All three programs receive a pointer-based COMM_AREA structure, declared by the LGCMAREA include. Its main parts are:

  • Header (18 bytes): CA_REQUEST_ID (6 characters), CA_RETURN_CODE (2 digits), CA_CUSTOMER_NUM (10 digits).
  • Customer section (72 bytes): name, date of birth, address, phone numbers, email.
  • Overlay areas: policy request (common fields plus endowment, house, motor, commercial and claim overlays) and customer-security request.
  • Raw view: COMM_AREA_RAW, declared CHAR(32500).

3. LGACUS01: Customer Lifecycle Orchestrator

3.1 Entry and Input Validation

On entry, INIT_CICS_VARIABLES captures EIBTRNID, EIBTRMID, EIBTASKN and EIBCALEN into working storage for diagnostics. CHECK_INPUTS then applies two checks:

  1. No COMMAREA (EIBCALEN = 0): write an error message and abend with LGCA, with no dump.
  2. Short COMMAREA: the minimum is the 18-byte header plus the 72-byte customer section, 90 bytes in total. If the COMMAREA is shorter, set CA_RETURN_CODE = '98' and return immediately.
PLI 
EXEC CICS ABEND ABCODE('LGCA') NODUMP;

3.2 Action Routing

After validation, a SELECT on ACTION_CODE chooses the operation. Each branch stamps CA_REQUEST_ID first.

ACTION_CODE CA_REQUEST_ID set Procedure Operation
'1' 01ICUS ONBOARD_CUSTOMER Add new customer
'2' 02OCUS OFFER_CUSTOMER Offer policy to customer
'3' 02UCUS TRANSFER_CUSTOMER Transfer policy
'4' 02DCUS DELETE_CUSTOMER Delete policy
other none none Falls through to EXEC CICS RETURN

The offer, transfer and delete dispatchers check that CA_REQUEST_ID is not '01ACLM'. This guard stops claim requests from triggering policy insert, transfer or delete.

3.3 Processing Flow

graph TD A([LGACUS01 Entry]) --> B[INIT_CICS_VARIABLES] B --> C[CHECK_INPUTS] C --> D{EIBCALEN = 0} D -- Yes --> E[Log error
ABEND LGCA] D -- No --> F[CA_RETURN_CODE = 00] F --> G{COMMAREA >= 90 bytes} G -- No --> H[CA_RETURN_CODE = 98
RETURN] G -- Yes --> I{ACTION_CODE} I -- 1 --> J[ONBOARD_CUSTOMER] I -- 2 --> K[OFFER_CUSTOMER] I -- 3 --> L[TRANSFER_CUSTOMER] I -- 4 --> M[DELETE_CUSTOMER] I -- Other --> N[No action] J --> Z([EXEC CICS RETURN]) K --> Z L --> Z M --> Z N --> Z

3.4 Onboarding Sequence in LGACUS01

ONBOARD_CUSTOMER zeroes DB2_OUT_INTEGERS and then runs these steps in strict order:

  1. OBTAIN_CUSTOMER_NUMBER
  2. INSERT_CUSTOMER
  3. EXEC CICS LINK to LGACVS01 (COMMAREA length 225)
  4. Populate CDB2AREA, then EXEC CICS LINK to LGACDB02 (length 32500)
  5. If CA_RETURN_CODE is not '00', return immediately

Section 4 describes the customer-number logic in detail.

4. LGACDB01: DB2 Insert with Customer Number Assignment

LGACDB01 is the dedicated add-customer program. It applies the same validation as LGACUS01 (abend LGCA on a missing COMMAREA, code '98' if shorter than 90 bytes) and then runs the add sequence without any routing step.

4.2 Customer Number Assignment

OBTAIN_CUSTOMER_NUMBER requests the next value from the CICS named counter GENACUSTNUM in pool GENA:

PLI 
EXEC CICS GET COUNTER(GENACOUNT) POOL(GENAPOOL)
          VALUE(LASTCUSTNUM) RESP(WS_RESP);
Counter outcome LGAC_NCS DB2_CUSTOMERNUM_INT Insert strategy
WS_RESP = DFHRESP(NORMAL) 'ON' LASTCUSTNUM Explicit CUSTOMERNUMBER
Any other response 'NO' 0 DEFAULT (DB2 IDENTITY)

The fallback is silent. No error is reported to the caller when the counter is unavailable.

4.3 Customer Insert

INSERT_CUSTOMER sets EM_SQLREQ to ' INSERT CUSTOMER' and then takes one of two paths.

Named counter path. All ten columns are supplied explicitly:

SQL 
EXEC SQL INSERT INTO CUSTOMER
   (CUSTOMERNUMBER, FIRSTNAME, LASTNAME, DATEOFBIRTH, HOUSENAME,
    HOUSENUMBER, POSTCODE, PHONEMOBILE, PHONEHOME, EMAILADDRESS)
   VALUES (:DB2_CUSTOMERNUM_INT, :CA_FIRST_NAME, :CA_LAST_NAME,
           :CA_DOB, :CA_HOUSE_NAME, :CA_HOUSE_NUM, :CA_POSTCODE,
           :CA_PHONE_MOBILE, :CA_PHONE_HOME, :CA_EMAIL_ADDRESS);

IDENTITY fallback path. CUSTOMERNUMBER is DEFAULT, and the generated number is then retrieved:

SQL 
EXEC SQL SET :DB2_CUSTOMERNUM_INT = IDENTITY_VAL_LOCAL();

In both paths, a non-zero SQLCODE sets CA_RETURN_CODE = '90', calls WRITE_ERROR_MESSAGE, and issues EXEC CICS RETURN. On success, CA_CUSTOMER_NUM is set from DB2_CUSTOMERNUM_INT, so the caller receives the new number.

4.4 Security Record Creation

After the VSAM link, the program populates CDB2AREA and links to LGACDB02:

Field Value
D2_CUSTOMER_NUM New customer number (DB2_CUSTOMERNUM_INT)
D2_REQUEST_ID '02ACUS' (Add Customer Security)
D2_CUSTSECR_PASS Fixed initial hash literal (LGACDB01 only)
D2_CUSTSECR_COUNT '0000'
D2_CUSTSECR_STATE 'N' (new)

LGACUS01 populates the request ID, count and state fields. The documentation lists the hardcoded password hash only for LGACDB01.

5. LGACVS01: VSAM Synchronisation

5.1 Purpose

LGACVS01 keeps the VSAM customer file KSDSCUST in step with DB2. It is linked after a successful DB2 customer insert. It writes the received COMMAREA as a new keyed record, using the 10-digit customer number as the key.

5.2 Processing Flow

graph TD A([LGACVS01 Start]) --> B[WS_Commarea_Len = EIBCALEN] B --> C[EXEC CICS WRITE FILE KSDSCUST
RIDFLD CA_Customer_Num
KEYLENGTH 10] C --> D{WS_RESP = NORMAL} D -- Yes --> E([Return to caller]) D -- No --> F[WS_RESP2 = EIBRESP2] F --> G[CA_RETURN_CODE = 80] G --> H[WRITE_ERROR_MESSAGE
ASKTIME, FORMATTIME,
LINK LGSTSQ x2] H --> I[ABEND LGV0 NODUMP] I --> J([RETURN])

5.3 The VSAM Write

PLI 
WS_Commarea_Len = EIBCALEN;

EXEC CICS WRITE FILE('KSDSCUST')
          FROM(CA_Customer_Num)
          LENGTH(WS_Commarea_Len)
          RIDFLD(CA_Customer_Num)
          KEYLENGTH(10)
          RESP(WS_RESP);
  • The record image starts at the CA_CUSTOMER_NUM field, not at CA_REQUEST_ID.
  • The record length is the received COMMAREA length.
  • A duplicate key or an unavailable file produces a non-NORMAL response, which triggers the error path.
  • The program does not touch DB2.

5.4 Failure Behaviour

On failure, LGACVS01 captures EIBRESP2 and sets CA_RETURN_CODE = '80'. It then logs the failure and abends the task:

PLI 
EXEC CICS ABEND ABCODE('LGV0') NODUMP;

Because the task abends, the abend is the dominant signal to the caller. The '80' value is set only before the abend takes effect.

7. Delete and Policy Operations (LGACUS01)

The delete operation removes a policy row, not the customer row. LGACUS01 also contains the policy offer and transfer logic. All three operations act on the DB2 POLICY table.

7.1 Policy Delete (ACTION_CODE = '4')

DELETE_CUSTOMER_POLICY sets EM_SQLREQ to ' DELETE POLICY ' and issues:

SQL 
EXEC SQL DELETE FROM POLICY
   WHERE (CUSTOMERNUMBER = :DB2_CUSTOMERNUM_INT
      AND POLICYNUMBER   = :DB2_POLICYNUM_INT);
  • Both customer and policy numbers must match, so a policy can only be removed under its owning customer.
  • SQLCODE 0 (deleted) and 100 (row not found) both count as success, because the desired end state is the same.
  • Any other non-zero SQLCODE sets CA_RETURN_CODE = '90', logs the error, and returns.
  • DB2 foreign-key cascade rules propagate the delete to the policy-type tables (endowment, house, motor, commercial, claim).

7.2 Policy Offer and Transfer (ACTION_CODE = '2' and '3')

INSERT_CUSTOMER_POLICY and TRANSFER_CUSTOMER_POLICY are functionally identical. Each performs these steps:

  1. Convert CA_BROKERID and CA_PAYMENT to FIXED BIN(31) host variables (DB2_BROKERID_INT, DB2_PAYMENT_INT).
  2. Insert the policy with a DB2-generated policy number and a DB2-generated timestamp.
  3. Evaluate SQLCODE.
  4. Retrieve the generated policy number and the LASTCHANGED timestamp.
SQL 
EXEC SQL INSERT INTO POLICY
   VALUES (DEFAULT, :DB2_CUSTOMERNUM_INT, :CA_ISSUE_DATE,
           :CA_EXPIRY_DATE, :DB2_POLICYTYPE, CURRENT TIMESTAMP,
           :DB2_BROKERID_INT, :CA_BROKERSREF, :DB2_PAYMENT_INT);

(Column list abbreviated here. The documented columns are POLICYNUMBER, CUSTOMERNUMBER, ISSUEDATE, EXPIRYDATE, POLICYTYPE, LASTCHANGED, BROKERID, BROKERSREFERENCE, PAYMENT.)

SQL 
EXEC SQL SET :DB2_POLICYNUM_INT = IDENTITY_VAL_LOCAL();

EXEC SQL SELECT LASTCHANGED INTO :CA_LASTCHANGED
           FROM POLICY WHERE POLICYNUMBER = :DB2_POLICYNUM_INT;

7.3 Policy Insert/Delete Decision Flow

graph TD A{CA_REQUEST_ID
not 01ACLM} -- No --> Z([RETURN]) A -- Yes --> B{Operation} B -- Offer / Transfer --> C[INSERT INTO POLICY] B -- Delete --> D[DELETE FROM POLICY] C --> E{SQLCODE} E -- 0 --> F[IDENTITY_VAL_LOCAL
SELECT LASTCHANGED] E -- -530 --> G[Return code 70] E -- Other --> H[Return code 90] F --> Z G --> Z H --> Z D --> I{SQLCODE 0 or 100} I -- Yes --> Z I -- No --> H

The IDENTITY_VAL_LOCAL() call must directly follow the policy insert so no other SQL can change the identity value first.

CUSTOMER and KSDSCUST hold the same logical customer, in DB2 and VSAM respectively. The relationship in the diagram is logical, not a DB2 constraint.

9. Return Codes and COMMAREA Contract

Code Set by Meaning
00 LGACUS01, LGACDB01 Success
70 LGACUS01 Referential integrity violation (SQLCODE -530) on policy insert
80 LGACVS01 VSAM write to KSDSCUST failed (followed by abend LGV0)
90 LGACUS01, LGACDB01 General SQL or system error
98 LGACUS01, LGACDB01 COMMAREA shorter than 90 bytes

Output fields

  • CA_CUSTOMER_NUM: the assigned customer number.
  • CA_POLICY_NUM: the policy number from a policy insert.
  • CA_LASTCHANGED: the DB2 timestamp from a policy insert.
  • CA_REQUEST_ID: the request ID stamped by LGACUS01.

Field sizes

10. Error Handling

10.1 Strategy

  • Hard abend: used only for a missing COMMAREA (LGCA, in LGACUS01 and LGACDB01) or a failed VSAM write (LGV0, in LGACVS01).
  • Controlled return: all DB2 and post-link failures set CA_RETURN_CODE and issue EXEC CICS RETURN, so the caller can inspect the result.
  • Short COMMAREA: returns '98' without logging.
  • Named counter failure: handled by the silent IDENTITY fallback and never reported as an error.

10.2 Centralised Logging (WRITE_ERROR_MESSAGE)

Each program has its own WRITE_ERROR_MESSAGE procedure. It follows this pattern:

  1. EXEC CICS ASKTIME, then FORMATTIME to obtain EM_DATE and EM_TIME.
  2. Fill ERROR_MSG.
    • LGACUS01 and LGACDB01 record the program name, SQL request label and SQLCODE. LGACUS01 also records the customer and policy numbers.
    • LGACVS01 records the customer number, RESP and RESP2.
  3. EXEC CICS LINK PROGRAM('LGSTSQ') with ERROR_MSG.
  4. If EIBCALEN > 0, copy up to 90 bytes of the raw COMMAREA into CA_DATA and link to LGSTSQ a second time.
PLI 
EXEC CICS LINK PROGRAM('LGSTSQ')
          COMMAREA(ERROR_MSG)
          LENGTH(STG(ERROR_MSG));

IF EIBCALEN > 0 THEN DO;
   IF EIBCALEN < 91 THEN
      CA_DATA = LEFT(COMM_AREA_RAW, EIBCALEN);
   ELSE
      CA_DATA = LEFT(COMM_AREA_RAW, 90);
   EXEC CICS LINK PROGRAM('LGSTSQ')
             COMMAREA(CA_ERROR_MSG)
             LENGTH(STG(CA_ERROR_MSG));
END;

10.3 Error Paths by Program

Program Condition Result
LGACUS01 EIBCALEN = 0 Log, abend LGCA
LGACUS01 EIBCALEN < 90 '98', return
LGACUS01 Customer insert SQLCODE <> 0 '90', log, return (VSAM and security links not reached)
LGACUS01 Policy insert SQLCODE = -530 '70', log, return
LGACUS01 Policy insert other error '90', log, return
LGACUS01 Policy delete not 0 and not 100 '90', log, return
LGACDB01 EIBCALEN = 0 Log, abend LGCA
LGACDB01 EIBCALEN < 90 '98', return
LGACDB01 Insert SQLCODE <> 0 '90', log, return
LGACVS01 Write RESP <> NORMAL '80', log, abend LGV0
LGACUS01, LGACDB01 CA_RETURN_CODE <> '00' after the LGACDB02 link Return immediately, propagating the failure

11. Constraints and Operational Notes

11.1 Sequencing Rules

  • Validation runs before any business logic.
  • The customer number must be obtained before the customer insert.
  • The strict order is DB2 insert, then LGACVS01, then LGACDB02.
  • If the DB2 insert fails, the program returns before the VSAM and security links, so no VSAM record or security row is created for a failed customer.
  • The security return code is checked only after the LGACDB02 link.

11.2 Fixed Interface Parameters

Parameter Value
LGACVS01 link length 225 bytes
LGACDB02 link length 32500 bytes
D2_REQUEST_ID '02ACUS'
D2_CUSTSECR_STATE 'N'
D2_CUSTSECR_COUNT '0000'
Named counter / pool GENACUSTNUM / GENA
VSAM file / key length KSDSCUST / 10
Maximum COMMAREA 32,500 bytes
Error dump At most 90 bytes of COMMAREA

11.3 Design Observations

  • Caller cannot choose identifiers. Customer numbers come only from the counter or the IDENTITY column. Policy numbers are always DB2-generated and LASTCHANGED is always CURRENT TIMESTAMP.
  • Shared initial credential. LGACDB01 hardcodes the initial password hash, so every new customer starts with the same credential value.
  • CA_REQUEST_ID truncation. The field is CHAR(6), so longer request strings are silently truncated. This is inherited COBOL behaviour.
  • LGACVS01 has no explicit COMMAREA check. It does not test EIBCALEN = 0. A zero-length write would simply fail and enter the error path.
  • LGACUS01 routing defect. Because ACTION_CODE is always '0', none of its business branches run in the current implementation.

12. Examples

12.1 Successful Onboarding (Named Counter Available)

Input field Value
CA_FIRST_NAME 'John '
CA_LAST_NAME 'Smith'
CA_DOB '1980-05-12'
CA_POSTCODE 'SW1A 1AA'
Named counter returns 1042

Processing:

  1. The length check passes (EIBCALEN >= 90), and CA_RETURN_CODE is '00'.
  2. The counter returns 1042, so DB2_CUSTOMERNUM_INT = 1042 and LGAC_NCS = 'ON'.
  3. The INSERT INTO CUSTOMER runs with CUSTOMERNUMBER = 1042 and returns SQLCODE 0.
  4. LGACVS01 writes KSDSCUST with key 0000001042.
  5. LGACDB02 is linked with D2_CUSTOMER_NUM = 1042 and D2_REQUEST_ID = '02ACUS'.
Output field Value
CA_RETURN_CODE '00'
CA_CUSTOMER_NUM 0000001042

12.2 Named Counter Unavailable (IDENTITY Fallback)

  1. GET COUNTER returns a non-NORMAL response, so LGAC_NCS = 'NO' and DB2_CUSTOMERNUM_INT = 0.
  2. The insert uses DEFAULT for CUSTOMERNUMBER.
  3. IDENTITY_VAL_LOCAL() returns the generated number, for example 5001.
  4. CA_CUSTOMER_NUM is 0000005001 and CA_RETURN_CODE is '00'.

12.3 Insufficient COMMAREA

With EIBCALEN = 10, the required length of 18 + 72 = 90 is not met. CA_RETURN_CODE becomes '98' and the program returns. No counter, DB2 or link calls are made.

12.4 DB2 Insert Failure

The counter returns 1000044, but the insert returns a non-zero SQLCODE such as a duplicate key. CA_RETURN_CODE becomes '90', and two entries are written through LGSTSQ (the error message and a COMMAREA snapshot). The program then returns without calling LGACVS01 or LGACDB02.

12.5 VSAM Duplicate Key

A second add for customer 0000000042 makes the WRITE FILE('KSDSCUST') return a non-NORMAL response such as DUPREC.

  • CA_RETURN_CODE is set to '80'.
  • LGSTSQ receives two records:
    • The structured message: MM/DD/YYYY HH:MM:SS LGACVS01 CNUM=0000000042 Write file KSDSCUST RESP= <n> RESP2= <n>
    • The first 90 bytes of the COMMAREA, prefixed with COMMAREA=.
  • The task abends with LGV0.

12.6 Policy Offer for an Existing Customer (ACTION_CODE = '2')

Input field Value
CA_CUSTOMER_NUM / DB2_CUSTOMERNUM_INT 0000001042 / 1042
CA_ISSUE_DATE / CA_EXPIRY_DATE '2024-01-01' / '2025-01-01'
DB2_POLICYTYPE 'H'
CA_BROKERID 0000000099
CA_PAYMENT 001200

Processing:

  1. CA_REQUEST_ID is set to '02OCUS'.
  2. The request is not a claim (≠ '01ACLM'), so INSERT_CUSTOMER_POLICY runs.
  3. DB2_BROKERID_INT = 99 and DB2_PAYMENT_INT = 1200.
  4. The INSERT INTO POLICY returns SQLCODE 0.
  5. IDENTITY_VAL_LOCAL() returns the policy number, for example 3007, and the SELECT returns LASTCHANGED.
Output field Value
CA_RETURN_CODE '00'
CA_POLICY_NUM 0000003007
CA_LASTCHANGED DB2 timestamp

If the customer does not exist, the insert returns SQLCODE -530 and CA_RETURN_CODE becomes '70'.

12.7 Policy Delete (ACTION_CODE = '4')

  • The delete matches the row: SQLCODE 0, CA_RETURN_CODE = '00', and the cascade removes the subtype rows.
  • No matching row: SQLCODE 100, still treated as success, CA_RETURN_CODE = '00'.
  • Any other SQLCODE: CA_RETURN_CODE = '90' and the error is logged.
