Batch Motor Policy Extract

1. Overview

LGMOTOUT is a batch, non-interactive PL/I program designed to extract all motor insurance policy records from the DB2 GENASA1.MOTOR table and serialize them into a sequential, fixed-block physical output file named MOTOROUT. Acting as a pure read-only utility, the program systematically scans the entire motor insurance table using a DB2 cursor, maps the retrieved columns to a formatted data layout, and outputs exactly one 132-byte fixed-length record per policy.

The main business and technical objectives of the program include:

  • Full Database Extraction: Reading all vehicle and policy attributes (e.g., policy number, manufacture details, insurance premiums, accident records) without active filtering.
  • Data Standardization: Formatting and converting binary database types (such as FIXED BIN integers) into structured, readable character representation templates (using PL/I PIC picture formats).
  • Audit and Verification: Generating a final record count upon normal execution to verify data integrity against operational batch expectations.
  • Robust Failure Isolation: Gracefully trapping and reporting DB2 errors and z/OS file allocation or I/O failures, using distinctive batch return codes (0, 8, or 12) to communicate step status directly to the job control scheduler.

2. System Architecture

LGMOTOUT runs as a standard batch job step in a z/OS mainframe environment. It connects to a DB2 subsystem to execute read-only queries and interfaces with the z/OS Data Management services to write output records to sequential datasets.

2.1 System Components and Relationships

The program serves as the processing logic hub. It depends on several external system components: the DB2 subsystem hosting the motor database table, the z/OS dataset allocation services providing the physical sequential file, and the z/OS runtime environment that manages job steps and records output messages in the console log.

3. Technical Inputs and Outputs

3.1 DB2 Database - GENASA1.MOTOR Table (Inputs)

All database values are retrieved sequentially using the DB2 cursor MOTOR_CSR. The program maps SQL column results directly into equivalent PL/I host variables:

  • POLICYNUMBER (fetched into HV_POLICY_NUMBER as FIXED BIN(31)): The unique identifier of the motor insurance policy.
  • MAKE (fetched into HV_MAKE as CHAR(15)): The vehicle manufacturer.
  • MODEL (fetched into HV_MODEL as CHAR(15)): The model identifier.
  • VALUE (fetched into HV_VALUE as FIXED BIN(31)): The declared monetary value of the vehicle.
  • REGNUMBER (fetched into HV_REGNUMBER as CHAR(7)): The legal vehicle registration plate number.
  • COLOUR (fetched into HV_COLOUR as CHAR(8)): The physical vehicle color.
  • CC (fetched into HV_CC as FIXED BIN(15)): The engine’s cubic centimeter displacement capacity.
  • YEAROFMANUFACTURE (fetched into HV_YEAROFMANUFACTURE as CHAR(10)): The manufacturing date/year.
  • PREMIUM (fetched into HV_PREMIUM as FIXED BIN(31)): The calculated insurance premium.
  • ACCIDENTS (fetched into HV_ACCIDENTS as FIXED BIN(31)): The historic accident count associated with the vehicle.

3.2 Sequential Output File - MOTOROUT (Outputs)

The output destination is a sequential dataset referred to via the MOTOROUT DD statement. It must be allocated as a Fixed-Block (FB) dataset with a record length (LRECL) of exactly 132 bytes.

The logical record structure, defined by the WS_MOTOR_LINE structure, organizes the output data fields:

  • WS_OUT_POLNUM (PIC '999999999'): 9-position policy number.
  • WS_OUT_MAKE (CHAR(15)): 15-character vehicle manufacturer.
  • WS_OUT_MODEL (CHAR(15)): 15-character vehicle model name.
  • WS_OUT_VALUE (PIC '999999999'): 9-position vehicle value.
  • WS_OUT_REGNUMBER (CHAR(7)): 7-character registration plate.
  • WS_OUT_COLOUR (CHAR(8)): 8-character vehicle color.
  • WS_OUT_CC (PIC '9999'): 4-position engine cubic capacity.
  • WS_OUT_YEAROFMFR (CHAR(10)): 10-character year of manufacture.
  • WS_OUT_PREMIUM (PIC '999999999'): 9-position insurance premium.
  • WS_OUT_ACCIDENTS (PIC '999999999'): 9-position recorded accident count.

3.3 Operational and Error Messages

The program communicates its execution state using standard system console output:

  • Normal Termination Message: Displays the exact count of lines written to the sequential dataset: LGMOTOUT: ROWS WRITTEN=<WS_ROW_COUNT>
  • File Open Diagnostic Failure: Outputs an explicit message when file allocation or availability fails: LGMOTOUT: OPEN MOTOROUT FAILED
  • File Write Diagnostic Failure: Outputs a message indicating a physical write failure: LGMOTOUT: WRITE FAILED
  • Centralized DB2 SQL Error Message: Displays a formatted, timestamped record containing critical SQL failure parameters: <DATE> <TIME> LGMOTOUT <OPERATION_NAME> SQLCODE=<SQL_CODE>

4.3 Detailed Procedure Descriptions

The functionality is structured into four main procedures:

4.3.1 LGMOTOUT (Main Procedure)

The primary execution module handles system initialization, resource opening, the main processing loop, and program shutdown. It establishes the ON UNDEFINEDFILE error handler for the file allocation check and handles the high-level response to DB2 database connection results. If the cursor opens successfully, it initiates a DO WHILE execution loop that calls FETCH_MOTOR_ROWS repeatedly. Once processing completes or terminates on error, this procedure closes all system assets and passes execution control back to the z/OS host with a designated status return code.

4.3.2 FETCH_MOTOR_ROWS

This sub-procedure issues a FETCH statement against the active database cursor to extract the next row of data into the registered PL/I host variables. It manages SQL execution checks using a structured SELECT (SQLCODE) block:

  • WHEN (0): Calls WRITE_MOTOR_ROW to format and write the fetched record.
  • WHEN (100): Evaluates as a standard end-of-file signal, letting the main loop terminate normally.
  • OTHERWISE: Treats the result as a database failure, logging the details using WRITE_ERROR_MESSAGE and setting the job return code to 8.

4.3.3 WRITE_MOTOR_ROW

This sub-procedure maps the raw host variables into the corresponding display fields in the structured WS_MOTOR_LINE record. It utilizes the PL/I STRING built-in function to serialize the structured layout into a 132-byte flat-character buffer. To handle physical I/O write failures, it registers a local ON TRANSMIT error handler. If the write executes successfully, the program increments the successful record counter (WS_ROW_COUNT). If a write failure occurs, the program reports the error and continues processing subsequent rows.

4.3.4 WRITE_ERROR_MESSAGE

This utility procedure formats and writes error diagnostics to the SYSOUT log. It combines the current system date, time, the failing DB2 operation name (such as open, close, or fetch), and the numeric SQLCODE return value into a single, structured log message.

5. Environmental and System Dependencies

5.1 DB2 Subsystem & Plan Bindings

  • Target Subsystem: The database engine executes in a DB2 environment (default subsystem DBD1).
  • Table Definition: Requires structural access to the GENASA1.MOTOR database table.
  • Compile-Time Interface: Uses SQLCA via EXEC SQL INCLUDE SQLCA to retrieve status codes after every database action.
  • Bind Requirement: A JCL bind job (as defined in GenAppBind.jcl) must package the compilation’s database request module (DBRM) into an active execution package on the host DB2 engine before program execution.

5.2 Sequential File Configuration

The program requires runtime allocation of the sequential output file. If the file is not allocated via JCL or dynamic allocation, execution fails immediately.

  • DD Name: MOTOROUT
  • Physical Properties: Fixed Blocked (FB), Record Length (LRECL) of exactly 132 bytes.

5.3 Runtime Environment & Compilers

  • Language & Compiler: Compiled using the Enterprise PL/I for z/OS compiler.
  • Execution Environment: Run within a batch environment under the z/OS Operating System.
  • Execution Libraries: Relies on PL/I runtime library routines for error-trapping and data serialization, including PLIRETC (return code setting), STRING (structure concatenation), and STOP / RETURN execution control.

6.2 Output File Structure Constraints

  • Record Integrity: The sequential dataset MOTOROUT is defined with a fixed record length of 132 bytes. The structural mapping in the program (WS_MOTOR_LINE) totals 119 characters of active data and separator fields, followed by a 13-character trailing space filler. This ensures the output record matches the 132-byte physical allocation exactly.
  • Single-Record Output: The program uses a single-record write model. Blocked or multi-row writes are not supported.

6.3 DB2 Access Constraints

  • No Modifications: The SQL cursor is opened as FOR READ ONLY. Program actions are limited to extraction.
  • Unfiltered Extractor: The SQL command contains no WHERE filtering clause. The program performs a full table scan.
  • Data Integrity: Adding or removing columns in GENASA1.MOTOR without matching modifications in the PL/I source code will result in a compiler mismatch or runtime SQL bind error.

6.4 Sequencing & Operational Order Constraints

  1. File Opening: The sequential output file must be opened before opening the DB2 cursor. If file opening fails, the program terminates immediately with return code 12 before initiating any DB2 operations.
  2. Cursor Status Check: The program checks the cursor open status before attempting any fetch operations. If the open fails, the program logs the error, closes the sequential file, and exits with return code 12.
  3. Process Ordering: Each database row must be successfully fetched (SQLCODE = 0) before a write operation is attempted.
  4. Resource Cleanup: When execution completes, the program closes the DB2 cursor before closing the output sequential file.

7. Error Handling and Recovery Strategy

The program implements a structured, multi-tier error containment strategy to handle physical dataset and database failures.

7.1 File I/O Error Handling

The program handles file-level errors using specific runtime handlers:

7.1.1 Fatal Dataset Open Failure

  • Handler: ON UNDEFINEDFILE(MOTOROUT)
  • Reasoning: Executed if the output dataset is unallocated, locked, or incorrectly defined in the JCL.
  • Recovery Action: Displays a terminal diagnostic message (LGMOTOUT: OPEN MOTOROUT FAILED), registers a return code of 12 using PLIRETC, and halts program execution immediately via a STOP command.

7.1.2 Physical Output Write Failure

  • Handler: ON TRANSMIT(MOTOROUT) (registered in the WRITE_MOTOR_ROW block).
  • Reasoning: Traps output failures, such as a full disk or an out-of-space condition on the sequential dataset.
  • Recovery Action: Sets the logical tracking flag MOTOROUT_OK to '0'B (false) when an error occurs. The program displays LGMOTOUT: WRITE FAILED, calls the centralized log procedure, and continues processing the remaining database rows. The row count for the failed record is not incremented, keeping the audit log accurate.

7.2 DB2 SQL Error Handling

Every database access point is protected by explicit condition checks:

  • Cursor Open Check: Checked immediately after the cursor open call. If SQLCODE != 0, the program calls WRITE_ERROR_MESSAGE, closes MOTOROUT, sets return code 12, and returns.
  • Fetch Integrity Check: Controlled by a strict loop condition: DO WHILE (SQLCODE ^= 100 & SQLCODE >= 0) This prevents the loop from processing further if a negative SQLCODE (indicating a database error) is encountered.
  • Fetch Level Failures: Managed within the fetch procedure’s SELECT (SQLCODE) block. When an unexpected code is received, the program logs the failure, sets the return code to 8 via PLIRETC(8), and exits the processing loop.

7.3 Centralized Error Reporting

Database diagnostics are centralized in the WRITE_ERROR_MESSAGE procedure. This module formats a standard message containing:

  • The system date (EM_DATE) and time (EM_TIME).
  • The program name LGMOTOUT.
  • The active SQL request value (EM_SQLREQ), representing the last attempted action (such as open, fetch, or close).
  • The raw numeric SQLCODE error code (EM_SQLRC).

7.4 Program Return Code Strategy
