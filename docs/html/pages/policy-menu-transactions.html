Policy Maintenance Menus (SSP1–SSP4)

The Policy Maintenance Menus are four CICS pseudo-conversational PL/I transactions. They give terminal operators a BMS-driven front end for the General Insurance (GenApp) policy lifecycle.

Transaction Program Policy type BMS map Operations
SSP1 LGTESTP1 Motor SSMAPP1 Inquire, Add, Delete, Update
SSP2 LGTESTP2 Endowment (life) SSMAPP2 Inquire, Add, Delete, Update
SSP3 LGTESTP3 House SSMAPP3 Inquire, Add, Delete, Update
SSP4 LGTESTP4 Commercial SSMAPP4 Inquire, Add, Delete

1. Overview

1.1 Purpose

Each menu program shows a BMS screen from mapset SSMAP. The operator types a one-character option and the policy details. The program then:

  1. Builds a request in the shared 32,500-byte COMM_AREA (copybook LGCMAREA).
  2. Sets a six-character CA_REQUEST_ID that tells the back end which operation to run.
  3. Routes the request to a back-end policy program with EXEC CICS LINK.
  4. Shows the result, either a confirmation or a specific error message, on the same screen.

The menus do no database work themselves and issue no SQL. All persistence is done by the linked programs.

1.2 Menu options

Option Action Back-end program Notes
1 Inquire LGIPOL01 Displays the policy fields returned.
2 Add LGAPOL01 Returns the newly assigned policy number.
3 Delete LGDPOL01 Clears the policy fields on screen.
4 Update LGIPOL01, then LGUPOL01 Two-phase. SSP1–SSP3 only.
Other Invalid none Shows “Please enter a valid option” and positions the cursor.

1.3 Request identifiers

CA_REQUEST_ID is a six-character code. The first two characters are 01 (or 02, 03, 05 for the commercial inquiry variants). The third character is the operation: I, A, D or U. The last three characters are the policy type: MOT, END, HOU or COM.

Policy type Inquire Add Delete Update
Motor (SSP1) 01IMOT 01AMOT 01DMOT 01UMOT
Endowment (SSP2) 01IEND 01AEND 01DEND 01UEND
House (SSP3) 01IHOU 01AHOU 01DHOU 01UHOU
Commercial (SSP4) 01ICOM, 02ICOM, 03ICOM, 05ICOM 01ACOM 01DCOM not supported

2. System Architecture

2.1 Component view

graph TD User[Terminal Operator] --> T1[SSP1 - LGTESTP1 Motor] User --> T2[SSP2 - LGTESTP2 Endowment] User --> T3[SSP3 - LGTESTP3 House] User --> T4[SSP4 - LGTESTP4 Commercial] T1 --> MAP[BMS Mapset SSMAP] T2 --> MAP T3 --> MAP T4 --> MAP T1 --> CA[COMM_AREA 32500 bytes - LGCMAREA] T2 --> CA T3 --> CA T4 --> CA CA --> INQ[LGIPOL01 Inquiry] CA --> ADD[LGAPOL01 Add] CA --> DEL[LGDPOL01 Delete] CA --> UPD[LGUPOL01 Update] INQ --> DB[(Policy data stores)] ADD --> DB DEL --> DB UPD --> DB

The menu programs form a thin presentation and routing layer. The back-end orchestrators (LGIPOL01, LGAPOL01, LGDPOL01, LGUPOL01) are shared by all four menus and select the policy-type logic from CA_REQUEST_ID.

2.2 Menu-to-map-to-program relationships

graph LR SSP1 --- P1[LGTESTP1] --- M1[SSMAPP1] SSP2 --- P2[LGTESTP2] --- M2[SSMAPP2] SSP3 --- P3[LGTESTP3] --- M3[SSMAPP3] SSP4 --- P4[LGTESTP4] --- M4[SSMAPP4] M1 --- S[Mapset SSMAP] M2 --- S M3 --- S M4 --- S

All four programs include the same SSMAP copybook, which declares every map structure (SSMAPC1, SSMAPP1 to SSMAPP5). Each program uses only its own map.

2.3 Key architectural characteristics

  • Pseudo-conversational design. Every normal exit is EXEC CICS RETURN TRANSID('SSPn') COMMAREA(COMM_AREA). No task is held while the operator thinks.
  • Reentrant PL/I. The programs are compiled with Options(Main,Reentrant) and take DFHEIPTR and COMM_AREA_PTR as parameters.
  • Fixed COMMAREA contract. All LINK calls pass LENGTH(32500). COMM_AREA_RAW is CHAR(32500), made up of:
    • CA_REQUEST_ID (6 bytes)
    • CA_RETURN_CODE (2 bytes)
    • CA_CUSTOMER_NUM (10 bytes)
    • CA_REQUEST_INITIALISER (32,482 bytes), which overlays the policy-specific data
  • Policy-type unions. The policy-specific part of the COMMAREA holds CA_MOTOR, an endowment block, CA_HOUSE or CA_COMMERCIAL, depending on the policy type.

3. Common Processing Model

3.1 Program skeleton

The four programs share one structure:

  1. EIBCALEN = 0 marks the first invocation. The program initialises the COMMAREA and map, then sends the map with ERASE.
  2. A_GAIN registers the AID and condition handlers, then receives the map.
  3. A SELECT on the option field dispatches to the inquire, add, delete or update logic.
  4. The program exits through ENDIT_STARTIT, ENDIT, CLEARIT or ERROR_OUT.
PLI 
EXEC CICS HANDLE AID CLEAR(CLEARIT) PF3(ENDIT);
EXEC CICS HANDLE CONDITION MAPFAIL(ENDIT);
EXEC CICS RECEIVE MAP('SSMAPP1') INTO(SSMAPP1I) MAPSET('SSMAP');

3.2 Sequence of a typical transaction

sequenceDiagram participant U as Operator participant M as LGTESTPn Menu participant C as CICS participant B as Back-end LGxPOL01 U->>C: Start transaction SSPn C->>M: Invoke (EIBCALEN = 0) M->>U: SEND MAP ERASE (blank menu) M->>C: RETURN TRANSID(SSPn) COMMAREA U->>C: Enter option and data C->>M: Re-invoke with COMMAREA M->>M: RECEIVE MAP, SELECT option M->>B: LINK PROGRAM COMMAREA(32500) B-->>M: CA_RETURN_CODE and data alt CA_RETURN_CODE = 0 M->>U: SEND MAP with result else CA_RETURN_CODE > 0 M->>U: SEND MAP with error message end M->>C: RETURN TRANSID(SSPn) COMMAREA

3.3 Generic control flow

graph TD A([Start]) --> B{EIBCALEN = 0} B -- Yes --> C[Init COMMAREA and map, SEND MAP ERASE] B -- No --> D[HANDLE AID and CONDITION] C --> D D --> E[RECEIVE MAP] E --> F{Option} F -- 1 --> G[Inquire via LGIPOL01] F -- 2 --> H[Add via LGAPOL01] F -- 3 --> I[Delete via LGDPOL01] F -- 4 --> J[Inquire then Update via LGUPOL01] F -- Other --> K[Invalid option message] G --> R{CA_RETURN_CODE > 0} H --> R I --> R J --> R R -- No --> S[SEND MAP with result] R -- Yes --> T[Rollback if add or delete, error label] T --> U[ERROR_OUT] S --> V[ENDIT_STARTIT] K --> V U --> V V --> W([RETURN TRANSID SSPn])

3.4 Exit labels

Label Trigger Behaviour
ENDIT_STARTIT Normal completion EXEC CICS RETURN TRANSID('SSPn') COMMAREA(COMM_AREA)
ENDIT PF3 or MAPFAIL Sends “Transaction ended” with ERASE FREEKB, then does a plain RETURN.
CLEARIT CLEAR key Blanks the map, sends it MAPONLY, then returns with the transaction ID.
ERROR_OUT Any error label Sends the map with the error, resets the map and COMMAREA, then goes to ENDIT_STARTIT.
PLI 
ENDIT_STARTIT:
  EXEC CICS RETURN TRANSID('SSP1') COMMAREA(COMM_AREA);

ENDIT:
  EXEC CICS SEND TEXT FROM(MSGEND) ERASE FREEKB;
  EXEC CICS RETURN;

4. Motor Policy Menu (SSP1 / LGTESTP1)

4.1 Operations

  • Inquire (1).
    • Sets CA_REQUEST_ID = '01IMOT'.
    • Takes the customer and policy numbers from ENP1CNOO and ENP1PNOO.
    • Links to LGIPOL01.
    • On success, copies the issue and expiry dates, make, model, value, registration, colour, CC, manufacture date, premium and accidents to the map.
  • Add (2).
    • Sets 01AMOT.
    • Takes the customer number from ENP1CNOI and zeroes the payment and broker fields.
    • Maps the screen input fields to CA_MOTOR.
    • Links to LGAPOL01.
    • On success, echoes the customer and policy numbers and shows “New Motor Policy Inserted”.
  • Delete (3).
    • Sets 01DMOT and links to LGDPOL01.
    • On success, blanks the detail fields and shows “Motor Policy Deleted”.
  • Update (4).
    • Phase A inquires with 01IMOT and sends the data to the screen.
    • The program then issues a second RECEIVE MAP to collect the operator’s edits.
    • Phase B sets 01UMOT and links to LGUPOL01.
    • On success, shows “Motor Policy Updated”.
PLI 
CA_REQUEST_ID = '01IMOT';
CA_CUSTOMER_NUM = ENP1CNOO;
CA_POLICY_NUM = ENP1PNOO;
EXEC CICS LINK PROGRAM('LGIPOL01') COMMAREA(COMM_AREA) LENGTH(32500);
IF CA_RETURN_CODE > 0 THEN GO TO NO_DATA;

4.2 Update sequence

sequenceDiagram participant U as Operator participant P as LGTESTP1 participant I as LGIPOL01 participant X as LGUPOL01 U->>P: Option 4, customer, policy P->>I: LINK (01IMOT) I-->>P: Current motor policy P->>U: SEND MAP with existing data U->>P: RECEIVE MAP with edits P->>X: LINK (01UMOT) X-->>P: CA_RETURN_CODE P->>U: "Motor Policy Updated" or error

5. Endowment Policy Menu (SSP2 / LGTESTP2)

5.1 Operations

The structure matches SSP1, with endowment request IDs (01IEND, 01AEND, 01DEND, 01UEND) and these fields:

  • fund name
  • term
  • sum assured
  • life assured
  • with-profits flag
  • managed-fund flag
  • equities flag

6.1 Operations

Screen field COMMAREA field Size
ENP3TYPI CA_H_PROPERTY_TYPE CHAR(15)
ENP3BEDI CA_H_BEDROOMS PIC '999'

ENP3HNMI CA_H_HOUSE_NAME CHAR(20)

The messages are:

  • “New House Policy Inserted”
  • “House Policy Deleted”
  • “House Policy Updated”
  • “Error Adding House Policy”
  • “Error Updating House Policy”
  • “Error Deleting House Policy”

7. Commercial Policy Menu (SSP4 / LGTESTP4)

7.1 Operations

SSP4 supports only Inquire, Add and Delete. It has no update option. Its distinguishing feature is its flexible inquiry.

Inquiry request routing

Condition CA_REQUEST_ID Search key
Customer and policy supplied 01ICOM Customer and policy
Policy only 02ICOM Policy
Customer only 03ICOM Customer
Postcode non-blank (overrides the others) 05ICOM Postcode (CA_B_Postcode)
graph TD A[Option 1 selected] --> B{Customer and policy both given} B -- Yes --> C[01ICOM] B -- No --> D{Policy only} D -- Yes --> E[02ICOM] D -- No --> F[03ICOM] C --> G{Postcode ENP4HPCO non-blank} E --> G F --> G G -- Yes --> H[Override with 05ICOM, set CA_B_Postcode] G -- No --> I[LINK LGIPOL01] H --> I I --> J{CA_RETURN_CODE > 0} J -- Yes --> K[NO_DATA] J -- No --> L[Map CA_COMMERCIAL to screen, SEND MAP]

7.2 Commercial data

The commercial block carries these fields:

  • address (CA_B_Address)
  • postcode
  • latitude and longitude
  • customer description
  • property type
  • four peril and premium pairs for fire, crime, flood and weather
  • status (CA_B_Status)
  • reject reason (CA_B_RejectReason)

The screen fields for address, customer, property type and reject reason hold only 25 characters, against 255 in the COMMAREA.

The messages are:

  • “New Commercial Policy Inserted”
  • “Commercial Policy Deleted”
  • “Error Adding Commercial Policy”
  • “Error Deleting Commercial Policy”

8. Error Handling

8.1 Error handling in the four menus

Condition Mechanism Result
PF3 HANDLE AID PF3(ENDIT) “Transaction ended”, then the task ends.
CLEAR HANDLE AID CLEAR(CLEARIT) Blank map is resent and the transaction continues.
Empty screen (MAPFAIL) HANDLE CONDITION MAPFAIL(ENDIT) The transaction ends.
Invalid option OTHERWISE branch “Please enter a valid option”. ENPnOPTL = -1 puts the cursor on the option field.
Inquire failure CA_RETURN_CODE > 0 leads to NO_DATA “No data was returned.”
Add failure SYNCPOINT ROLLBACK, then NO_ADD Return code 70 gives “Customer does not exist”. Any other code gives the generic add error.
Delete failure SYNCPOINT ROLLBACK, then NO_DELETE Generic delete error.
Update failure NO_UPD Generic update error (SSP1–SSP3). No explicit rollback.
PLI 
NO_ADD:
  SELECT (CA_RETURN_CODE);
    WHEN (70) ERP1FLDO = 'Customer does not exist';
    OTHERWISE ERP1FLDO = 'Error Adding Motor Policy';
  END;
  GO TO ERROR_OUT;

8.2 Error flow

graph TD L[LINK returns] --> RC{CA_RETURN_CODE > 0} RC -- No --> OK[Success path] RC -- Yes --> OP{Operation} OP -- Inquire --> ND[NO_DATA] OP -- Add --> RB1[SYNCPOINT ROLLBACK] --> NA[NO_ADD] OP -- Delete --> RB2[SYNCPOINT ROLLBACK] --> NDL[NO_DELETE] OP -- Update --> NU[NO_UPD] NA --> EO[ERROR_OUT] ND --> EO NDL --> EO NU --> EO EO --> RST[Send map, reset map and COMMAREA] RST --> ES[ENDIT_STARTIT]

ERROR_OUT clears COMM_AREA_RAW, CA_REQUEST_ID, CA_RETURN_CODE, CA_CUSTOMER_NUM and CA_REQUEST_INITIALISER. This stops residual data from affecting the next request.

9. Constraints and Dependencies

9.1 Constraints

  • Option values. Valid options are 1–4 for SSP1–SSP3 and 1–3 for SSP4.
  • No local format validation. Dates and numeric content are not checked in the menus. The back end validates them. Values longer than the declared field widths are truncated.
  • Update needs a successful inquiry. The two-phase flow (SSP1–SSP3) cannot reach the update step if the first inquiry fails.
  • Broker and payment fields. On add and update, CA_PAYMENT and CA_BROKERID are set to 0 and CA_BROKERSREF is blanked. The screens have no input for them.
  • Fixed COMMAREA length. Every LINK must use LENGTH(32500).
  • Rollback scope. Rollback is issued only for add and delete failures.

9.2 Dependencies

Dependency Role
CICS transactions SSP1–SSP4 Must be defined so each program can re-invoke itself.
Mapset SSMAP Provides maps SSMAPP1–SSMAPP4 for send and receive.
Copybook LGCMAREA Defines the shared COMMAREA.
Copybook SSMAP Defines the symbolic map structures.
LGIPOL01, LGAPOL01, LGDPOL01, LGUPOL01 Back-end inquiry, add, delete and update orchestrators.

10.2 Add a house policy for a non-existent customer

Field Value
Option 2
Customer (ENP3CNOI) 9999999999
  1. The program sets 01AHOU and links to LGAPOL01.
  2. The back end returns CA_RETURN_CODE = 70.
  3. The program issues SYNCPOINT ROLLBACK.
  4. NO_ADD sets ERP3FLDO = 'Customer does not exist'.
  5. ERROR_OUT resets the state and the transaction continues.

10.3 Commercial inquiry by postcode

Field Value
Option 1
Postcode (ENP4HPCO) SW1A 1AA

The non-blank postcode overrides the key-based routing. The program sets CA_REQUEST_ID = '05ICOM' and CA_B_Postcode, then links to LGIPOL01.

10.4 Invalid option

If the operator enters 9, no back-end program is called. The map is redisplayed with “Please enter a valid option” and the cursor is placed on the option field.
