Customer Inquiry & Update Programs

This page documents the full inquiry and update path for customer records within the GenApp general insurance application. It covers five Enterprise PL/I programs hosted under CICS: LGICUS01 (inquiry front-end / orchestrator), LGICDB01 (DB2 retrieval backend), LGUCUS01 (update orchestrator), LGUCDB01 (DB2 update backend), and LGUCVS01 (VSAM update backend). Together, these programs form a two-pronged pipeline — one for reading customer data and one for writing it — sharing a common communication area structure, error-logging pattern, and diagnostic framework.

1. System Architecture

The five programs are arranged in two distinct call chains: an inquiry path and an update path. Both paths originate from a CICS-linked orchestrator that validates the incoming request and delegates actual data access to one or more specialised backend programs. No orchestrator program touches a database directly; all DB2 and VSAM I/O is encapsulated in the backend tier.

All five programs share the same 32,500-byte LGCMAREA communication area structure, defined in plinc/LGCMAREA.inc. The COMMAREA is passed by reference through every CICS LINK in the chain, so response fields written by a backend program are immediately visible to the orchestrator and ultimately to the original caller. Error logging in every program is routed through the shared LGSTSQ utility, which writes timestamped diagnostic records to a CICS Transient Data Queue (TDQ).

2. Overview

2.1 Shared Communication Area

All programs in both paths communicate through a single 32,500-byte COMMAREA defined by the LGCMAREA copybook. Key header fields used across the entire pipeline are:

Field Type Description
CA_REQUEST_ID CHAR(6) Identifies the requested operation (e.g., 01ICUS, 01UCUS)
CA_RETURN_CODE PIC '99' Outcome code; 00 = success, non-zero = error
CA_CUSTOMER_NUM PIC '9999999999' 10-digit customer primary key
CA_NUM_POLICIES PIC '999' Count of policies linked to the customer
CA_FIRST_NAME CHAR(10) Customer first name
CA_LAST_NAME CHAR(20) Customer last name
CA_DOB CHAR(10) Date of birth
CA_HOUSE_NAME CHAR(20) Property/house name
CA_HOUSE_NUM CHAR(4) Street number
CA_POSTCODE CHAR(8) Postal code
CA_PHONE_MOBILE CHAR(20) Mobile phone number
CA_PHONE_HOME CHAR(20) Home phone number
CA_EMAIL_ADDRESS CHAR(100) Email address
CA_POLICY_DATA CHAR(32267) Serialised policy records payload

The COMMAREA minimum valid length for customer operations is 90 bytes (18-byte header/trailer + 72-byte customer record).

2.2 Shared Error Handling Pattern

Every program in both paths follows an identical three-step error handling pattern:

  1. COMMAREA guard — if EIBCALEN = 0, log the failure and issue EXEC CICS ABEND ABCODE('LGCA') NODUMP
  2. Length validation — if EIBCALEN < 90, set CA_RETURN_CODE = '98' and return immediately
  3. Diagnostic logging — on any fatal condition, call WRITE_ERROR_MESSAGE, which timestamps the event via EXEC CICS ASKTIME / EXEC CICS FORMATTIME and writes a structured record plus up to 90 bytes of raw COMMAREA to the TDQ via LGSTSQ

2.3 Return Code Summary

Return Code Meaning Set By
00 Success All programs
98 COMMAREA too short LGICUS01, LGICDB01
99 Invalid request ID LGUCUS01
01 Customer not found (SQLCODE 100 or -913) LGICDB01, LGUCDB01
90 Unexpected DB2 error LGICDB01, LGUCDB01
81 VSAM read failure LGUCVS01
82 VSAM rewrite failure LGUCVS01

3. Inquiry Path

The inquiry path retrieves a customer record from DB2 and returns it to the caller. It consists of two programs: the front-end orchestrator LGICUS01 and the DB2 backend LGICDB01.

3.1 LGICUS01 — Inquiry Orchestrator

3.1.1 Purpose

LGICUS01 is the business logic entry point for customer inquiry. It validates the COMMAREA, reads a CICS Temporary Storage queue (GENAWMQC) to detect a runtime MQ routing override, and then delegates the actual data retrieval to LGICDB01 (standard DB2 path) or to a placeholder alternate program (AAAAAAAA) if the MQ routing flag MQHIT= is found.

3.1.2 Processing Flow

sequenceDiagram participant Caller as Calling Program participant LGICUS01 as LGICUS01 participant TSQUEUE as GENAWMQC TS Queue participant LGICDB01 as LGICDB01 participant LGSTSQ as LGSTSQ (Logger) Caller->>LGICUS01: EXEC CICS LINK (COMMAREA) LGICUS01->>LGICUS01: Capture EIBTRNID / EIBTRMID / EIBTASKN alt EIBCALEN = 0 LGICUS01->>LGSTSQ: LINK — log NO COMMAREA RECEIVED LGICUS01-->>Caller: ABEND LGCA else EIBCALEN < 90 LGICUS01-->>Caller: CA_RETURN_CODE = 98, CICS RETURN end LGICUS01->>LGICUS01: Init CA_RETURN_CODE=00, CA_NUM_POLICIES=0 LGICUS01->>TSQUEUE: READQ TS ITEM(1) — scan for MQHIT= loop Read all TS queue records TSQUEUE-->>LGICUS01: 80-byte record end alt MQ_HIT = 0 (no routing record found) LGICUS01->>LGICDB01: EXEC CICS LINK (COMMAREA 32500 bytes) LGICDB01-->>LGICUS01: Customer data populated in COMMAREA else MQ_HIT = 1 LGICUS01->>LGICUS01: EXEC CICS LINK PROGRAM('AAAAAAAA') end LGICUS01-->>Caller: EXEC CICS RETURN (enriched COMMAREA)

Key processing steps:

  1. Capture EIBTRNID, EIBTRMID, and EIBTASKN into WS_HEADER for diagnostics.
  2. If EIBCALEN = 0: log error, issue EXEC CICS ABEND ABCODE('LGCA') NODUMP.
  3. Initialise CA_RETURN_CODE = '00', CA_NUM_POLICIES = 0.
  4. Validate EIBCALEN >= 90; if not, set CA_RETURN_CODE = '98' and return.
  5. Copy CA_CUSTOMER_NUM into EM_CUSNUM for diagnostic context.
  6. Call GET_CUSTOMER_INFO — scan GENAWMQC TS queue for MQHIT=.
  7. If MQ_HIT = 0: EXEC CICS LINK PROGRAM('LGICDB01') COMMAREA(COMM_AREA) LENGTH(32500).
  8. If MQ_HIT = 1: EXEC CICS LINK PROGRAM('AAAAAAAA') COMMAREA(COMM_AREA) LENGTH(32500).
  9. EXEC CICS RETURN to caller.

3.1.3 MQ Routing Logic

The TS queue GENAWMQC acts as a runtime routing switch. The program reads it sequentially, inspecting the first 6 characters of each 80-byte record for the literal 'MQHIT='. This allows the inquiry path to be redirected at runtime without recompiling any code.

CODE 
/* Routing decision pseudocode */
MQ_HIT = 0;
EXEC CICS READQ TS QUEUE('GENAWMQC') INTO(MQ_READ_RECORD) ITEM(1) RESP(WS_RESP);
DO UNTIL (WS_RESP > 0);
    IF WS_RESP = DFHRESP(NORMAL) AND SUBSTR(MQ_READ_RECORD,1,6) = 'MQHIT=' THEN
        MQ_HIT = 1;
    EXEC CICS READQ TS QUEUE('GENAWMQC') INTO(MQ_READ_RECORD) NEXT RESP(WS_RESP);
END;

IF MQ_HIT = 0 THEN
    EXEC CICS LINK PROGRAM('LGICDB01') COMMAREA(COMM_AREA) LENGTH(32500);
ELSE
    EXEC CICS LINK PROGRAM('AAAAAAAA') COMMAREA(COMM_AREA) LENGTH(32500);

3.2 LGICDB01 — DB2 Retrieval Backend

3.2.1 Purpose

LGICDB01 is the DB2 backend for customer inquiry. It executes a single-row SELECT against the CUSTOMER table, populating up to nine customer demographic fields in the COMMAREA, and returns outcome codes 00 (found), 01 (not found or deadlock), 90 (unexpected DB2 error), or 98 (COMMAREA too short) to the caller.

3.2.2 Processing Flow

Key processing steps:

  1. Capture EIB diagnostic fields; zero out DB2 host variable block.
  2. If EIBCALEN = 0: log error, EXEC CICS ABEND ABCODE('LGCA') NODUMP.
  3. Set CA_RETURN_CODE = '00'; validate EIBCALEN >= 90.
  4. Convert CA_CUSTOMER_NUM → DB2_CUSTOMERNUMBER_INT (FIXED BIN(31)); load into EM_CUSNUM.
  5. Call GET_CUSTOMER_INFO:
SQL 
EXEC SQL
  SELECT FIRSTNAME, LASTNAME, DATEOFBIRTH,
         HOUSENAME, HOUSENUMBER, POSTCODE,
         PHONEMOBILE, PHONEHOME, EMAILADDRESS
  INTO   :CA_FIRST_NAME, :CA_LAST_NAME, :CA_DOB,
         :CA_HOUSE_NAME, :CA_HOUSE_NUM, :CA_POSTCODE,
         :CA_PHONE_MOBILE, :CA_PHONE_HOME, :CA_EMAIL_ADDRESS
  FROM   CUSTOMER
  WHERE  CUSTOMERNUMBER = :DB2_CUSTOMERNUMBER_INT
END-EXEC
  1. Evaluate SQLCODE:
    • 0 → CA_RETURN_CODE = '00'
    • 100 or -913 → CA_RETURN_CODE = '01'
    • Other → CA_RETURN_CODE = '90', call WRITE_ERROR_MESSAGE, EXEC CICS RETURN
  2. EXEC CICS RETURN to caller.

4. Update Path

The update path modifies an existing customer record in both DB2 and VSAM. It consists of three programs: the front-end orchestrator LGUCUS01, the DB2 backend LGUCDB01, and the VSAM backend LGUCVS01.

4.1 LGUCUS01 — Update Orchestrator

4.1.1 Purpose

LGUCUS01 is the business logic entry point for customer updates. It validates the COMMAREA, checks that CA_REQUEST_ID = '01UCUS', and delegates the entire update to LGUCDB01 via a single CICS LINK. It performs no database access itself.

4.1.2 Processing Flow

sequenceDiagram participant Caller as Calling Program participant LGUCUS01 as LGUCUS01 participant LGUCDB01 as LGUCDB01 participant LGSTSQ as LGSTSQ (Logger) Caller->>LGUCUS01: EXEC CICS LINK (COMMAREA with CA_REQUEST_ID=01UCUS) LGUCUS01->>LGUCUS01: Capture EIB fields alt EIBCALEN = 0 LGUCUS01->>LGSTSQ: LINK — log NO COMMAREA RECEIVED LGUCUS01-->>Caller: ABEND LGCA end LGUCUS01->>LGUCUS01: Init CA_RETURN_CODE=00, CA_NUM_POLICIES=0 LGUCUS01->>LGUCUS01: Copy CA_CUSTOMER_NUM → EM_CUSNUM alt CA_REQUEST_ID ≠ 01UCUS LGUCUS01-->>Caller: CA_RETURN_CODE=99, CICS RETURN end LGUCUS01->>LGUCDB01: EXEC CICS LINK (COMMAREA 32500 bytes) LGUCDB01-->>LGUCUS01: CA_RETURN_CODE set by DB2 backend LGUCUS01-->>Caller: EXEC CICS RETURN (updated COMMAREA)

Key processing steps:

  1. Capture EIBTRNID, EIBTRMID, EIBTASKN.
  2. If EIBCALEN = 0: log error, EXEC CICS ABEND ABCODE('LGCA') NODUMP.
  3. Initialise CA_RETURN_CODE = '00', CA_NUM_POLICIES = 0.
  4. Copy CA_CUSTOMER_NUM into EM_CUSNUM.
  5. Validate CA_REQUEST_ID = '01UCUS'; if not, set CA_RETURN_CODE = '99' and return.
  6. Call UPDATE_CUSTOMER_INFO → EXEC CICS LINK PROGRAM('LGUCDB01') COMMAREA(COMM_AREA) LENGTH(32500).
  7. EXEC CICS RETURN to caller.

4.1.3 Request ID Validation

LGUCUS01 rejects any request where CA_REQUEST_ID ≠ '01UCUS' with return code 99. This is a hard guard — no error message is logged; the return code alone signals the rejection.

CODE 
/* Request ID validation pseudocode */
IF CA_REQUEST_ID ^= '01UCUS' THEN DO;
    CA_RETURN_CODE = '99';
    EXEC CICS RETURN;
END;
CALL UPDATE_CUSTOMER_INFO;

4.2 LGUCDB01 — DB2 Update Backend

4.2.1 Purpose

LGUCDB01 executes the DB2 UPDATE against the CUSTOMER table and then chains to LGUCVS01 to keep the VSAM file store consistent. It sets CA_RETURN_CODE to '00' (success), '01' (not found), or '90' (unexpected DB2 error).

4.2.2 Processing Flow

Key processing steps:

  1. Capture EIB fields; if EIBCALEN = 0, abend LGCA.
  2. Set CA_RETURN_CODE = '00'.
  3. Convert CA_CUSTOMER_NUM → DB2_CUSTOMERNUM_INT; copy to EM_CUSNUM.
  4. Call UPDATE_CUSTOMER_INFO:
SQL 
EXEC SQL
  UPDATE CUSTOMER
     SET FIRSTNAME      = :CA_FIRST_NAME,
         LASTNAME       = :CA_LAST_NAME,
         DATEOFBIRTH    = :CA_DOB,
         HOUSENAME      = :CA_HOUSE_NAME,
         HOUSENUMBER    = :CA_HOUSE_NUM,
         POSTCODE       = :CA_POSTCODE,
         PHONEMOBILE    = :CA_PHONE_MOBILE,
         PHONEHOME      = :CA_PHONE_HOME,
         EMAILADDRESS   = :CA_EMAIL_ADDRESS
   WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUM_INT
END-EXEC
  1. Evaluate SQLCODE:
    • 0 → leave CA_RETURN_CODE = '00'
    • 100 → CA_RETURN_CODE = '01'
    • Other → CA_RETURN_CODE = '90', call WRITE_ERROR_MESSAGE
  2. After UPDATE_CUSTOMER_INFO returns: EXEC CICS LINK PROGRAM('LGUCVS01') COMMAREA(COMM_AREA) LENGTH(225).
  3. EXEC CICS RETURN to caller.

Note: LGUCVS01 is always linked after UPDATE_CUSTOMER_INFO returns — even when CA_RETURN_CODE is '01' or '90'. There is no conditional guard on the VSAM link.

4.2.3 DB2 Table — CUSTOMER

The same CUSTOMER table is targeted for both reads (inquiry path) and writes (update path). In the update path, all nine customer attribute columns are overwritten unconditionally in a single UPDATE statement — partial updates are not supported.

4.3 LGUCVS01 — VSAM Update Backend

4.3.1 Purpose

LGUCVS01 updates the VSAM KSDS customer file KSDSCUST. It reads the existing record with exclusive update intent, then rewrites it with the new customer data from the COMMAREA. It is the final program in the update chain and is always called by LGUCDB01 after the DB2 update.

4.3.2 Processing Flow

Key processing steps:

  1. Capture EIBCALEN into WS_Commarea_Len and WS_Commarea_LenF.
  2. Issue EXEC CICS READ FILE('KSDSCUST') INTO(WS_Customer_Area) RIDFLD(CA_CUSTOMER_NUM) KEYLENGTH(10) UPDATE RESP(WS_RESP).
  3. If read fails: set CA_RETURN_CODE = '81', log via WRITE_ERROR_MESSAGE, abend LGV1.
  4. Issue EXEC CICS REWRITE FILE('KSDSCUST') FROM(CA_CUSTOMER_NUM) LENGTH(WS_Commarea_LenF) RESP(WS_RESP).
  5. If rewrite fails: set CA_RETURN_CODE = '82', log via WRITE_ERROR_MESSAGE, abend LGV2.
  6. RETURN to caller.

6. Shared WRITE_ERROR_MESSAGE Pattern

All five programs implement an identical WRITE_ERROR_MESSAGE internal procedure. It is invoked on fatal error conditions and writes two records to the CICS TDQ via LGSTSQ:

  1. Structured error record (ERROR_MSG) — contains date, time, program name, customer number, SQL request label, and SQLCODE (or CICS RESP codes for VSAM programs).
  2. COMMAREA dump (CA_ERROR_MSG) — contains up to 90 bytes of the raw COMMAREA, prefixed with 'COMMAREA='.
CODE 
/* WRITE_ERROR_MESSAGE — common pattern across all five programs */
WRITE_ERROR_MESSAGE: PROC;
    EM_SQLRC = SQLCODE;                         /* capture SQLCODE */
    EXEC CICS ASKTIME ABSTIME(WS_ABSTIME);      /* get current time */
    EXEC CICS FORMATTIME ABSTIME(WS_ABSTIME)
              MMDDYYYY(WS_DATE) TIME(WS_TIME);  /* format date/time */
    EM_DATE = WS_DATE;
    EM_TIME = WS_TIME;
    /* Write primary error record */
    EXEC CICS LINK PROGRAM('LGSTSQ')
              COMMAREA(ERROR_MSG) LENGTH(STG(ERROR_MSG));
    /* Conditionally write COMMAREA dump */
    IF (EIBCALEN > 0) THEN DO;
        IF (EIBCALEN < 91) THEN
            CA_DATA = LEFT(COMM_AREA_RAW, EIBCALEN);
        ELSE
            CA_DATA = LEFT(COMM_AREA_RAW, 90);
        EXEC CICS LINK PROGRAM('LGSTSQ')
                  COMMAREA(CA_ERROR_MSG) LENGTH(STG(CA_ERROR_MSG));
    END;
    RETURN;
END WRITE_ERROR_MESSAGE;

The COMMAREA dump is always capped at 90 bytes (matching the fixed CA_DATA CHAR(90) field) and is only written when EIBCALEN > 0. The NODUMP option on all abends means this TDQ log is the primary diagnostic artefact for post-failure analysis.

7. Constraints and Operational Notes

7.1 COMMAREA Constraints

  • Minimum size: 90 bytes (WS_CA_HEADERTRAILER_LEN(18) + WS_CUSTOMER_LEN(72)) for both inquiry and update paths.
  • Maximum size: 32,500 bytes as declared by COMM_AREA_RAW CHAR(32500).
  • VSAM LINK length: LGUCDB01 passes only LENGTH(225) to LGUCVS01 — only the first 225 bytes of the COMMAREA are visible to the VSAM backend.
  • DB2 LINK length: Both LGICUS01 and LGUCUS01 pass LENGTH(32500) to their respective backends — the full buffer is always forwarded.

7.2 Data Type Constraints

  • CA_CUSTOMER_NUM must be a valid 10-digit numeric string. Converting a non-numeric value to FIXED BIN(31) for the DB2 WHERE clause will cause a PL/I conversion error at runtime.
  • DB2_CUSTOMERNUMBER_INT is FIXED BIN(31), limiting valid customer numbers to the signed 31-bit integer range (≤ 2,147,483,647).
  • All nine customer attribute columns are updated unconditionally in the DB2 UPDATE — callers must supply all field values; partial updates are not supported.

7.3 Sequencing Constraints

  • In LGUCVS01, READ ... UPDATE must precede REWRITE. CICS requires the exclusive lock established by the read before a rewrite can be issued.
  • In LGUCDB01, the DB2 UPDATE always executes before the CICS LINK to LGUCVS01, regardless of outcome. The VSAM link is not conditional on DB2 success.
  • In both orchestrators, COMMAREA validation precedes all other processing — no COMMAREA fields are read before the EIBCALEN guard passes.

7.4 VSAM Abend Behaviour

Unlike the DB2 backends (which set a return code and return cleanly on most errors), LGUCVS01 issues a hard CICS abend on any file I/O failure:

  • LGV1 (read failure) — task terminates after logging; REWRITE is never attempted.
  • LGV2 (rewrite failure) — task terminates after logging.

Both abends use NODUMP, so the TDQ log written by WRITE_ERROR_MESSAGE is the only diagnostic output.
