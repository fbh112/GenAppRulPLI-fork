Logging & Error Handling

This page documents the shared LGSTSQ logging utility used across GenApp programs. At the application level, LGSTSQ is the standard mechanism for capturing diagnostic text, identifying the originating CICS region, and recording the result in both operational and application-facing queues. It accepts message content either from a caller-supplied COMMAREA or from direct terminal input, prefixes each entry with the CICS SYSID, writes to the CICS transient data queue CSMT, and writes to a GenApp temporary storage queue that defaults to GENAERRS but can be redirected to GENAnnnn using an inline Q=nnnn prefix. In practice, calling programs build detailed, timestamped messages that may include SQLCODE, CICS RESP values, and even raw COMMAREA snapshots before linking to LGSTSQ.

1. Overview

LGSTSQ is the centralized error and diagnostic logging utility for GenApp. Its behavior is intentionally simple and uniform:

  • accept a text message
  • determine whether the message came from:
    • another program through COMMAREA, or
    • an operator through terminal input
  • prepend the CICS region identifier (SYSID)
  • write the entry to:
    • transient data queue CSMT
    • temporary storage queue GENAERRS by default, or GENAnnnn when overridden
  • optionally clear the terminal if invoked interactively
  • return to CICS without abending

At the application level, this makes LGSTSQ the shared sink for cross-program diagnostics. GenApp programs can standardize around a common message format while relying on one utility to route entries consistently to both system-level and application-level destinations.

1.1 Primary responsibilities

LGSTSQ performs five core responsibilities:

  1. detect invocation mode
  2. normalize input text into a shared output structure
  3. apply queue-routing rules
  4. stamp the record with SYSID
  5. write the record to both TDQ and TSQ targets

1.2 What calling programs typically log

Although LGSTSQ itself only writes the text it receives, the application-level pattern is for callers to assemble rich diagnostic strings before invoking it. Typical content includes:

  • date and time stamp
  • program name
  • transaction or business function context
  • SQLCODE for DB2-related failures
  • CICS RESP / RESP2 style outcomes where available
  • key business identifiers
  • raw COMMAREA or input snapshots
  • free-form explanatory text

A representative caller-generated message might look like this:

TEXT 
2026-10-25 14:03:18 LGSICVP SQLCODE=-305 RESP=16 Policy not found COMMAREA=...

1.3 Logging objectives

The utility serves two distinct logging purposes:

Destination Role
CSMT Operational visibility in the standard CICS message log
GENAERRS / GENAnnnn Application-oriented retention and categorization of errors

This dual-write model gives operations staff a standard CICS trail while preserving GenApp-specific entries in TSQ storage for later review or downstream tooling.

2. System Architecture

At a high level, GenApp programs and terminal users feed diagnostic text into LGSTSQ, which enriches the output with region identity and persists the result to two CICS queueing mechanisms.

graph TD A[GenApp Calling Programs] --> B[LGSTSQ Logging Utility] C[Terminal User / Operator] --> B B --> D[CICS ASSIGN Services] D --> E[SYSID / STARTCODE / PRINSYSID / INVOKINGPROG] B --> F[TDQ CSMT] B --> G[TSQ GENAERRS] B --> H[TSQ GENAnnnn]

This architecture shows LGSTSQ as a shared application service rather than a business transaction program. It does not perform database work or business updates. Its job is to standardize how diagnostics enter the CICS logging landscape.

2.1 Architectural components

2.1.1 Message producers

Producers are the upstream sources of log text:

  • GenApp programs invoking LGSTSQ via EXEC CICS LINK
  • terminal users invoking it directly through a CICS transaction

2.1.2 Logging core

LGSTSQ itself is a single monolithic PL/I procedure that:

  • initializes buffers
  • interrogates the CICS runtime
  • determines input source
  • optionally parses a queue override directive
  • writes the message to the configured destinations

2.1.3 Runtime context providers

EXEC CICS ASSIGN supplies context that shapes processing:

  • SYSID
  • STARTCODE
  • PRINSYSID
  • INVOKINGPROG

Only SYSID is embedded directly in the written log record, but the other values drive invocation-path behavior.

2.1.4 Output targets

LGSTSQ always targets:

  • TDQ CSMT
  • TSQ GENAERRS unless overridden

If the incoming text begins with Q=nnnn, the TSQ target becomes GENAnnnn.

2.2 Entity relationships

graph TD A[Caller COMMAREA] --> B[WRITE_MSG_MSG] C[Terminal Input] --> B D[ASSIGN SYSID] --> E[WRITE_MSG_SYSID] E --> F[WRITE_MSG] B --> F F --> G[WRITEQ TD CSMT] F --> H[WRITEQ TS GENAERRS] B --> I[Q=nnnn Prefix Check] I --> H I --> J[WRITEQ TS GENAnnnn]

This relationship view emphasizes that the logged record is always built from two conceptual parts:

  • a SYSID prefix
  • a message payload

The queue override changes only the TSQ destination, not the record format itself.

3. Inputs and Invocation Modes

LGSTSQ supports two mutually exclusive invocation paths.

3.1 Program-to-program invocation via COMMAREA

When ASSIGN INVOKINGPROG returns a non-blank value, LGSTSQ treats the request as a linked call from another program.

In this mode:

  • WS_FLAG is set to C
  • COMMA_DATA is copied into WRITE_MSG_MSG
  • WS_RECV_LEN is set from EIBCALEN

This is the normal application logging path used by GenApp programs.

3.1.1 COMMAREA content expectations

The COMMAREA carries up to 90 bytes of text. The caller is therefore responsible for pre-formatting the message compactly. In practice, this means prioritizing the most valuable diagnostics first, such as:

  • timestamp
  • error code
  • key business identifier
  • short description

3.1.2 Example caller-side payload

TEXT 
20261025-140318 SQLCODE=-305 RESP=16 Cust=1234567890 Null host var in insert

3.2 Direct terminal invocation

When ASSIGN INVOKINGPROG is blank, LGSTSQ assumes direct terminal use.

In this mode:

  • EXEC CICS RECEIVE reads terminal input
  • the 5-byte transaction prefix is excluded
  • WS_FLAG is set to R
  • the entered data becomes the logged message

After writing the log entry, the program sends a blank SEND TEXT with ERASE and FREEKB, effectively clearing and unlocking the screen.

3.3 Invocation decision logic

graph TD A[Start] --> B[ASSIGN INVOKINGPROG] B --> C{INVOKINGPROG blank?} C -->|No| D[Use COMMAREA] C -->|Yes| E[RECEIVE terminal input] D --> F[Populate WRITE_MSG_MSG] E --> F F --> G[Continue logging flow]

This branch is the program’s key defensive control. It prevents terminal I/O when the request originated from another program and prevents COMMAREA-based assumptions during an interactive invocation.

4. Message Construction and Record Format

The written log record is built in WRITE_MSG and has a simple fixed structure:

  • 4-byte SYSID
  • 1-byte separator filler
  • up to 90 bytes of message text

4.1 Record structure

Field Purpose
WRITE_MSG_SYSID CICS region identifier
FILLER_X Single blank separator
WRITE_MSG_MSG Caller or terminal supplied message text

4.2 Effective write length

The actual number of bytes written depends on:

  • EIBCALEN for COMMAREA calls, or receive length for terminal calls
  • subtraction of 5 bytes for terminal transaction-id handling
  • subtraction of 7 bytes if Q=nnnn is present
  • addition of 5 bytes for SYSID plus separator

This means the utility does not blindly write the full 95-byte structure every time; it writes the meaningful portion.

4.3 Application-level message composition guidance

Because LGSTSQ does not generate timestamps or decode error codes on its own, the caller should format the text before linking. A practical application pattern is:

TEXT 
<timestamp> <program> SQLCODE=<value> RESP=<value> <business context> COMMAREA=<snapshot>

Example:

TEXT 
2026-10-25T14:03:18 LGSICDB SQLCODE=-911 RESP=16 Claim=000471 COMMAREA=...

4.4 Code example: conceptual caller formatting

The following example illustrates the application-level pattern described in the documentation, where a calling program assembles a complete diagnostic text and passes it to LGSTSQ through COMMAREA:

PLI 
/* Conceptual caller-side pattern */
DCL 1 ERR_MSG,
      2 ERR_TEXT CHAR(90);

ERR_TEXT =
   '2026-10-25T14:03:18 LGSICVP SQLCODE=-305 RESP=16 COMMAREA=...';

EXEC CICS LINK
     PROGRAM('LGSTSQ')
     COMMAREA(ERR_TEXT)
     LENGTH(LENGTH(ERR_TEXT));

5. Queue Routing and Storage Targets

LGSTSQ always writes to CSMT and also writes to one application TSQ.

5.1 Standard destinations

5.1.1 TDQ destination

  • queue name: CSMT
  • purpose: CICS operational/system log visibility

5.1.2 TSQ destination

  • default queue name: GENAERRS
  • purpose: application-level error persistence

5.2 Dynamic TSQ override

If the message text begins with Q=nnnn, the queue suffix in positions 3 through 6 replaces the final four bytes of the default queue name, producing GENAnnnn.

Examples:

Input prefix Resulting TSQ
Q=0042 GENA0042
Q=ABCD GENAABCD

The prefix is removed from the logged message before the record is written.

5.3 Routing flow

graph TD A[Incoming Message] --> B{Starts with Q=?} B -->|No| C[Use default TSQ GENAERRS] B -->|Yes| D[Extract chars 3-6] D --> E[Build TSQ GENAnnnn] C --> F[Write to CSMT] D --> F F --> G[Write to selected TSQ]

This routing model gives callers a lightweight in-band mechanism to categorize or partition error logs without changing the interface to LGSTSQ.

5.4 Code example: queue override usage

TEXT 
Q=0042Policy limit exceeded for account 99

This produces:

  • TSQ destination: GENA0042
  • logged text body: Policy limit exceeded for account 99

6. Processing Sequence

The utility’s logic is linear and intentionally compact.

6.1 End-to-end sequence

sequenceDiagram participant Caller as Calling Program / Terminal participant LG as LGSTSQ participant CICS as CICS Runtime participant TDQ as TDQ CSMT participant TSQ as TSQ GENAERRS/GENAnnnn Caller->>LG: Invoke with COMMAREA or terminal input LG->>CICS: ASSIGN SYSID LG->>CICS: ASSIGN STARTCODE LG->>CICS: ASSIGN PRINSYSID LG->>CICS: ASSIGN INVOKINGPROG LG->>LG: Determine invocation mode LG->>LG: Populate WRITE_MSG_MSG LG->>LG: Check for Q=nnnn override LG->>LG: Adjust write length and prepend SYSID LG->>TDQ: WRITEQ TD to CSMT LG->>TSQ: WRITEQ TS NOSUSPEND alt Terminal invocation LG->>CICS: SEND TEXT ERASE FREEKB end LG-->>Caller: RETURN to CICS

This sequence shows that all environmental interrogation happens before message handling, and that queue writes are consistently ordered: TDQ first, then TSQ.

6.2 Ordered processing steps

6.2.1 Initialization

WRITE_MSG and WS_RECV are cleared to blanks.

6.2.2 CICS environment capture

The program issues four ASSIGN commands to obtain:

  • SYSID
  • STARTCODE
  • PRINSYSID
  • INVOKINGPROG

6.2.3 Message acquisition

The utility selects one source:

  • COMMAREA from a calling program
  • terminal input from RECEIVE

6.2.4 Optional queue override

The program checks whether the message starts with Q=.

6.2.5 Length adjustment

It recalculates the output length based on source and prefix handling.

6.2.6 Queue writes

The same composed record is written to:

  1. CSMT
  2. selected TSQ

6.2.7 Terminal cleanup

For terminal invocations only, a blank response is sent to clear the screen.

6.2.8 Return

The task ends with EXEC CICS RETURN.

7. Error Handling Strategy

LGSTSQ is a logging utility, but it also embodies a particular error-handling philosophy: absorb CICS command failures, avoid making logging itself disruptive, and return cleanly.

7.1 RESP-based capture

Every EXEC CICS command uses RESP(WS_RESP).

This means:

  • CICS response outcomes are captured numerically
  • default condition handling is suppressed
  • the program avoids abending because of command-level errors alone

7.2 Silent continuation

A critical characteristic of LGSTSQ is that WS_RESP is captured but never explicitly tested afterward.

Implications:

  • failed ASSIGN calls do not trigger alternate logic
  • failed RECEIVE calls do not stop the program
  • failed queue writes do not produce recursive logging
  • processing continues to RETURN

This makes the utility resilient and non-intrusive, but also means failures can be silent.

7.3 TSQ best-effort behavior with NOSUSPEND

The TSQ write uses NOSUSPEND.

Operationally, this means:

  • if TSQ storage is constrained, the task is not suspended
  • the TSQ write may be dropped
  • the program continues

This is appropriate for a utility whose purpose is diagnostic support rather than business-critical state change.

7.4 Differential handling between TDQ and TSQ

Queue type Command Behavior
TDQ CSMT WRITEQ TD no NOSUSPEND; still captured via RESP
TSQ GENAERRS / GENAnnnn WRITEQ TS NOSUSPEND best-effort, non-blocking

7.5 Invocation-aware safeguards

The program avoids invalid terminal operations by sending terminal output only when WS_FLAG = 'R'. This prevents attempts to write to a non-existent terminal during linked program execution.

7.6 No recursive self-reporting

LGSTSQ does not attempt to log its own internal failures by calling another logger or issuing an abend. That avoids recursion and keeps the utility lightweight.

8. Operational Constraints and Limitations

8.1 Data size limits

  • COMMAREA message payload: up to 90 bytes
  • terminal usable message text: 74 bytes
  • output structure max size: 95 bytes including SYSID and separator
  • WS_RECV_LEN initialized to 80 and adjusted during processing

8.2 COMMAREA dependency for linked calls

When invoked programmatically, LGSTSQ assumes the COMMAREA is valid and dereferences it. If a caller links incorrectly, that can cause failure outside the program’s own defensive checks.

8.3 Strict queue override syntax

The override must appear exactly as:

TEXT 
Q=nnnn

at the start of the message. Lowercase, leading spaces, or variant formats do not trigger special routing.

8.4 No DB2 interaction

LGSTSQ itself does not access DB2 tables. Any SQLCODE values seen in log records are caller-supplied text, not values gathered by LGSTSQ.

9. Application Integration Pattern

From an application perspective, LGSTSQ should be treated as the standard logging endpoint for abnormal conditions and significant diagnostics.

9.1 Recommended caller pattern

A GenApp caller should:

  1. detect the exception or failure
  2. gather the relevant context
  3. build a compact diagnostic string
  4. optionally prepend Q=nnnn if specialized TSQ routing is needed
  5. LINK to LGSTSQ with the message in COMMAREA

9.2 Recommended diagnostic fields

A compact but useful message often includes:

  • timestamp
  • program name
  • transaction or function name
  • SQLCODE
  • CICS RESP
  • business key
  • short reason text
  • COMMAREA snapshot or truncated image

9.3 Example application-level messages

9.3.1 Default queue logging

TEXT 
2026-10-25T14:03:18 LGSICVP SQLCODE=-305 RESP=16 Cust=1234567890 COMMAREA=...

9.3.2 Routed queue logging

TEXT 
Q=00422026-10-25T14:03:18 LGSICVP SQLCODE=-911 RESP=16 Account=99 COMMAREA=...

In the second example:

  • TSQ becomes GENA0042
  • the Q=0042 prefix is not retained in the logged text body

10. Code Examples from the Utility Behavior

10.1 Terminal invocation example

TEXT 
Input from terminal:
LGSQ Account 888 is invalid

Resulting logged record:

TEXT 
GENL Account 888 is invalid

The first 5 bytes of terminal data are treated as the transaction prefix and are not part of the logged message body.

10.2 Program-linked invocation example

TEXT 
COMMAREA:
Policy not found for customer 1234567890

Resulting outputs to CSMT and GENAERRS:

TEXT 
GENL Policy not found for customer 1234567890

10.3 Queue override example

TEXT 
COMMAREA:
Q=0042Policy limit exceeded for account 99

Result:

TEXT 
Logged text:
GENL Policy limit exceeded for account 99

Destination queues:

  • TDQ: CSMT
  • TSQ: GENA0042

11. Summary

LGSTSQ provides GenApp with a shared, low-friction logging and error-handling utility. It accepts diagnostic text from either COMMAREA or terminal input, prefixes each record with the originating CICS SYSID, writes to both CSMT and an application TSQ, and supports lightweight TSQ routing through a Q=nnnn convention. Its design favors availability and non-disruption: RESP is captured on all CICS commands, the TSQ write is best-effort through NOSUSPEND, terminal output is conditional, and the program always returns normally.

At the application level, the quality of logging depends largely on what callers place into the COMMAREA. For that reason, GenApp programs should construct concise but information-rich, timestamped messages containing items such as SQLCODE, RESP values, business identifiers, and raw COMMAREA snapshots before invoking LGSTSQ.
