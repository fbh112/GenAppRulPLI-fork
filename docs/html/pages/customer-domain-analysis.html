Customer Domain Analysis

This page provides an application-level analysis of the customer domain, covering its layered architecture, shared data model, key programs, customer inquiry/add/update transaction flows, and the mechanisms used to keep customer data aligned across DB2 and VSAM. The domain is implemented as a consistent three-tier pattern: presentation-driven orchestration, DB2-centric business persistence, and a VSAM mirror layer used for secondary storage and lookup support.

1. Overview

The customer domain is responsible for three primary business operations:

  • Customer addition
  • Customer inquiry
  • Customer update

At runtime, these operations are initiated by the presentation program LGTESTC1, which passes a shared COMMAREA into domain-specific orchestrators:

  • LGACUS01 — Add customer orchestrator
  • LGICUS01 — Inquire customer orchestrator
  • LGUCUS01 — Update customer orchestrator

These orchestrators delegate to DB2 backend programs for primary persistence and retrieval:

  • LGACDB01 — Add customer in DB2
  • LGICDB01 — Inquire customer in DB2
  • LGUCDB01 — Update customer in DB2

The DB2 layer then coordinates with VSAM mirror programs:

  • LGACVS01 — Add customer to VSAM
  • LGICVS01 — Discover a customer number from VSAM/range metadata
  • LGUCVS01 — Update customer in VSAM

A specialized security backend, LGACDB02, is invoked during customer creation to create a related CUSTOMER_SECURE row.

The domain uses a shared COMMAREA contract (LGCMAREA.inc) across all programs. This gives the domain a uniform interface, but also creates tight coupling across the full call chain.

2. System Architecture

The customer domain follows a strict layered architecture in which each operation passes through presentation, orchestration, DB2 persistence, and, where required, VSAM mirroring.

graph TD A[LGTESTC1 Presentation] --> B[Orchestrator Layer] B --> C[LGACUS01 Add] B --> D[LGICUS01 Inquire] B --> E[LGUCUS01 Update] C --> F[LGACDB01 DB2 Add] D --> G[LGICDB01 DB2 Inquire] E --> H[LGUCDB01 DB2 Update] F --> I[LGACVS01 VSAM Add] H --> J[LGUCVS01 VSAM Update] F --> K[LGACDB02 Security Add] G --> L[GENASA1.CUSTOMER] F --> L H --> L K --> M[GENASA1.CUSTOMER_SECURE] I --> N[KSDSCUST VSAM] J --> N D -. optional utility path .-> O[LGICVS01 Discovery Utility] O --> P[GENACNTL TS Queue] O --> N

This architecture shows an important design principle: DB2 is the primary system of record for customer data, while VSAM acts as a mirrored secondary store for selected customer information. Inquiry is primarily DB2-based, while add and update perform dual-write behavior across DB2 and VSAM.

2.1. Architectural Layers

2.1.1. Presentation Layer

  • Program: LGTESTC1
  • Initiates customer operations
  • Populates COMMAREA fields such as:
    • CA_REQUEST_ID
    • CA_CUSTOMER_NUM
    • CA_FIRST_NAME
    • CA_LAST_NAME
    • CA_EMAIL_ADDRESS
  • Uses CICS LINK to invoke orchestrators

2.1.2. Orchestrator Layer

  • Programs: LGACUS01, LGICUS01, LGUCUS01
  • Performs:
    • COMMAREA length validation
    • Request ID gating
    • Basic routing
    • Error propagation

This layer does not own the actual persistence logic; instead, it enforces flow control and business entry-point discipline.

2.1.3. DB2 Backend Layer

  • Programs: LGACDB01, LGICDB01, LGUCDB01
  • Primary responsibilities:
    • SQL INSERT
    • SQL SELECT
    • SQL UPDATE
    • Customer number generation coordination
    • Invocation of VSAM mirror operations
    • Invocation of security-record creation during add

2.1.4. VSAM Mirror Layer

  • Programs: LGACVS01, LGICVS01, LGUCVS01
  • Maintains a secondary keyed customer representation in KSDSCUST
  • Uses:
    • WRITE for add
    • READ UPDATE + REWRITE for update
    • GTEQ READ in the inquiry utility path

2.2. Supporting Infrastructure

The domain also depends on infrastructure resources:

  • Named counter: GENACUSTNUM in pool GENA
  • TS queues:
    • GENACNTL for customer number range discovery
    • GENAWMQC for an MQ cache-hit hook
  • Shared error logging program: LGSTSQ

3. Data Model

The customer domain data model spans DB2, VSAM, and the shared COMMAREA contract.

3.1. Core Entities

The primary persistent entities are:

Entity Store Purpose
CUSTOMER DB2 (GENASA1.CUSTOMER) Primary customer master record
CUSTOMER_SECURE DB2 (GENASA1.CUSTOMER_SECURE) Security-related customer record created during add
KSDSCUST VSAM KSDS Mirrored customer record keyed by customer number
COMMAREA (LGCMAREA.inc) Inter-program contract Shared request/response structure

3.2. Entity Relationships

graph TD A[LGCMAREA Shared Contract] --> B[CUSTOMER] A --> C[CUSTOMER_SECURE] A --> D[KSDSCUST] B --> C[Security record for customer] B --> E[POLICY FK dependency] D --> B[Mirrors selected customer fields]

The relationships above illustrate that CUSTOMER is the central master entity. CUSTOMER_SECURE is created as an associated security record during onboarding. KSDSCUST mirrors customer data but is not the primary inquiry path. There is also an external dependency from the POLICY table to CUSTOMER.

3.3. COMMAREA Contract

The domain boundary is defined by LGCMAREA.inc. It carries both control metadata and customer data. Important fields include:

  • CA_REQUEST_ID
  • CA_RETURN_CODE
  • CA_CUSTOMER_NUM
  • CA_FIRST_NAME
  • CA_LAST_NAME
  • CA_EMAIL_ADDRESS

This shared contract is used by all customer-domain programs and by the calling presentation layer. Because layout compatibility is required end-to-end, any change to field sizes or positions is a breaking application-wide change.

3.4. Data Ownership and Persistence Roles

Data Element Primary Owner Secondary Copy Notes
Customer master attributes DB2 CUSTOMER VSAM KSDSCUST DB2 is authoritative
Customer number CICS named counter / DB2 fallback Passed in COMMAREA and stored in both DB2/VSAM Dual-source risk exists
Security password hash DB2 CUSTOMER_SECURE None Created only during add
Inquiry result fields DB2 None for standard inquiry DB2 is the runtime retrieval path

4. Key Programs and Responsibilities

4.1. Entry and Orchestration Programs

4.1.1. LGTESTC1

  • Presentation/menu driver
  • Calls orchestrators using CICS LINK
  • Sometimes calls LGICVS01 separately to discover a sample customer number

4.1.2. LGACUS01

  • Add-customer orchestrator
  • Validates COMMAREA minimum length
  • Routes request to LGACDB01

4.1.3. LGICUS01

  • Inquiry orchestrator
  • Checks TS queue GENAWMQC for MQHIT=
  • Normally routes to LGICDB01
  • If MQ hit is detected, branches to placeholder program AAAAAAAA

4.1.4. LGUCUS01

  • Update orchestrator
  • Validates CA_REQUEST_ID='01UCUS'
  • Returns 99 for invalid request ID/system error
  • Routes to LGUCDB01

4.2. DB2 Backend Programs

4.2.1. LGACDB01

  • Gets next customer number from CICS named counter GENACUSTNUM
  • Inserts row into GENASA1.CUSTOMER
  • Links to LGACVS01 to mirror data into VSAM
  • Links to LGACDB02 to create CUSTOMER_SECURE

4.2.2. LGICDB01

  • Executes SELECT from GENASA1.CUSTOMER
  • Maps row back into COMMAREA fields
  • Returns 01 when SQLCODE is 100 or -913

4.2.3. LGUCDB01

  • Executes UPDATE on GENASA1.CUSTOMER
  • Links to LGUCVS01 to rewrite VSAM mirror record

4.3. VSAM and Utility Programs

4.3.1. LGACVS01

  • Writes customer record into KSDSCUST
  • Receives only a fixed 225-byte portion of the COMMAREA

4.3.2. LGICVS01

  • Not part of the normal inquiry path
  • Reads GENACNTL TS queue for customer number range
  • Performs GTEQ read on KSDSCUST
  • Returns a valid customer number for discovery/demo purposes

4.3.3. LGUCVS01

  • Reads KSDSCUST with update intent
  • Rewrites the record after DB2 update

4.3.4. LGACDB02

  • Receives a separate CDB2AREA
  • Inserts into GENASA1.CUSTOMER_SECURE
  • Uses a hardcoded MD5 password hash:
    • 5732fec825535eeafb8fac50fee3a8aa

5. Transaction Flow: Add Customer

The add flow is a coordinated multi-step transaction spanning customer-number generation, DB2 insert, VSAM mirror creation, and security record creation.

sequenceDiagram participant User as LGTESTC1 participant Orc as LGACUS01 participant DB as LGACDB01 participant CTR as GENACUSTNUM Counter participant CUST as DB2 CUSTOMER participant VS as LGACVS01 participant KS as KSDSCUST participant SEC as LGACDB02 participant CS as DB2 CUSTOMER_SECURE User->>Orc: LINK add request (01ACUS) Orc->>Orc: Validate COMMAREA length Orc->>DB: LINK full COMMAREA DB->>CTR: Get next customer number CTR-->>DB: Next number DB->>CUST: INSERT customer row CUST-->>DB: SQLCODE / row stored DB->>VS: LINK 225-byte customer segment VS->>KS: WRITE record KS-->>VS: RESP DB->>SEC: LINK security area (02ACUS) SEC->>CS: INSERT secure row CS-->>SEC: SQLCODE SEC-->>DB: Return code DB-->>Orc: Customer number + return code Orc-->>User: Customer number + return code

The add operation is notable because it establishes customer identity and then creates records in multiple stores. The intended business sequence is:

  1. Validate the request
  2. Assign customer number
  3. Insert master customer row in DB2
  4. Mirror customer data to VSAM
  5. Create the security row

5.1. Add Flow Characteristics

  • Primary persistence is to DB2
  • VSAM receives only a subset of the COMMAREA
  • Security data is handled through a separate COMMAREA structure
  • The generated customer number is central to all downstream writes

5.2. Customer Number Generation

The preferred source of customer number is the CICS named counter:

  • Counter: GENACUSTNUM
  • Pool: GENA

If that call fails, the application falls back to DB2 identity generation and uses IDENTITY_VAL_LOCAL() to recover the assigned value. This creates a dual-source identity model that can lead to inconsistency if callers assume the counter always succeeded.

5.3. Example Logic Pattern

PLI 
/* Simplified add-path pattern */
CALL LGACUS01;
IF CA_RETURN_CODE = '00' THEN DO;
   /* Customer inserted successfully */
   /* CA_CUSTOMER_NUM returned to caller */
END;
SQL 
INSERT INTO GENASA1.CUSTOMER
    (CUSTOMERNUMBER, FIRSTNAME, LASTNAME, EMAILADDRESS)
VALUES
    (:CA_CUSTOMER_NUM, :CA_FIRST_NAME, :CA_LAST_NAME, :CA_EMAIL_ADDRESS);

6. Transaction Flow: Inquire Customer

The inquiry flow is simpler than add/update because it is primarily DB2-based. However, it includes an inactive integration hook for MQ cache bypass logic.

sequenceDiagram participant User as LGTESTC1 participant Orc as LGICUS01 participant MQ as GENAWMQC TS Queue participant DB as LGICDB01 participant CUST as DB2 CUSTOMER User->>Orc: LINK inquire request (01ICUS) Orc->>MQ: READQ TS GENAWMQC MQ-->>Orc: MQHIT record or none alt Normal path Orc->>DB: LINK COMMAREA DB->>CUST: SELECT by customer number CUST-->>DB: Customer row DB-->>Orc: Fields + return code else MQ cache hit Orc->>Orc: LINK PROGRAM('AAAAAAAA') end Orc-->>User: Customer fields + return code

This diagram highlights the distinction between the real inquiry path and the latent MQ cache hook. In practice, customer inquiry is fulfilled by LGICDB01 querying DB2 directly.

6.1. Normal Inquiry Path

  1. LGTESTC1 sends a customer number
  2. LGICUS01 checks GENAWMQC
  3. If no cache-hit marker is found, it calls LGICDB01
  4. LGICDB01 selects the customer row from DB2
  5. Retrieved fields are placed back into COMMAREA
  6. Control returns to the caller

6.2. Inquiry Utility Path via LGICVS01

LGICVS01 is not used to retrieve customer details in normal inquiry processing. Instead, it is a customer number discovery utility. It:

  • Reads GENACNTL for low/high customer-number range
  • Performs a GTEQ read against KSDSCUST
  • Returns a valid customer number for test/demo usage

This is an important distinction: the VSAM inquiry program does not function as a parallel inquiry backend for customer master data.

6.3. Inquiry Return Behavior

LGICDB01 sets:

  • CA_RETURN_CODE='00' on success
  • CA_RETURN_CODE='01' for:
    • SQLCODE 100 (not found)
    • SQLCODE -913 (deadlock/timeout treated as not found)

This means operational failures and business absence are partially conflated in the interface contract.

6.4. Example Logic Pattern

PLI 
CALL LGICUS01;
IF CA_RETURN_CODE = '00' THEN DO;
   /* Use returned CA_FIRST_NAME, CA_LAST_NAME, CA_EMAIL_ADDRESS */
END;
ELSE IF CA_RETURN_CODE = '01' THEN DO;
   /* Customer not found or DB2 contention surfaced as not found */
END;
SQL 
SELECT FIRSTNAME, LASTNAME, EMAILADDRESS
  INTO :CA_FIRST_NAME, :CA_LAST_NAME, :CA_EMAIL_ADDRESS
  FROM GENASA1.CUSTOMER
 WHERE CUSTOMERNUMBER = :CA_CUSTOMER_NUM;

7. Transaction Flow: Update Customer

The update flow changes customer data in DB2 and then rewrites the corresponding VSAM mirror record.

sequenceDiagram participant User as LGTESTC1 participant Orc as LGUCUS01 participant DB as LGUCDB01 participant CUST as DB2 CUSTOMER participant VS as LGUCVS01 participant KS as KSDSCUST User->>Orc: LINK update request (01UCUS) Orc->>Orc: Validate request ID Orc->>DB: LINK COMMAREA DB->>CUST: UPDATE customer row CUST-->>DB: SQLCODE DB->>VS: LINK 225-byte customer segment VS->>KS: READ UPDATE VS->>KS: REWRITE record KS-->>VS: RESP DB-->>Orc: Return code Orc-->>User: Return code

The update path is operationally straightforward but carries an important concurrency concern: the VSAM update uses a record-level lock as part of the read-for-update/rewrite sequence.

7.1. Update Steps

  1. Presentation sends update request with CA_REQUEST_ID='01UCUS'
  2. LGUCUS01 validates the request ID
  3. LGUCDB01 updates the DB2 CUSTOMER row
  4. LGUCVS01 reads the matching VSAM record for update
  5. LGUCVS01 rewrites the VSAM record
  6. Return code is propagated back to caller

7.2. Concurrency Behavior

The VSAM rewrite path uses a read-for-update followed by rewrite. Because this occurs in the same CICS task as the DB2 update, there is risk under concurrent updates to the same customer:

  • one task may hold or wait on a VSAM lock
  • another may be updating the same logical customer
  • contention windows increase as the dual-write sequence spans both DB2 and VSAM

7.3. Example Logic Pattern

PLI 
IF CA_REQUEST_ID ^= '01UCUS' THEN
   CA_RETURN_CODE = '99';
ELSE
   CALL LGUCDB01;
SQL 
UPDATE GENASA1.CUSTOMER
   SET FIRSTNAME    = :CA_FIRST_NAME,
       LASTNAME     = :CA_LAST_NAME,
       EMAILADDRESS = :CA_EMAIL_ADDRESS
 WHERE CUSTOMERNUMBER = :CA_CUSTOMER_NUM;

8. Data Consistency Across DB2 and VSAM

The customer domain keeps DB2 and VSAM aligned through application-managed dual writes rather than through a unified transactional persistence mechanism.

8.1. Consistency Model

The consistency strategy is:

  • DB2 is the authoritative master store
  • VSAM is maintained as a mirrored secondary representation
  • Add and update operations explicitly invoke both DB2 and VSAM backends
  • Inquiry uses DB2 as the standard retrieval source

This means consistency is maintained procedurally by program logic rather than by a single atomic database transaction.

graph TD A[Customer Request] --> B[Orchestrator] B --> C[DB2 Primary Operation] C --> D[VSAM Mirror Operation] C --> E[Security Record Creation] D --> F[Return Code to Caller] E --> F C -. if DB2 succeeds and VSAM fails .-> G[Potential divergence]

The model above emphasizes that mirror consistency depends on successful completion of all application steps. There is no evidence of rollback coordination between DB2 and VSAM.

8.2. Add Consistency Behavior

During add:

  • DB2 insert occurs first
  • VSAM write follows
  • Security record creation occurs after customer insert

Potential inconsistency scenarios include:

  • DB2 insert succeeds, VSAM write fails
  • DB2 insert succeeds, security insert fails
  • Counter retrieval fails and DB2 identity fallback changes the assigned number source

8.3. Update Consistency Behavior

During update:

  • DB2 update executes first
  • VSAM rewrite follows

Potential inconsistency scenario:

  • DB2 update succeeds, VSAM rewrite fails with 81 or 82

In that case, the customer record may be current in DB2 but stale in VSAM.

8.4. Why Inquiry Remains DB2-Centric

Because standard inquiry reads directly from DB2, customer inquiry generally reflects the authoritative version of customer data even if VSAM mirroring is temporarily inconsistent. This reduces business impact for inquiry, but does not eliminate downstream risk for any function that depends on VSAM content.

9.4. Cross-Domain Constraint

The POLICY table has a foreign-key dependency on CUSTOMER with ON DELETE CASCADE. Although delete is not implemented in this domain, this is an important application-level dependency: any future delete operation would implicitly affect policy data.

10. Return Codes and Error Semantics

The domain uses CA_RETURN_CODE in COMMAREA for status reporting.

Code Meaning Typical Source
00 Success All programs
01 Customer not found / SQLCODE 100 / SQLCODE -913 LGICDB01
80 VSAM write failure LGACVS01
81 VSAM read-for-update failure LGUCVS01
82 VSAM rewrite failure LGUCVS01
90 Unexpected DB2 SQLCODE DB2 backends and LGACDB02
98 COMMAREA too short Orchestrators and DB2 backends
99 Invalid request ID or system error LGUCUS01, LGACDB02

10.1. Interpretation Notes

Two aspects are especially significant:

  • 01 can mean either true absence or a DB2 contention condition (-913)
  • 99 is used as a broad invalid/system-error category in selected programs

This makes troubleshooting dependent on supporting logs and operational diagnostics rather than on return codes alone.

11. Key Risks and Notable Findings

11.1. Dual Customer Number Sources

  • Primary source: CICS named counter
  • Fallback source: DB2 identity

Impact: potential mismatch between expected and actual assigned customer number under counter failure conditions.

11.2. No Coordinated DB2/VSAM Rollback

If DB2 succeeds and VSAM fails, the stores can diverge.

Impact: high consistency risk for add and update operations.

11.3. VSAM Locking Risk During Update

The read-for-update/rewrite pattern introduces record-level locking risk.

Impact: medium concurrency/deadlock exposure.

11.4. Dead MQ Bypass Path

LGICUS01 can branch to placeholder program AAAAAAAA if GENAWMQC indicates an MQ hit.

Impact: latent runtime failure if ever activated.

11.5. Hardcoded Initial Password Hash

The initial password hash is hardcoded as:

TEXT 
5732fec825535eeafb8fac50fee3a8aa

Impact: security weakness and onboarding rigidity.

11.6. COMMAREA as a Blast-Radius Multiplier

LGCMAREA.inc is shared across all customer programs and the presentation layer.

Impact: any structural change can break multiple programs simultaneously.

13. Summary

The customer domain is a tightly structured, layered application component centered on DB2 as the master customer repository and VSAM as a mirrored secondary store. It uses a common COMMAREA contract, predictable orchestrator/backend separation, and explicit add/inquire/update program families.

Its main strengths are consistency of layering and a clear operational model. Its main weaknesses are in cross-store consistency management, identity generation fallback behavior, shared-contract fragility, and latent dead code in the MQ bypass path. From an application architecture perspective, the domain is best understood as a DB2-first customer service with application-managed VSAM synchronization rather than a fully atomic dual-database transaction model.
