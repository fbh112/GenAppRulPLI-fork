Customer VSAM Back-End Programs

The Customer VSAM Back-End Programs form the persistence layer for the customer domain in the General Insurance Application (GenApp). These three PL/I programs — LGACVS01, LGICVS01, and LGUCVS01 — are CICS-hosted components that interact exclusively with the VSAM Key-Sequenced Data Set (KSDS) file KSDSCUST. Together they cover the full lifecycle of a customer record at the VSAM level: creating a new record, randomly selecting an existing customer number, and updating an existing record. All three programs share a common error-handling pattern: structured diagnostic logging via the LGSTSQ utility program, ENQ/DEQ-based serialization where required, and controlled CICS ABEND on failure.

1. Overview

The three VSAM back-end programs each address a distinct operation against the KSDSCUST KSDS file:

Program Operation ABEND Code(s) Return Code on Failure
LGACVS01 Add (write) a new customer record LGV0 80
LGICVS01 Randomly select a valid customer number via GTEQ browse (none — no abend on VSAM failure) N/A
LGUCVS01 Update (read-for-update + rewrite) an existing customer record LGV1 (read), LGV2 (rewrite) 81 (read), 82 (rewrite)

All three programs:

  • Are written in Enterprise PL/I for z/OS and run under CICS.
  • Reference the shared COMMAREA copybook LGCMAREA for the communication area layout.
  • Use CA_CUSTOMER_NUM (a 10-digit numeric PIC field) as the VSAM KSDS record key.
  • Delegate error message persistence to the logging utility LGSTSQ via EXEC CICS LINK.
  • Return operation outcomes to the caller through CA_RETURN_CODE in the shared COMMAREA.

2. System Architecture

The VSAM back-end programs sit at the bottom of a two-tier CICS application stack. Front-end orchestrators (e.g., LGACUS01, LGUCUS01, LGICUS01) receive requests from terminals or external callers, then delegate to the back-end programs via EXEC CICS LINK. The back-end programs perform the actual VSAM I/O and return results through the shared COMMAREA.

3. Shared COMMAREA Layout

All three programs share the COMMAREA structure defined in the PL/I include member LGCMAREA. The calling program passes this area via EXEC CICS LINK, and the back-end programs overlay a based structure on the received pointer.

3.1 Key COMMAREA Fields

Field Type Description
CA_REQUEST_ID CHAR(6) Operation code identifying the request type
CA_RETURN_CODE PIC '99' Two-digit outcome code; set by the back-end on failure
CA_CUSTOMER_NUM PIC '9999999999' 10-digit customer identifier; serves as the VSAM KSDS key
CA_FIRST_NAME CHAR(10) Customer first name
CA_LAST_NAME CHAR(20) Customer last name
CA_DOB CHAR(10) Customer date of birth
CA_POSTCODE CHAR(8) Customer postcode
CA_NUM_POLICIES PIC '999' Count of policies linked to this customer
CA_PHONE_MOBILE CHAR(20) Mobile phone number
CA_PHONE_HOME CHAR(20) Home phone number
CA_EMAIL_ADDRESS CHAR(100) Email address
CA_POLICY_DATA CHAR(32267) Raw policy data block appended to the customer record
COMM_AREA_RAW CHAR(32500) Unstructured view of the full COMMAREA; used in error diagnostics

3.2 VSAM Key Construction

The VSAM KSDS key is always CA_CUSTOMER_NUM — a 10-digit numeric picture field. All three programs use KEYLENGTH(10) when issuing CICS file commands. The key uniquely identifies a customer record in KSDSCUST.

CODE 
RIDFLD(CA_CUSTOMER_NUM)  KEYLENGTH(10)

4. LGACVS01 — Add New Customer Record

4.1 Purpose

LGACVS01 adds a new customer record to the VSAM KSDS file KSDSCUST. It receives the fully populated customer COMMAREA from its caller, writes the entire COMMAREA as a new keyed record using CA_CUSTOMER_NUM as the key, and either returns normally on success or signals failure via CA_RETURN_CODE = '80' and issues CICS ABEND LGV0.

4.2 Processing Flow

The program follows a linear, single-path flow: initialize, write, check, and either return or error-handle.

4.3 VSAM Write Command

PLI 
EXEC CICS WRITE FILE('KSDSCUST')
     FROM    (CA_Customer_Num)
     LENGTH  (WS_Commarea_Len)
     RIDFLD  (CA_Customer_Num)
     KEYLENGTH(10)
     RESP    (WS_RESP);
  • FROM(CA_Customer_Num) — the data written starts at the CA_CUSTOMER_NUM field within the COMMAREA, anchoring the full customer record layout.
  • LENGTH(WS_Commarea_Len) — dynamic byte count derived from EIBCALEN, ensuring exactly the received bytes are stored.
  • RIDFLD(CA_Customer_Num) — establishes the KSDS primary key for the new record.
  • KEYLENGTH(10) — explicit 10-byte key declaration.

4.4 Error Handling

On a non-NORMAL CICS response:

Step Action
1 Capture EIBRESP2 into WS_RESP2
2 Set CA_RETURN_CODE = '80'
3 Call WRITE_ERROR_MESSAGE
4 Link to LGSTSQ with ERROR_MSG (timestamp + customer number + response codes)
5 Conditionally link to LGSTSQ with CA_ERROR_MSG (up to 90 bytes of raw COMMAREA)
6 Issue EXEC CICS ABEND ABCODE('LGV0') NODUMP
7 Issue EXEC CICS RETURN as a defensive safety net

4.5 Example: Successful Add

Input COMMAREA:

Field Value
CA_REQUEST_ID ACUST0
CA_RETURN_CODE 00
CA_CUSTOMER_NUM 0000000042
CA_FIRST_NAME JOHN
CA_LAST_NAME SMITH
CA_DOB 1980-03-15
CA_POSTCODE SW1A 2AA

Outcome: A new record keyed 0000000042 is written to KSDSCUST. CA_RETURN_CODE remains 00. No messages are written to the log queue.

4.6 Example: Failed Add — Duplicate Key

Scenario: A record with key 0000000042 already exists.

Outcome:

  • CA_RETURN_CODE = 80
  • Two messages written to the CICS TS queue via LGSTSQ:
    • MM/DD/YYYY HH:MM:SS LGACVS01 CNUM=0000000042 Write file KSDSCUST RESP=<n> RESP2=<n>
    • COMMAREA=ACUST000000000000042JOHN SMITH… (first 90 bytes of inbound COMMAREA)
  • Task abends with code LGV0.

5. LGICVS01 — Random Customer Number Selection

5.1 Purpose

LGICVS01 randomly selects a valid customer number from KSDSCUST. It manages a customer number range in a CICS Temporary Storage queue (GENACNTL), protected by ENQ/DEQ serialization, generates a pseudo-random number within that range seeded by the CICS task number (EIBTASKN), and then performs a GTEQ read against KSDSCUST to resolve the nearest actual customer key. Results are returned via COMMAREA (when linked) or displayed on a 3270 terminal (when invoked interactively).

5.2 Invocation Modes

The program detects its invocation context on startup using two CICS ASSIGN values:

ASSIGN Field Meaning Action
STARTCODE starts with 'D' Transaction-started invocation WS_FLAG = 'C' → use COMMAREA
INVOKINGPROG not blank Called via EXEC CICS LINK WS_FLAG = 'C' → use COMMAREA
Neither condition true Interactive terminal invocation WS_FLAG = 'R' → EXEC CICS RECEIVE / SEND TEXT

5.3 Processing Flow

5.4 ENQ/DEQ Serialization

Access to the GENACNTL TS queue is serialized using CICS ENQ/DEQ:

PLI 
EXEC CICS ENQ RESOURCE(STSQ_NAME) LENGTH(STG(STSQ_NAME));
/* ... all READQ TS and WRITEQ TS operations ... */
EXEC CICS DEQ RESOURCE(STSQ_NAME) LENGTH(STG(STSQ_NAME));

This prevents race conditions where multiple concurrent tasks could simultaneously find the control records absent and write duplicate entries to GENACNTL.

5.5 GENACNTL TS Queue Structure

The GENACNTL queue holds three record types, each written with NOSUSPEND:

Record Type Content Size Flag
Eyecatcher **** GENAPP CNTL 20 bytes WS_FLAG_TSQE
LOW CUSTOMER LOW CUSTOMER= + 10-digit low value 23 bytes WS_FLAG_TSQL
HIGH CUSTOMER HIGH CUSTOMER= + 10-digit high value 24 bytes WS_FLAG_TSQH

Each flag starts as 'Y' (assumed absent). A flag is cleared to ' ' only when the corresponding record is successfully read from the queue. If a record is absent after the read loop, the corresponding WRITEQ TS call creates it with the default value 1000001.

5.6 Random Number Generation

PLI 
WS_RANDOM_NUMBER = FLOOR(
    RANDOM(EIBTASKN) * FLOAT(WS_CUST_HIGH - WS_CUST_LOW) + WS_CUST_LOW
);
  • Seed: EIBTASKN — the CICS task number, providing per-task variation.
  • Range: [WS_CUST_LOW, WS_CUST_HIGH).
  • Result: an integer customer number used as the GTEQ VSAM key.

5.7 GTEQ VSAM Read

PLI 
EXEC CICS READ FILE('KSDSCUST')
     INTO      (CA_AREA)
     LENGTH    (F82)
     RIDFLD    (WRITE_MSG_HIGH)
     KEYLENGTH (F10)
     GTEQ
     RESP      (WS_RESP);

The GTEQ option ensures that even if the exact random number does not exist as a VSAM key, the nearest real customer record at or above that number is returned. If no record exists at or above the generated number, WRITE_MSG_HIGH retains the raw random value and the program proceeds without error.

5.8 Example: First-Time Invocation via CICS LINK

Scenario: GENACNTL queue does not exist. KSDSCUST has a record at key 0001000050. EIBTASKN = 1234.

Processing:

  1. WS_FLAG = 'C' (LINK invocation).
  2. All three TS queue flags remain 'Y' — queue absent.
  3. Three WRITEQ TS calls create GENACNTL with defaults (LOW=1000001, HIGH=1000001).
  4. Random number collapses to 1000001 (zero-width range).
  5. GTEQ read finds key 0001000050.
  6. COMMAREA returned: COMMA_DATA_HIGH = 0001000050.

6. LGUCVS01 — Update Existing Customer Record

6.1 Purpose

LGUCVS01 updates an existing customer record in KSDSCUST. It issues a read-for-update (acquiring an exclusive CICS lock on the record), then rewrites the record with the new customer data carried in the COMMAREA. Distinct return codes (81 for read failure, 82 for rewrite failure) and distinct ABEND codes (LGV1 / LGV2) allow precise identification of which phase failed.

6.2 Processing Flow

graph TD classDef startEnd fill:#b5ead7,stroke:#4a9e7f,color:#000 classDef process fill:#c7ceea,stroke:#5a67a0,color:#000 classDef decision fill:#ffdac1,stroke:#c47a3a,color:#000 classDef error fill:#ffb7b2,stroke:#c0504d,color:#000 classDef sub fill:#e2f0cb,stroke:#6a994e,color:#000 A([Start LGUCVS01]):::startEnd B[Capture EIBCALEN into\nWS_Commarea_Len and WS_Commarea_LenF]:::process C[EXEC CICS READ FILE KSDSCUST\nInto WS_Customer_Area\nKey = CA_CUSTOMER_NUM\nUPDATE lock acquired]:::process D{{READ RESP\n= NORMAL}}:::decision E[Set CA_RETURN_CODE = 81\nCapture EIBRESP2]:::error F[Call WRITE_ERROR_MESSAGE]:::sub G[EXEC CICS ABEND ABCODE LGV1 NODUMP\nEXEC CICS RETURN]:::error H[EXEC CICS REWRITE FILE KSDSCUST\nFrom CA_CUSTOMER_NUM area\nLength = WS_Commarea_LenF]:::process I{{REWRITE RESP\n= NORMAL}}:::decision J[Set CA_RETURN_CODE = 82\nCapture EIBRESP2]:::error K[Call WRITE_ERROR_MESSAGE]:::sub L[EXEC CICS ABEND ABCODE LGV2 NODUMP\nEXEC CICS RETURN]:::error M([Return to caller — Success]):::startEnd A --> B --> C --> D D -- Yes --> H D -- No --> E --> F --> G H --> I I -- Yes --> M I -- No --> J --> K --> L

The two-phase structure is clearly visible: a failed READ terminates with LGV1 / RC 81; a successful READ followed by a failed REWRITE terminates with LGV2 / RC 82. Only when both phases succeed does the program reach the normal return.

6.3 READ FILE with UPDATE Lock

PLI 
EXEC CICS READ FILE('KSDSCUST')
     INTO      (WS_Customer_Area)
     LENGTH    (WS_Commarea_Len)
     RIDFLD    (CA_Customer_Num)
     KEYLENGTH (10)
     UPDATE
     RESP      (WS_RESP);

The UPDATE option places an exclusive enqueue lock on the record. No other CICS task can update or delete this record until the same task issues a REWRITE, DELETE, or UNLOCK against it.

6.4 REWRITE FILE

PLI 
EXEC CICS REWRITE FILE('KSDSCUST')
     FROM   (CA_Customer_Num)
     LENGTH (WS_Commarea_LenF)
     RESP   (WS_RESP);

FROM(CA_Customer_Num) writes the updated customer data sourced from the COMMAREA starting at the CA_CUSTOMER_NUM field — the full updated record layout as defined by LGCMAREA. The record length is driven by WS_Commarea_LenF, which is initialized from EIBCALEN.

6.5 Error Handling and ABEND Codes

Phase Return Code ABEND Code Trigger
READ UPDATE 81 LGV1 WS_RESP ≠ DFHRESP(NORMAL) after READ
REWRITE 82 LGV2 WS_RESP ≠ DFHRESP(NORMAL) after REWRITE

Both error paths invoke the shared WRITE_ERROR_MESSAGE sub-procedure before issuing the ABEND:

PLI 
WS_RESP2 = EIBRESP2;
CA_RETURN_CODE = '81';   /* or '82' for rewrite */
CALL WRITE_ERROR_MESSAGE;
EXEC CICS ABEND ABCODE('LGV1') NODUMP;  /* or LGV2 */
EXEC CICS RETURN;

Example 1 — Successful Update:

Field Value

7. Shared Error Handling Pattern

All three programs share a consistent error handling sub-procedure (WRITE_ERROR_MESSAGE) that is invoked whenever a CICS file or queue operation fails. The pattern is identical across LGACVS01 and LGUCVS01 (LGICVS01 has no abend path for VSAM failures).

7.1 WRITE_ERROR_MESSAGE Sequence

sequenceDiagram participant P as Back-End Program participant CICS as CICS Runtime participant LGSTSQ as LGSTSQ Logger participant TSQ as CICS TS Queue P->>CICS: EXEC CICS ASKTIME ABSTIME(WS_ABSTIME) CICS-->>P: Absolute time value P->>CICS: EXEC CICS FORMATTIME ABSTIME → WS_DATE / WS_TIME CICS-->>P: Formatted date and time P->>P: Populate ERROR_MSG\n(program ID · CNUM · RESP · RESP2 · date · time) P->>LGSTSQ: EXEC CICS LINK COMMAREA(ERROR_MSG) LGSTSQ->>TSQ: Write structured error message LGSTSQ-->>P: Return alt EIBCALEN > 0 P->>P: Extract up to 90 bytes of COMM_AREA_RAW\ninto CA_Data P->>LGSTSQ: EXEC CICS LINK COMMAREA(CA_ERROR_MSG) LGSTSQ->>TSQ: Write COMMAREA dump LGSTSQ-->>P: Return end P->>CICS: EXEC CICS ABEND ABCODE(...) NODUMP P->>CICS: EXEC CICS RETURN

This sequence ensures that:

  1. A human-readable timestamp is always included in the error record.
  2. Both the primary CICS response code (RESP) and the supplementary code (RESP2) are captured.
  3. Up to 90 bytes of the inbound COMMAREA are logged as a diagnostic snapshot.
  4. Error logging always completes before the ABEND is issued.
  5. NODUMP suppresses system dump generation, keeping abend overhead low.

7.2 ERROR_MSG Structure

The ERROR_MSG structure passed to LGSTSQ includes static literal labels embedded as INIT values, producing a self-describing log line:

CODE 
MM/DD/YYYY HH:MM:SS  LGACVS01 CNUM=0000000042 Write file KSDSCUST RESP= 16 RESP2= 8
Field Source
EM_DATE EXEC CICS FORMATTIME → WS_DATE
EM_TIME EXEC CICS FORMATTIME → WS_TIME
EM_CUSNUM CA_CUSTOMER_NUM
EM_RESPRC WS_RESP (primary CICS response code)
EM_RESP2RC WS_RESP2 (from EIBRESP2)

7.3 COMMAREA Diagnostic Dump Logic

PLI 
IF EIBCALEN > 0 THEN DO;
    IF EIBCALEN < 91 THEN
        CA_Data = LEFT(COMM_AREA_RAW, EIBCALEN);
    ELSE
        CA_Data = LEFT(COMM_AREA_RAW, 90);
    EXEC CICS LINK PROGRAM('LGSTSQ')
         COMMAREA(CA_ERROR_MSG)
         LENGTH(STG(CA_ERROR_MSG));
END;

The LEFT built-in function extracts a bounded, printable excerpt of the COMMAREA regardless of its actual size, capping the logged content at 90 characters (CA_Data CHAR(90)) to prevent buffer overflow.

8. ENQ/DEQ Serialization (LGICVS01)

LGICVS01 is the only program in this group that uses CICS ENQ/DEQ serialization. The lock resource is the TS queue name GENACNTL itself:

PLI 
EXEC CICS ENQ RESOURCE(STSQ_NAME) LENGTH(STG(STSQ_NAME));
/* Read GENACNTL, conditionally write missing records */
EXEC CICS DEQ RESOURCE(STSQ_NAME) LENGTH(STG(STSQ_NAME));

8.1 Why Serialization Is Needed

The GENACNTL TS queue stores the customer number range boundaries shared across all tasks that invoke LGICVS01. Without serialization, two tasks could simultaneously:

  1. Both read the queue and find a record absent (WS_FLAG = 'Y').
  2. Both issue WRITEQ TS for the same record type — creating duplicate control entries.

ENQ/DEQ ensures only one task at a time reads and conditionally initializes the queue.

8.2 Serialization Scope

The ENQ/DEQ bracket covers only the TS queue operations. The VSAM READ FILE GTEQ and all output operations (COMMAREA population or SEND TEXT) occur outside the lock, minimizing contention.

9. Abend Behaviour Summary

Program Condition Return Code ABEND Code Dump
LGACVS01 VSAM WRITE fails 80 LGV0 NODUMP
LGUCVS01 VSAM READ UPDATE fails 81 LGV1 NODUMP
LGUCVS01 VSAM REWRITE fails 82 LGV2 NODUMP
LGICVS01 VSAM READ GTEQ fails N/A (none) N/A

All abends use NODUMP to suppress system dump generation, relying solely on the LGSTSQ TS queue entries for post-failure diagnosis. The four-character abend codes (LGV0–LGV2) are distinct and appear in CICS system logs and monitoring, allowing operations staff to pinpoint the failing program and operation at a glance.
