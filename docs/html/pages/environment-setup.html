Environment Setup & Initialisation

1. Overview

LGSETUP is a CICS PL/I program that serves as the bootstrap utility for the entire GenApp insurance application environment. Invoked directly from a CICS terminal by an operator or system administrator, it performs a complete teardown and controlled reconstruction of all GenApp runtime infrastructure — ensuring every subsequent GenApp transaction begins from a clean, predictable state.

At its core, LGSETUP manages two categories of CICS resources: Temporary Storage (TS) Queues and Named Counters. It deletes and recreates the four GenApp TS queues (GENACNTL, GENASTAT, GENASTRT, GENAERRS), writes a fresh environment configuration record — including the customer number range — into the control queue, redefines the GENACUSTNUM named customer-number counter seeded at the configured upper bound, and zeroes all 36 transaction statistics counters that track success and failure outcomes across every policy operation type.

An optional high customer number may be passed on the terminal command line at invocation time (e.g., LGSE 0000000050); if omitted, the system defaults to 11. Once all resources have been reset, the operator receives a terminal confirmation displaying the configured high customer number, signalling that setup completed successfully.

LGSETUP sits at the intersection of three CICS service domains: the terminal interface (for operator input and confirmation), the Temporary Storage facility (for queue management), and the Named Counter Service (for sequence and statistics counters). All interactions are orchestrated within a single sequential PL/I procedure with no sub-procedures or branches beyond the optional high-customer-number override at startup.

3. Inputs

3.1 Terminal Input Buffer

LGSETUP reads its input via EXEC CICS RECEIVE into an 80-byte buffer (WS_RECV) structured as follows:

Field Type Length Description
WS_RECV_TRANID CHAR(5) 5 bytes Transaction ID (e.g., LGSE )
WS_RECV_DATA CHAR(74) 74 bytes Optional operator-supplied data

3.2 Optional High Customer Number Parameter

If the operator appends a numeric value after the transaction ID (e.g., LGSE 0000000050), the program detects this by checking whether the received length (WS_RECV_LEN) exceeds 5. When it does, the trailing portion of WS_RECV_DATA is extracted and converted into LASTCUSTNUM, overriding the compiled-in default of 11.

Parameter Default Source Purpose
LASTCUSTNUM 11 Terminal input or compile-time init Upper bound of the customer number range
FRSTCUSTNUM 1 Hardcoded Lower bound of the customer number range

4. Outputs

4.1 CICS Temporary Storage Queue Writes — GENACNTL

After deletion, the control queue is repopulated with exactly three records:

Record Field Content Length
1 WRITE_MSG_E **** GENAPP CNTL 20 bytes
2 WRITE_MSG_L LOW CUSTOMER= + 10-digit FRSTCUSTNUM 23 bytes
3 WRITE_MSG_H HIGH CUSTOMER= + 10-digit LASTCUSTNUM 24 bytes

All three writes use NOSUSPEND, meaning the write returns immediately with an error code rather than blocking if storage is unavailable.

4.2 CICS Temporary Storage Queue Deletions

The following queues are deleted unconditionally — a QIDERR response (queue not found) is silently tolerated:

Queue Name Internal Variable Purpose
GENAERRS STSQ_ERRS Error-tracking log
GENASTRT STSQ_STRT Start/heartbeat event queue
GENASTAT STSQ_STAT Transaction statistics queue
GENACNTL STSQ_NAME Environment control queue

4.3 CICS Named Counter Operations — Pool GENA

4.3.1 Customer Number Counter

Counter Name Operation Seed Value
GENACUSTNUM DELETE then DEFINE LASTCUSTNUM (default 11)

4.3.2 Transaction Statistics Counters

All 36 named counters are deleted and redefined with VALUE(0). They follow a naming pattern encoding the operation type, entity, and outcome:

Operation Entity Success Counter Failure Counter
Insert (I) Customer (CUS) GENA01ICUS00 GENA01ICUS99
Insert (I) Motor (MOT) GENA01IMOT00 GENA01IMOT99
Add (A) Endowment (END) GENA01AEND00 GENA01AEND99
Delete (D) House (HOU) GENA01DHOU00 GENA01DHOU99
Update (U) Commercial (COM) GENA01UCOM00 GENA01UCOM99
… … … …

4.4 Terminal Display

Upon completion, the program sends the 24-byte high customer record (WRITE_MSG_H) to the initiating terminal:

CODE 
HIGH CUSTOMER=0000000011

The send uses ERASE, WAIT, and FREEKB options — clearing the screen, waiting for the output to complete, and unlocking the keyboard before returning.

5.2 Step-by-Step Processing Description

5.2.1 Step 1 — Receive Terminal Input

EXEC CICS RECEIVE INTO(WS_RECV) LENGTH(WS_RECV_LEN) RESP(WS_RESP) reads up to 80 bytes from the operator terminal. The buffer is split into a 5-character transaction ID prefix (WS_RECV_TRANID) and a 74-character data area (WS_RECV_DATA).

PLI 
DCL WS_RECV CHAR(80);
DCL WS_RECV_LEN FIXED BIN(15) INIT(80);
DCL WS_RESP    FIXED BIN(31);

EXEC CICS RECEIVE INTO(WS_RECV)
                  LENGTH(WS_RECV_LEN)
                  RESP(WS_RESP);

5.2.2 Step 2 — Optional High Customer Number Override

If WS_RECV_LEN > 5, the operator typed data beyond the transaction ID. The program subtracts 5 from the received length and converts the remainder of WS_RECV_DATA into LASTCUSTNUM:

PLI 
DCL LASTCUSTNUM FIXED BIN(31) INIT(11);
DCL FRSTCUSTNUM FIXED BIN(31) INIT(1);

IF WS_RECV_LEN > 5 THEN DO;
   WS_RECV_LEN = WS_RECV_LEN - 5;
   LASTCUSTNUM = SUBSTR(WS_RECV_DATA, 1, WS_RECV_LEN);
END;

If no data follows the transaction ID, LASTCUSTNUM retains its default value of 11.

5.2.3 Step 3 — Delete All Four GenApp TS Queues

Four unconditional EXEC CICS DELETEQ TS calls purge all existing GenApp queues. Response codes are captured in WS_RESP but never tested — errors such as QIDERR (queue not found) are silently absorbed:

PLI 
DCL STSQ_ERRS CHAR(8) STATIC INIT('GENAERRS');
DCL STSQ_STRT CHAR(8) STATIC INIT('GENASTRT');
DCL STSQ_STAT CHAR(8) STATIC INIT('GENASTAT');
DCL STSQ_NAME CHAR(8) STATIC INIT('GENACNTL');

EXEC CICS DELETEQ TS QUEUE(STSQ_ERRS) RESP(WS_RESP);
EXEC CICS DELETEQ TS QUEUE(STSQ_STRT) RESP(WS_RESP);
EXEC CICS DELETEQ TS QUEUE(STSQ_STAT) RESP(WS_RESP);
EXEC CICS DELETEQ TS QUEUE(STSQ_NAME) RESP(WS_RESP);

5.2.4 Step 4 — Rebuild the Control Queue (GENACNTL)

WRITE_MSG_LOW and WRITE_MSG_HIGH are stamped with the resolved customer number boundaries. Three records are written to the freshly cleared GENACNTL queue using NOSUSPEND:

PLI 
WRITE_MSG_LOW  = FRSTCUSTNUM;   /* Always 1        */
WRITE_MSG_HIGH = LASTCUSTNUM;   /* 11 or override  */

EXEC CICS WRITEQ TS QUEUE(STSQ_NAME)
                    FROM(WRITE_MSG_E)
                    LENGTH(20)
                    NOSUSPEND
                    RESP(WS_RESP);

EXEC CICS WRITEQ TS QUEUE(STSQ_NAME)
                    FROM(WRITE_MSG_L)
                    LENGTH(23)
                    NOSUSPEND
                    RESP(WS_RESP);

EXEC CICS WRITEQ TS QUEUE(STSQ_NAME)
                    FROM(WRITE_MSG_H)
                    LENGTH(24)
                    NOSUSPEND
                    RESP(WS_RESP);

5.2.5 Step 5 — Reset the Customer Number Counter

The existing GENACUSTNUM counter is deleted from pool GENA, then immediately redefined seeded at LASTCUSTNUM. All new customer additions will increment from this value to generate unique customer IDs:

PLI 
DCL GENACOUNT CHAR(16) STATIC INIT('GENACUSTNUM');
DCL GENAPOOL  CHAR(8)  STATIC INIT('GENA');

EXEC CICS DELETE COUNTER(GENACOUNT)
                 POOL(GENAPOOL)
                 RESP(WS_RESP);

EXEC CICS DEFINE COUNTER(GENACOUNT)
                 POOL(GENAPOOL)
                 VALUE(LASTCUSTNUM)
                 RESP(WS_RESP);

5.2.6 Step 6 — Reset the 36 Transaction Statistics Counters

A DO loop iterates over all 36 entries in COUNTER_TABLE. For each entry, the counter is deleted and redefined with VALUE(0):

PLI 
DCL COUNTER_COUNT FIXED BIN(15) STATIC INIT(36);
DCL ZERO_VALUE    FIXED BIN(31) INIT(0);
DCL COUNTER_IDX   FIXED BIN(15);

DO COUNTER_IDX = 1 TO COUNTER_COUNT;
   EXEC CICS DELETE COUNTER(COUNTER_NAME(COUNTER_IDX))
                    POOL(GENAPOOL)
                    RESP(WS_RESP);

   EXEC CICS DEFINE COUNTER(COUNTER_NAME(COUNTER_IDX))
                    POOL(GENAPOOL)
                    VALUE(ZERO_VALUE)
                    RESP(WS_RESP);
END;

5.2.7 Step 7 — Confirm to the Terminal and Return

The high customer record is sent to the operator terminal with ERASE, WAIT, and FREEKB, then EXEC CICS RETURN cleanly ends the task:

PLI 
EXEC CICS SEND TEXT FROM(WRITE_MSG_H)
                    TERMINAL
                    WAIT
                    ERASE
                    LENGTH(24)
                    FREEKB
                    RESP(WS_RESP);

EXEC CICS RETURN;

The diagram below shows the chronological message sequence between the operator, LGSETUP, the TS Facility, and the Named Counter Service:

The sequence makes clear that all queue deletions occur before any writes, that the control queue is fully populated before the customer counter is defined, and that the operator confirmation is the very last operation — ensuring the terminal display acts as an implicit end-to-end completion signal.

7. Dependencies

7.1 CICS Services

Service Commands Used Purpose
CICS Transaction Manager EXEC CICS RECEIVE, EXEC CICS RETURN Dispatch, terminal I/O, task termination
CICS Temporary Storage EXEC CICS DELETEQ TS, EXEC CICS WRITEQ TS Queue lifecycle management
CICS Named Counter Service EXEC CICS DELETE COUNTER, EXEC CICS DEFINE COUNTER Counter lifecycle management
CICS Terminal Facility EXEC CICS SEND TEXT Operator confirmation display

The Named Counter Service must have the pool GENA defined and available in CICS before LGSETUP is invoked. If the pool is unavailable, all counter operations will return non-normal response codes, though execution will continue.

7.2 Runtime Input

  • Operator terminal — Optional numeric string appended after the transaction ID on the command line (e.g., LGSE 0000000050). Drives the upper bound of the customer number range.

7.3 Internal Configuration Constants

LASTCUSTNUM FIXED BIN(31) 11 (default, overridable) Upper bound of customer range

COUNTER_COUNT FIXED BIN(15) 36 (static) Number of statistics counters
ZERO_VALUE FIXED BIN(31) 0 Reset value for all stats counters

8. Constraints

8.1 Input / Data Validation Constraints

  • The WS_RECV buffer is fixed at 80 bytes; terminal input longer than 80 characters is silently truncated.
  • The high-customer-number override is accepted only when WS_RECV_LEN > 5 — no format, range, or sign validation is applied to the supplied string. A non-numeric input will cause a PL/I conversion error at runtime.
  • FRSTCUSTNUM is hardcoded to 1 and cannot be changed without a code modification.
  • WRITE_MSG_LOW and WRITE_MSG_HIGH are declared PIC '9999999999', imposing an implicit ceiling of 9,999,999,999 on any customer number written to the control queue.

8.2 Named Counter Constraints

  • Exactly 36 statistics counters are always reset — partial resets are not possible; COUNTER_COUNT is a static compile-time constant.
  • All counters (both GENACUSTNUM and all 36 statistics counters) must reside in pool GENA. If the pool is unavailable, all counter operations silently fail.
  • Counter names are fixed-length CHAR(16) fields; shorter names are right-padded with blanks by PL/I.
  • The GENACUSTNUM counter is seeded at LASTCUSTNUM, not at 1 or 0. New customer IDs are assigned by incrementing from this seed.

8.3 Temporary Storage Queue Constraints

  • All four TS queue names (GENACNTL, GENASTAT, GENASTRT, GENAERRS) are hardcoded CHAR(8) STATIC constants and cannot be changed at runtime.
  • Control queue records have fixed, predetermined lengths (20, 23, 24 bytes). Consumer programs must parse GENACNTL records at exactly these offsets.
  • All WRITEQ TS calls use NOSUSPEND; a queue storage shortage will cause a silent failure, potentially leaving GENACNTL with fewer than three records.

8.4 Sequencing / Ordering Constraints

  • EXEC CICS RECEIVE is the very first executable statement — LASTCUSTNUM must be resolved before any queue or counter operations begin.
  • All four DELETEQ TS calls complete before any WRITEQ TS calls, ensuring GENACNTL starts fresh.
  • The GENACNTL control queue is fully populated before GENACUSTNUM is defined.
  • EXEC CICS SEND TEXT is the last operation before EXEC CICS RETURN.

9. Error Handling

9.1 CICS Response Code Capture (Passive Collection)

Every EXEC CICS command in LGSETUP specifies RESP(WS_RESP). This suppresses the default CICS condition-handling mechanism — abnormal responses do not cause an automatic task abend. Response codes are captured in WS_RESP after every call but are never inspected or acted upon.

9.2 Conditional Input Validation

After EXEC CICS RECEIVE, a length check (IF WS_RECV_LEN > 5) guards against applying an absent or empty value to LASTCUSTNUM. If the condition is false, the default of 11 is retained.

9.3 Tolerance of Non-Existent Resources

All four DELETEQ TS calls and all 37 DELETE COUNTER calls are issued unconditionally. A QIDERR or NOTFND response from a non-existent resource is silently absorbed via the RESP capture mechanism, allowing the program to proceed to the DEFINE step regardless.

9.4 Write Contention Prevention

NOSUSPEND on all three WRITEQ TS calls prevents the task from being suspended if TS queue storage is temporarily unavailable. The task returns immediately with a non-normal response rather than blocking, keeping the setup transaction non-suspending.

9.5 Terminal Feedback as Implicit Completion Signal

EXEC CICS SEND TEXT … ERASE WAIT FREEKB is issued only after all queue and counter operations complete. The appearance of the HIGH CUSTOMER= confirmation on the terminal is an implicit indication that execution reached the end of the setup logic without being interrupted by an unhandled abend.

9.6 No Active Error Branching

The program contains no IF WS_RESP = … condition checks, no EXEC CICS ABEND, no PL/I ON ERROR or ON CONDITION handlers, and no error message routines. This is a deliberate design choice for an administrative utility: all steps are attempted in full regardless of intermediate failures.

10. Examples

10.1 Example 1 — Default Setup (No High Customer Number Supplied)

Terminal input:

CODE 
LGSE

(Transaction ID only — 5 characters, no trailing data)

Processing outcome:

  • WS_RECV_LEN = 5 → IF WS_RECV_LEN > 5 is false → LASTCUSTNUM stays at 11.
  • All four TS queues are deleted.
  • GENACNTL is repopulated:
    • **** GENAPP CNTL (20 bytes)
    • LOW CUSTOMER=0000000001 (23 bytes)
    • HIGH CUSTOMER=0000000011 (24 bytes)
  • GENACUSTNUM counter deleted and redefined with VALUE(11).
  • All 36 statistics counters reset to VALUE(0).

Terminal display:

CODE 
HIGH CUSTOMER=0000000011

10.2 Example 2 — Custom High Customer Number Supplied

Terminal input:

CODE 
LGSE 0000000050

(Transaction ID + space + 0000000050 — total 15 characters)

Processing outcome:

  • WS_RECV_LEN = 15 → IF WS_RECV_LEN > 5 is true.
    • Adjusted length = 15 − 5 = 10.
    • LASTCUSTNUM set from SUBSTR(WS_RECV_DATA, 1, 10) → 50.
  • All four TS queues are deleted.
  • GENACNTL is repopulated:
    • **** GENAPP CNTL (20 bytes)
    • LOW CUSTOMER=0000000001 (23 bytes)
    • HIGH CUSTOMER=0000000050 (24 bytes)
  • GENACUSTNUM counter deleted and redefined with VALUE(50).
  • All 36 statistics counters reset to VALUE(0).

Terminal display:

CODE 
HIGH CUSTOMER=0000000050

Any new customer created after this setup will be assigned a number drawn from the counter sequence up to 50, and the GENACNTL TS queue will reflect this range for any downstream program that reads it to determine valid customer number boundaries.
