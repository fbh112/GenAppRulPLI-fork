1. Application Architecture & Component Inventory

1. Overview

GenApp is a general insurance application for z/OS, written in Enterprise PL/I. It has two parts:

  • Online CICS transactions that manage customers and four kinds of insurance policy: Motor, Endowment, House and Commercial.
  • Batch programs for reporting and data extraction.

The code base has 35 PL/I programs (in /pli/) and 6 include files (in /plinc/). Online processing uses a strict three-tier layering:

  1. BMS presentation programs.
  2. Orchestration programs that hold the business logic.
  3. Backend programs that do the DB2 and VSAM I/O.

Four supporting CICS programs provide cross-cutting services such as error logging and statistics. All CICS programs talk to each other through COMMAREAs, using EXEC CICS LINK.

This page covers:

  • The architecture and layering conventions.
  • The communication area (COMMAREA) and include-file conventions.
  • The complete component catalog across the customer and policy domains.
  • Data-store access summaries and external dependencies.

3. Layering Conventions

3.1 Tier 1: Presentation

These programs receive control directly from CICS transactions. They:

  • Present BMS maps to the terminal.
  • Collect user input.
  • Dispatch to the orchestration tier with EXEC CICS LINK.

They contain no DB2 or VSAM access. Their entry convention is reentrant:

PLI 
Proc(DFHEIPTR, COMM_AREA_PTR) Options(Main, Reentrant)

Each menu program includes the BMS map structures and the COMMAREA layout:

PLI 
%INCLUDE SSMAP
%INCLUDE LGCMAREA

3.2 Tier 2: Orchestration

Orchestrators validate the COMMAREA, apply business rules and dispatch to the backend. They link to the backend dynamically, using a program-name variable. The exception is LGUPOL01, which uses the hardcoded string 'LGUPDB01'.

PLI 
Proc(COMM_AREA_PTR) Options(Main)

3.3 Tier 3: Backend

Backend programs perform all embedded SQL (DB2 programs) or CICS File Control operations (VSAM programs). They communicate only through the COMMAREA. A DB2 backend that maintains a VSAM mirror links on to the VSAM counterpart. For example, LGAPDB01 links to LGAPVS01, and LGDPDB01 links to LGDPVS01.

3.4 Naming Conventions

The program names follow a positional pattern: LG + operation + domain/store + 01.

Position Code Meaning
3 A / I / D / U Add / Inquire / Delete / Update
4–5 PO / CU Policy / Customer orchestrator
4–5 PD / CD Policy / Customer DB2 backend
4–5 PV / CV Policy / Customer VSAM backend
Prefix LGTEST BMS menu program (P1–P4 for policy types, C1 for customer)

For example, LGAPDB01 is Add Policy DB2, and LGICVS01 is Inquire Customer VSAM.

4. Communication Area Structures and Include Files

4.1 COMMAREA Convention

All CICS programs, except the two no-COMMAREA daemons (LGWEBST5, LGSETUP), use the shared LGCMAREA layout. It carries customer and policy fields, such as CA_CUSTOMER_NUM. CA_CUSTOMER_NUM is also the contract that joins the Customer and Policy domains. Programs receive it through the pointer parameter:

PLI 
Proc(COMM_AREA_PTR) Options(Main)

The batch programs reuse the same layout by including it through the SQL preprocessor:

PLI 
EXEC SQL INCLUDE SQLCA
EXEC SQL INCLUDE LGCMAREA

The LGBATCHF formatting subroutine receives a pointer to a populated COMMAREA. Its signature is shown in section 6.5.

Other COMMAREA uses:

  • LGSTSQ takes up to 90 bytes of message text through its COMMAREA.
  • LGASTAT1 reads the request ID and return code from either the COMMAREA or the DFHEP event channel.
  • LGIPVS01 uses a different entry convention, Proc(COMMA_PTR) Options(Main), and accepts a partial key from a COMMAREA or terminal input.

5.6 Supporting CICS Programs

Program Type Entry Purpose
LGSTSQ Shared service Proc(COMM_AREA_PTR) Options(Main) Central error writer. Receives up to 90 bytes of message text and writes it to the CSMT TDQ and the GENAERRS TSQ (or a custom queue if started with Q=nnnn).
LGASTAT1 Event Processing adapter Proc(COMM_AREA_PTR) Options(Main) Reads the request ID and return code from the DFHEP.DATA.00001 / DFHEP.DATA.00002 channel containers, or from the COMMAREA. Increments the named counter GENA<request><rc> in pool GENA. Also reads GENASTRT.
LGWEBST5 Statistics daemon Proc Options(Main) Queries GENA counters, computes per-minute rates as current minus previous, stores values in TS queues GENA<code>V, and restarts itself every minute via transaction SSST. It drives 34 counter blocks from an internal table.
LGSETUP Admin utility Proc Options(Main) One-time setup. Deletes and recreates TS queues GENAERRS and GENASTRT, defines or resets the 36 named counters in pool GENA, and writes GENACNTL. Accepts the high customer number from terminal input (default 11).

11. Cross-Cutting Error Handling

The programs share one error-handling convention. A program that detects an error builds a message and links to LGSTSQ, passing the text in its COMMAREA. LGSTSQ is called by every orchestrator and backend except LGIPVS01 and LGICVS01, which make no LINK calls. It writes to both the CSMT TDQ and the GENAERRS TSQ.

graph LR ORCH[Orchestrators] -.->|LINK on error| STSQ[LGSTSQ] DB2[DB2 Backends] -.->|LINK on error| STSQ VS[VSAM Backends] -.->|LINK on error| STSQ STSQ --> TDQ[CSMT TDQ] STSQ --> TSQ[GENAERRS TSQ]

Statistics are collected separately. LGASTAT1 increments the GENA named counters for each request. LGWEBST5 runs under transaction SSST, computes per-minute rates and restarts itself every minute. LGSETUP initialises both the queues and the counters.
