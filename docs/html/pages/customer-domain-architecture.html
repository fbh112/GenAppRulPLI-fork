Customer Domain Architecture

1. Overview

The Customer Domain of the GenApp PL/I application suite handles customer inquiry, add and update. It is built from four layers:

Layer Responsibility Programs
Menu / presentation 3270 BMS menu on CICS transaction SSC1 LGTESTC1
Business logic (orchestrators) Validate the COMMAREA, route the request, return outcome codes LGICUS01, LGUCUS01, LGACUS01
DB2 persistence SQL access to CUSTOMER and CUSTOMER_SECURE LGICDB01, LGUCDB01, LGACDB01, LGACDB02
VSAM persistence KSDS counterparts of the DB2 operations LGICVS01, LGUCVS01, LGACVS01

All layers communicate through EXEC CICS LINK with a shared COMMAREA (LGCMAREA, up to 32,500 bytes). Every program logs errors through the shared utility LGSTSQ.

The key business entity is the customer, identified by CUSTOMER_NUMBER (CA_CUSTOMER_NUM, 10 digits). This number is the contract between the Customer Domain and the Policy domain. Policy entities (POLICY, MOTOR, ENDOWMENT, HOUSE, COMMERCIAL, CLAIM) hold foreign-key references to it.

1.1 Scope

This page covers:

  • How the menu, business-logic, DB2 and VSAM layers interact for inquiry, add and update.
  • How the programs relate to each other.
  • The domain boundaries: Policy, Batch/Reporting and Security.
  • Return codes, validation rules and error-handling conventions.

The diagram shows these relationships:

  • The menu program is the only entry point. It links to one orchestrator per operation.
  • Orchestrators hold no screen logic. They validate input and delegate persistence.
  • LGICDB01 is the inquiry backend. In the documented code path, LGICUS01 links only to this program. LGICVS01 exists as the VSAM inquiry counterpart, but the documented LGICUS01 flow does not link to it.
  • The update path chains DB2 to VSAM: LGUCDB01 runs the SQL UPDATE and then links to LGUCVS01.
  • The add path writes to DB2, VSAM and the security table.

The program documentation for LGACUS01 shows the orchestrator itself issuing the INSERT INTO CUSTOMER and linking to LGACVS01 and LGACDB02. The domain-level view attributes the CUSTOMER insert and the VSAM link to LGACDB01. The diagram shows both, because both appear in the source material.

2.4 Entity Relationships

erDiagram CUSTOMER { int CUSTOMERNUMBER "Identity PK" string FIRSTNAME "length 10" string LASTNAME "length 20" string DATEOFBIRTH "length 10" string HOUSENAME "length 20" string HOUSENUMBER "length 4" string POSTCODE "length 8" string PHONEMOBILE "length 20" string PHONEHOME "length 20" string EMAILADDRESS "length 100" } CUSTOMER_SECURE { int CUSTOMERNUMBER "FK to CUSTOMER" string CUSTSECR_PASS "length 32" string CUSTSECR_COUNT "length 4" string CUSTSECR_STATE "length 1" string CUSTSECR_DATA "length 32445" } POLICY { int POLICYNUMBER "Identity PK" int CUSTOMERNUMBER "FK to CUSTOMER" string ISSUEDATE "length 10" string EXPIRYDATE "length 10" string POLICYTYPE "length 1" string LASTCHANGED "timestamp" int BROKERID string BROKERSREFERENCE "length 10" int PAYMENT } CUSTOMER ||--o{ POLICY : "has" CUSTOMER ||--o| CUSTOMER_SECURE : "secured by"

CUSTOMER is the parent entity. Policies reference it by foreign key, so a policy insert with no matching customer fails with SQLCODE -530. LGACUS01 maps this to return code 70. CUSTOMER_SECURE is kept apart from the demographic data to isolate sensitive payment and security details.

3. Transactions and Entry Point

The Customer Domain has one dedicated CICS transaction:

Transaction ID Menu program Description
SSC1 LGTESTC1 3270 BMS menu for customer management operations (Add, Inquire, Update)

The transactions SSP1 to SSP4 belong to the Policy and Product domains (Motor, Endowment, House, Commercial). SSST is a shared stats/web transaction.

4. Shared COMMAREA Contract

The orchestrators share one COMMAREA layout, LGCMAREA. It is a PL/I UNION BASED structure over CHAR(32500), so the raw view and the structured views overlay the same storage.

Field Format Purpose
CA_REQUEST_ID CHAR(6) Operation identifier, for example 01ICUS, 01UCUS, 02ACUS
CA_RETURN_CODE PIC '99' Outcome code returned to the caller
CA_CUSTOMER_NUM PIC '9999999999' Customer key
CA_FIRST_NAME … CA_EMAIL_ADDRESS Fixed-length CHAR Customer demographics (name 10/20, DOB 10, house name 20, house number 4, postcode 8, phones 20, email 100)
CA_NUM_POLICIES PIC '999' Policy count, initialised to 0
CA_POLICY_DATA CHAR(32267) Policy payload returned by the inquiry

4.1 Return Codes

Code Meaning Set by
00 Success All orchestrators
70 Referential integrity violation (SQLCODE -530 on POLICY insert) LGACUS01
90 SQL or system error LGACUS01
98 COMMAREA shorter than the 90-byte minimum LGACUS01, LGICUS01
99 Invalid request ID LGUCUS01

5. Customer Inquiry Flow

LGICUS01 is the front door for inquiry. It does no database access itself. After validating the COMMAREA, it scans the TS queue GENAWMQC for a routing record starting with MQHIT=. With no such record, it links to LGICDB01. With one, it links to the alternate program AAAAAAAA.

sequenceDiagram participant User as 3270 User participant Menu as LGTESTC1 participant Inq as LGICUS01 participant TSQ as TS Queue GENAWMQC participant DB as LGICDB01 participant DB2 as DB2 CUSTOMER User->>Menu: Enter customer number (SSC1) Menu->>Inq: EXEC CICS LINK (COMMAREA, 01ICUS) Inq->>Inq: EIBCALEN checks (0 = abend, <90 = RC 98) Inq->>TSQ: READQ TS ITEM(1) then NEXT TSQ-->>Inq: Records (MQHIT= ?) alt No MQHIT= record Inq->>DB: EXEC CICS LINK LGICDB01 DB->>DB2: SELECT customer DB2-->>DB: Customer row DB-->>Inq: COMMAREA populated else MQHIT= found Inq->>Inq: EXEC CICS LINK AAAAAAAA end Inq-->>Menu: EXEC CICS RETURN Menu-->>User: Display customer details

If the control queue is missing or unreadable, MQ_HIT stays 0. The request then follows the standard DB2 path, so a missing queue is not an error.

Routing code from GET_CUSTOMER_INFO, as described in the program documentation:

PLI 
/* Scan the control queue, then route */
MQ_HIT = 0;
EXEC CICS READQ TS QUEUE(MQ_CONTROL) INTO(MQ_READ_RECORD)
          RESP(WS_RESP) ITEM(1);
/* DO UNTIL (WS_RESP > 0): READQ TS ... NEXT;
   IF first 6 chars = 'MQHIT=' THEN MQ_HIT = 1; */

IF MQ_HIT = 0 THEN
   EXEC CICS LINK PROGRAM(LGICDB01) COMMAREA(COMM_AREA) LENGTH(32500);
ELSE
   EXEC CICS LINK PROGRAM('AAAAAAAA') COMMAREA(COMM_AREA) LENGTH(32500);

6. Customer Update Flow

LGUCUS01 is a gatekeeper. It accepts only CA_REQUEST_ID = '01UCUS'. Any other value gets return code 99 and an immediate return, and no update is attempted. A valid request is passed in full to LGUCDB01, which applies the SQL UPDATE to CUSTOMER and then links to LGUCVS01 to keep VSAM in step.

ABEND LGCA Upd->>Upd: CA_REQUEST_ID = 01UCUS ? alt Invalid request ID Upd-->>Menu: CA_RETURN_CODE = 99 else Valid Upd->>DB: EXEC CICS LINK LGUCDB01 (32500) DB->>DB2: UPDATE CUSTOMER DB->>VS: EXEC CICS LINK LGUCVS01 VS->>KS: Update record DB-->>Upd: Return code in COMMAREA Upd-->>Menu: EXEC CICS RETURN end

Request validation and delegation in LGUCUS01:

PLI 
IF CA_REQUEST_ID ^= '01UCUS' THEN DO;
   CA_RETURN_CODE = '99';
   EXEC CICS RETURN;
END;

CALL UPDATE_CUSTOMER_INFO;   /* EXEC CICS LINK PROGRAM(LGUCDB01)
                                COMMAREA(COMM_AREA) LENGTH(32500) */
EXEC CICS RETURN;

7. Customer Add Flow

LGACUS01 is the most complex program in the domain. It is the dual-write point for DB2 and VSAM, and it creates the security record.

7.1 Onboarding Sequence

The documented onboarding steps run in strict order:

  1. OBTAIN_CUSTOMER_NUMBER issues EXEC CICS GET COUNTER against counter GENACUSTNUM in pool GENA.
  2. INSERT_CUSTOMER inserts the row into CUSTOMER. It uses either the counter value or DB2’s identity column.
  3. EXEC CICS LINK PROGRAM(LGACVS01) writes the VSAM copy, passing a COMMAREA of 225 bytes.
  4. EXEC CICS LINK PROGRAM(LGACDB02) creates the security record, passing a CDB2AREA of 32,500 bytes.
  5. CA_RETURN_CODE is checked. Anything other than 00 causes an immediate return.
sequenceDiagram participant Menu as LGTESTC1 participant Add as LGACUS01 participant CNT as CICS Named Counter participant DB2 as DB2 CUSTOMER participant VS as LGACVS01 participant SEC as LGACDB02 participant TS as DB2 CUSTOMER_SECURE participant LOG as LGSTSQ Menu->>Add: EXEC CICS LINK (COMMAREA) Add->>Add: CHECK_INPUTS (EIBCALEN, min 90 bytes) Add->>CNT: GET COUNTER GENACUSTNUM / GENA alt Counter available CNT-->>Add: LASTCUSTNUM Add->>DB2: INSERT with explicit CUSTOMERNUMBER else Counter unavailable Add->>DB2: INSERT with DEFAULT identity Add->>DB2: SET = IDENTITY_VAL_LOCAL() end alt SQLCODE not 0 Add->>LOG: WRITE_ERROR_MESSAGE Add-->>Menu: RC 90 else SQLCODE = 0 Add->>VS: EXEC CICS LINK LGACVS01 (225) Add->>SEC: EXEC CICS LINK LGACDB02 (02ACUS) SEC->>TS: INSERT security row SEC-->>Add: D2_RETURN_CODE Add-->>Menu: CA_RETURN_CODE, CA_CUSTOMER_NUM end

7.2 Customer Number Strategy

Number assignment falls back automatically to DB2 identity when the CICS named counter fails:

PLI 
EXEC CICS GET COUNTER(GENACOUNT) POOL(GENAPOOL)
          VALUE(LASTCUSTNUM) RESP(WS_RESP);
IF WS_RESP ^= DFHRESP(NORMAL) THEN DO;
   LGAC_NCS = 'NO';            /* fall back to DB2 IDENTITY */
   DB2_CUSTOMERNUM_INT = 0;
END;
ELSE DB2_CUSTOMERNUM_INT = LASTCUSTNUM;

When LGAC_NCS is not 'ON', the insert supplies DEFAULT for CUSTOMERNUMBER, and the generated value is read back:

PLI 
EXEC SQL SET :DB2_CUSTOMERNUM_INT = IDENTITY_VAL_LOCAL();
CA_CUSTOMER_NUM = DB2_CUSTOMERNUM_INT;

7.3 Security Record Preparation

Before linking to LGACDB02, the orchestrator populates the security request area:

PLI 
D2_CUSTOMER_NUM   = CA_CUSTOMER_NUM;
D2_REQUEST_ID     = '02ACUS';
D2_CUSTSECR_COUNT = '0000';
D2_CUSTSECR_STATE = 'N';
EXEC CICS LINK PROGRAM(LGACDB02) COMMAREA(CDB2AREA) LENGTH(32500);

7.4 Policy Operations and the Cross-Domain Bridge

LGACUS01 also contains policy routines that run SQL directly against POLICY. This is the main coupling between the Customer and Policy domains.

Action code Procedure SQL
'1' ONBOARD_CUSTOMER INSERT into CUSTOMER, then VSAM and security links
'2' OFFER_CUSTOMER → INSERT_CUSTOMER_POLICY INSERT into POLICY, IDENTITY_VAL_LOCAL(), SELECT LASTCHANGED
'3' TRANSFER_CUSTOMER → TRANSFER_CUSTOMER_POLICY Same as the offer path
'4' DELETE_CUSTOMER → DELETE_CUSTOMER_POLICY DELETE FROM POLICY

Claim requests (CA_REQUEST_ID = '01ACLM') are blocked from the offer, transfer and delete paths.

Runtime caveat: ACTION_CODE is initialised to '0' and never changed. This is a known defect carried over from the original COBOL program. In the current implementation, only the OTHERWISE branch is taken. LGACUS01 therefore validates its input and returns, and none of the four branches runs.

Policy insert and SQLCODE handling:

PLI 
EXEC SQL INSERT INTO POLICY
   VALUES (DEFAULT, :DB2_CUSTOMERNUM_INT, :CA_ISSUE_DATE,
           :CA_EXPIRY_DATE, :DB2_POLICYTYPE, CURRENT TIMESTAMP,
           :DB2_BROKERID_INT, :CA_BROKERSREF, :DB2_PAYMENT_INT);

SELECT (SQLCODE);
   WHEN (0)    CA_RETURN_CODE = '00';
   WHEN (-530) DO; CA_RETURN_CODE = '70';  /* RI violation */
                   CALL WRITE_ERROR_MESSAGE;
                   EXEC CICS RETURN; END;
   OTHERWISE   DO; CA_RETURN_CODE = '90';
                   CALL WRITE_ERROR_MESSAGE;
                   EXEC CICS RETURN; END;
END;

For deletes, SQLCODE 0 (deleted) and 100 (row not found) both count as success. Foreign-key cascade rules propagate the delete to the policy-type subtables.

9. Validation and Error Handling

9.1 Common Entry Checks

All three orchestrators begin with the same checks:

  • They capture EIBTRNID, EIBTRMID and EIBTASKN into working storage for diagnostics.
  • If EIBCALEN = 0, they log NO COMMAREA RECEIVED and issue EXEC CICS ABEND ABCODE('LGCA') NODUMP.
  • They initialise CA_RETURN_CODE = '00' and CA_NUM_POLICIES = 0.
  • LGICUS01 and LGACUS01 also require a COMMAREA of at least 90 bytes (18-byte header plus 72-byte customer area). A shorter COMMAREA gets return code 98.

9.2 Centralised Error Logging

Each program has a WRITE_ERROR_MESSAGE procedure that calls the shared LGSTSQ utility. The sequence is:

  1. EXEC CICS ASKTIME and FORMATTIME produce the date and time.
  2. The ERROR_MSG record carries the date, time, program name, customer number, policy number, SQL request label and SQLCODE. LGSTSQ writes it to the queue.
  3. A second call writes CA_ERROR_MSG, which is COMMAREA= followed by up to 90 bytes of the raw COMMAREA.
PLI 
EXEC CICS ASKTIME ABSTIME(WS_ABSTIME);
EXEC CICS FORMATTIME ABSTIME(WS_ABSTIME)
          MMDDYYYY(WS_DATE) TIME(WS_TIME);
EXEC CICS LINK PROGRAM('LGSTSQ')
          COMMAREA(ERROR_MSG) LENGTH(STG(ERROR_MSG));

IF EIBCALEN > 0 THEN DO;
   IF EIBCALEN < 91 THEN CA_DATA = LEFT(COMM_AREA_RAW, EIBCALEN);
   ELSE                  CA_DATA = LEFT(COMM_AREA_RAW, 90);
   EXEC CICS LINK PROGRAM('LGSTSQ')
             COMMAREA(CA_ERROR_MSG) LENGTH(STG(CA_ERROR_MSG));
END;

9.3 Failure Behaviour by Program

Program Condition Result
All orchestrators No COMMAREA Log, then ABEND LGCA
LGICUS01 COMMAREA < 90 bytes RC 98, return with no logging
LGICUS01 GENAWMQC queue missing Silent fallback to LGICDB01
LGUCUS01 Request ID is not 01UCUS RC 99, return with no logging
LGACUS01 Customer INSERT SQLCODE is not 0 RC 90, log, return; VSAM and security links are skipped
LGACUS01 POLICY insert, SQLCODE -530 RC 70, log, return
LGACUS01 LGACDB02 returns a non-00 code Return to the caller immediately

10. Domain Boundaries

graph TD subgraph Customer_Domain [Customer Domain] ORCH[Orchestrators] BE[DB2 and VSAM backends] CUST[(CUSTOMER)] SEC[(CUSTOMER_SECURE)] end subgraph Policy_Domain [Policy / Product Domain] POL[(POLICY and subtables)] end subgraph Batch_Domain [Batch and Reporting] LGBATCH[LGBATCH] LGBATDB2[LGBATDB2] end ORCH --> BE BE --> CUST BE --> SEC ORCH -.->|Cross-domain SQL by LGACUS01| POL POL -.->|CUSTOMER_NUMBER FK| CUST LGBATCH -->|SELECT| CUST LGBATDB2 -->|SELECT| CUST

10.1 Customer Domain and Policy Domain

  • The boundary contract is CUSTOMER_NUMBER (CA_CUSTOMER_NUM).
  • Customer records are the master entities. Policy tables hold foreign keys to them.
  • LGACUS01 runs SELECT, INSERT and DELETE directly against POLICY. This is the main coupling point.

10.2 Customer Domain and Batch/Reporting Domain

  • LGBATCH and LGBATDB2 read CUSTOMER in bulk. LGBATCHF handles the flat-file distribution. This access is read-only and bypasses the online CICS transactions.

10.3 Customer Domain and Security Data

  • Demographic data (CUSTOMER) is isolated from sensitive payment and security details (CUSTOMER_SECURE, written only by LGACDB02).

11. Shared Infrastructure

LGSTSQ is the CICS TS queue error logger. It is invoked from all Customer programs (LGACDB01, LGACDB02, LGACUS01, LGICDB01, LGICUS01, LGUCDB01, LGUCUS01, LGACVS01, LGICVS01, LGUCVS01) and from the Policy programs. Centralising logging keeps the error record format consistent across domains.

12. Design Observations

  • Layered LINK architecture. Each layer talks only to the next through CICS LINK and the shared COMMAREA. A persistence layer can change without affecting the menu.
  • Dual-write persistence. The add and update paths write to DB2 and VSAM. The inquiry path documented here reads from DB2 only.
  • Resilient number assignment. The CICS named counter is preferred, with an automatic fall-back to DB2 identity.
  • Runtime-switchable routing. The inquiry path can be redirected through the GENAWMQC queue without recompiling.
  • Known defect. ACTION_CODE in LGACUS01 is fixed at '0', so the onboarding, offer, transfer and delete branches never execute.
  • Domain coupling. The direct POLICY SQL in LGACUS01 ties the Customer Domain to the Policy schema.
