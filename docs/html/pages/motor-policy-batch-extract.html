Motor Policy Batch Extraction Utility

1. Overview

The Motor Policy Batch Extraction Utility (program LGMOTOUT) is a batch PL/I program, not CICS. It reads every row of the GENASA1.MOTOR DB2 table and writes each one as a formatted, fixed-length 132-byte record to a sequential output file named MOTOROUT. It captures vehicle attributes (make, model, value, registration, colour, engine capacity, year of manufacture), policy coverage data (policy number, premium) and accident history (accident count).

The utility is read-only. It never inserts, updates or deletes DB2 data. When it finishes, it displays the number of records written as an audit count. If DB2 or file I/O errors occur, it displays diagnostics and sets a non-zero return code for the calling JCL.

1.1 Key Characteristics

Characteristic Description
Program name LGMOTOUT
Language Enterprise PL/I for z/OS (V52 compiler)
Execution mode Batch, non-CICS
Data source DB2 table GENASA1.MOTOR through cursor MOTOR_CSR (FOR READ ONLY)
Data target Sequential FB file MOTOROUT, RECSIZE(132)
Selection Full table scan with no WHERE clause
Return codes 0 success, 8 fetch error, 12 open/cursor error

1.2 Business Purpose

  • Exports motor policy data for downstream reporting, reconciliation or data-sharing jobs.
  • Produces a flat file with predictable column positions.
  • Reports an auditable count of rows written.
  • Signals failure to the JCL job step through return codes.

2. System Architecture

2.1 Component Overview

The utility is one load module containing a main procedure and three internal procedures. It depends on one DB2 table and one DD-allocated output file, and writes diagnostics to SYSOUT or the operator console.

3.3 Output Record Layout

The WS_MOTOR_LINE structure holds 119 bytes of fields and separators, followed by a 13-byte space filler. The total is the 132 bytes of MOTOROUT_REC. The program serialises it with MOTOROUT_REC = STRING(WS_MOTOR_LINE).

4.3 Step-by-Step Description

4.3.1 Initialisation and File Open

The program registers an ON UNDEFINEDFILE(MOTOROUT) handler and then opens the output file. If the file can’t be opened, for example because the DD statement is missing, the handler displays a message, sets PLIRETC(12) and issues STOP.

PLI 
ON UNDEFINEDFILE(MOTOROUT) BEGIN;
   DISPLAY('LGMOTOUT: OPEN MOTOROUT FAILED');
   CALL PLIRETC(12);
   STOP;
END;
OPEN FILE(MOTOROUT);

4.3.2 Cursor Open

EM_SQLREQ is set to ' OPEN MOTOR-CSR ', then the cursor is opened. If SQLCODE is not 0, the program writes an error message, closes MOTOROUT, sets return code 12 and returns.

4.3.3 Fetch Loop

The loop runs while SQLCODE ^= 100 & SQLCODE >= 0. Each iteration calls FETCH_MOTOR_ROWS.

PLI 
DO WHILE (SQLCODE ^= 100 & SQLCODE >= 0);
   CALL FETCH_MOTOR_ROWS;
END;

4.3.4 Fetch Dispatch

FETCH_MOTOR_ROWS fetches one row into the ten host variables and dispatches with SELECT (SQLCODE):

SQLCODE Action
0 Call WRITE_MOTOR_ROW
100 No-op, so the loop ends on its next test
Other Capture the code, call WRITE_ERROR_MESSAGE, set PLIRETC(8)

4.3.5 Record Formatting and Writing

WRITE_MOTOR_ROW moves each host variable into WS_MOTOR_LINE and converts the structure to the 132-byte buffer. It sets an ON TRANSMIT(MOTOROUT) handler and initialises MOTOROUT_OK to true. After the write it checks the flag: a failed write displays LGMOTOUT: WRITE FAILED and calls WRITE_ERROR_MESSAGE. A successful write increments WS_ROW_COUNT.

4.3.6 Termination

After the loop, the program closes MOTOR_CSR and then MOTOROUT. It then displays LGMOTOUT: ROWS WRITTEN=<count>.

6. Inputs and Outputs

6.1 Inputs

The program has no parameters or user input. Its only data source is GENASA1.MOTOR, read through MOTOR_CSR. It also requires the MOTOROUT DD allocation before it can run.

6.2 Outputs

Output Description
MOTOROUT file One 132-byte FB record per successfully fetched and written row
LGMOTOUT: ROWS WRITTEN=<n> Final audit count of rows written
LGMOTOUT: OPEN MOTOROUT FAILED Displayed when the output file can’t be opened
LGMOTOUT: WRITE FAILED Displayed when a write raises TRANSMIT
Structured DB2 error message Date, time, LGMOTOUT, SQL request name and SQLCODE
Return code 0, 8 or 12 through PLIRETC

6.3 Return Codes

Code Meaning Trigger
0 Success Normal completion
8 Fetch error FETCH returned an SQLCODE other than 0 or 100
12 Fatal open error MOTOROUT open failed or OPEN MOTOR_CSR returned a non-zero SQLCODE

7.2 File I/O Errors

  • Open failure: ON UNDEFINEDFILE displays the message, sets return code 12 and stops the program.
  • Write failure: ON TRANSMIT sets MOTOROUT_OK to '0'B. The program displays a message, calls WRITE_ERROR_MESSAGE, does not count the row and carries on with the next row.
PLI 
ON TRANSMIT(MOTOROUT) MOTOROUT_OK = '0'B;
MOTOROUT_OK = '1'B;
WRITE FILE(MOTOROUT) FROM(MOTOROUT_REC);
IF ^MOTOROUT_OK THEN DO;
   DISPLAY('LGMOTOUT: WRITE FAILED');
   CALL WRITE_ERROR_MESSAGE;
END;
ELSE WS_ROW_COUNT = WS_ROW_COUNT + 1;

7.3 DB2 Errors

  • Cursor open: any non-zero SQLCODE is fatal. The program reports the error, closes the file and sets return code 12.
  • Fetch: SELECT (SQLCODE) separates success, end of data and error. An error reports the diagnostic and sets return code 8.

7.4 Centralised Diagnostics

8. Constraints and Limitations

8.1 Data Format Constraints

  • Numeric fields (POLICYNUMBER, VALUE, PREMIUM, ACCIDENTS) are output as 9-digit unsigned pictures. They can’t exceed 999,999,999 or be negative.
  • CC is output as PIC '9999', so it is limited to 0–9,999 and has FIXED BIN(15) as its host type.
  • Character fields are fixed length (MAKE and MODEL 15, REGNUMBER 7, COLOUR 8, YEAROFMANUFACTURE 10). Longer values are truncated.
  • WS_ROW_COUNT is PIC '999999999', so it overflows past 999,999,999.
  • The program does no content or range validation on the year of manufacture.

8.2 File and DB2 Constraints

  • Every record is exactly 132 bytes. Any change to field widths breaks record alignment.
  • One record is written per fetched row.
  • The cursor is FOR READ ONLY with no WHERE clause, so all rows are always extracted.
  • Rows are fetched one at a time with no array fetch.
  • The 10-column fetch is tied to the table definition. Changing the table requires program changes.

8.3 Operational Order Constraints

  1. MOTOROUT is opened before the cursor.
  2. The cursor must open successfully before any fetch.
  3. A write happens only after a successful fetch (SQLCODE = 0).
  4. The cursor is closed before the file.
  5. The row count increases only on successful writes.

8.4 Known Risks

  • Warning SQLCODEs: the loop exits only on SQLCODE = 100 or SQLCODE < 0. An unexpected positive SQLCODE other than 100 could keep the loop running.
  • Blank timestamps: WS_DATE and WS_TIME are never set in the program, so error messages may show blank date and time values.
  • SQLCODE range: EM_SQLRC can only represent −99,999 to +99,999.
  • Write failures: these don’t change the return code, so the output file can be incomplete while the job still ends with a code that shows no problem. Only the displayed row count shows the shortfall.

CODE

9.2 DB2 Cursor Open Failure

If GENASA1.MOTOR does not exist, OPEN MOTOR_CSR returns SQLCODE = -204. The program displays the diagnostic, closes MOTOROUT, writes no records and ends with return code 12.

CODE 
20240101 103045 LGMOTOUT OPEN MOTOR-CSR  SQLCODE= -204

9.3 Write Failure for One Record

The first record is written successfully. The second raises TRANSMIT, so the program displays a message and does not count that row. The run finishes with one row counted.

CODE 
LGMOTOUT: WRITE FAILED
20240101 103045 LGMOTOUT FETCH MOTOR-CSR  SQLCODE=    0
LGMOTOUT: ROWS WRITTEN=000000001

Here the diagnostic shows FETCH MOTOR-CSR with SQLCODE = 0. That is because EM_SQLREQ still holds the last SQL request name, even though the failure came from the file write.
