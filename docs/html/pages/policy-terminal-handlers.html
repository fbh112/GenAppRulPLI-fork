Policy Terminal Menu Handlers

This page documents the four CICS interactive terminal programs that form the front-end layer of the GenApp general insurance application. Each program presents a BMS screen to a terminal operator, accepts a single-character menu option, populates a shared communication area (COMMAREA) with the relevant policy data, and routes the request to a dedicated back-end policy orchestrator via EXEC CICS LINK. Results are reflected back to the screen, and each program re-invokes itself pseudo-conversationally under its own transaction ID, maintaining session continuity until the operator exits.

1. System Architecture

The four menu handler programs share a common architectural pattern. They sit at the presentation layer of a three-tier CICS application: the terminal operator interacts with a BMS map, the menu handler programs manage screen I/O and routing, and a set of shared back-end policy orchestrators perform the actual database operations.

All four programs use:

  • BMS Mapset SSMAP for screen layout definitions.
  • A shared 32,500-byte COMMAREA structure defined by the LGCMAREA copybook.
  • EXEC CICS LINK to call the same set of four back-end orchestrators (LGIPOL01, LGAPOL01, LGDPOL01, LGUPOL01).
  • The pseudo-conversational CICS pattern — ending each task with EXEC CICS RETURN TRANSID(...) to preserve state across user interactions without holding CICS resources between keystrokes.

2. Overview

2.2 Shared Design Pattern

Each program follows the same structural flow on every invocation:

  1. First-entry guard — Test EIBCALEN = 0; if true, initialise COMMAREA and send the blank map with ERASE.
  2. AID and condition handlers — Register HANDLE AID (CLEAR, PF3) and HANDLE CONDITION MAPFAIL to intercept terminal key presses.
  3. Receive user input — EXEC CICS RECEIVE MAP reads screen fields into the map input structure.
  4. Option dispatch — A SELECT on the option field routes to one of four (or three, for LGTESTP4) processing paths.
  5. COMMAREA population — Set CA_REQUEST_ID and all relevant policy fields before calling the back-end.
  6. Back-end call — EXEC CICS LINK to the appropriate orchestrator with the 32,500-byte COMMAREA.
  7. Return-code check — Test CA_RETURN_CODE; on failure, optionally issue SYNCPOINT ROLLBACK and route to an error label.
  8. Screen update — Populate map output fields from the COMMAREA and EXEC CICS SEND MAP.
  9. Pseudo-conversational return — EXEC CICS RETURN TRANSID('SSPx') COMMAREA(COMM_AREA).

3. LGTESTP1 — Motor Policy Menu Handler

3.1 Purpose

LGTESTP1 runs under transaction SSP1 and manages motor insurance policy maintenance. It presents screen SSMAPP1 and supports four operations — Inquire, Add, Delete, and Update — delegating each to LGIPOL01, LGAPOL01, LGDPOL01, or LGUPOL01 respectively. Motor-specific attributes (vehicle make, model, registration number, colour, engine capacity, manufacture date, premium, and accident history) flow through the COMMAREA sub-structure CA_MOTOR.

3.5 Update Option — Two-Phase Interaction

Option 4 (Update) is unique in that it requires two consecutive screen interactions within a single program dispatch:

  1. Phase A — Pre-fetch: Sets CA_REQUEST_ID = '01IMOT' and calls LGIPOL01 to retrieve the current policy record. On success, populates the screen with the existing data and issues a second EXEC CICS RECEIVE MAP to wait for the user’s edits.
  2. Phase B — Commit: Sets CA_REQUEST_ID = '01UMOT', maps the edited screen fields back to the COMMAREA, and calls LGUPOL01 to apply the changes.

7. Pseudo-Conversational Flow

All four programs implement the same pseudo-conversational CICS design pattern. Rather than holding a CICS task open while waiting for user input (which would consume server resources), each program ends its task after every screen send and re-arms itself for the next interaction.

sequenceDiagram participant User as Terminal Operator participant CICS as CICS Task Manager participant Pgm as LGTESTPx (SSPx) Note over User,Pgm: Session Start User->>CICS: Invoke transaction SSPx CICS->>Pgm: Start new task (EIBCALEN=0) Pgm->>User: SEND MAP (blank screen) Pgm->>CICS: RETURN TRANSID(SSPx) COMMAREA Note over CICS: Task ends — no resources held Note over User,Pgm: Subsequent Interactions User->>CICS: Press Enter (with screen data) CICS->>Pgm: Re-invoke task (EIBCALEN > 0, COMMAREA passed) Pgm->>Pgm: Process option, call back-end Pgm->>User: SEND MAP (result / error) Pgm->>CICS: RETURN TRANSID(SSPx) COMMAREA Note over CICS: Task ends — state preserved in COMMAREA Note over User,Pgm: Session End User->>CICS: Press PF3 (or MAPFAIL) CICS->>Pgm: Re-invoke task Pgm->>User: SEND TEXT "Transaction ended" Pgm->>CICS: RETURN (no TRANSID) Note over CICS: Transaction chain permanently ended

The COMMAREA (32,500 bytes, defined by LGCMAREA) is the sole persistence mechanism between invocations. It carries:

  • CA_REQUEST_ID — the last operation performed
  • CA_RETURN_CODE — the last return code from the back-end
  • CA_CUSTOMER_NUM / CA_POLICY_NUM — the identifiers active in the current session
  • All policy-type-specific fields in the appropriate union member

8. Common Error Handling Pattern

All four programs share an identical error handling architecture. Every error path sets a message into the screen error field, then falls through to a centralised ERROR_OUT routine.

8.1 Syncpoint Rollback

For Add and Delete operations only, a failed back-end call triggers EXEC CICS SYNCPOINT ROLLBACK before the error message is displayed. This ensures any partial database changes made by the back-end orchestrator within the same CICS unit of work are reversed, maintaining data integrity. Inquiry and Update failures do not issue a rollback.

9. COMMAREA Structure

All four programs share the same 32,500-byte COMMAREA layout defined in the LGCMAREA copybook. The first portion is common to all policy types; the remainder is a union that overlays the policy-type-specific data block.

The CA_REQUEST_ID value tells both the menu handler and the linked back-end orchestrators which union member is active for any given interaction.
