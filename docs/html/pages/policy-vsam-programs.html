Policy VSAM Back-End Programs

This page documents the VSAM KSDS access layer for the insurance policy domain. Four CICS-hosted Enterprise PL/I programs collectively manage the full lifecycle of policy records stored in the KSDSPOLY Key-Sequenced Dataset: LGAPVS01 adds new records, LGIPVS01 browses for existing records using a generic GTEQ search, LGUPVS01 performs read-update/rewrite operations, and LGDPVS01 deletes records by composite key. All four programs share a common 21-byte composite key structure and a consistent error-handling pattern — setting a return code in the Communication Area and logging structured diagnostics to the LGSTSQ utility program on failure.

1. System Architecture

The four VSAM back-end programs sit in the middle tier of the insurance application’s layered architecture. Upstream orchestrator programs (e.g., LGAPOL01) assemble a Communication Area and invoke the back-end programs via EXEC CICS LINK. The back-end programs issue CICS file-control commands against the KSDSPOLY VSAM KSDS dataset, returning results — or error codes — through the same Communication Area. On failure, every program delegates structured diagnostic logging to the shared LGSTSQ utility.

2. Overview

2.1 Shared VSAM Key Structure

Every program in this layer uses the same 21-byte composite key to uniquely identify a policy record within KSDSPOLY:

Byte(s) Field Width Source
1 Policy type indicator (C, E, H, M) 1 Character 4 of CA_REQUEST_ID
2–11 Customer number 10 CA_CUSTOMER_NUM
12–21 Policy number 10 CA_POLICY_NUM

The 64-byte VSAM record is composed of this 21-byte key followed by a 43-byte union payload whose layout depends on the policy type.

2.2 Policy Types

All four programs recognise the same four policy type codes, driven by the fourth character of CA_REQUEST_ID:

Code Policy Type Key Policy-Specific Fields
C Commercial Postcode, Status, Customer name
E Endowment With-Profits flag, Equities flag, Managed Fund flag, Fund Name, Life Assured
H House Property Type, Bedrooms, Value, Postcode, House Name
M Motor Make, Model, Value, Registration Number

2.4 Common Error-Handling Pattern

All programs follow the same error response protocol on CICS file-command failure:

  1. Capture EIBRESP2 for supplementary diagnostic detail.
  2. Set CA_RETURN_CODE in the Communication Area to a program-specific error value.
  3. Call the internal WRITE_ERROR_MESSAGE procedure, which timestamps the error, assembles a structured ERROR_MSG, links to LGSTSQ, and optionally dumps up to 90 bytes of the raw Communication Area.
  4. Terminate via EXEC CICS RETURN (or EXEC CICS ABEND + EXEC CICS RETURN for LGUPVS01).

3. LGAPVS01 — Add New Policy Record

3.1 Purpose

LGAPVS01 adds a new insurance policy record to KSDSPOLY. It receives policy details through the Communication Area, extracts the policy type indicator from CA_REQUEST_ID[4], selects the appropriate policy-specific data fields, and issues a CICS WRITE FILE command to persist the new 64-byte record. If the write fails, it sets CA_RETURN_CODE = '80' and logs diagnostics before returning.

3.2 Processing Flow

3.3 CICS Commands

Command Purpose Key Options
EXEC CICS WRITE FILE('KSDSPOLY') Insert new 64-byte record FROM(WF_Policy_Info), LENGTH(64), RIDFLD(WF_Policy_Key), KEYLENGTH(21), RESP(WS_RESP)
EXEC CICS ASKTIME Obtain current time for error log ABSTIME(WS_ABSTIME)
EXEC CICS FORMATTIME Format timestamp MMDDYYYY(WS_DATE), TIME(WS_TIME)
EXEC CICS LINK PROGRAM('LGSTSQ') Dispatch error message COMMAREA(ERROR_MSG)
EXEC CICS RETURN Return to caller —

3.4 Response Codes

CA_RETURN_CODE Meaning
(unchanged) Write succeeded
80 CICS WRITE FILE returned non-normal response

3.5 Code Example — Write and Response Check

PLI 
EXEC CICS WRITE FILE('KSDSPOLY')
     FROM    (WF_Policy_Info)
     LENGTH  (64)
     RIDFLD  (WF_Policy_Key)
     KEYLENGTH(21)
     RESP    (WS_RESP);

IF WS_RESP ^= DFHRESP(NORMAL) THEN DO;
   WS_RESP2       = EIBRESP2;
   CA_RETURN_CODE = '80';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS RETURN;
END;

3.6 Error Handling Detail

  • The only explicit runtime validation is the CICS WRITE FILE response check.
  • On failure, WRITE_ERROR_MESSAGE captures EXEC CICS ASKTIME / EXEC CICS FORMATTIME to timestamp the error, builds an ERROR_MSG structure (date, time, customer number, RESP, RESP2, literal 'Write file KSDSPOLY'), and links to LGSTSQ.
  • If EIBCALEN > 0, up to 90 bytes of the raw Communication Area are also forwarded to LGSTSQ for context.
  • An unrecognised policy type falls to the OTHERWISE branch, which blanks WF_Policy_Text — no error is raised and the write is still attempted.

4. LGIPVS01 — Generic GTEQ Policy Browse

4.1 Purpose

LGIPVS01 performs a generic greater-than-or-equal (GTEQ) key browse against KSDSPOLY to locate the first policy record matching or following a supplied partial key. It supports two invocation modes: programmatic (via EXEC CICS LINK with a COMMAREA) and direct terminal invocation. After retrieving the record it validates that the returned record’s policy type matches the requested type, then returns a policy key or an error indicator to the caller.

4.2 Invocation Modes

COMMAREA (WS_FLAG = 'C') WS_STARTCODE starts with 'D' or WS_INVOKEPROG non-blank COMMA_DATA_TEXT + COMMA_DATA_KEY in DFHCOMMAREA Updated COMMA_DATA_TEXT + COMMA_DATA_KEY
Terminal (WS_FLAG = 'R') Neither condition above is true EXEC CICS RECEIVE into WS_RECV EXEC CICS SEND TEXT to terminal

4.5 Post-Read Validation

After the GTEQ read, both conditions are checked together:

PLI 
IF  CA_POLICY_TYPE ^= PART_KEY_TYPE
 OR WS_RESP        ^= DFHRESP(NORMAL) THEN DO;
   WRITE_MSG_TEXT    = 'Policy Bad=';
   WRITE_MSG_CUSTNUM = 13;
   WRITE_MSG_POLNUM  = 13;
END;
ELSE DO;
   WRITE_MSG_KEY_CH = CA_POLICY_TYPE || CA_CUSTOMER_NUM;
END;

The sentinel value 13 in both numeric sub-fields is a deliberate error indicator that is distinguishable from any valid customer or policy number.

4.6 Output Labels

WRITE_MSG_TEXT Meaning
'Policy Key=' Valid matching record found
'Policy Bad=' No match, type mismatch, or CICS error

5. LGUPVS01 — Read-Update / Rewrite Policy Record

5.1 Purpose

LGUPVS01 updates existing insurance policy records in KSDSPOLY. It issues a CICS READ UPDATE to lock the target record, populates the appropriate policy-type overlay from the Communication Area, then issues a CICS REWRITE to persist the change. Two distinct abend codes (LGV3 for read failure, LGV4 for rewrite failure) differentiate the two possible failure points.

5.2 Processing Flow

The flow highlights the sequential nature of the read-then-rewrite pattern. A failure at either step triggers its own distinct error path before the program terminates.

5.3 CICS Commands

Command Purpose Key Options
EXEC CICS READ FILE('KSDSPOLY') UPDATE Lock target record RIDFLD(WF_Policy_Key), KEYLENGTH(21), INTO(WS_FileIn), RESP(WS_RESP)
EXEC CICS REWRITE FILE('KSDSPOLY') Persist updated record FROM(WF_Policy_Info), LENGTH(64), RESP(WS_RESP)
EXEC CICS ABEND ABCODE('LGV3') NODUMP Signal read-phase failure —
EXEC CICS ABEND ABCODE('LGV4') NODUMP Signal rewrite-phase failure —
EXEC CICS LINK PROGRAM('LGSTSQ') Error logging COMMAREA(ERROR_MSG)
EXEC CICS RETURN Return to caller —

5.4 Return and Abend Codes

CA_RETURN_CODE Abend Code Failure Point
(unchanged) — Both operations succeeded
81 LGV3 EXEC CICS READ UPDATE returned non-normal response
82 LGV4 EXEC CICS REWRITE returned non-normal response

5.5 Code Example — Read-Update / Rewrite Pattern

PLI 
/* --- READ for UPDATE --- */
EXEC CICS READ FILE('KSDSPOLY')
     INTO      (WS_FileIn)
     LENGTH    (WS_Commarea_Len)
     RIDFLD    (WF_Policy_Key)
     KEYLENGTH (21)
     UPDATE
     RESP      (WS_RESP);

IF WS_RESP ^= DFHRESP(NORMAL) THEN DO;
   WS_RESP2       = EIBRESP2;
   CA_RETURN_CODE = '81';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS ABEND ABCODE('LGV3') NODUMP;
   EXEC CICS RETURN;
END;

/* --- REWRITE --- */
EXEC CICS REWRITE FILE('KSDSPOLY')
     FROM   (WF_Policy_Info)
     LENGTH (WS_Commarea_LenF)   /* fixed 64 */
     RESP   (WS_RESP);

IF WS_RESP ^= DFHRESP(NORMAL) THEN DO;
   WS_RESP2       = EIBRESP2;
   CA_RETURN_CODE = '82';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS ABEND ABCODE('LGV4') NODUMP;
   EXEC CICS RETURN;
END;

5.6 Key Constraints

  • CICS mandates that a REWRITE must be preceded by a successful READ UPDATE against the same file within the same CICS task. The program enforces this by aborting on any read failure before the rewrite is attempted.
  • The READ UPDATE uses the dynamic COMMAREA length (EIBCALEN) as the read length; the REWRITE always uses the fixed value 64.
  • The NODUMP option on both abend commands suppresses a full system dump, limiting diagnostic overhead to the LGSTSQ log entries.

6. LGDPVS01 — Delete Policy Record

6.1 Purpose

LGDPVS01 deletes a specific insurance policy record from KSDSPOLY by composite key. It assembles the 21-byte key from the Communication Area, issues a single CICS DELETE command, and returns silently on success. On failure it sets CA_RETURN_CODE = '81' and logs structured diagnostics before returning.

6.2 Processing Flow

The delete program has the simplest flow of the four: one key construction step, one CICS command, and then either a silent return or a structured error path.

6.5 Code Example — Delete and Response Check

     RIDFLD    (WF_Policy_Key)
     KEYLENGTH (21)
     RESP      (WS_RESP);

   CA_RETURN_CODE = '81';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS RETURN;
END;

RETURN;  /* silent success */

6.6 Error Logging Detail

WRITE_ERROR_MESSAGE constructs and dispatches two log records on failure:

  1. Primary ERROR_MSG — contains: formatted date/time, program identifier LGDPVS01, customer number, fixed text 'Delete file KSDSPOLY', primary RESP, and secondary RESP2.
  2. Supplementary CA_ERROR_MSG — contains: the literal prefix 'COMMAREA=' followed by up to 90 bytes of raw Communication Area content (exact byte count governed by EIBCALEN).
