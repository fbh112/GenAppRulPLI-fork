Customer DB2 Back-End Programs

This page documents the DB2-layer programs in the customer domain: LGACDB01 (add customer), LGACDB02 (add customer security), LGICDB01 (inquire customer), and LGUCDB01 (update customer). Together, these programs implement the DB2-facing portion of customer create, read, and update processing in a CICS/PL/I application. They use a shared COMMAREA contract, interact primarily with the DB2 CUSTOMER and CUSTOMER_SECURE tables, propagate business outcome codes through CA_RETURN_CODE, and rely on common error logging through the LGSTSQ utility.

1. Overview

The customer DB2 back-end layer is a set of CICS-linked Enterprise PL/I programs that encapsulate customer persistence operations:

  • LGACDB01 inserts a new row into the CUSTOMER table and coordinates follow-on work.
  • LGACDB02 inserts a related row into CUSTOMER_SECURE.
  • LGICDB01 retrieves a single customer profile from CUSTOMER.
  • LGUCDB01 updates an existing customer row in CUSTOMER.

At an application level, these programs share several architectural characteristics:

  • They are invoked with a pointer to a caller-supplied COMM_AREA.
  • They use CICS EIB fields such as EIBCALEN, EIBTRNID, EIBTRMID, and EIBTASKN.
  • They validate COMMAREA presence before processing.
  • They use DB2 SQLCODE as the primary technical status indicator after SQL execution.
  • They map technical outcomes into business return codes in CA_RETURN_CODE.
  • They centralize diagnostics through WRITE_ERROR_MESSAGE, which links to LGSTSQ.
  • They participate in a hybrid persistence model in which DB2 is authoritative but some flows also update VSAM peers (LGACVS01, LGUCVS01).

From a business transaction perspective, the four programs cover the core customer lifecycle supported by the DB2 back end:

  • Create customer: LGACDB01
  • Create customer security record: LGACDB02
  • Read customer: LGICDB01
  • Update customer: LGUCDB01

2. System Architecture

The customer DB2 back-end layer sits behind higher-level customer transaction logic and coordinates among CICS, DB2, shared COMMAREA structures, logging, and selected VSAM companion programs. The architecture is intentionally modular: each DB2 program owns a focused operation and exposes outcome through the same COMMAREA pattern.

graph TD A[Caller / Customer Orchestrator] --> B[Shared COMMAREA] B --> C[LGACDB01 Add Customer] B --> D[LGICDB01 Inquiry Customer] B --> E[LGUCDB01 Update Customer] C --> F[DB2 CUSTOMER] C --> G[LGACDB02 Add Customer Security] G --> H[DB2 CUSTOMER_SECURE] C --> I[LGACVS01 VSAM Add Mirror] E --> J[LGUCVS01 VSAM Update Mirror] D --> F E --> F C --> K[LGSTSQ Error Logging] D --> K E --> K G --> K C --> L[CICS Named Counter Service]

This architecture shows that LGACDB01 is the most orchestration-heavy DB2 program. It not only inserts into CUSTOMER, but also:

  • obtains a customer number from the CICS Named Counter Service when available,
  • links to LGACVS01 to mirror the add into VSAM,
  • links to LGACDB02 to create the security row.

By contrast:

  • LGICDB01 is a read-only DB2 access module,
  • LGUCDB01 updates DB2 and then mirrors the update to VSAM,
  • LGACDB02 is a focused security-record insert module.

3. Program Inventory and Responsibilities

3.1 LGACDB01 — Insert New Customer

LGACDB01 implements the end-to-end add-customer DB2 transaction. It accepts customer biographical and contact details through the COMMAREA, validates input length, derives a new customer number, inserts the customer row into DB2, returns the assigned customer number to the caller, mirrors the add to VSAM, and provisions the initial security record by linking to LGACDB02.

Primary responsibilities:

  • validate COMMAREA presence and minimum length,
  • obtain the next customer number from CICS Named Counter Service,
  • fall back to DB2 identity generation when the counter is unavailable,
  • insert the CUSTOMER row,
  • return CA_CUSTOMER_NUM,
  • link to LGACVS01,
  • build CDB2AREA and link to LGACDB02,
  • log DB2 failures through LGSTSQ.

3.2 LGACDB02 — Insert Customer Security Record

LGACDB02 inserts a row into CUSTOMER_SECURE for a newly created customer. It is designed to receive a request identifier of 02ACUS and to persist:

  • customer number,
  • password,
  • state indicator,
  • password-change count.

It is normally driven by LGACDB01, though its interface is generic enough to function as a standalone linked module for that request type.

3.3 LGICDB01 — Retrieve Customer Profile

LGICDB01 performs a singleton DB2 SELECT against the CUSTOMER table using CA_CUSTOMER_NUM as the lookup key. On success, it populates the customer details directly back into the COMMAREA. It distinguishes among:

  • success,
  • not found / resource conflict (SQLCODE 100 or -913),
  • unexpected DB2 failure,
  • invalid COMMAREA length.

3.4 LGUCDB01 — Update Customer Record

LGUCDB01 updates an existing customer in the CUSTOMER table using CA_CUSTOMER_NUM as the row selector and replacing all nine maintained customer attributes in one UPDATE statement. After the DB2 update path completes, it links to LGUCVS01 to propagate the same update to VSAM.

4. Shared Interface and Control Model

4.1 Common Invocation Pattern

All four programs are CICS-linked PL/I modules with a pointer parameter:

PLI 
LGACDB01: Proc(COMM_AREA_PTR) Options(Main);
LGACDB02: Proc(COMM_AREA_PTR) Options(Main);
LGICDB01: Proc(COMM_AREA_PTR) Options(Main);
LGUCDB01: Proc(COMM_AREA_PTR) Options(Main);

They all operate on a caller-owned COMMAREA overlaid by a shared structure defined by LGCMAREA.inc.

4.2 Common Runtime Inputs

The following CICS runtime fields are used across the documented programs:

Field Usage
EIBCALEN Validates COMMAREA presence and, where implemented, minimum length
EIBTRNID Captured into working storage for diagnostics
EIBTRMID Captured into working storage for diagnostics
EIBTASKN Captured into working storage for diagnostics

4.3 Common Error Logging Pattern

All programs implement or use a WRITE_ERROR_MESSAGE procedure pattern that:

  1. captures SQLCODE,
  2. obtains date/time with EXEC CICS ASKTIME and FORMATTIME,
  3. builds an ERROR_MSG structure,
  4. links to LGSTSQ to write the main error record,
  5. optionally writes up to 90 bytes of raw COMMAREA content via CA_ERROR_MSG.

This gives the customer DB2 layer a consistent operational support model.

5. End-to-End Data Flow

The following diagram shows how the customer create, inquiry, and update flows move through the DB2 back-end layer.

graph TD A[Caller with COMM_AREA] --> B{Requested operation} B -->|Add customer| C[LGACDB01] B -->|Inquiry customer| D[LGICDB01] B -->|Update customer| E[LGUCDB01] C --> F[Get customer number] F --> G[Insert into CUSTOMER] G --> H[Return CA_CUSTOMER_NUM] H --> I[LINK LGACVS01] I --> J[LINK LGACDB02] J --> K[Insert into CUSTOMER_SECURE] D --> L[SELECT from CUSTOMER] L --> M[Populate customer fields in COMMAREA] E --> N[UPDATE CUSTOMER] N --> O[LINK LGUCVS01] C --> P[LGSTSQ on error] D --> P E --> P J --> P

This flow highlights two important design patterns:

  • Create is multi-step and cross-resource: DB2 customer row first, then VSAM mirror, then DB2 security row.
  • Read and update are narrower: inquiry is DB2-only, while update is DB2 followed by a VSAM mirror.

6. Database Entities and Relationships

The customer DB2 back-end programs primarily operate on two tables.

graph TD A[CUSTOMER] --> B[CUSTOMER_SECURE] B --> C[Security state] B --> D[Password hash] B --> E[Password change count] A --> F[Identity / customer number] A --> G[Personal data] A --> H[Address data] A --> I[Contact data]

At a logical level:

  • CUSTOMER stores customer identity and profile data.
  • CUSTOMER_SECURE stores security credentials and status for the same customer number.
  • LGACDB01 and LGICDB01 interact with CUSTOMER.
  • LGUCDB01 updates CUSTOMER.
  • LGACDB02 inserts into CUSTOMER_SECURE.

8.1 LGACDB01 — Add Customer DB2 Back End

8.1.1 Business Function

LGACDB01 adds a new customer, assigns a system-generated customer number, persists the record in DB2, mirrors it to VSAM, and initializes the corresponding security row.

8.1.2 Key Inputs

Input Type Role

CA_LAST_NAME CHAR(20) DB2 host variable for LASTNAME

CA_POSTCODE CHAR(8) DB2 host variable for POSTCODE

Code Meaning
00 Success
98 COMMAREA shorter than 90 bytes

8.1.6 Processing Sequence

sequenceDiagram participant Caller participant LGACDB01 participant NCS as CICS Named Counter participant DB2 as DB2 CUSTOMER participant VSAM as LGACVS01 participant SEC as LGACDB02 Caller->>LGACDB01: LINK with COMM_AREA LGACDB01->>LGACDB01: Validate EIBCALEN LGACDB01->>NCS: GET COUNTER GENACUSTNUM NCS-->>LGACDB01: Customer number or failure LGACDB01->>DB2: INSERT CUSTOMER DB2-->>LGACDB01: SQLCODE LGACDB01->>VSAM: LINK LGACVS01 LGACDB01->>SEC: LINK LGACDB02 SEC-->>LGACDB01: Security insert result LGACDB01-->>Caller: Return code and customer number

This sequence is important because customer creation is not just a single insert. It is a coordinated transaction path spanning customer ID generation, DB2 insert, VSAM mirror, and security provisioning.

8.1.7 Representative Code Example

PLI 
EXEC SQL
    INSERT INTO CUSTOMER
      (CUSTOMERNUMBER, FIRSTNAME, LASTNAME, DATEOFBIRTH,
       HOUSENAME, HOUSENUMBER, POSTCODE, PHONEMOBILE,
       PHONEHOME, EMAILADDRESS)
    VALUES
      (:DB2_CUSTOMERNUM_INT, :CA_FIRST_NAME, :CA_LAST_NAME, :CA_DOB,
       :CA_HOUSE_NAME, :CA_HOUSE_NUM, :CA_POSTCODE, :CA_PHONE_MOBILE,
       :CA_PHONE_HOME, :CA_EMAIL_ADDRESS);

Fallback path:

PLI 
EXEC SQL
    INSERT INTO CUSTOMER
      (CUSTOMERNUMBER, FIRSTNAME, LASTNAME, DATEOFBIRTH,
       HOUSENAME, HOUSENUMBER, POSTCODE, PHONEMOBILE,
       PHONEHOME, EMAILADDRESS)
    VALUES
      (DEFAULT, :CA_FIRST_NAME, :CA_LAST_NAME, :CA_DOB,
       :CA_HOUSE_NAME, :CA_HOUSE_NUM, :CA_POSTCODE, :CA_PHONE_MOBILE,
       :CA_PHONE_HOME, :CA_EMAIL_ADDRESS);

8.1.8 Notable Design Detail

If the CICS Named Counter Service is unavailable, the program does not fail immediately. Instead, it allows DB2 to generate the customer number through the identity column and then recovers that value with IDENTITY_VAL_LOCAL(). This makes the add-customer path resilient to named-counter outages.

8.3.7 Representative Code Example

PLI

           HOUSENUMBER, POSTCODE, PHONEMOBILE, PHONEHOME,
           EMAILADDRESS
      INTO :CA_FIRST_NAME, :CA_LAST_NAME, :CA_DOB, :CA_HOUSE_NAME,

8.3.8 Notable Design Detail

LGICDB01 maps both SQLCODE 100 and SQLCODE -913 to CA_RETURN_CODE = '01'. That means callers cannot distinguish “customer not found” from “resource unavailable/deadlock” using only the business return code.

10. Return Code Contract Across Programs

10.1 Unified View

Program 00 01 90 98 99
LGACDB01 Success — DB2 insert failure COMMAREA too short —
LGACDB02 Success — — DB2 insert failure Unrecognized request
LGICDB01 Success Not found / -913 Unexpected DB2 error COMMAREA too short —
LGUCDB01 Success Customer not found Unexpected DB2 error — —

10.2 Interpretation Notes

  • 98 does not mean the same thing in every module:
    • in LGACDB01 and LGICDB01, it means COMMAREA length failure;
    • in LGACDB02, it means DB2 insert failure.
  • 01 also differs by module context:
    • in LGICDB01, it means not found or deadlock/timeout;
    • in LGUCDB01, it means update target row not found.
  • 99 appears only in LGACDB02 for invalid request dispatch.

11. Error Handling and Diagnostics

11.1 Common Error Categories

Across the customer DB2 back-end programs, the major error categories are:

  • missing COMMAREA (EIBCALEN = 0) → EXEC CICS ABEND ABCODE('LGCA') NODUMP
  • insufficient COMMAREA length → business return code, immediate return
  • DB2 SQL error → return code plus LGSTSQ logging
  • invalid request ID (security add only) → return code 99

11.2 Error Logging Flow

graph TD A[Program detects error] --> B[Set CA_RETURN_CODE if applicable] B --> C[Capture SQLCODE into EM_SQLRC] C --> D[EXEC CICS ASKTIME] D --> E[EXEC CICS FORMATTIME] E --> F[Populate ERROR_MSG] F --> G[LINK LGSTSQ] G --> H{EIBCALEN > 0} H -->|Yes| I[Copy up to 90 bytes of COMM_AREA_RAW] I --> J[LINK LGSTSQ with CA_ERROR_MSG] H -->|No| K[Return or ABEND] J --> K

This common diagnostic flow matters operationally because it gives support staff both:

  • a structured event record with timestamp, program name, SQL request label, and SQLCODE,
  • a raw input snapshot to help reconstruct what request failed.

11.3 ABEND Behavior

The add, security-add, inquiry, and update programs all share the same fatal entry guard:

PLI 
EXEC CICS ABEND ABCODE('LGCA') NODUMP

This occurs when no COMMAREA is passed (EIBCALEN = 0). It is a hard failure path rather than a business return.

12. Operational Constraints and Behavioral Notes

12.1 COMMAREA Constraints

  • LGACDB01 and LGICDB01 require a minimum COMMAREA length of 90 bytes.
  • All programs assume a maximum raw COMMAREA size of 32,500 bytes.
  • Logged COMMAREA diagnostic data is capped at 90 bytes.

12.2 Data Constraints

  • CA_CUSTOMER_NUM is treated as a 10-digit picture field.
  • CA_CUSTSECR_PASS is limited to 32 characters.
  • CA_CUSTSECR_COUNT must be convertible to an integer in LGACDB02.
  • Customer profile fields are fixed-length and may be padded or truncated based on host-variable definitions.

12.3 Sequencing Constraints

  • In create flow, customer number generation precedes insert.
  • In create flow, DB2 customer insert precedes VSAM mirror and security insert.
  • In update flow, DB2 update precedes VSAM mirror.
  • In inquiry flow, COMMAREA validation always precedes DB2 access.

12.4 Consistency Model

The application uses a dual-write pattern in create and update scenarios:

  • DB2 is updated,
  • then a VSAM companion module is linked.

This means consistency across DB2 and VSAM is maintained procedurally rather than through a single storage engine.

13.1 Create, Read, Update Coverage

13.2 Architectural Characterization

  • LGACDB01 is a transaction coordinator for add-customer.
  • LGACDB02 is a specialized security persistence module.
  • LGICDB01 is a read-only query module.
  • LGUCDB01 is an update-plus-mirror module.

15. Summary

The customer DB2 back-end programs form a cohesive persistence layer for customer lifecycle processing in a CICS/DB2 application. LGACDB01 and LGACDB02 implement customer creation and security provisioning, LGICDB01 handles profile retrieval, and LGUCDB01 applies profile updates. Across all four modules, the design is characterized by:

  • shared COMMAREA-based interfaces,
  • DB2 host-variable binding from fixed-format customer fields,
  • consistent use of CICS runtime metadata for diagnostics,
  • business return-code signaling through CA_RETURN_CODE,
  • centralized operational logging through LGSTSQ,
  • selective coordination with VSAM mirror programs.

Taken together, these programs represent the application-level DB2 back-end contract for the customer domain.
