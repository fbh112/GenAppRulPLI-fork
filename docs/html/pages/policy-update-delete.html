Policy Update & Delete Programs

1. Overview

The GenApp insurance system provides a dedicated set of CICS-hosted PL/I programs for updating and deleting insurance policy records stored in DB2. These programs follow a consistent two-tier architecture: a front-end orchestrator that validates incoming requests and routes them appropriately, and a back-end database worker that performs the actual SQL operations.

Four programs form this subsystem:

Program Role Policy Operations
LGUPOL01 Update front-end / orchestrator Endowment (01UEND), House (01UHOU), Motor (01UMOT)
LGUPDB01 Update DB2 back-end with optimistic locking Endowment, House, Motor
LGDPOL01 Delete front-end / orchestrator Endowment (01DEND), House (01DHOU), Commercial (01DCOM), Motor (01DMOT)
LGDPDB01 Delete DB2 back-end with referential integrity cascade Endowment, House, Commercial, Motor

All four programs share a common COMMAREA contract defined in LGCMAREA.inc, use the LGSTSQ utility for structured error logging to a CICS Transient Data Queue (TDQ), and follow the same guard-then-delegate pattern: validate COMMAREA presence and length first, identify the policy type via CA_REQUEST_ID, then delegate the database work downstream.

2. System Architecture

The subsystem fits into the broader GenApp CICS application as follows. A calling menu program (e.g., LGTESTP1–LGTESTP4) populates a COMMAREA and issues an EXEC CICS LINK to either the update or delete front-end. The front-end validates the request and links to the appropriate DB2 back-end. The DB2 back-end performs all SQL work and then calls a VSAM synchronisation program (LGUPVS01 / LGDPVS01) to keep both storage tiers consistent.

The architecture enforces a strict separation of concerns:

  • Front-end programs (LGUPOL01, LGDPOL01) handle CICS interfacing, COMMAREA validation, and policy-type routing. They contain no SQL.
  • Back-end programs (LGUPDB01, LGDPDB01) contain all SQL logic, concurrency controls, and transactional error handling.
  • VSAM sync programs (LGUPVS01, LGDPVS01) maintain parity between DB2 and VSAM stores.
  • LGSTSQ provides a shared, consistent error-logging channel writing to the CICS TDQ.

3. Policy Update Programs

3.1 LGUPOL01 — Update Front-End

3.1.1 Purpose

LGUPOL01 is the CICS-hosted PL/I orchestrator for policy update requests. It receives a COMMAREA identifying the policy type to update, validates the COMMAREA length against the required minimum for that type, and delegates the actual DB2 update to LGUPDB01 via EXEC CICS LINK. It handles three policy types: Endowment (01UEND), House (01UHOU), and Motor (01UMOT).

3.1.2 Processing Flow

3.1.3 COMMAREA Minimum Length Requirements

LGUPOL01 enforces a minimum COMMAREA size per policy type before delegating to the DB2 back-end. The header is always 28 bytes.

CA_REQUEST_ID Policy Type Header (bytes) Data (bytes) Minimum Total
01UEND Endowment 28 124 152
01UHOU House 28 130 158
01UMOT Motor 28 137 165

If the received COMMAREA is shorter than the required minimum, CA_RETURN_CODE is set to '98' and the program returns immediately — LGUPDB01 is never called.

3.1.4 Return Codes

Code Meaning
'00' Success — request delegated to LGUPDB01
'98' COMMAREA too short for the requested policy type
'99' Unrecognised CA_REQUEST_ID

3.1.5 Key Code Example — Policy Type Routing

The core routing logic in LGUPOL01 uses a PL/I SELECT statement. If the COMMAREA is sufficiently long, UPDATE_POLICY_DB2_INFO is called; if not, return code 98 is set and control is returned immediately.

PLI 
SELECT (CA_REQUEST_ID);
  WHEN ('01UEND')
    DO;
      WS_REQUIRED_CA_LEN = WS_CA_HEADER_LEN + WS_FULL_ENDOW_LEN; /* 28 + 124 = 152 */
      IF EIBCALEN < WS_REQUIRED_CA_LEN THEN
        DO;
          CA_RETURN_CODE = '98';
          EXEC CICS RETURN;
        END;
    END;
  WHEN ('01UHOU')
    DO;
      WS_REQUIRED_CA_LEN = WS_CA_HEADER_LEN + WS_FULL_HOUSE_LEN; /* 28 + 130 = 158 */
      IF EIBCALEN < WS_REQUIRED_CA_LEN THEN
        DO;
          CA_RETURN_CODE = '98';
          EXEC CICS RETURN;
        END;
    END;
  WHEN ('01UMOT')
    DO;
      WS_REQUIRED_CA_LEN = WS_CA_HEADER_LEN + WS_FULL_MOTOR_LEN; /* 28 + 137 = 165 */
      IF EIBCALEN < WS_REQUIRED_CA_LEN THEN
        DO;
          CA_RETURN_CODE = '98';
          EXEC CICS RETURN;
        END;
    END;
  OTHERWISE
    CA_RETURN_CODE = '99';
END;
CALL UPDATE_POLICY_DB2_INFO;
EXEC CICS RETURN;

Note: The OTHERWISE branch (return code '99') does not issue an early EXEC CICS RETURN. Execution falls through to CALL UPDATE_POLICY_DB2_INFO, allowing the downstream program to also apply its own validation. Only the '98' path returns early.

3.2 LGUPDB01 — Update DB2 Back-End

3.2.1 Purpose

LGUPDB01 is the DB2 back-end program for persisting policy updates. It implements an optimistic locking strategy using a SELECT FOR UPDATE cursor on the POLICY table to detect concurrent modifications before applying any changes. After a successful update to the policy-type-specific table (ENDOWMENT, HOUSE, or MOTOR), it updates the main POLICY table with a new LASTCHANGED timestamp, then calls LGUPVS01 to synchronise the VSAM store.

3.2.2 Optimistic Locking and Processing Flow

The optimistic locking mechanism is the defining feature of LGUPDB01. When a user retrieves a policy for editing, the LASTCHANGED timestamp is returned as part of the record. When the user submits their changes, that timestamp is passed back in CA_LASTCHANGED. LGUPDB01 fetches the current timestamp from DB2 and compares them — if they differ, another user has modified the record in the interim and the update is rejected with return code '02'.

3.2.5 Key Code Example — Optimistic Locking and Positioned Update

PLI 
/* Fetch the current row and compare timestamps */
CALL FETCH_DB2_POLICY_ROW;

IF SQLCODE = 0 THEN
  DO;
    IF CA_LASTCHANGED = DB2_LASTCHANGED THEN   /* Timestamps match — safe to update */
      DO;
        /* Update the type-specific table first */
        SELECT (CA_REQUEST_ID);
          WHEN ('01UEND') CALL UPDATE_ENDOW_DB2_INFO;
          WHEN ('01UHOU') CALL UPDATE_HOUSE_DB2_INFO;
          WHEN ('01UMOT') CALL UPDATE_MOTOR_DB2_INFO;
        END;

        IF CA_RETURN_CODE ^= '00' THEN
          DO;
            CALL CLOSE_PCURSOR;
            EXEC CICS RETURN;
          END;

        /* Update the POLICY header with a fresh timestamp */
        EXEC SQL UPDATE POLICY
          SET ISSUEDATE         = :CA_ISSUE_DATE,
              EXPIRYDATE        = :CA_EXPIRY_DATE,
              LASTCHANGED       = CURRENT TIMESTAMP,
              BROKERID          = :DB2_BROKERID_INT,
              BROKERSREFERENCE  = :CA_BROKERSREF
          WHERE CURRENT OF POLICY_CURSOR;

        /* Retrieve the new timestamp for the caller */
        EXEC SQL SELECT LASTCHANGED INTO :CA_LASTCHANGED
          FROM POLICY
          WHERE POLICYNUMBER = :DB2_POLICYNUM_INT;

        IF SQLCODE ^= 0 THEN
          DO;
            EXEC CICS SYNCPOINT ROLLBACK;
            CA_RETURN_CODE = '90';
            CALL WRITE_ERROR_MESSAGE;
          END;
      END;
    ELSE
      CA_RETURN_CODE = '02';   /* Concurrent update — reject */
  END;

4. Policy Delete Programs

4.1 LGDPOL01 — Delete Front-End

4.1.1 Purpose

LGDPOL01 is the CICS-hosted PL/I orchestrator for policy delete requests. It validates the incoming COMMAREA, normalises the CA_REQUEST_ID to uppercase, routes the request to LGDPDB01 via EXEC CICS LINK, and returns a standardised result to the caller. It supports four policy types: Endowment (01DEND), House (01DHOU), Commercial (01DCOM), and Motor (01DMOT) — one more type than the update path.

4.2 LGDPDB01 — Delete DB2 Back-End

4.2.1 Purpose

LGDPDB01 is the DB2 back-end program for policy deletion. It executes a single DELETE FROM POLICY statement keyed on customer and policy numbers. The delete propagates to the type-specific child table (ENDOWMENT, HOUSE, MOTOR, or COMMERCIAL) automatically via DB2 referential integrity cascade rules — no explicit child-table deletes are coded. After a successful DB2 delete, it calls LGDPVS01 to remove the same policy from the VSAM file store.

4.2.2 Processing Flow

4.2.3 DB2 Referential Integrity Cascade

LGDPDB01 deletes only from the parent POLICY table. The child tables are cleaned up automatically by DB2:

Deleting a single row from POLICY automatically removes the associated row in whichever child table (ENDOWMENT, HOUSE, MOTOR, or COMMERCIAL) holds the policy-type-specific data. This is enforced by the DB2 schema’s foreign key definitions — LGDPDB01 itself issues no SQL against the child tables.

4.2.4 Return Codes

Code Meaning
'00' Successful deletion
'90' DB2 error during DELETE FROM POLICY
'98' COMMAREA too small (< 28 bytes)
'99' Unrecognised CA_REQUEST_ID

Note: SQLCODE = 100 (row not found) is treated as a successful outcome — the end state (policy absent) is the same regardless of whether the row existed before the delete was issued.

4.2.5 Key Code Example — DB2 Delete with Cascade

PLI 
DELETE_POLICY_DB2_INFO: PROCEDURE;
    EM_SQLREQ = ' DELETE POLICY  ';

    EXEC SQL
      DELETE FROM POLICY
      WHERE (CUSTOMERNUMBER = :DB2_CUSTOMERNUM_INT
        AND  POLICYNUMBER   = :DB2_POLICYNUM_INT);

    /* SQLCODE 0 = success; SQLCODE 100 = row not found (also acceptable)     */
    /* DB2 FK cascade automatically removes the child ENDOWMENT/HOUSE/MOTOR/  */
    /* COMMERCIAL row — no additional DELETE statements are required.          */
    IF SQLCODE ^= 0 THEN
      DO;
        CA_RETURN_CODE = '90';
        CALL WRITE_ERROR_MESSAGE;
        EXEC CICS RETURN;
      END;

END DELETE_POLICY_DB2_INFO;

5.2 Error Logging — WRITE_ERROR_MESSAGE and LGSTSQ

Each program implements a WRITE_ERROR_MESSAGE internal procedure that follows an identical pattern. It is invoked on any error condition requiring diagnostic output:

  1. Capture SQLCODE into EM_SQLRC.
  2. Call EXEC CICS ASKTIME ABSTIME(WS_ABSTIME) to obtain the current absolute time.
  3. Call EXEC CICS FORMATTIME to produce a human-readable date (MMDDYYYY) and time (HH:MM:SS).
  4. Populate the ERROR_MSG structure with date, time, program name, customer number, policy number, SQL operation label, and SQLCODE.
  5. Issue EXEC CICS LINK PROGRAM('LGSTSQ') COMMAREA(ERROR_MSG) to write the formatted message to the TDQ.
  6. Conditionally log up to 90 bytes of the raw COMMAREA for additional context:
    • If EIBCALEN is between 1 and 90: log exactly EIBCALEN bytes.
    • If EIBCALEN >= 91: log the first 90 bytes using the PL/I LEFT built-in.
PLI 
WRITE_ERROR_MESSAGE: PROCEDURE;
    EM_SQLRC = SQLCODE;
    EXEC CICS ASKTIME ABSTIME(WS_ABSTIME);
    EXEC CICS FORMATTIME ABSTIME(WS_ABSTIME)
                         MMDDYYYY(WS_DATE)
                         TIME(WS_TIME);
    EM_DATE = WS_DATE;
    EM_TIME = WS_TIME;

    EXEC CICS LINK PROGRAM('LGSTSQ')
        COMMAREA(ERROR_MSG)
        LENGTH(STG(ERROR_MSG));

    IF EIBCALEN > 0 THEN
      DO;
        IF EIBCALEN < 91 THEN
          CA_DATA = LEFT(COMM_AREA_RAW, EIBCALEN);
        ELSE
          CA_DATA = LEFT(COMM_AREA_RAW, 90);

        EXEC CICS LINK PROGRAM('LGSTSQ')
            COMMAREA(CA_ERROR_MSG)
            LENGTH(STG(CA_ERROR_MSG));
      END;
END WRITE_ERROR_MESSAGE;

5.3 CICS Abend on Missing COMMAREA

All four programs apply the same guard at entry. If EIBCALEN = 0 (no COMMAREA passed), the program logs an error message and issues:

PLI 
EXEC CICS ABEND ABCODE('LGCA') NODUMP;

The NODUMP option suppresses a system transaction dump, keeping the failure lightweight while still producing an identifiable abend code (LGCA) visible in the CICS transaction log and the CSMT queue.

6. End-to-End Examples

6.1 Example: Successful Motor Policy Update

A caller submits a motor policy update with a fully populated COMMAREA (EIBCALEN = 200).

Step Program Action Result
1 LGUPOL01 Checks EIBCALEN (200 ≥ 165) Length OK
2 LGUPOL01 Routes CA_REQUEST_ID = '01UMOT' Matches
3 LGUPOL01 Links to LGUPDB01 Control transferred
4 LGUPDB01 Opens POLICY_CURSOR FOR UPDATE SQLCODE 0
5 LGUPDB01 Fetches row, compares CA_LASTCHANGED Timestamps match
6 LGUPDB01 Calls UPDATE_MOTOR_DB2_INFO MOTOR table updated
7 LGUPDB01 Updates POLICY table with CURRENT TIMESTAMP SQLCODE 0
8 LGUPDB01 Selects new LASTCHANGED back into COMMAREA Caller gets new token
9 LGUPDB01 Links to LGUPVS01 VSAM synced
10 LGUPOL01 EXEC CICS RETURN CA_RETURN_CODE = '00'

6.2 Example: Concurrent Update Rejected

A user submits an update but another user has modified the same policy in the interim.

Step Program Action Result
1 LGUPDB01 Fetches row from DB2 DB2_LASTCHANGED = '2024-01-15-12.00.00'
2 LGUPDB01 Compares with CA_LASTCHANGED = '2024-01-15-09.00.00' Mismatch
3 LGUPDB01 Sets CA_RETURN_CODE = '02' No update performed
4 LGUPDB01 Closes cursor, returns CA_RETURN_CODE = '02'

6.3 Example: Successful Motor Policy Deletion with Cascade

A caller requests deletion of a motor policy.

Step Program Action Result
1 LGDPOL01 Checks EIBCALEN (≥ 28) Length OK
2 LGDPOL01 Normalises CA_REQUEST_ID via UPPERCASE() '01DMOT'
3 LGDPOL01 Routes to DELETE_POLICY_DB2_INFO Links to LGDPDB01
4 LGDPDB01 DELETE FROM POLICY WHERE CUSTOMERNUMBER=x AND POLICYNUMBER=y SQLCODE 0
5 DB2 FK cascade fires — deletes matching MOTOR row Automatic
6 LGDPDB01 Links to LGDPVS01 VSAM record removed
7 LGDPOL01 EXEC CICS RETURN CA_RETURN_CODE = '00'
