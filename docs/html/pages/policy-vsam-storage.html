Policy VSAM Storage Services

1. Overview

Policy VSAM Storage Services is a set of four CICS PL/I programs that maintain the insurance policy store held in the VSAM KSDS file KSDSPOLY. Together they cover the full record lifecycle:

Program Operation CICS file command Failure return code
LGAPVS01 Create (add) a policy record WRITE FILE 80
LGIPVS01 Generic browse by partial key READ FILE ... GENERIC GTEQ Sentinel Policy Bad= / 13 (no CA_RETURN_CODE)
LGUPVS01 Read-for-update, then rewrite READ ... UPDATE, REWRITE 81 (read), 82 (rewrite)
LGDPVS01 Delete a policy record DELETE FILE 81

All four programs share these conventions:

  • Composite 21-byte key. The key is a 1-byte policy type, a 10-byte customer number and a 10-byte policy number. The type is the 4th character of CA_REQUEST_ID.
  • Four policy types. Commercial (C), Endowment (E), House (H) and Motor (M) share one fixed 64-byte record layout. Their type-specific data overlays a common 43-byte area.
  • Common error handling. The programs test RESP against DFHRESP(NORMAL). On failure they set a return code and log diagnostics through the LGSTSQ logging program.
  • COMMAREA-driven interface. Callers pass a COMM_AREA (layout from the LGCMAREA include). LGAPVS01, LGUPVS01 and LGDPVS01 receive it as COMM_AREA_PTR. LGIPVS01 uses its own DFHCOMMAREA layout. The caller is typically the policy orchestrator, for example LGAPOL01.

These programs only touch VSAM. They issue no SQL, so none of them accesses a Db2 table.

3. KSDSPOLY Data Model

3.1 Composite Key and Record Layout

Every record is 64 bytes: a 21-byte key followed by 43 bytes of policy-type-specific data.

Segment Field Length Source
Key WF_REQUEST_ID 1 4th character of CA_REQUEST_ID (C, E, H, M)
Key WF_CUSTOMER_NUM 10 CA_CUSTOMER_NUM
Key WF_POLICY_NUM 10 CA_POLICY_NUM
Data WF_POLICY_DATA (UNION) 43 One of the four policy overlays

3.2 Policy-Type Overlays

erDiagram KSDSPOLY_RECORD ||--|| WF_POLICY_KEY : "has key" KSDSPOLY_RECORD ||--|| WF_POLICY_DATA : "has data (UNION)" WF_POLICY_DATA ||--o| COMMERCIAL : "type C" WF_POLICY_DATA ||--o| ENDOWMENT : "type E" WF_POLICY_DATA ||--o| HOUSE : "type H" WF_POLICY_DATA ||--o| MOTOR : "type M" WF_POLICY_KEY { char WF_REQUEST_ID "1 byte" char WF_CUSTOMER_NUM "10 bytes" char WF_POLICY_NUM "10 bytes" } COMMERCIAL { char WF_B_POSTCODE "8" num WF_B_STATUS "status code" char WF_B_CUSTOMER "31" } ENDOWMENT { char WF_E_WITH_PROFITS "1" char WF_E_EQUITIES "1" char WF_E_MANAGED_FUND "1" char WF_E_FUND_NAME "10" char WF_E_LIFE_ASSURED "30" } HOUSE { char WF_H_PROPERTY_TYPE "15" num WF_H_BEDROOMS "3 digits" num WF_H_VALUE "8 digits" char WF_H_POSTCODE "8" char WF_H_HOUSE_NAME "stored width less than COMMAREA" } MOTOR { char WF_M_MAKE "15" char WF_M_MODEL "15" num WF_M_VALUE "6 digits" char WF_M_REGNUMBER "7" }

Only the overlay that matches the policy type is populated. Because the data area is a UNION, all four overlays share the same storage.

3.3 Field Truncation on Assignment

COMMAREA fields are wider than their record counterparts in places. PL/I truncates silently on assignment:

COMMAREA field Record field Effect
CA_B_Customer (255) WF_B_Customer (31) Truncated to 31 characters
CA_E_LIFE_ASSURED (31) WF_E_LIFE_ASSURED (30) Truncated to 30 characters
CA_H_HOUSE_NAME (20) WF_H_HOUSE_NAME (narrower) Only the leading characters are retained; the update program’s documentation gives 9

4. Policy Creation — LGAPVS01

4.1 Purpose

LGAPVS01 adds a new policy record. It extracts the policy type, builds the key, copies the matching policy data and issues EXEC CICS WRITE FILE('KSDSPOLY').

4.2 Processing Flow

flowchart TD A([Start]) --> B[Save EIBCALEN
Build WF_Request_ID, WF_Customer_Num, WF_Policy_Num] B --> C{WF_Request_ID} C -- C --> D[Copy commercial data] C -- E --> E1[Copy endowment data] C -- H --> F[Copy house data] C -- M --> G[Copy motor data] C -- Other --> H[Blank WF_Policy_Text] D --> I[Reassign WF_Policy_Num] E1 --> I F --> I G --> I H --> I I --> J[EXEC CICS WRITE FILE KSDSPOLY] J --> K{RESP = NORMAL} K -- Yes --> L([RETURN]) K -- No --> M[WS_RESP2 = EIBRESP2
CA_RETURN_CODE = 80] M --> N[WRITE_ERROR_MESSAGE] N --> O([EXEC CICS RETURN])

4.3 Key Behaviours

  • The policy type comes only from the 4th character of CA_REQUEST_ID.
  • An unrecognised type is not rejected. The OTHERWISE branch blanks WF_Policy_Text and the write still happens, so the record holds only its key.
  • WF_Policy_Num is assigned a second time just before the write.
  • Success leaves CA_RETURN_CODE untouched.
  • On failure the program sets CA_RETURN_CODE = '80', logs the error and returns without abending.

4.4 Code Example

The write command, as described for the program:

PLI 
EXEC CICS WRITE FILE('KSDSPOLY')
     FROM(WF_Policy_Info)
     LENGTH(64)
     RIDFLD(WF_Policy_Key)
     KEYLENGTH(21)
     RESP(WS_RESP);

IF (WS_RESP ^= DFHRESP(NORMAL)) THEN DO;
   WS_RESP2 = EIBRESP2;
   CA_RETURN_CODE = '80';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS RETURN;
END;

The type dispatch that precedes it:

PLI 
WF_Request_ID   = SUBSTR(CA_Request_ID,4,1);
WF_Policy_Num   = CA_Policy_Num;
WF_Customer_Num = CA_Customer_Num;

SELECT (WF_Request_ID);
   WHEN ('C') ... /* copy CA_B_Postcode, CA_B_Status, CA_B_Customer */
   WHEN ('E') ... /* copy flags, fund name, life assured */
   WHEN ('H') ... /* copy property type, bedrooms, value, postcode, name */
   WHEN ('M') ... /* copy make, model, value, registration */
   OTHERWISE  WF_Policy_Text = ' ';
END;

5. Generic Browse — LGIPVS01

5.1 Purpose

LGIPVS01 finds the first policy at or after a partial key. It is the only program in the group that supports two invocation modes:

  • LINK mode (WS_FLAG = 'C'). The program is called with a DFHCOMMAREA and returns its result in the same area.
  • Terminal mode (WS_FLAG = 'R'). The program receives typed input and sends the result back to the screen.

5.2 Processing Flow

graph TD A([Start]) --> B[Clear WS_RECV
ASSIGN SYSID, STARTCODE, INVOKINGPROG] B --> C{STARTCODE starts with D
or INVOKINGPROG not blank} C -- Yes --> D[WS_FLAG = C
WS_COMMAREA = text and key
WS_RECV_LEN = 10] C -- No --> E[EXEC CICS RECEIVE
WS_FLAG = R
WS_COMMAREA = WS_RECV_DATA
WS_RECV_LEN reduced by 6] D --> F[Clear CA_AREA
Build PART_KEY type and number] E --> F F --> G[READ FILE KSDSPOLY
GENERIC GTEQ, KEYLENGTH 11] G --> H{Type mismatch
or RESP not NORMAL} H -- Yes --> I[Policy Bad=
CUSTNUM and POLNUM = 13] H -- No --> J[Policy Key=
type + customer number] I --> K{WS_FLAG = R} J --> K K -- Yes --> L[SEND TEXT to terminal] K -- No --> M[Write result back to COMMAREA] L --> N([RETURN]) M --> N

5.3 Key Behaviours

  • Partial key. PART_KEY is 11 bytes: PART_KEY_TYPE (1) and PART_KEY_NUM (10 digits).
  • Single read. The program issues one GENERIC GTEQ read. There is no iterative browse. If the record returned has a different type from the one requested, the result is a failure.
  • Two checks decide success. Both WS_RESP = DFHRESP(NORMAL) and a policy-type match are needed.
  • Failure sentinel. The output label is Policy Bad= and both numeric subfields are 13.
  • Success output. The key is CA_POLICY_TYPE || CA_CUSTOMER_NUM, which is 11 of the 21 key characters.
  • Result channel. In terminal mode the 80-byte WRITE_MSG is sent. In LINK mode COMMA_DATA_TEXT and COMMA_DATA_KEY are overwritten in the caller’s COMMAREA.
  • No CA_RETURN_CODE. The result is carried entirely in the message text and key.

5.4 Code Example

PLI 
EXEC CICS READ FILE('KSDSPOLY')
     INTO(CA_AREA)
     LENGTH(F64)
     RIDFLD(PART_KEY)
     KEYLENGTH(F11)
     GENERIC
     GTEQ
     RESP(WS_RESP);

IF (CA_POLICY_TYPE ^= PART_KEY_TYPE) | (WS_RESP ^= DFHRESP(NORMAL)) THEN DO;
   WRITE_MSG_TEXT    = 'Policy Bad=';
   WRITE_MSG_CUSTNUM = 13;
   WRITE_MSG_POLNUM  = 13;
END;
ELSE
   WRITE_MSG_KEY_CH = CA_POLICY_TYPE || CA_CUSTOMER_NUM;

Response dispatch:

PLI 
IF WS_FLAG = 'R' THEN
   EXEC CICS SEND TEXT FROM(WRITE_MSG) TERMINAL WAIT ERASE LENGTH(80) FREEKB;
ELSE DO;
   COMMA_DATA      = ' ';
   COMMA_DATA_TEXT = WRITE_MSG_TEXT;
   COMMA_DATA_KEY  = WRITE_MSG_KEY_CH;
END;
EXEC CICS RETURN;

6. Read-for-Update and Rewrite — LGUPVS01

6.1 Purpose

LGUPVS01 updates an existing policy. It populates the working record from the COMMAREA, reads the target record with UPDATE to lock it, and rewrites it.

6.2 Processing Flow

graph TD A([Start]) --> B[Save EIBCALEN
Build key fields] B --> C{WF_Request_ID} C -- C / E / H / M --> D[Map policy-specific fields] C -- Other --> E[Blank WF_Policy_Text] D --> F[Reassign WF_Policy_Num] E --> F F --> G[READ FILE KSDSPOLY UPDATE
RIDFLD WF_Policy_Key, KEYLENGTH 21] G --> H{RESP = NORMAL} H -- No --> I[CA_RETURN_CODE = 81
WRITE_ERROR_MESSAGE
ABEND LGV3 NODUMP] H -- Yes --> J[REWRITE FILE KSDSPOLY
FROM WF_Policy_Info, LENGTH 64] J --> K{RESP = NORMAL} K -- No --> L[CA_RETURN_CODE = 82
WRITE_ERROR_MESSAGE
ABEND LGV4 NODUMP] K -- Yes --> M([RETURN])

6.3 Key Behaviours

  • Lock then rewrite. READ UPDATE must succeed before REWRITE. The program enforces this by abending with LGV3 on a read failure, so the rewrite is never reached.
  • Distinct codes. Return code 81 and abend LGV3 identify a read failure. Return code 82 and abend LGV4 identify a rewrite failure. Both abends use NODUMP.
  • Fixed rewrite length. The rewrite writes 64 bytes from WF_Policy_Info.
  • Input buffer. The existing record is read into WS_FileIn, a 1024-byte buffer, using the COMMAREA length as the read length.
  • Unknown types. An unrecognised type is not rejected. The data area is blanked and the update proceeds.

6.4 Code Example

PLI 
EXEC CICS READ FILE('KSDSPOLY')
     INTO(WS_FileIn)
     LENGTH(WS_Commarea_Len)
     RIDFLD(WF_Policy_Key)
     KEYLENGTH(21)
     UPDATE
     RESP(WS_RESP);

IF (WS_RESP ^= DFHRESP(NORMAL)) THEN DO;
   WS_RESP2 = EIBRESP2;
   CA_RETURN_CODE = '81';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS ABEND ABCODE('LGV3') NODUMP;
   EXEC CICS RETURN;
END;

EXEC CICS REWRITE FILE('KSDSPOLY')
     FROM(WF_Policy_Info)
     LENGTH(WS_Commarea_LenF)   /* initialised to 64 */
     RESP(WS_RESP);

IF (WS_RESP ^= DFHRESP(NORMAL)) THEN DO;
   WS_RESP2 = EIBRESP2;
   CA_RETURN_CODE = '82';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS ABEND ABCODE('LGV4') NODUMP;
   EXEC CICS RETURN;
END;

6.5 Update Sequence

sequenceDiagram participant Caller participant LGUPVS01 participant KSDSPOLY participant LGSTSQ Caller->>LGUPVS01: COMMAREA with updated policy data LGUPVS01->>KSDSPOLY: READ UPDATE (lock record) alt Read OK KSDSPOLY-->>LGUPVS01: Existing record LGUPVS01->>KSDSPOLY: REWRITE 64-byte record alt Rewrite OK LGUPVS01-->>Caller: RETURN else Rewrite fails LGUPVS01->>LGSTSQ: Log error, code 82 LGUPVS01-->>Caller: ABEND LGV4 end else Read fails (e.g. NOTFND) LGUPVS01->>LGSTSQ: Log error, code 81 LGUPVS01-->>Caller: ABEND LGV3 end

7. Deletion — LGDPVS01

7.1 Purpose

LGDPVS01 is the VSAM-side delete. It builds the 21-byte key and issues a keyed DELETE. It is the VSAM counterpart of the Db2-based LGDPDB01.

7.2 Processing Flow

graph TD A([Start]) --> B[WS_Commarea_Len = EIBCALEN] B --> C[Build WF_Policy_Key
type + customer + policy] C --> D[EXEC CICS DELETE FILE KSDSPOLY
RIDFLD WF_Policy_Key KEYLENGTH 21] D --> E{RESP = NORMAL} E -- Yes --> F([RETURN]) E -- No --> G[WS_RESP2 = EIBRESP2
CA_RETURN_CODE = 81] G --> H[WRITE_ERROR_MESSAGE] H --> I([EXEC CICS RETURN])

7.3 Key Behaviours

  • The delete is key-based only. There is no browse, generic access or retry.
  • Success writes no log entry and leaves CA_RETURN_CODE unchanged.
  • Any non-normal response sets CA_RETURN_CODE = '81'.
  • The program logs the customer number and both RESP codes. EM_POLNUM exists in the error structure, but the code does not assign it before the log call, so the logged policy number may be blank.
  • The program does not check EIBCALEN before reading the COMMAREA fields.

7.4 Code Example

PLI 
WF_Request_ID   = SUBSTR(CA_Request_ID,4,1);
WF_Policy_Num   = CA_Policy_Num;
WF_Customer_Num = CA_Customer_Num;

EXEC CICS DELETE FILE('KSDSPOLY')
     RIDFLD(WF_Policy_Key)
     KEYLENGTH(21)
     RESP(WS_RESP);

IF (WS_RESP <> DFHRESP(NORMAL)) THEN DO;
   WS_RESP2 = EIBRESP2;
   CA_RETURN_CODE = '81';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS RETURN;
END;
RETURN;

8. Shared Error Logging

8.1 WRITE_ERROR_MESSAGE Procedure

LGAPVS01, LGUPVS01 and LGDPVS01 each contain an internal WRITE_ERROR_MESSAGE procedure that works the same way:

  1. EXEC CICS ASKTIME obtains the absolute time. EXEC CICS FORMATTIME produces WS_DATE (MMDDYYYY) and WS_TIME.
  2. It fills ERROR_MSG with EM_DATE, EM_TIME, EM_CUSNUM, EM_RESPRC (from WS_RESP) and EM_RESP2RC (from WS_RESP2). The structure also carries the program identifier and an operation literal such as Write file KSDSPOLY, Re-write KSDSPOLY or Delete file KSDSPOLY.
  3. It links to LGSTSQ with ERROR_MSG.
  4. If EIBCALEN > 0, it copies up to 90 bytes of COMM_AREA_RAW into CA_DATA. It copies EIBCALEN bytes if that is fewer than 91, otherwise the first 90. It then links to LGSTSQ again with CA_ERROR_MSG, which is prefixed with COMMAREA=.
flowchart TD S([WRITE_ERROR_MESSAGE]) --> T[ASKTIME and FORMATTIME] T --> U[Populate ERROR_MSG] U --> V[LINK LGSTSQ with ERROR_MSG] V --> W{EIBCALEN greater than 0} W -- No --> Z([Return]) W -- Yes --> X{EIBCALEN less than 91} X -- Yes --> Y1[CA_Data = LEFT COMM_AREA_RAW, EIBCALEN] X -- No --> Y2[CA_Data = LEFT COMM_AREA_RAW, 90] Y1 --> Q[LINK LGSTSQ with CA_ERROR_MSG] Y2 --> Q Q --> Z

8.2 Code Example

PLI 
EXEC CICS ASKTIME ABSTIME(WS_ABSTIME);
EXEC CICS FORMATTIME ABSTIME(WS_ABSTIME)
     MMDDYYYY(WS_DATE) TIME(WS_TIME);

EM_Cusnum  = CA_Customer_Num;
EM_RespRC  = WS_RESP;
EM_Resp2RC = WS_RESP2;

EXEC CICS LINK PROGRAM('LGSTSQ')
     COMMAREA(ERROR_MSG)
     LENGTH(STG(ERROR_MSG));

IF (EIBCALEN > 0) THEN DO;
   IF (EIBCALEN < 91) THEN CA_Data = LEFT(COMM_AREA_RAW,EIBCALEN);
   ELSE                    CA_Data = LEFT(COMM_AREA_RAW,90);
   EXEC CICS LINK PROGRAM('LGSTSQ') COMMAREA(CA_ERROR_MSG) ...;
END;

LGIPVS01 does not use this mechanism. It reports failure only through its response message.

10. Constraints and Design Considerations

10.1 Key and Record Constraints

  • The key is always 21 bytes (KEYLENGTH(21)). Only the browse program uses an 11-byte generic key.
  • The record length is fixed at 64 bytes, which is a 21-byte key plus a 43-byte data area.
  • All programs hard-code the file name KSDSPOLY.
  • CA_CUSTOMER_NUM and CA_POLICY_NUM are 10-digit numeric pictures. They are used as character bytes in the key.

10.2 Input Validation

  • The policy type is not validated. Anything other than C, E, H or M produces a blank data area. The add and update programs still proceed.
  • LGAPVS01, LGUPVS01 and LGDPVS01 do not check EIBCALEN before reading the COMMAREA, so they assume the caller passes a COMMAREA that is large enough.
  • LGIPVS01 expects a numeric key portion. A non-numeric value would cause a PL/I conversion error. Its DFHCOMMAREA is a fixed layout: 11 bytes of text, a 21-byte key and 58 bytes of padding.

10.3 Sequencing

  • The key and policy data must be built before any file command.
  • The update program must complete READ UPDATE before REWRITE.
  • Time stamping (ASKTIME and FORMATTIME) happens only in the error path.

10.4 Diagnostic Limits

  • At most 90 bytes of the COMMAREA are logged, although the COMM_AREA_RAW overlay is 32,500 bytes.
  • No COMMAREA snapshot is logged when EIBCALEN is zero.
  • WS_RESP2 is captured only when an operation fails.

10.5 Build Environment

The update program is compiled with Enterprise PL/I for z/OS using SYSTEM(CICS),PP(MACRO,CICS). It is linked as a reentrant module with MAP,RENT,COMPAT(PM5) and deployed to the CICS load library.

11. Worked Examples

11.1 Add a Motor Policy

Field Value
CA_REQUEST_ID 01AMOT
CA_CUSTOMER_NUM 0000001234
CA_POLICY_NUM 0000009901
Motor data TOYOTA, COROLLA, 015000, AB12CDE

LGAPVS01 takes M from position 4. The composite key is M + 0000001234 + 0000009901. It writes the 64-byte record, RESP is NORMAL and the program returns without changing CA_RETURN_CODE.

11.2 Add with a Duplicate Key

The same input is submitted again and WRITE returns a non-normal response such as DUPREC. The program does the following:

  1. Captures EIBRESP2.
  2. Sets CA_RETURN_CODE = '80'.
  3. Logs a timestamped ERROR_MSG and a COMMAREA= snapshot (up to 90 bytes) through LGSTSQ.
  4. Returns to the caller.

11.3 Browse for an Endowment Policy (LINK Mode)

The caller passes COMMA_DATA_TEXT = 'Policy Key=' and COMMA_DATA_KEY = 'E0000000010'. LGIPVS01 detects the LINK invocation and builds PART_KEY = 'E' + '0000000010'. The generic GTEQ read returns an E record, so the types match. The COMMAREA is returned as Policy Key= / E0000000010.

11.4 Browse Failure from a Terminal

The operator enters a motor key that has no matching record. The read returns a different type or a non-normal response. The terminal receives Policy Bad= with 13 in both numeric fields.

11.5 Update a Motor Policy

For CA_REQUEST_ID = '01UMOT', LGUPVS01 builds the key, copies the motor fields and issues READ UPDATE. It then issues REWRITE with the 64-byte record. Both operations are normal, so the program returns and CA_RETURN_CODE is unchanged.

11.6 Update When the Record Is Missing

For a house update with customer and policy 9999999999, READ UPDATE fails. The program sets CA_RETURN_CODE = '81', logs the error and abends with LGV3.

11.7 Delete a Policy

For customer 0000012345 and policy 0000098765, the key is the 4th request-ID character + 0000012345 + 0000098765. If the record exists, DELETE succeeds and the program returns silently. If the record is absent, RESP is NOTFND and CA_RETURN_CODE is set to '81'. The error is logged and the program returns.
