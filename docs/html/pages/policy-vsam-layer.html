Policy VSAM Layer

1. Overview

The Policy VSAM Layer is a suite of four CICS-hosted Enterprise PL/I programs responsible for maintaining the KSDSPOLY VSAM Key-Sequenced Data Set (KSDS) in synchronisation with the DB2 policy store. Each program handles a distinct lifecycle operation — add, update, delete, and inquiry/browse — against the VSAM policy file, forming the VSAM-side counterpart to the DB2-based policy programs in the GenApp insurance application.

The four programs share a common architectural pattern: they receive all input through a CICS Communication Area (COMMAREA), construct a 21-byte composite VSAM key from the policy type, customer number, and policy number, perform the appropriate CICS file control operation against KSDSPOLY, and return a numeric return code in the COMMAREA to signal success or failure to the calling orchestrator. On failure, all programs (except LGIPVS01) invoke a structured error-logging routine that timestamps the failure, captures the CICS RESP and RESP2 codes, and forwards diagnostic details to the shared logging utility LGSTSQ.

Program Operation Return Code on Failure
LGAPVS01 Add (Write) new policy record 80
LGUPVS01 Update (Read-Update/Rewrite) existing policy record 81 (read), 82 (rewrite)
LGDPVS01 Delete existing policy record 81
LGIPVS01 Inquiry / Browse (GTEQ partial-key read) 'Policy Bad=' sentinel

2. System Architecture

The VSAM Layer programs sit between the policy orchestration layer (e.g., LGAPOL01) and the KSDSPOLY VSAM KSDS file. They are invoked via EXEC CICS LINK and interact with CICS file control services for all data access. The shared logging program LGSTSQ receives diagnostic output on any file operation failure.

The orchestration programs call the VSAM programs with a populated COMMAREA, which carries all policy data and receives the return code on completion. LGIPVS01 is unique in that it also accepts direct terminal invocation, making it useful for ad-hoc policy browsing.

3. Composite VSAM Key Structure

All four programs share the same 21-byte composite key structure to uniquely identify policy records within KSDSPOLY. This key is assembled from three components sourced from the COMMAREA before any file operation is issued.

CODE 
┌─────────────────────────────────────────────────┐
│              WF_POLICY_KEY  (21 bytes)           │
├────────────┬───────────────────┬─────────────────┤
│WF_REQUEST_ID│ WF_CUSTOMER_NUM  │  WF_POLICY_NUM  │
│  (1 byte)  │   (10 bytes)      │   (10 bytes)    │
│  C/E/H/M   │  e.g. 0000001234  │  e.g. 0000009901│
└────────────┴───────────────────┴─────────────────┘

The policy type byte is extracted from the 4th character of CA_REQUEST_ID in the COMMAREA. Supported policy type values are:

Code Policy Type
C Commercial
E Endowment
H House
M Motor

The remaining 43 bytes of each 64-byte VSAM record hold the policy-type-specific data payload, laid out as a PL/I UNION so that only the relevant overlay is written for each policy type.

4. LGAPVS01 — Add Policy

4.1 Purpose

LGAPVS01 inserts a new insurance policy record into the KSDSPOLY VSAM KSDS. It receives all policy details via COMMAREA, selects the appropriate policy-type data fields, and issues an EXEC CICS WRITE FILE command to persist the 64-byte record.

4.2 Data Flow

sequenceDiagram participant Caller as LGAPOL01 (Orchestrator) participant LGAPVS01 participant KSDSPOLY as KSDSPOLY (VSAM KSDS) participant LGSTSQ as LGSTSQ (Logger) Caller->>LGAPVS01: EXEC CICS LINK (COMMAREA with policy data) LGAPVS01->>LGAPVS01: Extract policy type from CA_REQUEST_ID[4] LGAPVS01->>LGAPVS01: Build 21-byte composite key LGAPVS01->>LGAPVS01: Populate policy-type-specific data (C/E/H/M) LGAPVS01->>KSDSPOLY: EXEC CICS WRITE FILE (64-byte record) alt Write succeeds (DFHRESP NORMAL) KSDSPOLY-->>LGAPVS01: WS_RESP = NORMAL LGAPVS01-->>Caller: RETURN (CA_RETURN_CODE unchanged) else Write fails KSDSPOLY-->>LGAPVS01: WS_RESP ≠ NORMAL LGAPVS01->>LGAPVS01: Set CA_RETURN_CODE = '80', capture EIBRESP2 LGAPVS01->>LGSTSQ: EXEC CICS LINK (ERROR_MSG with timestamp + RESP codes) LGAPVS01->>LGSTSQ: EXEC CICS LINK (CA_ERROR_MSG with raw COMMAREA ≤ 90 bytes) LGAPVS01-->>Caller: EXEC CICS RETURN (CA_RETURN_CODE = '80') end

4.3 Processing Logic

  1. Capture EIBCALEN into WS_Commarea_Len.
  2. Extract the 4th character of CA_REQUEST_ID → WF_REQUEST_ID (policy type discriminator).
  3. Copy CA_CUSTOMER_NUM → WF_CUSTOMER_NUM and CA_POLICY_NUM → WF_POLICY_NUM to form WF_POLICY_KEY.
  4. Execute a SELECT (WF_REQUEST_ID) block to populate the appropriate union overlay:
PLI 
SELECT (WF_REQUEST_ID);
  WHEN ('C') DO;
    WF_B_Postcode  = CA_B_Postcode;
    WF_B_Status    = CA_B_Status;
    WF_B_Customer  = CA_B_Customer;
  END;
  WHEN ('E') DO;
    WF_E_WITH_PROFITS  = CA_E_WITH_PROFITS;
    WF_E_EQUITIES      = CA_E_EQUITIES;
    WF_E_MANAGED_FUND  = CA_E_MANAGED_FUND;
    WF_E_FUND_NAME     = CA_E_FUND_NAME;
    WF_E_LIFE_ASSURED  = CA_E_LIFE_ASSURED;
  END;
  WHEN ('H') DO;
    WF_H_PROPERTY_TYPE = CA_H_PROPERTY_TYPE;
    WF_H_BEDROOMS      = CA_H_BEDROOMS;
    WF_H_VALUE         = CA_H_VALUE;
    WF_H_POSTCODE      = CA_H_POSTCODE;
    WF_H_HOUSE_NAME    = CA_H_HOUSE_NAME;
  END;
  WHEN ('M') DO;
    WF_M_MAKE      = CA_M_MAKE;
    WF_M_MODEL     = CA_M_MODEL;
    WF_M_VALUE     = CA_M_VALUE;
    WF_M_REGNUMBER = CA_M_REGNUMBER;
  END;
  OTHERWISE
    WF_Policy_Text = ' ';
END;
  1. Re-assert WF_POLICY_NUM = CA_POLICY_NUM (ensures key is correct before write).
  2. Issue the VSAM write:
PLI 
EXEC CICS WRITE FILE('KSDSPOLY')
    FROM(WF_Policy_Info)
    LENGTH(64)
    RIDFLD(WF_Policy_Key)
    KEYLENGTH(21)
    RESP(WS_RESP);
  1. Check WS_RESP. If not DFHRESP(NORMAL), set CA_RETURN_CODE = '80', call WRITE_ERROR_MESSAGE, and EXEC CICS RETURN.

4.4 Record Layout

Bytes Field Description
1 WF_REQUEST_ID Policy type (C, E, H, M)
2–11 WF_CUSTOMER_NUM 10-digit customer number
12–21 WF_POLICY_NUM 10-digit policy number
22–64 WF_POLICY_DATA 43-byte type-specific data (UNION)

4.5 Error Handling

  • On write failure, CA_RETURN_CODE is set to '80'.
  • WRITE_ERROR_MESSAGE captures a timestamp via EXEC CICS ASKTIME/FORMATTIME, populates ERROR_MSG with program ID, customer number, and RESP/RESP2 codes, and links to LGSTSQ.
  • Up to 90 bytes of the raw COMMAREA are also logged to LGSTSQ as a secondary diagnostic call.
  • The program terminates via EXEC CICS RETURN — no further processing occurs after a write failure.

5. LGUPVS01 — Update Policy

5.1 Purpose

LGUPVS01 updates an existing insurance policy record in KSDSPOLY using a CICS READ-for-UPDATE followed by a REWRITE pattern. It supports the same four policy types as LGAPVS01 and uses identical COMMAREA field mappings. Two distinct failure codes (81 for READ failure, 82 for REWRITE failure) allow the caller to distinguish between the two phases.

5.2 Data Flow

sequenceDiagram participant Caller as LGUPOL01 (Orchestrator) participant LGUPVS01 participant KSDSPOLY as KSDSPOLY (VSAM KSDS) participant LGSTSQ as LGSTSQ (Logger) Caller->>LGUPVS01: EXEC CICS LINK (COMMAREA with updated policy data) LGUPVS01->>LGUPVS01: Extract type, build composite key, map fields LGUPVS01->>KSDSPOLY: EXEC CICS READ FILE UPDATE (RIDFLD = 21-byte key) alt READ fails KSDSPOLY-->>LGUPVS01: WS_RESP ≠ NORMAL LGUPVS01->>LGUPVS01: Set CA_RETURN_CODE = '81' LGUPVS01->>LGSTSQ: EXEC CICS LINK (error + COMMAREA dump) LGUPVS01->>LGUPVS01: EXEC CICS ABEND ABCODE('LGV3') NODUMP LGUPVS01-->>Caller: EXEC CICS RETURN else READ succeeds KSDSPOLY-->>LGUPVS01: Record locked, WS_RESP = NORMAL LGUPVS01->>KSDSPOLY: EXEC CICS REWRITE FILE (FROM WF_Policy_Info, LENGTH 64) alt REWRITE fails KSDSPOLY-->>LGUPVS01: WS_RESP ≠ NORMAL LGUPVS01->>LGUPVS01: Set CA_RETURN_CODE = '82' LGUPVS01->>LGSTSQ: EXEC CICS LINK (error + COMMAREA dump) LGUPVS01->>LGUPVS01: EXEC CICS ABEND ABCODE('LGV4') NODUMP LGUPVS01-->>Caller: EXEC CICS RETURN else REWRITE succeeds KSDSPOLY-->>LGUPVS01: WS_RESP = NORMAL LGUPVS01-->>Caller: RETURN (success, no return code set) end end

5.3 Processing Logic

  1. Capture EIBCALEN → WS_Commarea_Len.
  2. Extract SUBSTR(CA_REQUEST_ID, 4, 1) → WF_Request_ID.
  3. Copy customer and policy numbers into key fields.
  4. Execute the SELECT block to populate the appropriate UNION overlay (same logic as LGAPVS01).
  5. Re-assert WF_Policy_Num = CA_Policy_Num after the SELECT.
  6. Issue READ for UPDATE:
PLI 
EXEC CICS READ FILE('KSDSPOLY')
    INTO(WS_FileIn)
    LENGTH(WS_Commarea_Len)
    RIDFLD(WF_Policy_Key)
    KEYLENGTH(21)
    UPDATE
    RESP(WS_RESP);
  1. On READ failure: set CA_RETURN_CODE = '81', call WRITE_ERROR_MESSAGE, abend LGV3, and EXEC CICS RETURN.
  2. Issue REWRITE:
PLI 
EXEC CICS REWRITE FILE('KSDSPOLY')
    FROM(WF_Policy_Info)
    LENGTH(WS_Commarea_LenF)  /* fixed at 64 */
    RESP(WS_RESP);
  1. On REWRITE failure: set CA_RETURN_CODE = '82', call WRITE_ERROR_MESSAGE, abend LGV4, and EXEC CICS RETURN.
  2. On success: plain RETURN — no return code is written, implying success to the caller.

5.4 Error Handling

Failure Phase Return Code Abend Code Description
READ UPDATE fails 81 LGV3 Record could not be locked or located
REWRITE fails 82 LGV4 Locked record could not be written back

Both error paths invoke WRITE_ERROR_MESSAGE, which logs a timestamped message and up to 90 bytes of raw COMMAREA to LGSTSQ before the abend is issued with NODUMP to suppress system dump generation.

6. LGDPVS01 — Delete Policy

6.1 Purpose

LGDPVS01 deletes a single insurance policy record from KSDSPOLY using a keyed EXEC CICS DELETE. It is the VSAM-side counterpart to the DB2-based delete program LGDPDB01. The program constructs the same 21-byte composite key, issues the delete, and returns 81 to the caller on any failure.

6.2 Data Flow

sequenceDiagram participant Caller as LGDPOL01 (Orchestrator) participant LGDPVS01 participant KSDSPOLY as KSDSPOLY (VSAM KSDS) participant LGSTSQ as LGSTSQ (Logger) Caller->>LGDPVS01: EXEC CICS LINK (COMMAREA with customer + policy number) LGDPVS01->>LGDPVS01: Read EIBCALEN, build 21-byte composite key LGDPVS01->>KSDSPOLY: EXEC CICS DELETE FILE (RIDFLD = WF_Policy_Key, KEYLENGTH 21) alt Delete succeeds (DFHRESP NORMAL) KSDSPOLY-->>LGDPVS01: WS_RESP = NORMAL LGDPVS01-->>Caller: RETURN (CA_RETURN_CODE unchanged) else Delete fails KSDSPOLY-->>LGDPVS01: WS_RESP ≠ NORMAL LGDPVS01->>LGDPVS01: Capture EIBRESP2, set CA_RETURN_CODE = '81' LGDPVS01->>LGSTSQ: EXEC CICS LINK (ERROR_MSG — timestamp, program, RESP codes) LGDPVS01->>LGSTSQ: EXEC CICS LINK (CA_ERROR_MSG — raw COMMAREA ≤ 90 bytes) LGDPVS01-->>Caller: EXEC CICS RETURN (CA_RETURN_CODE = '81') end

6.3 Processing Logic

  1. Capture EIBCALEN → WS_Commarea_Len.
  2. Build composite key:
PLI 
WF_Request_ID  = SUBSTR(CA_Request_ID, 4, 1);
WF_Policy_Num  = CA_Policy_Num;
WF_Customer_Num = CA_Customer_Num;
  1. Issue the delete:
PLI 
EXEC CICS DELETE FILE('KSDSPOLY')
    RIDFLD(WF_Policy_Key)
    KEYLENGTH(21)
    RESP(WS_RESP);
  1. Test WS_RESP against DFHRESP(NORMAL):
    • Success: fall through to RETURN — no changes to CA_RETURN_CODE.
    • Failure: capture EIBRESP2 → WS_RESP2, set CA_RETURN_CODE = '81', call WRITE_ERROR_MESSAGE, then EXEC CICS RETURN.

6.4 Key Difference from Update

Unlike LGUPVS01, LGDPVS01 does not require a READ UPDATE before the DELETE — EXEC CICS DELETE with a keyed RIDFLD directly removes the record in a single command. There is also no abend issued on failure; only the return code and log entry are produced before a clean EXEC CICS RETURN.

7. LGIPVS01 — Inquiry / Browse Policy

7.1 Purpose

LGIPVS01 performs a generic GTEQ (greater-than-or-equal) partial-key browse against KSDSPOLY to locate the first policy record matching or following a supplied partial key. It is unique among the four programs in supporting two invocation modes: programmatic COMMAREA-driven invocation via EXEC CICS LINK, and direct terminal invocation via EXEC CICS RECEIVE.

7.2 Dual Invocation Architecture

graph TD classDef mode fill:#c7ceea,stroke:#7e8ed0,color:#000 classDef process fill:#ffdac1,stroke:#f4a26a,color:#000 classDef io fill:#b5ead7,stroke:#6bba99,color:#000 classDef decision fill:#fffacd,stroke:#e6c84e,color:#000 A([LGIPVS01 Entry]) --> B[EXEC CICS ASSIGN\nSTARTCODE + INVOKINGPROG] B --> C{{STARTCODE starts with D\nOR INVOKINGPROG non-blank}} C -- Yes --> D[WS_FLAG = C\nLoad WS_COMMAREA from\nCOMMA_DATA_TEXT + COMMA_DATA_KEY\nWS_RECV_LEN = 10]:::mode C -- No --> E[EXEC CICS RECEIVE into WS_RECV\nWS_FLAG = R\nLoad WS_COMMAREA from WS_RECV_DATA\nWS_RECV_LEN -= 6]:::mode D --> F[Build PART_KEY\nPART_KEY_TYPE = WS_COMMAREA pos 1\nPART_KEY_NUM = WS_COMMAREA pos 2+]:::process E --> F F --> G[EXEC CICS READ FILE KSDSPOLY\nGENERIC GTEQ\nKEYLENGTH 11\nLENGTH 64]:::io G --> H{{CA_POLICY_TYPE ≠ PART_KEY_TYPE\nOR WS_RESP ≠ NORMAL}}:::decision H -- Error --> I[WRITE_MSG_TEXT = Policy Bad=\nWRITE_MSG_CUSTNUM = 13\nWRITE_MSG_POLNUM = 13]:::process H -- Success --> J[WRITE_MSG_KEY_CH =\nCA_POLICY_TYPE + CA_CUSTOMER_NUM]:::process I --> K{{WS_FLAG = R}}:::decision J --> K K -- Terminal --> L[EXEC CICS SEND TEXT\nWRITE_MSG 80 bytes ERASE FREEKB]:::io K -- COMMAREA --> M[Update COMMA_DATA_TEXT\nand COMMA_DATA_KEY in DFHCOMMAREA]:::io L --> N[EXEC CICS RETURN] M --> N N --> O([End])

7.3 Processing Logic

Invocation mode determination drives the entire input normalisation strategy. After three EXEC CICS ASSIGN calls:

  • If SUBSTR(WS_STARTCODE,1,1) = 'D' OR WS_INVOKEPROG ^= ' ' → COMMAREA mode (WS_FLAG = 'C'): input loaded from DFHCOMMAREA.
  • Otherwise → Terminal mode (WS_FLAG = 'R'): input read via EXEC CICS RECEIVE, with the 5-character transaction ID prefix stripped.

VSAM generic GTEQ read using an 11-byte partial key:

PLI 
EXEC CICS READ FILE('KSDSPOLY')
    INTO(CA_AREA)
    LENGTH(F64)
    RIDFLD(PART_KEY)
    KEYLENGTH(F11)
    GENERIC
    GTEQ
    RESP(WS_RESP);

Post-read validation — two conditions both must pass for success:

  1. WS_RESP = DFHRESP(NORMAL) — the CICS read completed without error.
  2. CA_POLICY_TYPE = PART_KEY_TYPE — the found record belongs to the requested policy class (a GTEQ may overshoot into a different type).

If either condition fails, the output is set to the error sentinel ('Policy Bad=' with customer number 13 and policy number 13). If both pass, the output key WRITE_MSG_KEY_CH is populated with CA_POLICY_TYPE || CA_CUSTOMER_NUM.

7.4 Invocation Modes Compared

Aspect COMMAREA Mode (WS_FLAG = 'C') Terminal Mode (WS_FLAG = 'R')
Trigger STARTCODE starts with D or INVOKINGPROG non-blank Neither condition above is true
Input source DFHCOMMAREA (COMMA_DATA_TEXT + COMMA_DATA_KEY) EXEC CICS RECEIVE → WS_RECV_DATA
Key length WS_RECV_LEN hardcoded to 10 Received length minus 6 (strips transaction ID prefix)
Result delivery Written back into COMMA_DATA_TEXT and COMMA_DATA_KEY of DFHCOMMAREA EXEC CICS SEND TEXT (80 bytes, ERASE, FREEKB)
Error indicator COMMA_DATA_TEXT = 'Policy Bad=', key fields = 13 Screen shows Policy Bad= + 13 sentinel values

7.5 Error Handling

LGIPVS01 does not log errors to LGSTSQ or issue abends. Error conditions are communicated purely through the output sentinel mechanism:

  • WRITE_MSG_TEXT = 'Policy Bad=' (vs 'Policy Key=' on success)
  • WRITE_MSG_CUSTNUM = 13, WRITE_MSG_POLNUM = 13

This lighter-weight error response reflects the inquiry/browse nature of the operation — no data is modified and the program always completes with EXEC CICS RETURN.

8. Shared Error Logging Pattern (WRITE_ERROR_MESSAGE)

Three of the four programs (LGAPVS01, LGUPVS01, LGDPVS01) share a common internal error logging procedure called WRITE_ERROR_MESSAGE. Its structure and behaviour are consistent across all three programs.

flowchart TD A([WRITE_ERROR_MESSAGE called]) --> B[EXEC CICS ASKTIME\nAbstime into WS_ABSTIME] B --> C[EXEC CICS FORMATTIME\nMMDDYYYY into WS_DATE\nHH:MM:SS into WS_TIME] C --> D[Populate ERROR_MSG\nDate + Time + Program ID\nCustomer Num + RESP + RESP2\nOperation literal] D --> E[EXEC CICS LINK PROGRAM LGSTSQ\nCOMMARE = ERROR_MSG] E --> F{{EIBCALEN > 0}} F -- No --> I([Return]) F -- Yes --> G{{EIBCALEN < 91}} G -- Yes --> H1[CA_DATA = LEFT of COMM_AREA_RAW\nby EIBCALEN bytes] G -- No --> H2[CA_DATA = LEFT of COMM_AREA_RAW\n90 bytes] H1 --> J[EXEC CICS LINK PROGRAM LGSTSQ\nCOMMARE = CA_ERROR_MSG\nprefix COMMAREA=] H2 --> J J --> I

The procedure always produces at least one log entry (the structured ERROR_MSG), and conditionally a second entry containing a raw COMMAREA snapshot for input-context diagnosis. The COMMAREA dump is capped at 90 bytes to match the CA_DATA field size, regardless of actual COMMAREA length.

9. Policy Type Data Payloads

Each 64-byte VSAM record contains a 21-byte key followed by a 43-byte UNION data area. Only the union overlay corresponding to the active policy type is populated. The table below summarises all fields across the four supported policy types.

Policy Type Field Type / Length Description
Commercial © WF_B_POSTCODE CHAR(8) Postcode of insured commercial property
WF_B_STATUS FIXED BIN(15) Commercial policy status code
WF_B_CUSTOMER CHAR(31) Commercial customer descriptor (truncated from 255)
Endowment (E) WF_E_WITH_PROFITS CHAR(1) With-profits participation flag
WF_E_EQUITIES CHAR(1) Equities participation flag
WF_E_MANAGED_FUND CHAR(1) Managed fund participation flag
WF_E_FUND_NAME CHAR(10) Investment fund name
WF_E_LIFE_ASSURED CHAR(30) Life assured name (truncated from 31)
House (H) WF_H_PROPERTY_TYPE CHAR(15) Property classification (e.g., DETACHED)
WF_H_BEDROOMS PIC '(3)9' Number of bedrooms (0–999)
WF_H_VALUE PIC '(8)9' Insured property value (0–99,999,999)
WF_H_POSTCODE CHAR(8) Property postcode
WF_H_HOUSE_NAME CHAR(9) House name (truncated from 20)
Motor (M) WF_M_MAKE CHAR(15) Vehicle manufacturer
WF_M_MODEL CHAR(15) Vehicle model
WF_M_VALUE PIC '(6)9' Insured vehicle value (0–999,999)
WF_M_REGNUMBER CHAR(7) Vehicle registration number

Truncation note: Several COMMAREA source fields are wider than their VSAM working-storage counterparts. Notably, CA_B_Customer (255 chars) is truncated to 31 bytes, CA_E_LIFE_ASSURED (31 chars) to 30 bytes, and CA_H_HOUSE_NAME (20 chars) to 9 bytes on write to VSAM.

10. COMMAREA Return Code Summary

The COMMAREA field CA_RETURN_CODE is the primary channel through which all four programs signal outcomes back to their callers.

Program Successful Return Read Failure Write / Delete / Browse Failure
LGAPVS01 No code set (unchanged) N/A '80'
LGUPVS01 No code set (unchanged) '81' + abend LGV3 '82' + abend LGV4
LGDPVS01 No code set (unchanged) N/A '81'
LGIPVS01 'Policy Key=' in text field N/A 'Policy Bad=' in text field + sentinel 13

For LGAPVS01, LGUPVS01, and LGDPVS01, the absence of an error code in CA_RETURN_CODE is the implied success indicator — the caller is expected to treat any non-zero return code as a failure condition.
