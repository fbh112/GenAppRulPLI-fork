Customer Domain Migration Risks & Impact Analysis

This document provides a comprehensive migration impact and risk analysis for the Customer Domain within the GenApp PL/I application suite. It synthesizes architectural structures, program complexities, shared resource couplings, and database dependencies to evaluate risks and define strategies for modernization and platform migration.

1. Overview

The Customer Domain is responsible for core customer lifecycle management in GenApp, including onboarding, inquiries, demographic updates, security credential management, and parallel shadow persistence.

Migrating this domain involves significant challenges due to deep architectural entanglements with the Policy Domain, monolithic shared structures across all CICS modules, distributed counter mechanisms, and uncoordinated dual-write persistence models. This analysis establishes an evidence-based technical inventory to support migration scoping, decomposition strategies, and risk mitigation.

2. System Architecture

The Customer Domain is structured across distinct tiers: a 3270 presentation layer, an orchestration and business logic tier, and a hybrid data persistence tier utilizing both IBM Db2 and VSAM KSDS data sets.

3.2 Primary Hot-Spot: LGACUS01

LGACUS01 represents the highest single risk in the application. It consolidates four distinct lifecycle operations (Onboard, Offer Policy, Transfer, and Delete) and spans 774 lines of PL/I logic across 13 internal procedures.

Procedure Breakdown and Cross-Domain Boundaries

Three of the thirteen procedures directly execute DML statements against the POLICY table:

  • INSERT_CUSTOMER_POLICY (Lines 590–647): Inserts a new policy record.
  • TRANSFER_CUSTOMER_POLICY (Lines 653–710): Re-assigns policies during transfers.
  • DELETE_CUSTOMER_POLICY (Lines 717–734): Removes policy records.

3.3 Presentation Hot-Spot: LGTESTC1

LGTESTC1 serves as the primary CICS BMS menu handler. It exhibits several complex control flow patterns:

  • Stateful Pseudo-Conversations: Returns control using EXEC CICS RETURN TRANSID('SSC1') COMMAREA(...), maintaining application state in memory between terminal turns.
  • Inline Multi-Step Operations: Option 4 performs an Inquire followed by an inline Update in the same interaction turn.
  • Presentation-Layer Locks: Explicitly executes EXEC CICS ENQ and EXEC CICS DEQ against the GENACNTL TS Queue.
  • Transaction Rollback in Presentation: Issues EXEC CICS SYNCPOINT ROLLBACK at line 790 upon customer creation failure.
  • Unstructured Flow: Employs legacy pre-structured conditions (HANDLE_AID, HANDLE_CONDITION) and multiple label branches (GO TO NO_DATA, GO TO ERROR_OUT, GO TO ENDIT_STARTIT).

3.4 Persistence Hot-Spots: LGACDB01 and LGICVS01

  • LGACDB01 Duplicate Implementation: Replicates the customer insertion logic present in LGACUS01. It interfaces with the GENACUSTNUM Named Counter, issues identical SQL inserts, and cascades uncoordinated updates to LGACVS01 and LGACDB02.
  • LGICVS01 Multi-Mode Invocation: Implements dual-mode entry, detecting via start code whether it was invoked via EXEC CICS LINK or executed directly as a terminal transaction via EXEC CICS RECEIVE. It contains logic to discover random customer numbers using EXEC CICS READ FILE('KSDSCUST') GTEQ after parsing customer boundaries from the GENACNTL TS queue.

4.1 LGCMAREA.inc Monolithic Data Contract

LGCMAREA.inc defines a single monolithic 32,500-byte structure (COMM_AREA) shared by every CICS program across both Customer and Policy domains:

CODE 
01 COMM_AREA.
   05 CA_HEADER.
      10 CA_REQUEST_ID      PIC X(6).
      10 CA_RETURN_CODE     PIC 9(2).
      10 CA_CUSTOMER_NUM    PIC 9(10).
   05 CA_CUSTOMER_DATA      PIC X(72).
   05 CA_SECURITY_OVERLAY   REDEFINES CA_CUSTOMER_DATA.
      10 CA_SEC_DATA        PIC X(32482).
   05 CA_POLICY_HEADER      PIC X(72).
   05 CA_POLICY_UNION       REDEFINES CA_POLICY_HEADER.
      10 CA_POLICY_DETAIL   PIC X(32400).

Because all fields and union overlays are bound at compile time, modifying any single domain’s interface necessitates the recompilation and re-testing of all CICS components across the enterprise.

4.2 LGPOLICY.inc Cross-Domain Host Structure

LGPOLICY.inc includes host structures for policies (DB2_POLICY, DB2_ENDOWMENT, DB2_HOUSE, DB2_MOTOR, DB2_COMMERCIAL, DB2_CLAIM) as well as DB2_CUSTOMER. LGACUS01 incorporates this include via EXEC SQL INCLUDE LGPOLICY, binding Customer domain code to Policy domain schema modifications.

4.3 Error Handling Infrastructure (LGSTSQ and WRITE_ERROR_MESSAGE)

All 9 Customer CICS programs implement a local copy of the WRITE_ERROR_MESSAGE procedure. Each local instance performs time formatting and issues repeated EXEC CICS LINK PROGRAM('LGSTSQ') calls to write error entries to a CICS Transient Data queue.

PLI 
/* Example duplicated error logging pattern */
 WRITE_ERROR_MESSAGE: PROCEDURE;
     DCL EM_DATE_TIME CHAR(20);
     EM_DATE_TIME = DATETIME();
     EXEC CICS LINK PROGRAM('LGSTSQ')
          COMMAREA(EM_RECORD)
          LENGTH(LENGTH(EM_RECORD));
 END WRITE_ERROR_MESSAGE;

4.4 GENACUSTNUM Named Counter & GENACNTL TS Queue

  • GENACUSTNUM: Customer number allocation relies on the CICS Named Counter facility using:
    PLI 
    EXEC CICS GET COUNTER(GENACOUNT) POOL(GENAPOOL) VALUE(LASTCUSTNUM);
    If the Named Counter server is unavailable (LGAC_NCS = 'NO'), both LGACUS01 and LGACDB01 fall back to DB2 generated identity defaults.
  • GENACNTL TS Queue: Stores transient upper and lower customer number bounds, accessed concurrently by LGTESTC1 and LGICVS01 under explicit ENQ/DEQ locks. This memory store is volatile across CICS region recycles.

5. Shared Data & Persistence Flows

5.1 Dual-Write Consistency Gap

When customer records are added or updated, writes must propagate to both relational tables and VSAM data sets.

Because DB2 and VSAM updates are not coordinated via a two-phase commit (2PC) or automated compensation transaction within the program, an environmental failure on KSDSCUST leaves the DB2 relational row orphaned without a corresponding VSAM shadow entry.

7. Risk Assessment

Risk ID Risk Description Category Likelihood Impact Severity Mitigation Strategy
R1 Direct SQL writes to POLICY in LGACUS01 prevent independent domain deployment. Cross-Domain Coupling High High 🔴 CRITICAL Decompose LGACUS01 by removing policy DML and routing through Policy domain APIs.
R2 LGCMAREA.inc monolithic layout forces cascading recompilations across all services. Shared Code High High 🔴 CRITICAL Replace monolithic buffer with domain-specific JSON/gRPC contracts or scoped DTOs.
R3 Relational FK (POLICY.CUSTOMERNUMBER → CUSTOMER) breaks if databases are split. Shared Data / RI High High 🔴 CRITICAL Introduce distributed verification or Saga orchestrations at the application layer.
R4 Independent duplicate customer add paths in LGACDB01 and LGACUS01. Shared Data High Medium 🟠 HIGH Unify customer onboarding logic into a single microservice/persistence layer.
R5 Lack of 2PC between DB2 and VSAM shadow store leads to data inconsistencies. Shared Data Medium High 🟠 HIGH Evaluate necessity of VSAM shadow; eliminate if obsolete or back with distributed CDC.
R6 LGTESTC1 BMS dependencies require 3270 emulation or presentation rewrite. Presentation High Medium 🟠 HIGH Decouple UI layer; expose backend customer APIs to modern web/REST presentation clients.
R7 GENACUSTNUM CICS Named Counter has no native equivalent in distributed environments. Infrastructure High Medium 🟠 HIGH Standardize on DB2 native sequence objects or distributed ID generation services.
R8 Hardcoded initial MD5 password hash (5732fec8...) creates security vulnerabilities. Security High Medium 🟠 HIGH Migrate to modern identity provider (IdP) integration with secure credential hashing.
R9 CUSTOMER_SECURE has no internal read path; external consumers are unknown. Shared Data Medium High 🟠 HIGH Identify external authentication callers before modifying schema or access endpoints.
R10 Duplicated WRITE_ERROR_MESSAGE logic in 9 separate programs increases maintenance effort. Shared Code High Low 🟡 MEDIUM Centralize logging logic into an externalized shared logging framework or interceptor.
R11 LGICVS01 dual invocation (LINK vs. direct terminal transaction) complicates porting. Hot-Spot Medium Medium 🟡 MEDIUM Remove direct terminal invocation path and retain only program-to-program linkages.
R12 Presentation layer SYNCPOINT ROLLBACK tightly couples transaction scopes across tiers. Architecture Medium Medium 🟡 MEDIUM Enforce transaction boundaries within the service/domain layer rather than presentation.
R13 Volatile runtime state in GENACNTL TS Queue lost on region recycling. Shared State Medium Low 🟡 MEDIUM Migrate dynamic customer number bounds and counters to durable persistence stores.
R14 Unresolved MQ integration stub (AAAAAAAA) in LGICUS01. External Coupling Low Medium 🟡 MEDIUM Confirm business requirements regarding asynchronous message handling and remove or implement.

8. Architectural Decision: LGACUS01 Decomposition

Resolving the architectural coupling in LGACUS01 is the critical path item for separating Customer and Policy domains during modernization.

8.1 Option Comparison

Strategy Description Advantages Disadvantages
Option A: Migrate As-Is (Monolith Lift) Maintain unified program logic retaining direct SQL writes to both CUSTOMER and POLICY tables. • Lowest immediate refactoring effort.
• Preserves local SQL atomic transactions.		 • Fails to achieve domain separation.
• Prevents independent scaling and lifecycle management.
Option B: Decompose Before Migration (Recommended) Extract policy procedures (INSERT_CUSTOMER_POLICY, etc.) out of LGACUS01 into Policy domain services in PL/I prior to target migration. • Clean bounded contexts established upfront.
• Eliminates cross-domain compile dependencies.
• Simplifies migration verification.		 • Requires intermediate PL/I refactoring.
• Requires transition from atomic local SQL commits to distributed/compensating patterns.
Option C: Decompose During Migration Redefine service boundaries concurrently during porting/re-platforming. • Eliminates intermediate mainframe refactoring step. • Increases cross-team coordination overhead.
• Heightens risk of scope bleed and migration defects.

9. Migration Effort Indicators

The migration items are categorized below by complexity, dependency chains, and operational effort:

Effort Tier Item / Component Technical Drivers
Large (High Effort) LGACUS01 Decomposition Decoupling cross-domain SQL DML, isolating Policy operations, implementing compensating transactional patterns.
Large (High Effort) LGCMAREA Contract Split Redefining a 32,500-byte shared data structure into granular domain DTOs across all calling modules.
Medium-Large LGTESTC1 Modernization Replacing 3270 BMS map layouts, pseudo-conversational session handling, and presentation-layer lock logic.
Medium CICS Named Counter Migration Replacing GENACUSTNUM with DB2 sequence objects or distributed primary key generators.
