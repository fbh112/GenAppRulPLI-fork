Policy Inquiry

The Policy Inquiry capability in the GenApp core insurance system provides comprehensive read-only access to customer policy records, covering multiple insurance lines of business (Endowment, House, Motor, and Commercial) as well as associated claims. The inquiry process is structured as a two-tier transaction architecture within CICS: LGIPOL01 acts as the front-end business logic and orchestration program, while LGIPDB01 serves as the back-end database access program handling relational queries, cursor operations, and payload marshalling against IBM Db2.

1. Overview

1.1 Business Purpose and Scope

The Policy Inquiry service fulfills operational requirements for customer service representatives, automated interfaces, and batch processes needing full visibility into existing insurance contracts and claim histories.

Key functional capabilities include:

  • Single Policy Inquiry: Retrieving common policy metadata (issue dates, renewal dates, premium payments, broker IDs) along with policy-specific attributes for Endowment, House, Motor, and Commercial contracts.
  • Single Claim Inquiry: Fetching detailed loss information, payment records, and assessment notes by unique claim number.
  • Multi-Record Customer Search: Querying all commercial policies or claims registered under a specific customer number using scrollable cursors and high-capacity CICS channels/containers.
  • Geographic Commercial Search: Fetching commercial policy portfolios filtered by postal code/ZIP code.

2. System Architecture

2.1 Multi-Tier Architecture and Component Structure

The inquiry architecture consists of three distinct layers:

  1. Presentation / Orchestration Layer (LGIPOL01): Implemented in Enterprise PL/I, this program acts as the safe entry point. It captures CICS runtime context (EIBTRNID, EIBTRMID, EIBTASKN), guards against missing or null communication areas, initializes status codes, and issues a synchronous EXEC CICS LINK to the database program.
  2. Data Access Layer (LGIPDB01): An Enterprise PL/I program with embedded SQL. It decodes request identifiers, resolves host-variable data types, enforces null-indicator validation, checks communication buffer capacities, and interfaces directly with Db2.
  3. Diagnostic and Logging Subsystem (LGSTSQ): An external CICS logging program invoked via EXEC CICS LINK to write diagnostic snapshots and SQL return codes to the CICS Transient Data Queue (TDQ CSMT).

4. Component Technical Details

4.1 Business Orchestration Layer (LGIPOL01)

LGIPOL01 serves as the frontline entry module. It executes top-down without embedding business retrieval logic or SQL syntax.

CODE 
*----------------------------------------------------------------*
* LGIPOL01 Execution Logic Outline:
* 1. Obtain EIB Runtime Context (TRANSID, TERMID, TASKNUM).
* 2. Inspect EIBCALEN. If 0 -> Write Diagnostic Log & Abend 'LGCA'.
* 3. Pre-initialize CA_RETURN_CODE to '00' (Optimistic Success).
* 4. Transfer Execution to Data Layer via EXEC CICS LINK (LGIPDB01).
* 5. Return Enriched Payload to Caller via EXEC CICS RETURN.
*----------------------------------------------------------------*

Entry Guard and Abend Implementation

5.2 Return Codes and Status Protocols

All inquiry programs adhere to a standardized 2-digit status protocol returned in CA_RETURN_CODE.

Code Status Meaning Trigger Condition System Action
'00' Success Query executed, row found, fields populated Enriched payload returned to caller
'01' Not Found SQLCODE = 100 on primary lookup Empty payload returned with code '01'
'88' Cursor Close Failure Non-zero SQLCODE during CLOSE Cursor Diagnostics written to TDQ via LGSTSQ
'89' Cursor Open Failure Non-zero SQLCODE during OPEN Cursor Diagnostics written to TDQ via LGSTSQ
'90' Db2 Database Failure Negative/unexpected SQLCODE during singleton SELECT SQLCODE & payload logged; code '90' returned
'98' Insufficient Buffer EIBCALEN < WS_REQUIRED_CA_LEN Execution aborted early; code '98' returned
'99' Unrecognized Request CA_REQUEST_ID not matched in SELECT dispatch Immediate return without database access
LGCA Abend Code (Transaction) EIBCALEN = 0 (No COMMAREA received) Immediate abnormal task termination (NODUMP)

5.3 Transient Data Queue Logging (LGSTSQ)

Diagnostic logging is centralized through the internal WRITE_ERROR_MESSAGE subroutine, which acquires timestamp data via CICS system services and issues synchronous links to LGSTSQ.

PLI 
WRITE_ERROR_MESSAGE: Proc;
  EM_SQLRC = SQLCODE;
  Exec CICS ASKTIME ABSTIME(ABS_TIME);
  Exec CICS FORMATTIME ABSTIME(ABS_TIME)
            MMDDYYYY(DATE1)
            TIME(TIME1);
  EM_DATE = DATE1;
  EM_TIME = TIME1;

  /* Write Primary Diagnostic Error Structure */
  Exec CICS Link Program('LGSTSQ')
            Commarea(ERROR_MSG)
            Length(Stg(ERROR_MSG));

  /* Write Inbound COMMAREA Snapshot (Bounded up to 90 bytes) */
  If EIBCALEN > 0 Then
    Do;
      If EIBCALEN < 91 Then
        CA_DATA = Left(COMM_AREA_RAW, EIBCALEN);
      Else
        CA_DATA = Left(COMM_AREA_RAW, 90);

      Exec CICS Link Program('LGSTSQ')
                Commarea(CA_ERROR_MSG)
                Length(Stg(CA_ERROR_MSG));
    End;
End WRITE_ERROR_MESSAGE;

6.1 Scenario 1: Motor Policy Inquiry (01IMOT)

A user retrieves a motor policy record for customer 12345 and policy 67890.

Policy Inquiry is a core business function within the GenApp insurance application designed to retrieve comprehensive policy and claim details across multiple insurance lines—including Endowment, House, Motor, Commercial, and Claims. The architecture follows a two-tier modular design implemented in Enterprise PL/I under CICS and Db2 for z/OS. 

The front-end orchestrator (`LGIPOL01`) handles CICS session context, performs entry validation, initializes transaction state, and delegates backend data retrieval. The backend database engine (`LGIPDB01`) interfaces with Db2 tables (`POLICY`, `CUSTOMER`, `ENDOWMENT`, `HOUSE`, `MOTOR`, `COMMERCIAL`, and `CLAIM`), supporting both singleton lookups and multi-row cursor operations across traditional CICS COMMAREAs and CICS Channels/Containers.

---

## 1. Overview

The Policy Inquiry process coordinates the flow of policy retrieval requests originating from user interfaces (such as CICS menu transactions `LGTESTP1`–`LGTESTP4`) down to the Db2 relational database.

<!--MERMAID_PLACEHOLDER_7-->

Key capabilities of the Policy Inquiry framework include:
- **Product-Agnostic Dispatching:** Supports five distinct insurance domains (Endowment, House, Motor, Commercial, Claim) using a single 6-character request identifier (`CA_REQUEST_ID`).
- **Flexible Data Transport:** Accommodates traditional fixed COMMAREA buffers (up to 32,500 bytes) as well as CICS Channels and Containers (`ICOM` channel with `ICOM-Data` and `ICOM-Count` containers) for high-volume multi-row queries.
- **Fail-Fast Input Validation:** Aborts immediately (`ABCODE('LGCA') NODUMP`) on empty communication buffers to protect transactional integrity.
- **Centralized Diagnostic Auditing:** Streams operational error logs and bounded COMMAREA memory dumps (up to 90 bytes) to CICS Transient Data Queues (TDQs) through a dedicated helper routine (`LGSTSQ`).

## 3. End-to-End Processing Flow and Sequence

The execution flow begins when a caller invokes `LGIPOL01` with an inquiry request. The orchestrator validates the input, initializes the state, and invokes `LGIPDB01`. `LGIPDB01` resolves the query against Db2, verifies buffer space, formats the output data, and returns the enriched structure back to the caller.

## 4. Program Modules Detailed Analysis

### 4.1 Front-End Orchestrator: LGIPOL01

`LGIPOL01` acts as a thin business-logic proxy and safety guard. It contains no embedded SQL and performs the following operational steps:

1. **Context Acquisition:** Captures runtime context from CICS Execute Interface Block (EIB) fields (`EIBTRNID`, `EIBTRMID`, `EIBTASKN`) into local working-storage headers (`WS_TRANSID`, `WS_TERMID`, `WS_TASKNUM`).
2. **Input Guard:** Verifies `EIBCALEN > 0`. If `EIBCALEN = 0`, it writes diagnostic records via `WRITE_ERROR_MESSAGE` and executes `EXEC CICS ABEND ABCODE('LGCA') NODUMP`.
3. **State Initialization:** Sets `CA_RETURN_CODE = '00'` and copies `CA_CUSTOMER_NUM` and `CA_POLICY_NUM` into error tracking fields (`EM_CUSNUM`, `EM_POLNUM`).
4. **Backend Delegation:** Issues `EXEC CICS LINK PROGRAM('LGIPDB01') COMMAREA(COMM_AREA) LENGTH(32000)`.
5. **Caller Return:** Issues `EXEC CICS RETURN` unconditionally upon completion of the backend program.
pl1

/* Excerpt: LGIPOL01 Main Procedure and Delegation */ LGIPOL01: Proc(COMM_AREA_PTR) Options(Main);

WS_TRANSID = EIBTRNID; WS_TERMID = EIBTRMID; WS_TASKNUM = EIBTASKN;

If EIBCALEN = 0 Then Do; EM_MSG_TEXT = ’ NO COMMAREA RECEIVED’; Call WRITE_ERROR_MESSAGE; EXEC CICS ABEND ABCODE(‘LGCA’) NODUMP; End;

CA_RETURN_CODE = ‘00’; WS_CALEN = EIBCALEN; WS_ADDR_DFHCOMMAREA = COMM_AREA_PTR;

EM_CUSNUM = CA_CUSTOMER_NUM; EM_POLNUM = CA_POLICY_NUM;

EXEC CICS LINK Program(‘LGIPDB01’) Commarea(COMM_AREA) Length(32000);

EXEC CICS RETURN; End LGIPOL01;

### 4.2 Db2 Retrieval Engine: LGIPDB01

`LGIPDB01` executes all SQL queries and manages result serializations.

1. **Container vs. COMMAREA Detection:** Attempts to read an incoming `ICOM-Data` container on channel `ICOM`. If present (`DFHRESP(NORMAL)`), it processes via container storage pointers. Otherwise, it falls back to the COMMAREA passed in `COMM_AREA_PTR` and checks `EIBCALEN`.
2. **Numeric Host Variable Conversion:** Converts zoned decimal / picture inputs (`CA_CUSTOMER_NUM`, `CA_POLICY_NUM`, `CA_C_Num`) into native binary integer host variables (`DB2_CUSTOMERNUM_INT`, `DB2_POLICYNUM_INT`, `DB2_CLAIMNUM_INT`).
3. **Dispatching:** Evaluates `WS_REQUEST_ID = UPPERCASE(CA_REQUEST_ID)` across nine supported inquiry codes.
4. **Buffer Size Enforcement:** Compares `EIBCALEN` against `WS_REQUIRED_CA_LEN` (header length 33 + entity length + optional VARCHAR padding length). If `EIBCALEN` is insufficient, it sets `CA_RETURN_CODE = '98'` and returns immediately without memory violation.
5. **Null Value Handling:** Uses indicator variables (`IND_BROKERID`, `IND_PAYMENT`, `IND_E_PADDINGDATA`) to prevent DB2 null-assignment exceptions.
6. **Data Delimiting:** Writes a literal `'FINAL'` delimiter at the trailing end of the populated policy structure (`CA_E_PADDING_DATA`, `CA_H_FILLER`, `CA_M_FILLER`, `CA_B_FILLER`, or `CA_C_FILLER`).
pl1

/* Excerpt: LGIPDB01 Singleton Motor Lookup and Size Validation */ GET_MOTOR_DB2_INFO: Proc; EM_SQLREQ = ’ SELECT MOTOR ';

EXEC SQL SELECT P.ISSUEDATE, P.EXPIRYDATE, P.LASTCHANGED, P.BROKERID, P.BROKERSREFERENCE, P.PAYMENT, M.MAKE, M.MODEL, M.VALUE, M.REGNUMBER, M.COLOUR, M.CC, M.YEAROFMANUFACTURE, M.PREMIUM, M.ACCIDENTS INTO :DB2_ISSUEDATE, :DB2_EXPIRYDATE, :DB2_LASTCHANGED, :DB2_BROKERID_INT INDICATOR :IND_BROKERID, :DB2_BROKERSREF INDICATOR :IND_BROKERSREF, :DB2_PAYMENT_INT INDICATOR :IND_PAYMENT, :DB2_M_MAKE, :DB2_M_MODEL, :DB2_M_VALUE_INT, :DB2_M_REGNUMBER, :DB2_M_COLOUR, :DB2_M_CC_SINT, :DB2_M_MANUFACTURED, :DB2_M_PREMIUM_INT, :DB2_M_ACCIDENTS_INT FROM POLICY P, MOTOR M WHERE P.POLICYNUMBER = :DB2_POLICYNUM_INT AND P.CUSTOMERNUMBER = :DB2_CUSTOMERNUM_INT AND P.POLICYNUMBER = M.POLICYNUMBER;

If SQLCODE = 0 Then Do; WS_REQUIRED_CA_LEN = WS_CA_HEADERTRAILER_LEN + WS_FULL_MOTOR_LEN; If EIBCALEN < WS_REQUIRED_CA_LEN Then Do; CA_RETURN_CODE = ‘98’; EXEC CICS RETURN; End;

  /* Integer to Picture transformations */
  DB2_M_VALUE     = DB2_M_VALUE_INT;
  DB2_M_CC        = DB2_M_CC_SINT;
  DB2_M_PREMIUM   = DB2_M_PREMIUM_INT;
  DB2_M_ACCIDENTS = DB2_M_ACCIDENTS_INT;
  
  SUBSTR(CA_POLICY_RAW, 1, WS_FULL_MOTOR_LEN) = DB2_MOTOR_TEXT;
  CA_M_FILLER(1) = 'FINAL';

End; Else If SQLCODE = 100 Then CA_RETURN_CODE = ‘01’; Else Do; CA_RETURN_CODE = ‘90’; Call WRITE_ERROR_MESSAGE; End; End GET_MOTOR_DB2_INFO;

## 5. Request Dispatching and Supported Inquiry Types

`LGIPDB01` supports 9 distinct transaction modes dispatched through the `WS_REQUEST_ID` variable:

| Request ID | Operation Subroutine | DB2 Search Predicates | Access Mode | Output Mechanism |
|---|---|---|---|---|
| `01IEND` | `GET_ENDOW_DB2_INFO` | `CustomerNumber`, `PolicyNumber` | Singleton `SELECT` | COMMAREA (Variable with Padding) |
| `01IHOU` | `GET_HOUSE_DB2_INFO` | `CustomerNumber`, `PolicyNumber` | Singleton `SELECT` | COMMAREA (130-byte house block) |
| `01IMOT` | `GET_MOTOR_DB2_INFO` | `CustomerNumber`, `PolicyNumber` | Singleton `SELECT` | COMMAREA (137-byte motor block) |
| `01ICOM` | `GET_COMMERCIAL_DB2_INFO_1` | `CustomerNumber`, `PolicyNumber` | Singleton `SELECT` | COMMAREA (1174-byte comm block) |
| `02ICOM` | `GET_COMMERCIAL_DB2_INFO_2` | `PolicyNumber` only | Singleton `SELECT` | COMMAREA (Customer number returned) |
| `03ICOM` | `GET_COMMERCIAL_DB2_INFO_3` | `CustomerNumber` | `Cust_Cursor` (Scroll) | CICS Containers (`ICOM-Data`, `ICOM-Count`) |
| `05ICOM` | `GET_COMMERCIAL_DB2_INFO_5` | `Zipcode` (`CA_B_POSTCODE`) | `Zip_Cursor` (Scroll) | COMMAREA (Iterative fetch) |
| `01ICLM` | `GET_CLAIM_DB2_INFO_1` | `ClaimNumber` (`CA_C_Num`) | Singleton `SELECT` | COMMAREA (Customer & Policy returned) |
| `02ICLM` | `GET_CLAIM_DB2_INFO_2` | `CustomerNumber` | `CusClaim_Cursor` (Scroll) | COMMAREA (Iterative fetch) |
| *Other* | *None* | N/A | None | Set `CA_RETURN_CODE = '99'` |

## 6. Data Structures and Database Models

### 6.1 Common Communication Area Layout (LGCMAREA)

The `COMM_AREA` structure shared between `LGIPOL01` and `LGIPDB01` contains a fixed header followed by an overlapping union mapping policy-specific data.

| Field Name | Type / Picture | Length (Bytes) | Description |
|---|---|---|---|
| `CA_REQUEST_ID` | `CHAR(6)` | 6 | Operation identifier (e.g., `01IMOT`, `01IEND`) |
| `CA_RETURN_CODE` | `PIC '99'` | 2 | Standard numeric status return code |
| `CA_CUSTOMER_NUM` | `PIC '9999999999'` | 10 | 10-digit customer identifier |
| `CA_POLICY_NUM` | `PIC '9999999999'` | 10 | 10-digit policy identifier |
| `CA_POLICY_COMMON` | Group | 65 | Common policy header: issue/expiry dates, payment, broker info |
| `CA_POLICY_RAW` | Union (`CHAR(32400)`) | 32,400 | Overlay containing product sub-structure: |
| ↳ `CA_ENDOWMENT` | Sub-structure | 124+ | Fund names, term, sum assured, variable padding |
| ↳ `CA_HOUSE` | Sub-structure | 130 | Property type, bedrooms, value, address lines |
| ↳ `CA_MOTOR` | Sub-structure | 137 | Make, model, CC, reg number, value, accidents |
| ↳ `CA_COMMERCIAL`| Sub-structure | 1,174 | Address, coordinates, 4 peril/premium pairs, status |
| ↳ `CA_CLAIM` | Sub-structure | 618 | Claim number, date, paid, value, cause, observations |

## 7. Error Handling and Diagnostic Logging

Both `LGIPOL01` and `LGIPDB01` utilize a standardized error and status protocol across all paths.

### 7.1 Status Return Code Summary

| Return Code | Severity | Meaning | Action Taken |
|---|---|---|---|
| `00` | Success | Policy inquiry completed successfully | COMMAREA populated with retrieved fields |
| `01` | Not Found | SQLCODE = 100 (Customer/Policy/Claim not found) | No DB2 data returned; caller informed |
| `88` | Error | Cursor CLOSE operation failed | `WRITE_ERROR_MESSAGE` logged to TDQ |
| `89` | Error | Cursor OPEN operation failed | `WRITE_ERROR_MESSAGE` logged to TDQ |
| `90` | Error | Unexpected DB2 SQL error (non-zero/non-100) | `WRITE_ERROR_MESSAGE` logged with SQLCODE |
| `98` | Error | `EIBCALEN` smaller than `WS_REQUIRED_CA_LEN` | Immediate `EXEC CICS RETURN`; prevents memory overrun |
| `99` | Error | Unrecognized `CA_REQUEST_ID` | Processing skipped; returned to caller |
| `LGCA` | Abend | Invocation with `EIBCALEN = 0` | Aborts transaction immediately with `NODUMP` |

---

### 7.2 Diagnostic Logging Subroutine (`WRITE_ERROR_MESSAGE`)

When an unexpected exception occurs, the internal procedure `WRITE_ERROR_MESSAGE` executes diagnostic logging to a CICS Transient Data Queue (TDQ) via program `LGSTSQ`:
pl1

WRITE_ERROR_MESSAGE: Proc; EM_SQLRC = SQLCODE; EXEC CICS ASKTIME ABSTIME(ABS_TIME); EXEC CICS FORMATTIME ABSTIME(ABS_TIME) MMDDYYYY(DATE1) TIME(TIME1); EM_DATE = DATE1; EM_TIME = TIME1; EM_PGMNAME = ‘LGIPDB01’; /* Or LGIPOL01 */

/* Write primary structured diagnostic record */ EXEC CICS LINK PROGRAM(‘LGSTSQ’) COMMAREA(ERROR_MSG) LENGTH(STG(ERROR_MSG));

/* Conditionally dump up to 90 bytes of raw input COMMAREA */ If EIBCALEN > 0 Then Do; If EIBCALEN < 91 Then CA_DATA = LEFT(COMM_AREA_RAW, EIBCALEN); Else CA_DATA = LEFT(COMM_AREA_RAW, 90);

  EXEC CICS LINK PROGRAM('LGSTSQ')
                 COMMAREA(CA_ERROR_MSG)
                 LENGTH(STG(CA_ERROR_MSG));

End; End WRITE_ERROR_MESSAGE;

## 8. Usage Examples

### 8.1 Successful Motor Policy Inquiry (`01IMOT`)

**Input Communication Area:**
- `CA_REQUEST_ID`: `'01IMOT'`
- `CA_CUSTOMER_NUM`: `0000012345`
- `CA_POLICY_NUM`: `0000067890`

**Execution Trace:**
1. `LGIPOL01` validates `EIBCALEN > 0`, initializes `CA_RETURN_CODE = '00'`, and links to `LGIPDB01`.
2. `LGIPDB01` casts `CA_CUSTOMER_NUM` to `12345` and `CA_POLICY_NUM` to `67890`.
3. Dispatches to `GET_MOTOR_DB2_INFO`, running SQL `SELECT` joining `POLICY` and `MOTOR`.
4. Retrieves row (`SQLCODE = 0`), validates COMMAREA size, converts binary integer host variables into display format, and sets delimiter `CA_M_FILLER(1) = 'FINAL'`.
5. Returns control through `LGIPOL01` back to the client.

**Populated Output COMMAREA:**

### 8.3 Error Scenario: Missing COMMAREA (Abend Path)

**Input Condition:**
- Transaction initiated without a COMMAREA (`EIBCALEN = 0`).

**Execution Trace:**
1. `LGIPOL01` checks `EIBCALEN = 0`.
2. Populates `EM_MSG_TEXT = ' NO COMMAREA RECEIVED'`.
3. Calls `WRITE_ERROR_MESSAGE`, which executes `EXEC CICS LINK PROGRAM('LGSTSQ')` to write the error to the CICS TDQ.
4. Executes `EXEC CICS ABEND ABCODE('LGCA') NODUMP`.
5. Task immediately terminates; no backend DB2 programs or database cursors are invoked.
