Customer VSAM File Services & Key Management

1. Overview

The Customer VSAM File Services & Key Management subsystem is a suite of three CICS-hosted PL/I programs that collectively manage the full lifecycle of customer profile records stored in the KSDSCUST VSAM Key-Sequenced Data Set (KSDS). Together, they provide synchronized write, random key selection, and update services that form the persistent storage backbone of the General Insurance Application (GenApp).

Program Role Operation
LGACVS01 Customer Record Addition Writes a new customer record to KSDSCUST using CA_CUSTOMER_NUM as the KSDS key
LGICVS01 Random Customer Key Selection Reads the GENACNTL TS queue for the valid customer number range and resolves a real customer key via a GTEQ read against KSDSCUST
LGUCVS01 Customer Record Update Reads an existing record from KSDSCUST with exclusive UPDATE intent and rewrites it with new data from the COMMAREA

All three programs share the same COMMAREA layout (defined in the LGCMAREA PL/I include member), use the same CICS error-logging utility (LGSTSQ), and treat CA_CUSTOMER_NUM as the canonical 10-digit KSDS record key. Failures in LGACVS01 and LGUCVS01 result in controlled CICS abends with distinct abend codes (LGV0, LGV1, LGV2) that are visible in operational monitoring.

2. System Architecture

The three programs operate in distinct layers: a caller layer (business orchestrators that invoke the VSAM programs via EXEC CICS LINK), a VSAM services layer (the three programs documented here), and a data/infrastructure layer (the VSAM KSDS file, the CICS TS control queue, and the error logging utility).

The caller layer programs are responsible for populating the COMMAREA and deciding which VSAM service program to invoke. The VSAM service programs are single-purpose: each performs exactly one class of file operation and returns a CA_RETURN_CODE to the caller indicating success or failure. The LGSTSQ error logger is shared across all three programs and writes structured diagnostic records — including timestamp, customer number, and CICS response codes — to a CICS Temporary Storage queue.

3. LGACVS01 — Customer Record Addition

3.1 Purpose

LGACVS01 is responsible for adding a new customer record to the KSDSCUST VSAM KSDS file. It receives a fully populated COMMAREA from its caller (typically LGACDB01, the DB2 Add-Customer back-end), uses CA_CUSTOMER_NUM as both the KSDS record key and the FROM anchor, writes the entire COMMAREA as a single new record, and either returns normally on success or signals failure via CA_RETURN_CODE = '80' and abends with code LGV0.

3.2 Inputs and Outputs

Primary Inputs

Field Type Description
CA_CUSTOMER_NUM PIC '9999999999' 10-digit KSDS key; used as both RIDFLD and FROM anchor
CA_FIRST_NAME CHAR(10) Customer first name
CA_LAST_NAME CHAR(20) Customer last name
CA_DOB CHAR(10) Date of birth
CA_EMAIL_ADDRESS CHAR(100) Email address
EIBCALEN EIB field Controls the byte length of the VSAM write

Primary Outputs

Output Value / Location Condition
New KSDS record in KSDSCUST Keyed by CA_CUSTOMER_NUM On success
CA_RETURN_CODE = '80' COMMAREA On VSAM WRITE failure
Error message via LGSTSQ CICS TS diagnostic queue On VSAM WRITE failure
CICS ABEND code LGV0 CICS system log On VSAM WRITE failure

3.3 Processing Flow

The program’s processing logic is minimal by design: it performs a single EXEC CICS WRITE FILE and either returns normally or enters a structured error path.

graph TD A([Start LGACVS01]) --> B[Capture COMMAREA length\nWS_Commarea_Len = EIBCALEN] B --> C[EXEC CICS WRITE FILE KSDSCUST\nKey = CA_CUSTOMER_NUM\nLength = WS_Commarea_Len] C --> D{{WS_RESP = DFHRESP NORMAL}} D -- Yes --> E([Return to caller — Success]) D -- No --> F[Capture WS_RESP2 = EIBRESP2\nSet CA_RETURN_CODE = 80] F --> G[Call WRITE_ERROR_MESSAGE\nASKTIME / FORMATTIME\nPopulate ERROR_MSG\nLINK to LGSTSQ\nDump COMMAREA via LGSTSQ] G --> H[EXEC CICS ABEND ABCODE LGV0 NODUMP] H --> I([EXEC CICS RETURN — End])

Step-by-step description:

  1. Initialise COMMAREA length — WS_Commarea_Len = EIBCALEN is the very first executable statement, ensuring the byte count is recorded before any CICS command can alter EIB fields.
  2. Write to KSDSCUST — EXEC CICS WRITE FILE('KSDSCUST') is issued with FROM(CA_CUSTOMER_NUM), LENGTH(WS_Commarea_Len), RIDFLD(CA_CUSTOMER_NUM), KEYLENGTH(10), and RESP(WS_RESP).
  3. Check response — If WS_RESP = DFHRESP(NORMAL), the program falls through to RETURN. Otherwise, error handling is initiated.
  4. Error handling — CA_RETURN_CODE is set to '80'; the WRITE_ERROR_MESSAGE procedure acquires a timestamp, assembles the ERROR_MSG structure, and links twice to LGSTSQ (once for the structured error, once for a raw COMMAREA dump of up to 90 bytes).
  5. Abend and return — EXEC CICS ABEND ABCODE('LGV0') NODUMP terminates the task; EXEC CICS RETURN follows as a defensive safety net.

3.4 CICS WRITE Command

CODE 
EXEC CICS WRITE
    FILE('KSDSCUST')
    FROM(CA_Customer_Num)
    LENGTH(WS_Commarea_Len)
    RIDFLD(CA_Customer_Num)
    KEYLENGTH(10)
    RESP(WS_RESP)
END-EXEC
