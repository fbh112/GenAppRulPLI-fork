Domain Map

1. Overview

The GenApp (PL/I) application is a CICS-based insurance processing system running on z/OS. It manages the full lifecycle of insurance customers and policies across four product lines — Motor, Endowment, House, and Commercial — as well as associated Claims. The application is organized into six distinct functional domains, each with clear responsibilities and well-defined integration points.

  • Presentation / Menu Domain acts as the user-facing entry point, routing terminal input to the appropriate business logic via CICS LINK calls.
  • Customer Management Domain handles the full customer lifecycle — creation, retrieval, and update — against both DB2 and VSAM backends.
  • Policy Management Domain manages all policy operations (Add, Inquire, Delete, Update) across all four product lines.
  • Business Rules Domain applies IBM Operational Decision Manager (ODM) underwriting rules specifically for Endowment policy additions.
  • Batch Reporting Domain provides offline reporting capabilities outside the CICS environment.
  • Operations & Infrastructure Domain underpins all other domains with error logging, statistics, counter management, and environment setup.

All online domains share a common COMMAREA structure (LGCMAREA), communicate via EXEC CICS LINK, and report errors through the shared LGSTSQ logger. Persistent state is held in DB2 (GENASA1 schema), VSAM datasets, and CICS TS queues.

2. System Architecture

The overall architecture follows a layered, request-routing pattern. Terminal menus at the top delegate work downward through orchestrators into backend programs and finally into data stores. A supporting infrastructure layer cuts across all domains horizontally.

3. Business Domains

3.1 Presentation / Menu Domain

The Presentation domain is the sole entry point for all online user interactions. Five BMS terminal menu programs correspond to the five business objects managed by the application: one for Customer management and one each for the four policy lines.

Aspect Detail
Business responsibility CICS BMS terminal menus; the user-facing entry point for all online policy and customer transactions. Accepts user input (customer/policy number, field values), routes to the appropriate operation orchestrator via EXEC CICS LINK, and displays results.
Programs LGTESTC1 (Customer menu), LGTESTP1 (Motor), LGTESTP2 (Endowment), LGTESTP3 (House), LGTESTP4 (Commercial)
Data stores None directly — pass/receive COMMAREA only
Key dependencies BMS mapset SSMAP (%INCLUDE SSMAP) · COMMAREA structure LGCMAREA · All orchestrators in Customer & Policy domains

Menu programs share BMS map structures via a common include:

PLI 
/* Include the BMS map structure for all menus */
%INCLUDE SSMAP;

Each menu populates the COMMAREA and issues a CICS LINK to the appropriate orchestrator:

PLI 
EXEC CICS LINK
    PROGRAM(CA-REQUEST-PROGRAM)
    COMMAREA(LGCMAREA)
    LENGTH(32500)
    END-EXEC;

3.2 Customer Management Domain

The Customer Management domain owns the complete customer lifecycle. Orchestrator programs validate incoming COMMAREs and dispatch dynamically to either the DB2 or VSAM backend program, providing storage-agnostic routing.

Aspect Detail
Business responsibility Full customer lifecycle: create, retrieve, and update a customer record. Maintains the CUSTOMER and CUSTOMER_SECURE DB2 tables and a parallel VSAM store.
Programs Orchestrators: LGACUS01 (Add), LGICUS01 (Inquire), LGUCUS01 (Update) · DB2 backends: LGACDB01, LGICDB01, LGUCDB01, LGACDB02 (security) · VSAM backends: LGACVS01, LGICVS01, LGUCVS01
Data stores DB2 tables GENASA1.CUSTOMER and GENASA1.CUSTOMER_SECURE · VSAM customer dataset · CICS Named Counter GENACUSTNUM (pool GENA)
Key dependencies COMMAREA structure LGCMAREA.inc · Error logger LGSTSQ · Called by Presentation domain
graph TD A["Presentation Menu\n(LGTESTC1)"] -->|EXEC CICS LINK| B["Customer Orchestrator\n(LGACUS01 / LGICUS01 / LGUCUS01)"] B -->|EXEC CICS LINK| C["DB2 Backend\n(LGACDB01 / LGICDB01 / LGUCDB01)"] B -->|EXEC CICS LINK| D["VSAM Backend\n(LGACVS01 / LGICVS01 / LGUCVS01)"] B -->|Security insert| E["DB2 Secure Backend\n(LGACDB02)"] C -->|EXEC SQL INSERT/SELECT/UPDATE| F[("DB2\nGENASA1.CUSTOMER\nGENASA1.CUSTOMER_SECURE")] D -->|VSAM WRITE/READ/REWRITE| G[("VSAM\nCustomer Dataset")] B -->|On error: EXEC CICS LINK| H["Error Logger\n(LGSTSQ)"]

A new customer number is generated using a CICS Named Counter to guarantee uniqueness across all concurrent transactions:

PLI 
EXEC CICS GET COUNTER('GENACUSTNUM')
    POOL('GENA')
    VALUE(WS-CUSTOMER-NUM)
    INCREMENT(1)
    END-EXEC;

3.3 Policy Management Domain

The Policy Management domain is the most complex in the application. It supports four distinct product lines, each with its own set of DB2 child tables (all foreign-keyed to the parent POLICY table), and optionally invokes the Business Rules domain for Endowment underwriting.

Aspect Detail
Business responsibility Full policy lifecycle (Add, Inquire, Delete, Update) for four product lines: Motor, Endowment, House, Commercial, plus Claims. Orchestrators resolve routing; DB2 backends own the SQL; VSAM backends provide alternative/fallback storage.
Programs Orchestrators: LGAPOL01, LGIPOL01, LGDPOL01, LGUPOL01 · DB2 backends: LGAPDB01, LGIPDB01, LGDPDB01, LGUPDB01 · VSAM backends: LGAPVS01, LGIPVS01, LGDPVS01, LGUPVS01
Data stores DB2 tables GENASA1.POLICY, ENDOWMENT, HOUSE, MOTOR, COMMERCIAL, CLAIM (all FK children of POLICY) · VSAM policy dataset
Key dependencies LGCMAREA.inc + product-specific fields (CA_MOTOR, CA_ENDOWMENT, CA_HOUSE, CA_COMMERCIAL, CA_CLAIM) · Business Rules domain (optional, Endowment Add only) · Error logger LGSTSQ
graph TD MENU["Presentation Menu\n(LGTESTPx)"] -->|EXEC CICS LINK| ORCH["Policy Orchestrator\n(LGAPOL01 / LGIPOL01 /\nLGDPOL01 / LGUPOL01)"] ORCH -->|Policy type = Endowment\nBUSINESS_RULES = Y| BR["Business Rules\n(LGAPBR01 — ODM)"] ORCH -->|EXEC CICS LINK| DB2B["DB2 Backend\n(LGAPDB01 / LGIPDB01 /\nLGDPDB01 / LGUPDB01)"] ORCH -->|EXEC CICS LINK| VSAMB["VSAM Backend\n(LGAPVS01 / LGIPVS01 /\nLGDPVS01 / LGUPVS01)"] DB2B -->|SQL| DB2[("DB2 GENASA1\nPOLICY\nMOTOR · ENDOWMENT\nHOUSE · COMMERCIAL\nCLAIM")] VSAMB -->|VSAM I/O| VSAM[("VSAM\nPolicy Dataset")] ORCH -->|On error| OPS["Error Logger\n(LGSTSQ)"]

The Policy Add orchestrator conditionally invokes the Business Rules engine only for Endowment policies when the underwriting flag is set:

PLI 
IF CA_POLICY_TYPE = 'E' &
   BUSINESS_RULES = 'Y' THEN DO;
    EXEC CICS LINK
        PROGRAM('LGAPBR01')
        COMMAREA(LGCMARER)
        LENGTH(LENGTH(LGCMARER))
        END-EXEC;
END;

3.4 Business Rules Domain

The Business Rules domain provides a narrow but critical integration point with IBM Operational Decision Manager (ODM). It is invoked exclusively during Endowment policy addition and receives a dedicated, purpose-built COMMAREA structure rather than the general LGCMAREA.

Aspect Detail
Business responsibility Applies IBM ODM underwriting rules to Endowment policy additions. Called optionally by the Policy Add orchestrator only when the BUSINESS_RULES flag is 'Y'.
Programs LGAPBR01 (external — not present as source in this workspace; referenced by LGAPOL01)
Data stores None directly; operates on the Endowment policy data passed in LGCMARER.inc
Key dependencies Caller: LGAPOL01 (CICS LINK, conditional) · Include LGCMARER.inc (business rule request/response structure)

The dedicated COMMAREA used for the ODM bridge is defined separately from the general-purpose COMMAREA:

PLI 
/* Business Rule Request/Response area — used only by LGAPOL01 and LGAPBR01 */
%INCLUDE LGCMARER;

3.5 Batch Reporting Domain

The Batch Reporting domain runs entirely outside the CICS environment as standard z/OS batch jobs. It reads from the operational DB2 tables and produces formatted sequential output files — a customer report and a motor policy extract — using static PL/I CALL statements rather than EXEC CICS LINK.

Aspect Detail
Business responsibility Non-CICS batch programs for offline reporting. LGBATCH reads customer keys from a sequential file, fetches each from DB2, and produces a formatted report via the reusable LGBATCHF subroutine. LGMOTOUT dumps all MOTOR table rows to a sequential output file.
Programs LGBATCH (customer report driver), LGBATDB2 (DB2 test driver), LGBATCHF (report formatter subroutine), LGMOTOUT (motor table extract)
Data stores DB2 GENASA1.CUSTOMER (read) · DB2 GENASA1.MOTOR (read) · Sequential flat files: CUSTIN (input key file), CUSTRPT (customer report), MOTOROUT (motor extract)
Key dependencies LGCMAREA.inc (used as work area) · No CICS dependency — runs as standard z/OS batch
graph LR CUSTIN[("Flat File\nCUSTIN\n(input keys)")] -->|Sequential read| LGBATCH["LGBATCH\n(Report Driver)"] LGBATCH -->|EXEC SQL SELECT| DB2C[("DB2\nGENASA1.CUSTOMER")] LGBATCH -->|Static CALL| LGBATCHF["LGBATCHF\n(Report Formatter)"] LGBATCHF -->|Sequential write| CUSTRPT[("Flat File\nCUSTRPT\n(customer report)")] LGMOTOUT["LGMOTOUT\n(Motor Extract)"] -->|EXEC SQL SELECT| DB2M[("DB2\nGENASA1.MOTOR")] LGMOTOUT -->|Sequential write| MOTOROUT[("Flat File\nMOTOROUT\n(motor extract)")]

The batch report driver uses a static CALL to invoke the formatter — no CICS context is required:

PLI 
/* Batch: call the report formatter as a standard PL/I subroutine */
CALL LGBATCHF(LGCMAREA, REPORT_LINE);

3.6 Operations & Infrastructure Domain

The Operations & Infrastructure domain is the horizontal backbone of the entire online application. It provides environment initialisation, event-driven statistics collection, periodic counter sampling, and a shared error-logging service consumed by every other online domain.

Aspect Detail
Business responsibility Environment lifecycle and operational observability. LGSETUP initialises all CICS named counters and TS queues. LGASTAT1 increments success/failure counters per transaction. LGWEBST5 samples all counters every minute. LGSTSQ is the shared error-logging service (writes to TDQ CSMT and TS queue GENAERRS).
Programs LGSETUP, LGASTAT1, LGWEBST5, LGSTSQ
Data stores CICS Named Counter pool GENA (36 counters) · CICS TS queues GENASTRT, GENASTAT, GENAERRS, GENACNTL, GENA<code>V (rate queues) · TDQ CSMT
Key dependencies No business data dependency · Consumed by all other online domains via EXEC CICS LINK LGSTSQ on every error path
sequenceDiagram participant Domain as Any Online Domain participant LGSTSQ as LGSTSQ (Error Logger) participant TDQ as TDQ CSMT participant TSQ as TS Queue GENAERRS participant LGASTAT1 as LGASTAT1 (Statistics) participant Counter as CICS Named Counter (GENA pool) Domain->>LGSTSQ: EXEC CICS LINK (on error) LGSTSQ->>TDQ: EXEC CICS WRITEQ TD (CSMT) LGSTSQ->>TSQ: EXEC CICS WRITEQ TS (GENAERRS) LGSTSQ-->>Domain: Return Domain->>LGASTAT1: EXEC CICS LINK (event notification) LGASTAT1->>Counter: EXEC CICS UPDATE COUNTER (increment success/fail) LGASTAT1-->>Domain: Return

The shared error logger is invoked consistently across all domains using the same pattern:

PLI 
/* Shared error logging — called on every error path */
EXEC CICS LINK
    PROGRAM('LGSTSQ')
    COMMAREA(LGCMAREA)
    LENGTH(LENGTH(LGCMAREA))
    END-EXEC;

5. Shared Integration Points

All domains interact through a small set of common artifacts. Understanding these integration points is essential for any cross-domain change analysis.

Artifact Type Used By
LGCMAREA.inc PL/I include (COMMAREA) All online programs
LGCMARER.inc PL/I include (BR request/response) LGAPOL01, LGAPBR01
SSMAP.inc BMS map structure All 5 menu programs
LGSTSQ Shared CICS service Every domain (error logging)
GENA named counter pool CICS infrastructure Customer Mgmt, Operations
DB2 database GENASA1 Relational store Customer, Policy, Batch domains

The COMMAREA structure LGCMAREA is the central data contract of the application. It carries the request identifier, customer and policy numbers, and all product-specific field overlays:

PLI 
/* Central COMMAREA — shared by all online domains */
%INCLUDE LGCMAREA;

/* Product-specific field overlays within LGCMAREA */
/*   CA_MOTOR      — Motor policy fields   */
/*   CA_ENDOWMENT  — Endowment policy fields */
/*   CA_HOUSE      — House policy fields   */
/*   CA_COMMERCIAL — Commercial policy fields */
/*   CA_CLAIM      — Claims fields         */

6. Data Model Overview

6.1 DB2 Schema (GENASA1)

The DB2 schema follows a hub-and-spoke model: CUSTOMER and POLICY are the two parent entities. All product-specific tables are child tables of POLICY via foreign key.

6.2 VSAM and Flat File Stores

In addition to DB2, the application maintains parallel VSAM stores for both customers and policies. These serve as an alternative storage path that the orchestrators can route to independently of DB2 availability. The Batch Reporting domain uses three sequential flat files that exist entirely outside the CICS/VSAM ecosystem:

File DD Name Direction Used By
Customer input keys CUSTIN Input LGBATCH
Customer report CUSTRPT Output LGBATCHF
Motor extract MOTOROUT Output LGMOTOUT
