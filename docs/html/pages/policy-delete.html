Policy Delete

1. Overview

The Policy Delete function removes an insurance policy from the General Insurance Application (GenApp). It is a three-program chain that runs under CICS and is written in Enterprise PL/I:

Program Role Data store
LGDPOL01 Front end. Validates the request and routes it. None (delegates)
LGDPDB01 Deletes the policy from DB2. Foreign-key cascade removes the policy-type row. DB2 (POLICY and child tables)
LGDPVS01 Deletes the matching record from the VSAM KSDS file KSDSPOLY. VSAM (KSDSPOLY)

The chain supports four policy types, each selected by CA_REQUEST_ID:

Request ID Policy type
01DEND Endowment
01DHOU House
01DCOM Commercial
01DMOT Motor

All programs share one COMMAREA layout, COMM_AREA, which comes from the LGCMAREA include. Each program reports its outcome in CA_RETURN_CODE. Failures are written to a transient data queue by the shared logging program LGSTSQ.

1.1 Return codes

Code Set by Meaning
00 LGDPOL01, LGDPDB01 Success. This is the initial value.
81 LGDPVS01 The VSAM DELETE of KSDSPOLY failed.
90 LGDPDB01 A DB2 error occurred on the DELETE from POLICY.
98 LGDPOL01, LGDPDB01 The COMMAREA is shorter than the 28-byte minimum header.
99 LGDPOL01, LGDPDB01 The request identifier is not recognised.

2.3 Shared COMMAREA

LGCMAREA is included in all three programs with %INCLUDE LGCMAREA;. It defines COMM_AREA as a BASED UNION over the COMM_AREA_PTR parameter. Fields used by this flow:

Field Type Used for
CA_REQUEST_ID CHAR(6) Selects the delete type. LGDPVS01 uses its 4th character in the VSAM key.
CA_RETURN_CODE PIC '99' Outcome reported to the caller.
CA_CUSTOMER_NUM PIC '9999999999' Customer key.
CA_POLICY_NUM PIC '9999999999' Policy key.
CA_POLICY_COMMON group Issue date, expiry date, broker ID, broker’s reference, payment. Passed through.
CA_ENDOWMENT, CA_HOUSE, CA_MOTOR, CA_COMMERCIAL union members Policy-type-specific data, passed through.
COMM_AREA_RAW CHAR(32500) Raw overlay, used for diagnostic dumps.

4. Front End: LGDPOL01

4.1 Responsibilities

LGDPOL01 is the business-logic entry point. It does the following:

  • Captures EIBTRNID, EIBTRMID and EIBTASKN into WS_HEADER for dump analysis.
  • Validates that a COMMAREA exists and is at least 28 bytes (WS_CA_HEADER_LEN).
  • Copies the customer and policy numbers into the error message structure ahead of time, so any later log entry is complete.
  • Normalises CA_REQUEST_ID to uppercase and routes it.
  • Delegates the delete to LGDPDB01 and passes the result back to the caller.

4.2 Validation and Routing

PLI 
IF EIBCALEN = 0 THEN DO;
   EM_MSG_TEXT = ' NO COMMAREA RECEIVED';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS ABEND ABCODE('LGCA') NODUMP;
END;

CA_RETURN_CODE = '00';
WS_CALEN = EIBCALEN;
IF EIBCALEN < WS_CA_HEADER_LEN THEN DO;
   CA_RETURN_CODE = '98';
   EXEC CICS RETURN;
END;

EM_CUSNUM = CA_CUSTOMER_NUM;
EM_POLNUM = CA_POLICY_NUM;
CA_REQUEST_ID = UPPERCASE(CA_REQUEST_ID);

SELECT (CA_REQUEST_ID);
  WHEN ('01DEND','01DHOU','01DCOM','01DMOT') DO;
     CALL DELETE_POLICY_DB2_INFO;
     IF CA_RETURN_CODE > 0 THEN
        EXEC CICS RETURN;
  END;
  OTHERWISE
     CA_RETURN_CODE = '99';
END;
EXEC CICS RETURN;

All four request types share one branch. The UPPERCASE built-in means mixed-case input is accepted.

4.3 DB2 Delegation

DELETE_POLICY_DB2_INFO is a thin wrapper that passes the whole COMMAREA to LGDPDB01:

PLI 
EXEC CICS LINK PROGRAM(LGDPDB01)
               COMMAREA(COMM_AREA)
               LENGTH(32500);

Any failure comes back through CA_RETURN_CODE. The caller checks it with CA_RETURN_CODE > 0.

5. DB2 Delete: LGDPDB01

5.1 Responsibilities

LGDPDB01 is the DB2 back end. It does the following:

  • Repeats the COMMAREA presence and length checks.
  • Converts CA_CUSTOMER_NUM and CA_POLICY_NUM to FIXED BIN(31) host variables (DB2_CUSTOMERNUM_INT, DB2_POLICYNUM_INT).
  • Issues one DELETE against POLICY.
  • On success, links to LGDPVS01 to remove the VSAM counterpart.

5.2 Routing and VSAM Hand-off

PLI 
SELECT (CA_REQUEST_ID);
  WHEN ('01DEND','01DHOU','01DCOM','01DMOT') DO;
     CALL DELETE_POLICY_DB2_INFO;
     EXEC CICS LINK PROGRAM('LGDPVS01')
                    COMMAREA(COMM_AREA)
                    LENGTH(32500);
  END;
  OTHERWISE
     CA_RETURN_CODE = '99';
END;
EXEC CICS RETURN;

If DELETE_POLICY_DB2_INFO hits a DB2 error, it issues EXEC CICS RETURN itself. The LGDPVS01 link is therefore skipped.

5.3 The DB2 DELETE

PLI 
EM_SQLREQ = ' DELETE POLICY  ';
EXEC SQL DELETE FROM POLICY
   WHERE ( CUSTOMERNUMBER = :DB2_CUSTOMERNUM_INT
       AND POLICYNUMBER   = :DB2_POLICYNUM_INT );

IF SQLCODE <> 0 THEN DO;
   CA_RETURN_CODE = '90';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS RETURN;
END;

The program never deletes from the policy-type tables explicitly. It relies on the foreign-key cascade defined in DB2.

The source says SQLCODE 100 (row not found) is acceptable. The IF SQLCODE <> 0 test as written would also catch 100 and set return code 90. The two statements are inconsistent, so check the actual behaviour in your environment.

6. VSAM Delete: LGDPVS01

6.1 Responsibilities

LGDPVS01 is the VSAM back end and the counterpart of the DB2 program. It builds a 21-byte composite key and deletes the matching record from KSDSPOLY.

6.2 Composite Key

Key part Source Length
WF_REQUEST_ID 4th character of CA_REQUEST_ID 1
WF_CUSTOMER_NUM CA_CUSTOMER_NUM 10
WF_POLICY_NUM CA_POLICY_NUM 10
Total 21

For 01DMOT, the 4th character is D. The source examples use a different sample ID (DPV001) whose 4th character is '0'.

6.3 Delete Logic

PLI 
WS_Commarea_Len = EIBCALEN;
WF_Request_ID   = SUBSTR(CA_Request_ID,4,1);
WF_Policy_Num   = CA_Policy_Num;
WF_Customer_Num = CA_Customer_Num;

EXEC CICS DELETE FILE('KSDSPOLY')
               RIDFLD(WF_Policy_Key)
               KEYLENGTH(21)
               RESP(WS_RESP);

IF WS_RESP <> DFHRESP(NORMAL) THEN DO;
   WS_RESP2 = EIBRESP2;
   CA_RETURN_CODE = '81';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS RETURN;
END;
RETURN;

Because the command uses RESP, a failure does not cause an implicit abend. The program handles the error itself.

6.4 Behavioural Notes

  • LGDPVS01 does no COMMAREA length validation of its own. It relies on its caller, LGDPDB01, having done that.
  • On success it leaves CA_RETURN_CODE unchanged, which is 00 after the earlier checks.
  • The error message populates EM_CUSNUM, EM_RESPRC and EM_RESP2RC. The program description lists EM_POLNUM, but the code shown never assigns it, so the logged policy number may be blank.

6.5 VSAM Delete Flow

graph TD A([Entry]) --> B[WS_Commarea_Len = EIBCALEN] B --> C[Build 21-byte WF_POLICY_KEY] C --> D[EXEC CICS DELETE KSDSPOLY] D --> E{RESP = NORMAL} E -- Yes --> F([RETURN success]) E -- No --> G[WS_RESP2 = EIBRESP2
RC = 81] G --> H[WRITE_ERROR_MESSAGE] H --> I([EXEC CICS RETURN])

7. Error Handling and Logging

7.1 Error Matrix

Condition Detected in Action Return code
EIBCALEN = 0 LGDPOL01, LGDPDB01 Log, then ABEND LGCA NODUMP None (task abends)
EIBCALEN < 28 LGDPOL01, LGDPDB01 Return immediately, no log 98
Unknown request ID LGDPOL01, LGDPDB01 Return, no log 99
DB2 SQLCODE <> 0 LGDPDB01 Log, return, skip VSAM 90
VSAM RESP <> NORMAL LGDPVS01 Log, return 81

7.2 Error Logging Sequence

Each program has its own WRITE_ERROR_MESSAGE procedure. All three work the same way:

sequenceDiagram participant P as Program participant CICS as CICS participant L as LGSTSQ participant Q as TD Queue P->>CICS: ASKTIME ABSTIME(WS_ABSTIME) P->>CICS: FORMATTIME MMDDYYYY(WS_DATE) TIME(WS_TIME) P->>L: LINK COMMAREA(ERROR_MSG) L->>Q: Write formatted error record alt EIBCALEN greater than 0 P->>P: CA_DATA = LEFT(COMM_AREA_RAW, min(EIBCALEN, 90)) P->>L: LINK COMMAREA(CA_ERROR_MSG) L->>Q: Write COMMAREA= snapshot end

7.3 Error Message Content

Field LGDPOL01 LGDPDB01 LGDPVS01
EM_DATE / EM_TIME Yes Yes Yes
Program name literal LGDPOL01 LGDPDB01 LGDPVS01
EM_CUSNUM Yes Yes Yes
EM_POLNUM Yes Yes Not assigned
EM_SQLREQ / EM_SQLRC No ' DELETE POLICY ' and SQLCODE No
EM_RESPRC / EM_RESP2RC No No Yes
Text ' NO COMMAREA RECEIVED' Same, or the SQL label ' Delete file KSDSPOLY'

7.4 COMMAREA Snapshot Rule

The snapshot is capped at 90 bytes, the size of CA_DATA:

PLI 
IF EIBCALEN > 0 THEN DO;
   IF EIBCALEN < 91 THEN
      CA_DATA = LEFT(COMM_AREA_RAW, EIBCALEN);
   ELSE
      CA_DATA = LEFT(COMM_AREA_RAW, 90);
   EXEC CICS LINK PROGRAM('LGSTSQ')
                  COMMAREA(CA_ERROR_MSG)
                  LENGTH(STG(CA_ERROR_MSG));
END;

8. Dependencies and Constraints

8.1 Dependencies

Dependency Used by Purpose
CICS runtime (EIB, LINK, RETURN, ABEND, ASKTIME, FORMATTIME) All Transaction services
LGCMAREA include All COMM_AREA layout
SQLCA include LGDPDB01 SQLCODE access
DB2 POLICY and type tables LGDPDB01 Policy data and cascade
VSAM KSDS KSDSPOLY LGDPVS01 Policy record store
LGSTSQ All Writes errors to the TD queue

8.2 Key Constraints

  • The COMMAREA must be at least 28 bytes. The maximum raw size is 32,500 bytes, and every LINK in the chain passes LENGTH(32500).
  • Customer and policy numbers are 10-digit pictures. LGDPDB01 converts them to FIXED BIN(31), so valid values are 0 to 2,147,483,647.
  • The DB2 delete needs both CUSTOMERNUMBER and POLICYNUMBER to match.
  • Order is fixed: LGDPOL01 validates, LGDPDB01 deletes from DB2, then LGDPVS01 deletes from VSAM. A DB2 error stops the chain before VSAM is touched.
  • The policy-type fields are members of a UNION and share storage. Only the layout matching CA_REQUEST_ID is meaningful.
  • The two stores are not updated in one unit of work by the program logic described here. An 81 from LGDPVS01 is reported after the DB2 row has already been deleted. The source documents do not describe any compensating action.
  • LGDPVS01 uses the key request-type character + customer + policy. The KSDS must be defined with exactly this 21-byte key.

9. Examples

9.1 Successful Motor Policy Delete

Input:

Field Value
CA_REQUEST_ID 01DMOT
CA_CUSTOMER_NUM 0000001234
CA_POLICY_NUM 0000005678
COMMAREA length 32500

Processing:

  1. LGDPOL01 passes the length checks and matches 01DMOT.
  2. LGDPDB01 runs DELETE FROM POLICY WHERE CUSTOMERNUMBER = 1234 AND POLICYNUMBER = 5678. DB2 cascades the delete to the MOTOR row. SQLCODE is 0.
  3. LGDPVS01 deletes the KSDSPOLY record. RESP is NORMAL.
  4. The caller receives CA_RETURN_CODE = '00'.

9.2 Unknown Request ID

Input: CA_REQUEST_ID = '01DTRV', with a valid length.

The OTHERWISE branch in LGDPOL01 sets CA_RETURN_CODE = '99'. LGDPDB01 is never linked, nothing is deleted, and nothing is logged.

9.3 COMMAREA Too Small

Input: a 20-byte COMMAREA.

EIBCALEN (20) is less than 28, so LGDPOL01 sets CA_RETURN_CODE = '98' and returns at once. No routing or database call happens.

9.4 DB2 Failure

Input: CA_REQUEST_ID = '01DHOU', and DB2 returns a non-zero SQLCODE such as -904.

LGDPDB01 sets CA_RETURN_CODE = '90' and writes two entries through LGSTSQ: the formatted message (date, time, customer, policy, ' DELETE POLICY ', SQLCODE) and a COMMAREA= snapshot of up to 90 bytes. It then returns without linking LGDPVS01. LGDPOL01 sees CA_RETURN_CODE > 0 and returns the 90 to the caller.

9.5 VSAM Failure

Input: a valid DB2 delete, but no KSDSPOLY record exists for the key. CICS returns NOTFND.

LGDPVS01 sets WS_RESP2 = EIBRESP2 and CA_RETURN_CODE = '81'. It logs ' Delete file KSDSPOLY' with both response codes, then returns. The DB2 delete has already been applied at this point.
