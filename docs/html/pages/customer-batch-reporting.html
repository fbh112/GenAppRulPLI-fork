Customer Batch Reporting & Test Drivers

1. Overview

The Customer Batch Reporting & Test Drivers area of the GenApp insurance application is a set of standalone PL/I programs that run outside CICS. They query customer data from DB2, format customer report lines, and produce batch output.

Program Role Type Output
LGBATCH Main batch report generator Proc Options(Main) Sequential file CUSTRPT (80-byte records)
LGBATCHF Report-line formatting subroutine Called subroutine (external entry) 80-character LS_LINE returned to caller
LGBATDB2 DB2 test driver for a single customer Proc Options(Main) DISPLAY output to SYSOUT

1.1 Business Purpose

  • LGBATCH reads a sequential list of customer numbers from CUSTIN. For each number it looks up the customer in the DB2 CUSTOMER table. It then asks LGBATCHF to format a report line and writes that line to CUSTRPT.
  • LGBATCHF is a pure formatting utility. It does no I/O or DB2 access. It takes the first word of the first name and the first word of the last name, and builds a line such as Customer 0000000042 is John Smith.
  • LGBATDB2 is a minimal test driver. It exercises the same DB2-to-formatter pipeline for the hard-coded customer number 1 and displays the result on the console.

1.2 Key Characteristics

  • None of the programs use CICS. They rely on embedded SQL (with SQLCA) and PL/I file handling.
  • All three share the LGCMAREA COMMAREA layout. It is a BASED structure overlaid on a 32,500-byte working storage buffer (BATCH_COMM_AREA).
  • The formatter is dynamically loaded with FETCH LGBATCHF and called with the signature ENTRY(PIC '9999999999', PTR, CHAR(80)).

3. Shared Data Structures

3.1 COMMAREA Overlay Pattern

The programs adapt the CICS COMMAREA idiom for batch use. A fixed-size character buffer provides the storage, and a BASED structure is overlaid on it through a pointer:

PLI 
COMM_AREA_PTR = ADDR(BATCH_COMM_AREA);
fetch lgbatchf;

LGBATCHF receives the pointer and re-binds its own BASED structure to the same storage:

PLI 
COMM_AREA_PTR = COMM_PTR;

3.2 Fields Used by the Batch Programs

Field Definition Use
CA_RETURN_CODE PIC '99' 00 success, 01 not found, 90 SQL error (set by LGBATCH)
CA_FIRST_NAME 10 chars Source for the first-name token
CA_LAST_NAME 20 chars Source for the last-name token
CA_DOB 10 chars Populated from DATEOFBIRTH
CA_HOUSE_NAME / CA_HOUSE_NUM 20 / 4 chars Populated from HOUSENAME / HOUSENUMBER
CA_POSTCODE 8 chars Populated from POSTCODE
CA_PHONE_MOBILE / CA_PHONE_HOME 20 chars each Populated from PHONEMOBILE / PHONEHOME
CA_EMAIL_ADDRESS 100 chars Populated from EMAILADDRESS

3.3 Customer Table Entity

erDiagram CUSTOMER { int CUSTOMERNUMBER "Primary key, WHERE predicate" string FIRSTNAME "length 10 - CA_FIRST_NAME" string LASTNAME "length 20 - CA_LAST_NAME" string DATEOFBIRTH "length 10 - CA_DOB" string HOUSENAME "length 20 - CA_HOUSE_NAME" string HOUSENUMBER "length 4 - CA_HOUSE_NUM" string POSTCODE "length 8 - CA_POSTCODE" string PHONEMOBILE "length 20 - CA_PHONE_MOBILE" string PHONEHOME "length 20 - CA_PHONE_HOME" string EMAILADDRESS "length 100 - CA_EMAIL_ADDRESS" }

Both LGBATCH and LGBATDB2 read exactly these nine columns, keyed on CUSTOMERNUMBER. Neither program updates the table.

4. LGBATCH – Batch Customer Report Generator

4.1 Purpose

LGBATCH is the production-style batch program. It loops over every customer number in CUSTIN and writes one 80-byte report line per customer to CUSTRPT.

4.2 Inputs and Outputs

Item Detail
CUSTIN Sequential, fixed-block, RECSIZE(10). Each record is CUSTIN_CUSTNUMBER PIC '9999999999'
CUSTRPT Sequential, fixed-block, RECSIZE(80). One CUSTRPT_LINE per input record
DB2 CUSTOMER Single-row SELECT per customer number
Return code PLIRETC(16) if CUSTIN cannot be opened. Otherwise the return code is implicitly 0
Console 'FILE STATUS AT OPEN CUSTIN' on open failure

4.3 Processing Flow

graph TD A([Start LGBATCH]) --> B[Set COMM_AREA_PTR to BATCH_COMM_AREA
FETCH LGBATCHF] B --> C[ON UNDEFINEDFILE CUSTIN
OPEN CUSTIN and CUSTRPT] C --> D{CUSTIN open failed?} D -- Yes --> E[DISPLAY message
PLIRETC 16
STOP] D -- No --> F[ON ENDFILE CUSTIN
READ first record] F --> G{FI_EOF false?} G -- Yes --> H[PROCESS_RECORD] H --> I[GET_CUSTOMER_INFO
SELECT from CUSTOMER] I --> J{SQLCODE} J -- 0 --> K[CA_RETURN_CODE = 00] J -- 100 --> L[CA_RETURN_CODE = 01] J -- Other --> M[CA_RETURN_CODE = 90
WRITE_ERROR_MESSAGE] K --> N[CALL LGBATCHF] L --> N M --> N N --> O[WRITE CUSTRPT_LINE] O --> P[READ next CUSTIN] P --> G G -- No --> Q[CLOSE files] Q --> R([RETURN])

4.4 Sequence of Operations per Record

sequenceDiagram participant Main as LGBATCH main loop participant PR as PROCESS_RECORD participant GCI as GET_CUSTOMER_INFO participant DB2 as DB2 CUSTOMER participant F as LGBATCHF participant Out as CUSTRPT Main->>PR: Customer number read from CUSTIN PR->>PR: DB2_CUSTOMERNUMBER_INT = CUSTIN_CUSTNUMBER PR->>GCI: Call GCI->>DB2: SELECT ... WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUMBER_INT DB2-->>GCI: Row data and SQLCODE GCI->>GCI: Set CA_RETURN_CODE (00, 01 or 90) GCI-->>PR: Return PR->>F: CALL LGBATCHF(CUSTIN_CUSTNUMBER, COMM_AREA_PTR, CUSTRPT_LINE) F-->>PR: Formatted CUSTRPT_LINE PR->>Out: WRITE FILE(CUSTRPT) PR-->>Main: Return, then READ next record

4.5 Key Procedures

4.5.1 Main Procedure

The main body does the following:

  1. Anchors the COMMAREA with COMM_AREA_PTR = ADDR(BATCH_COMM_AREA).
  2. Fetches LGBATCHF.
  3. Registers the UNDEFINEDFILE handler.
  4. Opens both files.
  5. Registers the ENDFILE handler, which sets FI_EOF = '1'B.
  6. Primes the loop with the first READ.
  7. Runs DO WHILE (^FI_EOF), calling PROCESS_RECORD and then reading the next record.
  8. Closes both files and returns.

The open-failure guard is:

PLI 
ON UNDEFINEDFILE(CUSTIN) BEGIN;
   DISPLAY('FILE STATUS AT OPEN CUSTIN');
   CALL PLIRETC(16);
   STOP;
END;

4.5.2 PROCESS_RECORD

  • It converts the picture-format customer number to the integer host variable. This is needed because the DB2 column is an integer.
  • It calls GET_CUSTOMER_INFO, then LGBATCHF, and then writes the output line.
  • It has no conditional logic of its own. SQL outcomes are handled entirely in GET_CUSTOMER_INFO.
PLI 
CALL LGBATCHF(CUSTIN_CUSTNUMBER, COMM_AREA_PTR, CUSTRPT_LINE);
WRITE FILE(CUSTRPT) FROM(CUSTRPT_LINE);

4.5.3 GET_CUSTOMER_INFO

It sets EM_SQLREQ to ' SELECT CUSTOMER', runs the SELECT ... INTO into the CA_* fields, and evaluates SQLCODE:

PLI 
SELECT (SQLCODE);
   WHEN (0)   CA_RETURN_CODE = '00';
   WHEN (100) CA_RETURN_CODE = '01';
   OTHERWISE  DO;
                 CA_RETURN_CODE = '90';
                 CALL WRITE_ERROR_MESSAGE;
              END;
END;

4.5.4 WRITE_ERROR_MESSAGE

It copies SQLCODE into EM_SQLRC, and copies WS_DATE and WS_TIME into EM_DATE and EM_TIME. The ERROR_MSG structure is built in memory only. It is never written to a file, queue or log.

4.6 Return-Code Semantics

SQLCODE CA_RETURN_CODE Behavior
0 00 Customer found. CA_* fields are populated
100 01 Not found. CA_* fields keep the previous customer’s values, and a line is still written
Other 90 Error context is captured in ERROR_MSG. Processing continues

5. LGBATCHF – Report Line Formatter

5.1 Purpose

LGBATCHF is a subroutine called by both LGBATCH and LGBATDB2. Its source header is Proc(CUSTNUMBER, COMM_PTR, LS_LINE), and the procedure is labelled LGBATCF in the code.

5.2 Interface

Parameter Type Direction Description
CUSTNUMBER PIC '9999999999' In Customer number embedded in the line
COMM_PTR PTR In Address of the populated COMMAREA
LS_LINE CHAR(80) Out Formatted report line

5.3 Name Token Extraction

The routine emulates the COBOL idiom STRING field DELIMITED BY SPACE. Each name keeps only the text before its first blank. INDEX(field, ' ') gives POS, and three cases follow:

POS Result
0 Use the entire field
1 Use an empty string (leading blank)
> 1 Use SUBSTR(field, 1, POS-1)
graph TD A([LGBATCHF called]) --> B[COMM_AREA_PTR = COMM_PTR] B --> C[POS = INDEX of blank in CA_FIRST_NAME] C --> D{POS} D -- 0 --> E[FIRST_TOKEN = full field] D -- 1 --> F[FIRST_TOKEN = empty] D -- greater than 1 --> G[FIRST_TOKEN = SUBSTR 1 to POS-1] E --> H[POS = INDEX of blank in CA_LAST_NAME] F --> H G --> H H --> I{POS} I -- 0 --> J[LAST_TOKEN = full field] I -- 1 --> K[LAST_TOKEN = empty] I -- greater than 1 --> L[LAST_TOKEN = SUBSTR 1 to POS-1] J --> M[Compose LS_LINE] K --> M L --> M M --> N[DISPLAY trace] N --> O([RETURN])

5.4 Line Composition and Trace

PLI 
LS_LINE = 'Customer ' || CUSTNUMBER || ' is ' ||
          FIRST_TOKEN || ' ' || LAST_TOKEN;
DISPLAY('LGBATCHF WAS HERE... ' || LS_LINE);
  • The prefix 'Customer ', the 10-digit number and ' is ' take 23 characters. With the maximum name tokens (10, 1 and 20 characters) the total is at most 54, so nothing is truncated in the 80-character field.
  • The DISPLAY trace fires on every call and cannot be suppressed.

5.5 Characteristics

  • It has no DB2, CICS, file or MQ interaction.
  • It performs no null-pointer or length checks. The caller must supply a valid, populated COMMAREA.
  • It uses a single shared POS variable, so the first-name logic must finish before the last-name logic starts.

6. LGBATDB2 – DB2 Test Driver

6.1 Purpose

LGBATDB2 verifies the DB2-to-formatter pipeline without needing an input file or an output dataset. It is hard-wired to customer number 1, processes exactly one record and has no loop.

6.2 Sequence of Operations

sequenceDiagram participant Main as LGBATDB2 Main participant PR as PROCESS_RECORD participant GCI as GET_CUSTOMER_INFO participant DB2 as DB2 CUSTOMER participant F as LGBATCHF participant Out as SYSOUT Main->>Main: COMM_AREA_PTR = ADDR(BATCH_COMM_AREA) Main->>F: FETCH LGBATCHF Main->>Out: DISPLAY SQLCODE and SQLSTATE Main->>Main: DB2_CUSTOMERNUMBER_INT = 1 Main->>PR: Call PR->>GCI: Call GCI->>DB2: SELECT ... WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUMBER_INT DB2-->>GCI: Customer row GCI-->>PR: COMM_AREA populated PR->>PR: CUSTIN_CUSTNUMBER = DB2_CUSTOMERNUMBER_INT PR->>F: CALL LGBATCHF(CUSTIN_CUSTNUMBER, COMM_AREA_PTR, CUSTRPT_LINE) F-->>PR: Formatted line PR->>Out: DISPLAY CUSTRPT_LINE PR-->>Main: Return

6.3 Console Output

Statement Purpose
DISPLAY('LGBATDB2 SQLCode : ' || SQLCODE) Baseline status at startup, before any SQL runs
DISPLAY('LGBATDB2 SQLState: ' || SQLSTATE) Standard five-character status at startup
DISPLAY(CUSTRPT_LINE) The formatted report line from LGBATCHF

The SQLCODE and SQLSTATE values are displayed before the SELECT runs, so they show the initial SQLCA state. They do not reflect the outcome of the customer query.

6.4 Differences from LGBATCH

Aspect LGBATCH LGBATDB2
Input CUSTIN file Hard-coded customer 1
Volume All records until EOF Exactly one customer
Output CUSTRPT file DISPLAY to SYSOUT
SQLCODE handling 0 / 100 / other mapped to CA_RETURN_CODE None
Open failure handling UNDEFINEDFILE plus PLIRETC(16) Not applicable (no files)
ERROR_MSG Built in memory Not present

7.1 Example Report Line

For customer 0000000042, first name John and last name Smith:

CODE 
Customer 0000000042 is John Smith

The line is padded with blanks to 80 characters. For customer 0000009999 with an empty first-name token (CA_FIRST_NAME = ' J '), the line contains a double space:

CODE 
Customer 0000009999 is  Doe

8. Constraints and Operational Considerations

8.1 File and Record Constraints

  • CUSTIN must be fixed-block with RECSIZE(10). Each record is a purely numeric 10-digit customer number.
  • CUSTRPT must be fixed-block with RECSIZE(80) and writable.
  • The DD statements for both files must be allocated before the step runs.
  • Processing ends at the first end-of-file. The FI_EOF flag starts as '0'B, becomes '1'B and cannot be reset.

8.2 Sequencing Constraints

  • COMM_AREA_PTR must be set before any COMM_AREA field is referenced.
  • FETCH LGBATCHF must succeed before the first CALL.
  • In LGBATCH the order is: FETCH, OPEN CUSTIN and CUSTRPT, register ENDFILE, first READ, then the loop.
  • GET_CUSTOMER_INFO must run before the formatter, so the COMMAREA holds current data.

8.3 DB2 Constraints

  • The lookup is a singleton SELECT with no cursor. It assumes a unique CUSTOMERNUMBER.
  • The customer number must fit in FIXED BIN(31) (0 to 2,147,483,647).
  • The programs need an SQL precompile, bind and a valid DB2 execution context. Both include SQLCA.

8.4 COMMAREA Constraints

  • The buffer is 32,500 bytes, which is the maximum usable COMMAREA size.
  • LGBATCH does not reinitialise the COMMAREA between records. This is what causes the stale-data behavior for not-found customers.

9. Error Handling

9.1 Summary by Program

Condition LGBATCH LGBATCHF LGBATDB2
Input file missing Message, PLIRETC(16), STOP N/A N/A
Customer not found CA_RETURN_CODE='01', stale data used N/A Not checked. SQLCODE is 100 but the program continues
SQL error CA_RETURN_CODE='90', in-memory ERROR_MSG N/A Not checked
Output file open failure No handler (unhandled PL/I condition) N/A N/A
Blank-position edge cases N/A POS = 0 or 1 guards N/A

9.2 Known Gaps

  • LGBATCH builds ERROR_MSG but never outputs it, so SQL errors leave no trace except in a dump.
  • LGBATCH writes a line for a not-found customer using the previous customer’s data.
  • Neither main program has a handler for CUSTRPT open or write failures.
  • LGBATDB2 does not test SQLCODE after the SELECT.
  • LGBATCHF does not check CA_RETURN_CODE, so it formats a line whatever the lookup result was.
  • Do not run LGBATCHF through CICS LINK. It has no CICS scaffolding and expects static call parameter passing.

10. Examples

10.1 Successful Lookup in LGBATCH

Input record: 0000000042

  1. DB2_CUSTOMERNUMBER_INT is set to 42.
  2. The SELECT returns SQLCODE 0, so CA_RETURN_CODE is '00' and the CA_* fields are populated.
  3. LGBATCHF builds Customer 0000000042 is John Smith.
  4. The line is written to CUSTRPT.

10.2 Customer Not Found in LGBATCH

Input record: 0000009999

  1. The SELECT returns SQLCODE 100, so CA_RETURN_CODE is '01'.
  2. The CA_* fields still hold the previous customer’s values.
  3. LGBATCHF is still called, and a line is still written. That line contains the previous customer’s name with the new customer number.

10.3 Unexpected SQL Error in LGBATCH

Input record: 0000000007 (for example, with SQLCODE -911)

  1. CA_RETURN_CODE is set to '90' and WRITE_ERROR_MESSAGE runs.
  2. The in-memory error record is conceptually:
    CODE 
    20250101 143022  LGBATCH CNUM=0000000007 PNUM=0000000000 SELECT CUSTOMER SQLCODE=  -911
  3. Processing continues, and a report line is still produced from the stale COMMAREA.

10.4 LGBATDB2 Console Output

Successful run:

CODE 
LGBATDB2 SQLCode : 0
LGBATDB2 SQLState: 00000
<line produced by LGBATCHF>

If customer 1 is missing, the first two lines show SQLCode : 100 and SQLState: 02000. The report line is built from unpopulated COMMAREA fields.

10.5 Formatter Edge Cases

CA_FIRST_NAME CA_LAST_NAME Result
'John ' 'Smith ' Customer 0000000042 is John Smith
'Jacqueline' 'Vandenberghe' Customer 0000001234 is Jacqueline Vandenberghe (no blank, so POS = 0 and the full field is used)
' J ' 'Doe ' Customer 0000009999 is Doe (POS = 1, so the first token is empty)
