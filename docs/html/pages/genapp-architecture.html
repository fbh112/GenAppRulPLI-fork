System Architecture

1. Overview

GenApp (General Insurance Application) is an IBM PL/I-based insurance management system running on z/OS, combining CICS online transaction processing, DB2 relational storage, VSAM file-based storage, and IBM Operational Decision Manager (ODM) for business rules. The application manages the full lifecycle of insurance customers and policies across four product lines — Motor, Endowment, House, and Commercial — plus Claims management.

The system is structured as a layered, CICS-driven architecture in which 3270 terminal users interact with BMS menu programs that orchestrate back-end operations via EXEC CICS LINK. Batch programs provide offline reporting and data extract capabilities independent of CICS. A shared infrastructure layer handles error logging, statistics collection, and environment initialisation across all domains.

2. System Architecture

The overall architecture is composed of six distinct layers, from the user-facing presentation tier down to physical data storage and batch processing. All online interactions are mediated through CICS using EXEC CICS LINK and a shared COMMAREA structure.

3. Functional Layers

3.1 Layer 1 — Presentation

The presentation layer comprises five BMS (Basic Mapping Support) menu programs, one per insurance domain. Each program is invoked by a dedicated CICS transaction and renders a 3270 full-screen map to the user. User input is collected, validated locally, and then forwarded to the appropriate orchestrator via EXEC CICS LINK.

Transaction ID Program Description
SSC1 LGTESTC1 Customer menu
SSP1 LGTESTP1 Motor policy menu
SSP2 LGTESTP2 Endowment policy menu
SSP3 LGTESTP3 House policy menu
SSP4 LGTESTP4 Commercial policy menu
LGSE LGSETUP Environment setup
LGCF LGICVS01 Direct VSAM customer inquire
LGPF LGIPVS01 Direct VSAM policy inquire

All five menus share a single BMS mapset SSMAP, with individual maps for each domain. The PL/I include SSMAP.inc provides the corresponding data-structure declarations used at compile time.

Map Name Used By Purpose
SSMAPP1 LGTESTP1 Motor policy fields
SSMAPP2 LGTESTP2 Endowment policy fields
SSMAPP3 LGTESTP3 House policy fields
SSMAPP4 LGTESTP4 Commercial policy fields
SSMAPC1 LGTESTC1 Customer fields

3.2 Layer 2 — Business Orchestration

Orchestrator programs sit between the presentation layer and the data access layer. They receive the COMMAREA from the calling menu program, validate its length and request ID, and route the request to the correct DB2 or VSAM backend via a further EXEC CICS LINK call. On any error, they call the shared error logger LGSTSQ.

Program Role Operation
LGACUS01 Customer Orchestrator Add
LGICUS01 Customer Orchestrator Inquire
LGUCUS01 Customer Orchestrator Update
LGAPOL01 Policy Orchestrator Add (+ optional ODM call)
LGIPOL01 Policy Orchestrator Inquire
LGDPOL01 Policy Orchestrator Delete
LGUPOL01 Policy Orchestrator Update

The orchestrators use the CA_REQUEST_ID field in the COMMAREA to determine the operation and entity type. The convention for this field is:

CODE 
CA_REQUEST_ID = XX + VERB + ENTITY  (6 characters total)

XX     = '01'  (standard operation)
VERB   = A(dd) | I(nquire) | D(elete) | U(pdate)
ENTITY = CUS(tomer) | MOT(or) | END(owment) | HOU(se) | COM(mercial)

Examples:
  '01ACUS' — Add Customer
  '01IMOT' — Inquire Motor
  '01DEND' — Delete Endowment
  '01UHOU' — Update House

Return codes follow a standard convention: '00' = success, '98' = bad COMMAREA length, '99' = DB2/system error.

3.3 Layer 3 — Data Access

Each orchestrator dispatches to a pair of backend implementations: one using DB2 embedded SQL and one using CICS VSAM file control. This parallel design provides either a relational or file-based persistence path for every operation.

DB2 Backends execute embedded EXEC SQL statements (INSERT, SELECT, UPDATE, DELETE) against the GENASA1 DB2 database.

VSAM Backends use EXEC CICS WRITE, READ, REWRITE, and DELETE commands against KSDS datasets (KSDSCUST and KSDSPOLY).

Subdomain DB2 Backend Programs VSAM Backend Programs
Customer Add LGACDB01, LGACDB02 LGACVS01
Customer Inquire LGICDB01 LGICVS01
Customer Update LGUCDB01 LGUCVS01
Policy Add LGAPDB01 LGAPVS01
Policy Inquire LGIPDB01 LGIPVS01
Policy Delete LGDPDB01 LGDPVS01
Policy Update LGUPDB01 LGUPVS01

3.4 Layer 4 — Data Storage

3.4.1 DB2 Schema (GENASA1)

The relational schema uses cascading foreign keys so that deleting a customer automatically removes associated policies, and deleting a policy removes its type-specific detail record.

Table Tablespace Key Relates To
CUSTOMER GENATS01 customerNumber (identity) —
CUSTOMER_SECURE GENATS0A customerNumber → CUSTOMER (cascade delete)
POLICY GENATS02 policyNumber (identity) → CUSTOMER (cascade delete)
ENDOWMENT GENATS03 policyNumber → POLICY (cascade delete)
HOUSE GENATS04 policyNumber → POLICY (cascade delete)
MOTOR GENATS05 policyNumber → POLICY (cascade delete)
COMMERCIAL GENATS06 policyNumber → POLICY (cascade delete)
CLAIM GENATS07 claimNumber (identity) → POLICY (cascade delete)

Policy type is encoded in POLICY.policyType (M=Motor, E=Endowment, H=House, C=Commercial).

This cascade relationship means that removing a customer record from the CUSTOMER table automatically removes all associated policies and their type-specific detail records, ensuring referential integrity without requiring explicit multi-table deletes in application code.

3.4.2 VSAM Storage

Two KSDS (Key-Sequenced Data Sets) provide VSAM-based persistence:

  • KSDSCUST — Customer records
  • KSDSPOLY — Policy records

3.4.3 CICS Temporary Storage & Named Counters

The infrastructure layer uses CICS Temporary Storage (TS) queues and named counters extensively:

Resource Type Purpose
GENACNTL TS Queue Control queue for environment state
GENAERRS TS Queue Error log entries written by LGSTSQ
GENASTRT TS Queue Startup state
GENASTAT TS Queue Statistics snapshot data
GENA<code>V TS Queue Per-operation rate queues
GENA pool Named Counter Pool 36 atomic counters for success/failure per operation

3.5 Layer 5 — Batch Processing

Batch programs run as standard z/OS jobs outside CICS. They access DB2 directly via embedded SQL and read/write sequential flat files.

Program Role
LGBATCH Reads customer keys from CUSTIN, fetches each from DB2, produces a report via LGBATCHF
LGBATDB2 Simpler single-customer DB2 test driver
LGBATCHF Reusable report formatter subroutine (called statically)
LGMOTOUT Dumps all MOTOR table rows to MOTOROUT sequential file

3.6 Layer 6 — Infrastructure & Utilities

Program Role
LGSETUP Initialises all CICS named counters and TS queues before system use
LGSTSQ Shared error-logging service; writes to TDQ CSMT and TS queue GENAERRS; invoked by every domain on error
LGASTAT1 Event-processing adapter; increments the appropriate success/failure named counter for each transaction
LGWEBST5 Periodically samples all counters, maintains delta values in TS queues, restarts itself every minute (transaction SSST)

5. CICS LINK and Communication Areas

5.1 EXEC CICS LINK Mechanism

All inter-program communication within the online tier uses EXEC CICS LINK. This is a synchronous call that passes control to a named program within the same CICS region, sharing a COMMAREA (communication area) as the sole data exchange mechanism. The called program executes within the caller’s transaction context.

PLI 
/* Example: Orchestrator calling a DB2 backend */
EXEC CICS LINK
    PROGRAM  ('LGAPDB01')
    COMMAREA (WS-COMMAREA)
    LENGTH   (32500)
    RESP     (WS-CICS-RESP)
    RESP2    (WS-CICS-RESP2);

5.2 COMMAREA Structure (LGCMAREA)

The primary COMMAREA is defined in the PL/I include file LGCMAREA.inc and is 32,500 bytes in length. It is shared by all online programs across every domain.

Field Description
CA_REQUEST_ID 6-char operation code (see convention in §3.2)
CA_RETURN_CODE 2-char result: '00'=OK, '98'=bad length, '99'=error
CA_CUSTOMER_NUM Customer number
CA_POLICY_NUM Policy number
CA_MOTOR UNION branch for Motor policy fields
CA_ENDOWMENT UNION branch for Endowment policy fields
CA_HOUSE UNION branch for House policy fields
CA_COMMERCIAL UNION branch for Commercial policy fields
CA_CLAIM UNION branch for Claim fields

5.3 ODM Request/Response Area (LGCMARER)

For the IBM ODM business rules invocation, a separate, compact 152-byte structure is used (LGCMARER.inc) rather than the full COMMAREA. This structure carries only the Endowment policy fields required by the underwriting rules engine.

6. Named Counters and Temporary Storage Queues

6.1 Named Counters

Named counters in the GENA pool provide atomic, CICS-managed integer counters used for both unique key generation and operational statistics. They are incremented using EXEC CICS INCREMENT COUNTER.

PLI 
/* Example: Incrementing a named counter for statistics */
EXEC CICS INCREMENT
    COUNTER ('GENACUSTNUM')
    POOL    ('GENA')
    VALUE   (WS-COUNTER-VALUE)
    RESP    (WS-CICS-RESP);

LGSETUP initialises all 36 counters during environment setup. LGASTAT1 increments the appropriate success or failure counter for each completed transaction. LGWEBST5 samples all counters periodically and stores delta values in TS queues for monitoring.

6.2 Temporary Storage Queues

TS queues provide a lightweight, CICS-managed scratchpad for state and error data:

PLI 
/* Example: Writing an error to a TS queue via LGSTSQ */
EXEC CICS WRITEQ TS
    QUEUE    ('GENAERRS')
    FROM     (WS-ERROR-RECORD)
    LENGTH   (WS-ERROR-LENGTH)
    RESP     (WS-CICS-RESP);
Queue Written By Read By Purpose
GENACNTL LGSETUP LGWEBST5 Environment control state
GENAERRS LGSTSQ Operations/monitoring Error log entries
GENASTRT LGSETUP LGWEBST5 Startup time marker
GENASTAT LGWEBST5 External monitors Statistics snapshots
GENA<code>V LGWEBST5 External monitors Per-operation transaction rates

7. IBM ODM Integration

IBM Operational Decision Manager (ODM) is integrated as an optional, externally-linked business rules engine invoked exclusively during Endowment policy additions. The integration is conditional — LGAPOL01 only invokes LGAPBR01 when an internal BUSINESS_RULES flag is set to 'Y'.

The ODM invocation uses the compact LGCMARER structure (152 bytes) rather than the full 32,500-byte COMMAREA to minimise data transfer overhead. The engine evaluates underwriting rules against the Endowment policy data and returns its decision, which LGAPOL01 uses to proceed, reject, or modify the transaction before passing it to the DB2 backend.

Aspect Detail
Caller LGAPOL01 (Policy Add Orchestrator)
Called program LGAPBR01 (external ODM adapter)
Invocation mechanism EXEC CICS LINK (conditional)
Data structure LGCMARER.inc — 152-byte request/response
Scope Endowment policy additions only
Condition BUSINESS_RULES flag = 'Y'
