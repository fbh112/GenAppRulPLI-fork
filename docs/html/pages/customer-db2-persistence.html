Customer DB2 Data Persistence & Security

This page documents the database access modules responsible for querying, inserting, and updating customer profiles and authentication credentials in DB2 tables within the GenApp insurance application. These PL/I programs, hosted under CICS, form the data persistence layer for all customer lifecycle operations — from initial registration through profile maintenance and security provisioning.

1. Overview

The customer data persistence layer is composed of four CICS-linked PL/I programs that collectively manage the full lifecycle of a customer record across both DB2 and VSAM datastores. Together they implement a coordinated pattern: every write operation (insert or update) is mirrored to a parallel VSAM file store to ensure consistency, and every customer addition automatically provisions a corresponding security record. All programs share a common COMMAREA structure (LGCMAREA), a common error-logging utility (LGSTSQ), and a uniform return code convention.

Program Operation Primary DB2 Target
LGACDB01 Add new customer + security provisioning CUSTOMER, CUSTOMER_SECURE
LGACDB02 Add customer security record CUSTOMER_SECURE
LGICDB01 Inquire / retrieve customer profile CUSTOMER (read-only)
LGUCDB01 Update customer profile CUSTOMER

Return Code Convention (shared across all modules):

Code Meaning
'00' Success
'01' Customer not found (or DB2 resource conflict)
'90' Unexpected DB2 error
'98' COMMAREA too short / invalid
'99' Unrecognized request identifier (LGACDB02 only)

2. System Architecture

The four programs operate as a layered set of CICS-linked modules. An upstream orchestrator (e.g., LGICUS01, LGUCUS01) invokes the appropriate DB2 backend program. Write operations then fan out to both a DB2 table and a VSAM file via a companion program, and security provisioning is chained as a sub-operation of customer creation.

All four programs share the same foundational design:

  • Invoked via EXEC CICS LINK with a pointer to a shared COMMAREA (LGCMAREA)
  • COMMAREA presence and minimum-length validated on every entry
  • DB2 SQLCODE checked after every SQL operation
  • Errors logged to a CICS Transient Data Queue via the shared utility LGSTSQ
  • Control returned to the caller via EXEC CICS RETURN with CA_RETURN_CODE set

3. Database Schema

The two DB2 tables involved form a one-to-one relationship. Every CUSTOMER row must have a corresponding CUSTOMER_SECURE row, provisioned automatically at insert time by LGACDB01 → LGACDB02.

erDiagram CUSTOMER { int CUSTOMERNUMBER "PK — from NCS or DB2 IDENTITY" string FIRSTNAME "CHAR 10" string LASTNAME "CHAR 20" string DATEOFBIRTH "CHAR 10" string HOUSENAME "CHAR 20" string HOUSENUMBER "CHAR 4" string POSTCODE "CHAR 8" string PHONEMOBILE "CHAR 20" string PHONEHOME "CHAR 20" string EMAILADDRESS "CHAR 100" } CUSTOMER_SECURE { int customerNumber "FK → CUSTOMER" string customerPass "CHAR 32 — MD5 password hash" string state_indicator "CHAR 1 — N=new" int pass_changes "number of password changes" } CUSTOMER ||--|| CUSTOMER_SECURE : "secured by"

The CUSTOMER table is the master record, holding all personal and contact information. The CUSTOMER_SECURE table holds authentication credentials, keyed by the same customerNumber. The security record is always created with an initial state of 'N' (new), a hardcoded default MD5 password hash, and a change count of 0.

4. Module: LGACDB01 — Add Customer

4.1. Purpose

LGACDB01 orchestrates the complete end-to-end “add customer” transaction. It accepts customer details from the CICS COMMAREA, obtains a unique customer number, inserts the customer record into DB2, mirrors the record to VSAM, and provisions an initial security record — all within a single synchronous CICS task.
