Batch Programs

1. Overview

The GenApp PL/I application includes a set of non-CICS batch programs responsible for producing customer reports, formatting report lines, testing DB2 connectivity, and extracting motor insurance policy data. These programs operate outside of the CICS transaction processing environment, running as standard z/OS batch jobs invoked via JCL.

The batch suite comprises four programs:

Program Role Primary I/O
LGBATCH Customer report generator Reads CUSTIN, queries DB2 CUSTOMER, writes CUSTRPT
LGBATCHF Report-line formatting subroutine In-memory only (called by LGBATCH)
LGBATDB2 Standalone DB2 test driver Queries DB2 CUSTOMER, displays to SYSOUT
LGMOTOUT Motor policy extract utility Reads DB2 GENASA1.MOTOR, writes MOTOROUT

All programs use Enterprise PL/I, embedded SQL for DB2 access, and the shared LGCMAREA communication area structure. Return codes are set via PLIRETC to communicate success or failure to the JCL job scheduler.

2. System Architecture

The batch programs form a layered architecture where the main driver programs interact with DB2 and sequential files, delegating formatting work to a shared subroutine.

The architecture follows a straightforward batch extract–transform–load pattern. LGBATCH and LGBATDB2 both delegate formatting to LGBATCHF, which is dynamically loaded via FETCH. LGMOTOUT operates independently, extracting motor policy data through a DB2 cursor and writing fixed-length records to its own output file.

3. LGBATCH — Customer Report Generator

3.1 Purpose

LGBATCH is the primary batch reporting program. It reads a sequential file of customer numbers (CUSTIN), queries the DB2 CUSTOMER table for each number to retrieve personal details (name, date of birth, address, contact information), and invokes the LGBATCHF subroutine to format and write an 80-character report line per customer to the CUSTRPT output file.

3.2 File DD Names and Record Layouts

DD Name Direction Format RECSIZE Description
CUSTIN Input FB 10 Sequential file of 10-digit customer numbers
CUSTRPT Output FB 80 Formatted customer report, one line per customer

3.3 Processing Flow

sequenceDiagram participant JCL as JCL / Batch participant LGBATCH as LGBATCH participant DB2 as DB2 CUSTOMER Table participant LGBATCHF as LGBATCHF (Formatter) participant CUSTRPT as CUSTRPT File JCL->>LGBATCH: Start program LGBATCH->>LGBATCH: FETCH LGBATCHF subroutine LGBATCH->>LGBATCH: OPEN CUSTIN, CUSTRPT loop For each CUSTIN record LGBATCH->>LGBATCH: READ customer number from CUSTIN LGBATCH->>DB2: EXEC SQL SELECT ... WHERE CUSTOMERNUMBER = :host_var DB2-->>LGBATCH: Customer data (or SQLCODE 100 / error) LGBATCH->>LGBATCH: Set CA_RETURN_CODE (00, 01, or 90) LGBATCH->>LGBATCHF: CALL LGBATCHF(CUSTNUMBER, COMM_AREA_PTR, CUSTRPT_LINE) LGBATCHF-->>LGBATCH: Formatted 80-char report line LGBATCH->>CUSTRPT: WRITE report line end LGBATCH->>LGBATCH: CLOSE CUSTIN, CUSTRPT LGBATCH-->>JCL: RETURN (RC=0 or RC=16)

3.4 Processing Logic

  1. Initialisation: COMM_AREA_PTR is set to the address of BATCH_COMM_AREA (a 32,500-byte working storage buffer). LGBATCHF is dynamically loaded via FETCH.
  2. File Setup: An ON UNDEFINEDFILE(CUSTIN) handler is registered. If the input file cannot be opened, the handler displays 'FILE STATUS AT OPEN CUSTIN', sets return code 16 via PLIRETC(16), and issues STOP.
  3. Main Loop: A DO WHILE (^FI_EOF) loop reads customer numbers, converts each to FIXED BIN(31) for the DB2 host variable, executes the SQL SELECT, evaluates SQLCODE, and delegates formatting to LGBATCHF.
  4. Termination: Both files are closed and the program returns.

3.5 SQLCODE Handling

SQLCODE CA_RETURN_CODE Action
0 '00' Customer found — COMMAREA populated with DB2 data
100 '01' Customer not found — COMMAREA retains stale data from previous row
Other '90' Unexpected error — WRITE_ERROR_MESSAGE called (in-memory only)

Known quirk: When a customer is not found (SQLCODE 100), the COMMAREA is not reinitialised, so the report line written by LGBATCHF will contain the previous customer’s data alongside the current customer number.

3.6 Return Codes

RC Condition
0 Normal completion (implicit)
16 CUSTIN file could not be opened (UNDEFINEDFILE condition)

3.7 Error Display Conventions

  • File open failure: DISPLAY('FILE STATUS AT OPEN CUSTIN') → PLIRETC(16) → STOP
  • SQL error: WRITE_ERROR_MESSAGE builds an in-memory ERROR_MSG structure containing date, time, program name (LGBATCH), customer number, policy number, SQL request identifier (' SELECT CUSTOMER'), and SQLCODE. This message is never written to any output file or log — it exists only in working storage.

3.8 Code Example — DB2 Customer Lookup

PLI 
GET_CUSTOMER_INFO: Proc;
    EM_SQLREQ = ' SELECT CUSTOMER';
    EXEC SQL
        SELECT FIRSTNAME, LASTNAME, DATEOFBIRTH,
               HOUSENAME, HOUSENUMBER, POSTCODE,
               PHONEMOBILE, PHONEHOME, EMAILADDRESS
        INTO :CA_FIRST_NAME, :CA_LAST_NAME, :CA_DOB,
             :CA_HOUSE_NAME, :CA_HOUSE_NUM, :CA_POSTCODE,
             :CA_PHONE_MOBILE, :CA_PHONE_HOME, :CA_EMAIL_ADDRESS
        FROM CUSTOMER
        WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUMBER_INT;

    SELECT (SQLCODE)
        WHEN (0)   CA_RETURN_CODE = '00';
        WHEN (100) CA_RETURN_CODE = '01';
        OTHERWISE DO;
            CA_RETURN_CODE = '90';
            CALL WRITE_ERROR_MESSAGE;
        END;
    END;
END GET_CUSTOMER_INFO;

4. LGBATCHF — Report Line Formatting Subroutine

4.1 Purpose

LGBATCHF is a pure data-formatting subroutine with no file I/O, no DB2 access, and no CICS dependencies. It accepts a customer number, a pointer to the LGCMAREA communication area, and an 80-character output buffer. It extracts the customer’s first and last name by trimming at the first blank, then assembles a report line of the form:

CODE 
Customer 0000000042 is John Smith

4.2 Interface

LGBATCHF is declared as:

PLI 
DCL LGBATCHF ENTRY(PIC '9999999999', PTR, CHAR(80));
Parameter Type Direction Description
CUSTNUMBER PIC '9999999999' Input 10-digit customer number
COMM_PTR PTR Input Pointer to the LGCMAREA communication area
LS_LINE CHAR(80) Output Formatted report line returned to caller

4.3 Name Token Extraction Logic

graph TD classDef process fill:#c7ceea,stroke:#6272a4,color:#000 classDef decision fill:#ffdac1,stroke:#e09060,color:#000 A[INDEX field for first blank] --> B{{POS value?}}:::decision B -- "POS = 0
(no blank)" --> C[Use entire field]:::process B -- "POS = 1
(leading blank)" --> D[Use empty string]:::process B -- "POS > 1" --> E["SUBSTR(field, 1, POS-1)"]:::process

This three-way logic is applied identically to both CA_FIRST_NAME (10 chars) and CA_LAST_NAME (20 chars), replicating the COBOL STRING ... DELIMITED BY SPACE idiom.

4.4 Code Example — Line Construction

PLI 
/* Extract first-name token */
POS = INDEX(CA_FIRST_NAME, ' ');
IF POS = 0 THEN FIRST_TOKEN = CA_FIRST_NAME;
ELSE IF POS = 1 THEN FIRST_TOKEN = '';
ELSE FIRST_TOKEN = SUBSTR(CA_FIRST_NAME, 1, POS-1);

/* Extract last-name token */
POS = INDEX(CA_LAST_NAME, ' ');
IF POS = 0 THEN LAST_TOKEN = CA_LAST_NAME;
ELSE IF POS = 1 THEN LAST_TOKEN = '';
ELSE LAST_TOKEN = SUBSTR(CA_LAST_NAME, 1, POS-1);

/* Compose the output line */
LS_LINE = 'Customer ' || CUSTNUMBER || ' is ' ||
          FIRST_TOKEN || ' ' || LAST_TOKEN;

DISPLAY('LGBATCHF WAS HERE... ' || LS_LINE);

4.5 Output Examples

CA_FIRST_NAME CA_LAST_NAME LS_LINE
'John ' 'Smith ' Customer 0000000042 is John Smith
'Jacqueline' 'Vandenberghe ' Customer 0000001234 is Jacqueline Vandenberghe
' J ' 'Doe ' Customer 0000009999 is Doe

4.6 Diagnostic Output

Every invocation unconditionally writes a trace message to SYSOUT:

CODE 
LGBATCHF WAS HERE... Customer 0000000042 is John Smith

5. LGBATDB2 — Standalone DB2 Test Driver

5.1 Purpose

LGBATDB2 is a minimal batch test driver that verifies DB2 connectivity and the LGBATCHF formatting pipeline. It always queries customer number 1 (hard-coded), passes the result to LGBATCHF, and displays the formatted report line. It has no input files and no output files — all output goes to SYSOUT via DISPLAY.

5.2 Processing Flow

sequenceDiagram participant JCL as JCL / Batch participant LGBATDB2 as LGBATDB2 participant DB2 as DB2 CUSTOMER Table participant LGBATCHF as LGBATCHF (Formatter) participant SYSOUT as SYSOUT Console JCL->>LGBATDB2: Start program LGBATDB2->>LGBATDB2: Set COMM_AREA_PTR, FETCH LGBATCHF LGBATDB2->>SYSOUT: DISPLAY SQLCODE and SQLSTATE (baseline) LGBATDB2->>LGBATDB2: Set DB2_CUSTOMERNUMBER_INT = 1 LGBATDB2->>DB2: EXEC SQL SELECT ... WHERE CUSTOMERNUMBER = 1 DB2-->>LGBATDB2: Customer data (or error) LGBATDB2->>LGBATDB2: Convert integer to PIC CUSTIN_CUSTNUMBER LGBATDB2->>LGBATCHF: CALL LGBATCHF(CUSTNUMBER, COMM_AREA_PTR, CUSTRPT_LINE) LGBATCHF-->>LGBATDB2: Formatted 80-char report line LGBATDB2->>SYSOUT: DISPLAY CUSTRPT_LINE LGBATDB2-->>JCL: RETURN

5.3 Key Characteristics

  • Hard-coded customer number: Always processes CUSTOMERNUMBER = 1; no input file or parameter.
  • No SQLCODE checking after SELECT: If the customer is not found (SQLCODE = 100) or a DB2 error occurs, the program continues silently with unpopulated COMMAREA fields.
  • No condition handlers: No ON ERROR, ON UNDEFINEDFILE, or other PL/I condition handlers are declared.
  • No file I/O: All output is via DISPLAY to the job log.

5.4 Expected Console Output (Successful)

CODE 
LGBATDB2 SQLCode : 0
LGBATDB2 SQLState: 00000
LGBATCHF WAS HERE... Customer 0000000001 is John Smith
Customer 0000000001 is John Smith

5.5 Expected Console Output (Customer Not Found)

LGBATDB2 SQLState: 02000

6. LGMOTOUT — Motor Policy Extract

6.1 Purpose

LGMOTOUT extracts all motor insurance policy records from the GENASA1.MOTOR DB2 table via a read-only cursor and writes them as formatted 132-byte fixed-length records to the MOTOROUT sequential output file. Upon completion, it reports the total number of records successfully written.

6.2 File DD Names and Record Layout

DD Name Direction Format RECSIZE Description
MOTOROUT Output FB 132 Formatted motor policy extract records

MOTOROUT Record Layout (WS_MOTOR_LINE, 132 bytes):

Field PIC / Type Width Source Column
WS_OUT_POLNUM PIC '999999999' 9 POLICYNUMBER
WS_OUT_MAKE CHAR(15) 15 MAKE
WS_OUT_MODEL CHAR(15) 15 MODEL
WS_OUT_VALUE PIC '999999999' 9 VALUE
WS_OUT_REGNUMBER CHAR(7) 7 REGNUMBER
WS_OUT_COLOUR CHAR(8) 8 COLOUR
WS_OUT_CC PIC '9999' 4 CC
WS_OUT_YEAROFMFR CHAR(10) 10 YEAROFMANUFACTURE
WS_OUT_PREMIUM PIC '999999999' 9 PREMIUM
WS_OUT_ACCIDENTS PIC '999999999' 9 ACCIDENTS
(filler) CHAR(13) 13 Trailing spaces
Total 132

6.3 Processing Flow

6.4 DB2 Cursor Declaration

The cursor reads all rows from the motor table with no filter:

PLI 
EXEC SQL DECLARE MOTOR_CSR CURSOR FOR
    SELECT POLICYNUMBER, MAKE, MODEL, VALUE,
           REGNUMBER, COLOUR, CC,
           YEAROFMANUFACTURE, PREMIUM, ACCIDENTS
    FROM GENASA1.MOTOR
    FOR READ ONLY;

6.5 Return Codes

RC Condition
0 Normal completion — all rows extracted successfully
8 Fetch-level error — unexpected SQLCODE during cursor processing
12 Fatal error — MOTOROUT file open failure or cursor open failure

6.6 Error Display Conventions

LGMOTOUT uses a centralised WRITE_ERROR_MESSAGE procedure that actually displays diagnostic messages (unlike LGBATCH where the error message is in-memory only):

CODE 
<EM_DATE> <EM_TIME> LGMOTOUT <EM_SQLREQ> SQLCODE=<EM_SQLRC>

Example error messages:

CODE 
20240101 103045 LGMOTOUT  OPEN MOTOR-CSR  SQLCODE=  -204
20240101 103045 LGMOTOUT  FETCH MOTOR-CSR  SQLCODE=  -911

Additional display messages:

  • LGMOTOUT: OPEN MOTOROUT FAILED — when the output file cannot be opened
  • LGMOTOUT: WRITE FAILED — when a physical write error occurs (TRANSMIT condition)
  • LGMOTOUT: ROWS WRITTEN=000000002 — audit count on successful completion

6.7 Output Example

For a table containing two motor policy rows, the MOTOROUT file would contain:

100000002 TOYOTA          COROLLA         000018000 XY99ZZZ RED      1800 2020-06-15 000001500 000000002

8. Shared Communication Area (LGCMAREA)

All four batch programs use the LGCMAREA include member, which defines a COMM_AREA union structure BASED on COMM_AREA_PTR. The backing storage is declared as:

PLI 
DCL BATCH_COMM_AREA CHAR(32500);
DCL COMM_AREA_PTR PTR;
COMM_AREA_PTR = ADDR(BATCH_COMM_AREA);

Key fields used by the batch programs:

Field Type Used By Purpose
CA_RETURN_CODE PIC '99' LGBATCH '00' success, '01' not found, '90' error
CA_CUSTOMER_NUM PIC '9999999999' All Customer identifier
CA_FIRST_NAME CHAR(10) LGBATCH, LGBATCHF Customer first name
CA_LAST_NAME CHAR(20) LGBATCH, LGBATCHF Customer last name
CA_DOB CHAR(10) LGBATCH Date of birth
CA_POSTCODE CHAR(8) LGBATCH Postal code
CA_PHONE_MOBILE CHAR(20) LGBATCH Mobile phone
CA_PHONE_HOME CHAR(20) LGBATCH Home phone
CA_EMAIL_ADDRESS CHAR(100) LGBATCH Email address

Important constraint: The COMMAREA is not reinitialised between records in LGBATCH. Data from one customer’s DB2 fetch persists into the next iteration, meaning a failed or not-found query leaves the prior customer’s data in place.

10. Known Limitations and Design Notes

  1. LGBATCH — Stale COMMAREA on not-found: When SQLCODE = 100 is returned for a customer number, the COMMAREA retains data from the previous successful row. The report line for the missing customer will contain the prior customer’s name, address, and contact details.

  2. LGBATCH — Error message not externalised: The WRITE_ERROR_MESSAGE procedure constructs a complete diagnostic message in working storage (ERROR_MSG) but never writes it to any file, queue, or log. Error details are only recoverable through a dump.

  3. LGBATCH — No CUSTRPT open guard: There is no ON UNDEFINEDFILE(CUSTRPT) handler; a failure to open the output file would result in an unhandled PL/I condition.

  4. LGBATDB2 — No SQL error handling: The test driver does not check SQLCODE after the SELECT INTO. If customer 1 does not exist, the program proceeds with uninitialised COMMAREA fields.

  5. LGBATDB2 — Hard-coded customer number: Always queries CUSTOMERNUMBER = 1; designed for testing only, not production use.

  6. LGMOTOUT — Date/time fields may be blank: WS_DATE and WS_TIME are declared but never explicitly populated from system clock values within the program. Error messages may display blank timestamps unless the runtime or JCL pre-initialises these fields.

  7. LGMOTOUT — Write failures are non-fatal: A TRANSMIT condition on MOTOROUT logs the error but does not abort processing — the program continues with the next fetched row, potentially producing an incomplete output file without a non-zero return code for that specific failure.
