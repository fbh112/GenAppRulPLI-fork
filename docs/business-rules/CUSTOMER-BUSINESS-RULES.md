# GenApp PL/I — Customer Domain: Business Rules

## Scope

This document captures the business-level rules and behaviours within the **Customer domain** that must be preserved when the domain is migrated off the mainframe. Focus is on online (CICS) operations. No dedicated customer batch exists.

Rules are grouped by functional topic. Each entry includes an ID, the rule in business terms, conditions, implementation location, data involved, whether it is explicit or inferred, and a verification example.

---

## Functional Topic 1 — Customer Identification

### BR-CUST-001 — Customer Number is the Unique Customer Identity

| Field | Value |
|-------|-------|
| **Rule** | Every customer is identified by a unique, system-generated integer `customerNumber` starting at 1000001. |
| **Condition** | Applied on every Add Customer request |
| **Outcome** | A new customer record is assigned a `customerNumber` ≥ 1000001 |
| **Implementation** | [`LGACUS01`](../../pli/LGACUS01.pli) `OBTAIN_CUSTOMER_NUMBER` + `INSERT_CUSTOMER`; [`LGACDB01`](../../pli/LGACDB01.pli) `OBTAIN_CUSTOMER_NUMBER` |
| **Data** | DB2 `CUSTOMER.customerNumber` — `GENERATED BY DEFAULT AS IDENTITY (START WITH 1000001, INCREMENT BY 1, CACHE 20)` |
| **Source** | Explicit — DDL in [`DDL/db2cre.jcl`](../../DDL/db2cre.jcl) lines 103-104 |
| **Example** | Input: Add Customer request with all personal details. Expected: New row in CUSTOMER with `customerNumber` = next identity value ≥ 1000001; `CA_CUSTOMER_NUM` returned in COMMAREA |

---

### BR-CUST-002 — Named Counter Drives Customer Number Assignment (Dual Path)

| Field | Value |
|-------|-------|
| **Rule** | If a CICS Named Counter `GENACUSTNUM` (pool `GENA`) is available, the customer number is obtained from that counter and used as an explicit value. If the counter is unavailable, DB2 IDENTITY is used and the resulting identity value is retrieved via `IDENTITY_VAL_LOCAL()`. |
| **Condition** | On every Add Customer — EXEC CICS GET COUNTER; if RESP ≠ NORMAL then `LGAC_NCS = 'NO'` |
| **Outcome** | Customer number is either counter-derived or DB2-auto-assigned; both paths populate `CA_CUSTOMER_NUM` |
| **Implementation** | [`LGACUS01`](../../pli/LGACUS01.pli) lines 233-248 (`OBTAIN_CUSTOMER_NUMBER`), lines 257-316 (`INSERT_CUSTOMER`) |
| **Data** | Named Counter `GENACUSTNUM`, `DB2_CUSTOMERNUM_INT`, `CA_CUSTOMER_NUM` |
| **Source** | Explicit |
| **Example** | Named Counter available: counter value 1000042 → INSERT with customerNumber=1000042. Counter unavailable: INSERT with DEFAULT → retrieve via IDENTITY_VAL_LOCAL() |

## Functional Topic 2 — Customer Registration

### BR-CUST-003 — COMMAREA Must Be Present and Minimum Length for All Customer Operations

| Field | Value |
|-------|-------|
| **Rule** | Any customer operation (add, inquire, update) requires a non-zero COMMAREA. If EIBCALEN = 0, the program abends (LGCA). If COMMAREA is shorter than the header (18 bytes) + customer data (72 bytes) = 90 bytes minimum, return code 98 is set and processing is abandoned. |
| **Condition** | Entry to LGACUS01, LGICUS01, LGUCUS01, LGICDB01, LGUCDB01 |
| **Outcome** | ABEND `LGCA` if no COMMAREA; `CA_RETURN_CODE = '98'` if COMMAREA too short |
| **Implementation** | [`LGACUS01`](../../pli/LGACUS01.pli) `CHECK_INPUTS` (lines 174-199); [`LGICUS01`](../../pli/LGICUS01.pli) lines 91-110; [`LGUCDB01`](../../pli/LGUCDB01.pli) lines 99-104 |
| **Data** | `EIBCALEN`, `WS_REQUIRED_CA_LEN`, `CA_RETURN_CODE` |
| **Source** | Explicit |
| **Example** | COMMAREA length = 0 → ABEND LGCA. Length = 50 → CA_RETURN_CODE = '98', return to caller. Length ≥ 90 → processing continues |

### BR-CUST-004 — Postcode Is Uppercased Before Storage

| Field | Value |
|-------|-------|
| **Rule** | The caller (LGTESTC1) uppercases the postcode value before passing it to LGACUS01 or LGUCUS01. Null bytes in the COMMAREA are also translated to blanks. |
| **Condition** | On Add Customer (option 2) and Update Customer (option 4) from LGTESTC1 |
| **Outcome** | `CA_POSTCODE` is stored in upper case; no embedded nulls |
| **Implementation** | [`LGTESTC1`](../../pli/LGTESTC1.pli) lines 114-115 (`TRANSLATE`+ `UPPERCASE`), lines 171-172 |
| **Data** | `CA_POSTCODE`, `COMM_AREA_RAW` |
| **Source** | Explicit |
| **Example** | Input postcode `sw1a 2aa` → stored as `SW1A 2AA` |

### BR-CUST-005 — Customer Profile Contains: Name, Address, DOB, Contact

| Field | Value |
|-------|-------|
| **Rule** | A customer record must include: first name (10), last name (20), date of birth (DATE), house name (20), house number (4), postcode (8), phone home (20), phone mobile (20), email address (100). No field-level NOT NULL constraint except customerNumber — other fields may be blank but must be present in the COMMAREA. |
| **Condition** | On INSERT into CUSTOMER |
| **Outcome** | All listed fields are stored; blanks are acceptable |
| **Implementation** | [`LGACDB01`](../../pli/LGACDB01.pli) / [`LGACUS01`](../../pli/LGACUS01.pli) `INSERT_CUSTOMER`; DDL |
| **Data** | `CA_FIRST_NAME`, `CA_LAST_NAME`, `CA_DOB`, `CA_HOUSE_NAME`, `CA_HOUSE_NUM`, `CA_POSTCODE`, `CA_PHONE_HOME`, `CA_PHONE_MOBILE`, `CA_EMAIL_ADDRESS` |
| **Source** | Explicit |
| **Example** | Add Customer: first=`John`, last=`Smith`, DOB=`1980-01-15`, postcode=`SW1A2AA` → row inserted with customerNumber returned |

### BR-CUST-006 — Customer Creation Triggers Security Record Creation

| Field | Value |
|-------|-------|
| **Rule** | Every new customer addition creates a corresponding row in `CUSTOMER_SECURE` with a default password of `'NewPass'`, state indicator `'N'` (new), and change count `0`. The request ID must be `'02ACUS'` to trigger this. |
| **Condition** | After successful INSERT into CUSTOMER, LGACUS01/LGACDB01 calls LGACDB02 with `CA_REQUEST_ID = '02ACUS'` |
| **Outcome** | Row in CUSTOMER_SECURE for the new customerNumber with initial password and state |
| **Implementation** | [`LGACUS01`](../../pli/LGACUS01.pli) lines 217-224 (`ONBOARD_CUSTOMER`); [`LGACDB02`](../../pli/LGACDB02.pli) lines 110-151 |
| **Data** | `CA_CUSTSECR_PASS = 'NewPass'`, `CA_CUSTSECR_STATE = 'N'`, `CA_CUSTSECR_COUNT = '0000'` |
| **Source** | Explicit |
| **Example** | Add Customer succeeds → CUSTOMER_SECURE row: customerNumber=1000042, customerPass='NewPass', state_indicator='N', pass_changes=0 |

### BR-CUST-007 — Security Record Only Created for `02ACUS` Request

| Field | Value |
|-------|-------|

| **Condition** | Entry to LGACDB02 with any `CA_REQUEST_ID` other than `'02ACUS'` |
| **Outcome** | `CA_RETURN_CODE = '99'`, immediate return |
| **Implementation** | [`LGACDB02`](../../pli/LGACDB02.pli) lines 111-122 |
| **Data** | `CA_REQUEST_ID` |
| **Source** | Explicit |
| **Example** | CA_REQUEST_ID = '01ICUS' → CA_RETURN_CODE = '99', no INSERT |

### BR-CUST-008 — Customer Record Is Mirrored to VSAM KSDSCUST

| Field | Value |
|-------|-------|
| **Rule** | Every add and update of a customer in DB2 is followed by a corresponding write/update to the VSAM KSDS file `KSDSCUST`. Both stores are kept in sync. |
| **Condition** | After DB2 INSERT in LGACDB01/LGACUS01 → EXEC CICS LINK to LGACVS01. After DB2 UPDATE in LGUCDB01 → EXEC CICS LINK to LGUCVS01 |
| **Outcome** | Customer data exists in both DB2 CUSTOMER and VSAM KSDSCUST |
| **Implementation** | [`LGACUS01`](../../pli/LGACUS01.pli) line 213; [`LGACDB01`](../../pli/LGACDB01.pli) line 148; [`LGUCDB01`](../../pli/LGUCDB01.pli) lines 119-122 |
| **Data** | DB2 CUSTOMER, VSAM KSDSCUST |
| **Source** | Explicit — dual-write pattern |
| **Example** | Add Customer → both DB2 row and VSAM record created. Update Customer → both DB2 row and VSAM record updated |

## Functional Topic 3 — Customer Inquiry

### BR-CUST-009 — Inquiry Uses DB2 as Primary Source; MQ Cache Overrides

| Field | Value |
|-------|-------|
| **Rule** | LGICUS01 first checks CICS TS Queue `GENAWMQC` for a record beginning with `'MQHIT='`. If such a record exists, it routes the inquiry to `AAAAAAAA` (an MQ-based cache handler). If not found, it routes to LGICDB01 (DB2). |
| **Condition** | On every Inquire Customer call |
| **Outcome** | Customer data returned from DB2 (normal path) or from MQ cache (when `MQHIT=` record present) |
| **Implementation** | [`LGICUS01`](../../pli/LGICUS01.pli) `GET_CUSTOMER_INFO` lines 124-155 |
| **Data** | TSQ `GENAWMQC`, `MQ_READ_RECORD`, `MQ_HIT` flag |
| **Source** | Explicit |
| **Example** | TSQ GENAWMQC has no `MQHIT=` record → LGICDB01 called, CA_RETURN_CODE = 00, customer data in COMMAREA. TSQ has `MQHIT=` record → AAAAAAAA called |

### BR-CUST-010 — Inquiry Returns `01` When Customer Not Found or Deadlock

| Field | Value |
|-------|-------|
| **Rule** | If the DB2 SELECT returns SQLCODE 100 (not found) or SQLCODE -913 (deadlock/timeout), `CA_RETURN_CODE = '01'` is set. Any other non-zero SQLCODE sets `CA_RETURN_CODE = '90'` and triggers error logging. |
| **Condition** | LGICDB01 SELECT CUSTOMER WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUMBER_INT |
| **Outcome** | RC='01' → customer not found / unavailable. RC='90' → system error |
| **Implementation** | [`LGICDB01`](../../pli/LGICDB01.pli) lines 165-175 |
| **Data** | `SQLCODE`, `CA_RETURN_CODE` |
| **Source** | Explicit |
| **Example** | customerNumber = 9999999 (not in DB) → SQLCODE 100 → CA_RETURN_CODE = '01'. DB2 unavailable → SQLCODE -904 → CA_RETURN_CODE = '90' |

## Functional Topic 4 — Customer Update

### BR-CUST-012 — Update Replaces All Modifiable Customer Fields

| Field | Value |
|-------|-------|
| **Rule** | An Update Customer operation overwrites all nine modifiable fields regardless of which ones changed. It is a full replace, not a partial update. |
| **Condition** | LGUCDB01 UPDATE CUSTOMER WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUM_INT |
| **Outcome** | All nine fields in CUSTOMER updated; customerNumber itself is never changed |
| **Implementation** | [`LGUCDB01`](../../pli/LGUCDB01.pli) `UPDATE_CUSTOMER_INFO` lines 132-161 |
| **Data** | All COMMAREA customer fields |
| **Source** | Explicit — SET clause covers all nine modifiable fields |
| **Example** | Update: change only email → all fields (including unchanged ones) written back to DB2 and VSAM |

| Field | Value |
|-------|-------|
| **Rule** | If the UPDATE affects zero rows (SQLCODE 100), `CA_RETURN_CODE = '01'` is set. This means the customerNumber does not exist. |
| **Condition** | SQLCODE = 100 after UPDATE CUSTOMER |
| **Outcome** | CA_RETURN_CODE = '01', no data changed |
| **Implementation** | [`LGUCDB01`](../../pli/LGUCDB01.pli) lines 150-158 |
| **Data** | `SQLCODE`, `CA_RETURN_CODE` |
| **Source** | Explicit |
| **Example** | Update for customerNumber = 9999999 (not in DB) → SQLCODE 100 → CA_RETURN_CODE = '01' |

### BR-CUST-014 — Update Flow: Inquire First, Then Update

| Field | Value |
|-------|-------|

| **Condition** | User enters option 4 on SSMAPC1 screen |
| **Outcome** | Current customer data shown before update is accepted |
| **Implementation** | [`LGTESTC1`](../../pli/LGTESTC1.pli) lines 134-186 |
| **Data** | COMMAREA customer fields, BMS map SSMAPC1 |
| **Source** | Explicit — UI workflow |
| **Example** | Option 4 entered: first LGICUS01 called → fields displayed → user modifies phone → LGUCUS01 called → fields updated |

## Functional Topic 5 — Customer-Policy Coupling

### BR-CUST-015 — Add Customer Can Simultaneously Create an Initial Policy

| Field | Value |
|-------|-------|
| **Rule** | When `ACTION_CODE = '2'` in LGACUS01 (`OFFER_CUSTOMER`), a POLICY row is inserted for the new customer immediately after customer creation. The policy uses broker, payment, issue/expiry dates from the COMMAREA. |
| **Condition** | ACTION_CODE = '2' in LGACUS01 (action not yet triggered by any CICS caller — ACTION_CODE is always '0' in this PL/I port) |
| **Outcome** | Both CUSTOMER and POLICY rows created atomically; CA_POLICY_NUM returned |
| **Implementation** | [`LGACUS01`](../../pli/LGACUS01.pli) `OFFER_CUSTOMER` / `INSERT_CUSTOMER_POLICY` lines 340-408 |
| **Data** | `CA_BROKERID`, `CA_PAYMENT`, `CA_ISSUE_DATE`, `CA_EXPIRY_DATE`, DB2 POLICY |
| **Source** | Explicit — *Note: ACTION_CODE is never set to '2' in the current PL/I port; this path is dormant* |
| **Example** | If ACTION_CODE were set to '2': new customer 1000042 + policy 2000010 created together |

### BR-CUST-016 — Policy FK Constraint Enforced on Insert (SQLCODE -530)

| Field | Value |
|-------|-------|
| **Rule** | When inserting a POLICY for a customer, if the customerNumber does not exist in CUSTOMER, DB2 raises SQLCODE -530 (FK violation). LGACUS01 maps this to `CA_RETURN_CODE = '70'` — a "customer not found" error for policy attach. |
| **Condition** | INSERT INTO POLICY with non-existent customerNumber |
| **Outcome** | CA_RETURN_CODE = '70', CICS RETURN; no policy row created |
| **Implementation** | [`LGACUS01`](../../pli/LGACUS01.pli) lines 379-392 |
| **Data** | `SQLCODE -530`, `CA_RETURN_CODE`, DB2 POLICY FK |
| **Source** | Explicit |
| **Example** | Insert policy for customerNumber=0 → SQLCODE -530 → CA_RETURN_CODE = '70' |

## Functional Topic 6 — Error Handling

### BR-CUST-017 — DB2 Errors Produce Return Code 90 and Audit Log

| Field | Value |
|-------|-------|
| **Rule** | Any unexpected DB2 error (non-zero, non-100 SQLCODE) sets `CA_RETURN_CODE = '90'` and calls LGSTSQ to write the error (date, time, program, customer number, policy number, SQL request, SQLCODE) plus a COMMAREA dump to a CICS TDQ for diagnostics. |
| **Condition** | SQLCODE ≠ 0 and SQLCODE ≠ 100 in any customer DB2 program |
| **Outcome** | RC='90', error written to TDQ via LGSTSQ |
| **Implementation** | `WRITE_ERROR_MESSAGE` procedure in LGACDB01, LGACDB02, LGICDB01, LGUCDB01 |
| **Data** | `SQLCODE`, `ERROR_MSG` structure, `CA_RETURN_CODE = '90'` |
| **Source** | Explicit — consistent across all DB2 programs |
| **Example** | DB2 unavailable → SQLCODE -904 during SELECT → RC='90' + TDQ error entry |

### BR-CUST-018 — COMMAREA Absence Causes Immediate ABEND

| Field | Value |
|-------|-------|
| **Rule** | All customer programs check `EIBCALEN = 0` at entry. If no COMMAREA was passed, `ABEND LGCA` is issued without a dump. This is an unrecoverable error indicating a programming fault in the calling program. |
| **Condition** | EIBCALEN = 0 at program entry |
| **Outcome** | CICS ABEND with code `LGCA` |
| **Implementation** | All customer CICS programs — entry validation |
| **Data** | `EIBCALEN` |
| **Source** | Explicit |
| **Example** | Program called with COMMAREA LENGTH(0) → ABEND LGCA |
